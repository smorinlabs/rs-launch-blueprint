Async, partial failure, status and resume
  src/doxa_research/run.py:411-448 submits async providers, saving each job ID
  in the checkpoint. If a later submit fails, earlier provider IDs remain in
  the failed checkpoint; a new submit must not be used in place of resume.
  src/doxa_research/run.py:815-958 polls each provider, retries transient
  status errors up to max_transient_errors=5, saves completed files, and marks
  permanent/cancelled failures. If at least one provider succeeds, the normal
  path can mark the aggregate completed and combine only available outputs;
  all-provider failure marks the operation failed.
  src/doxa_research/run.py:1194-1245 implements resume --async as one status
  check per non-completed provider, saving newly completed outputs. The
  aggregate becomes completed only when every provider is completed.
  src/doxa_research/run.py:1311-1362 refuses permanent aggregate failures,
  reconnects using persisted job IDs, and transitions failed/cancelled work
  back to running before a normal resume. It does not submit new jobs.

Duplicate billing risk
  src/doxa_research/providers/openai.py:321-325 retries submit on connection or
  timeout up to three attempts, with no idempotency key in
  src/doxa_research/providers/openai.py:327-378. If the server accepted a
  request before the client timed out, a retry can create another paid job.
  src/doxa_research/providers/gemini.py:763-775 likewise retries the DR create
  call up to three times with no idempotency key.
  src/doxa_research/providers/perplexity.py:603-615 creates one idempotency key
  before retrying; :608-610 explicitly requires reusing it. This protects the
  Perplexity async submit against duplicate creation on retry.
