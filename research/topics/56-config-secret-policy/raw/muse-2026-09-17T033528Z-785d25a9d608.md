### Principles and implementation

Q1 — the security principle behind each source policy. py's ADR-0002
(`py-launch-blueprint/docs/adr/0002-no-secrets-in-config-file.md:8-23`) states
the threat model plainly: config files "get copied, committed, backed up, and
shared in ways secret stores are not, and a 'convenient' token-in-file path
normalizes leaking". Its decision: token resolves from `--token` then
`$PLBP_TOKEN`, never from a file; a `token` key is silently ignored; `config
set`/`config get` operate only on the typed non-secret schema
(`_SECTIONS = {"output", "logging"}`, `core/settings.py:70-73`); the file is
still written 0600 as defense-in-depth. The decision removed a shipped
feature (`config set token`) and scoped OS keyring out ("the env-var contract
composes with any secret manager"). ts's policy is not a competing security
principle — it is the absence of one: D-017(1) applied the generic R5.1
flag > env > file chain to the token with no secrets override, storing it as
a `token` key in the 0600 user config (`src/lib/config.ts:177-180`,
schema at :33-41), and D-017(6) added the compensating control its own
choice made necessary: warn when that file's mode has group/other bits
(`:132-138`, gated on a token being present, non-Windows, and a `warn`
callback). D-017(5) is the one place ts reasoned about secret tiers, and it
only omitted `.env` while keeping the TOML `token` key.

Shared requirement, source, and agreement level. The requirement: *a bearer
token at rest must live only in channels whose sharing semantics the user
controls, and every channel it may occupy must be enumerable for audit.*
Sources: ADR-0002's threat model, R5.5/R10.1 MUSTs, 12-factor's check-in
risk, cargo/gh/git split-file practice, clig.dev's flag/env strictness.

| # | Principle | Agreement level | Must agree across py/ts/rs | May vary per ecosystem |
|---|---|---|---|---|
| S1 | The tool-managed config file never carries secrets | **standard** | that no `token` key is honored in the TOML, in any layer | the disposition of a stray key is this template's choice (rs: fatal `RSLB204`; see below) |
| S2 | Secrets are never accepted as plain flag/positional values | **standard** (R5.5 MUST) | that `--token <value>` goes away in all three repos' follow-on | the blessed intake per surface (`--token-file`, stdin, env) |
| C1 | Token resolves explicit-intake > env; missing token is an auth error (exit 4) | **capability** + R6.1 integers | the observable chain and the exit code | flag spelling, env name (F241 REUSE), `TokenSource` spelling |
| C2 | An overexposed on-disk secret produces a human-visible warning at load | **capability** | that the warning exists and is non-fatal | which file is checked (whichever carries the secret), mechanism (Node `statSync` vs `PermissionsExt`), rendering pipeline |
| P1 | Layered TOML merge for non-secret config (R5.1/R54) is orthogonal to secret sourcing | **architectural pattern** | that secret extraction sees only the merged non-secret map (i.e. never finds a token) | merge mechanics per R54 |

What must agree vs what may vary is the point of the table: S1/S2 are
standard-level (one rule, three repos); C1/C2 are capability-level (same
observable behavior, native mechanism); the stored-credential tier
(keychain/state-file + `auth` group) is deliberately *not* in the table — it
is a SHOULD-level extension each repo adopts when it ships an auth surface,
and this template does not.

Architectural alternatives compared before any library was chosen:

- A1 py's rule, verbatim (two-tier flag(value) > env; silent ignore). Keeps
  S1, violates S2 (both sources' plain `--token` violate the R5.5 MUST), and
  silent-ignore violates R5.8's SHOULD (precise diagnostics; "silently
  ignoring bad config" is the standard's ❌ example) while creating the
  "I set it but auth says absent" debug trap. Rejected as stated; its S1
  core is adopted.
- A2 ts's shape, verbatim (three-tier flag(value) > env > file + loose-perm
  warning). Violates S1 and S2 both; the warning is a compensating control
  for a risk the tool chose to create. Rejected.
- A3 Recommended: S1 + S2-conformant two-tier `--token-file <path>` > env,
  stray `token` key fatal `RSLB204`, loose-perm warning retargeted to the
  secret file. Satisfies every MUST, keeps the template std-only, and
  matches cargo (separate credentials file + stdin) and gh (keychain/stdin/
  env, no plain flag) in shape. Chosen.
- A4 Dedicated credentials TOML beside the config (cargo `credentials.toml`
  / AWS credentials-file shape, tool-managed). Strong practice precedent,
  but it needs a writer (`auth login`/`logout`) to be more than a second
  config file nobody manages, and neither source has that surface. Rejected
  for the template; it is the natural form of the deferred stored tier.
- A5 OS-keychain tier now (`keyring` + `auth login`). Matches R10.1's
  SHOULD most literally, but on Linux the default backend is the
  `zbus`-based Secret Service store (async stack + a running daemon — CI on
  `ubuntu-latest` has neither), uv hand-rolls instead of using the crate,
  and the `auth` command surface does not exist in any source. Deferred
  with trigger (see `token-source-policy` member).
- A6 `.env` runtime tier (`dotenvy`). Excluded by ts D-017(5)'s explicit,
  reasoned omission (R5.1 has no `.env` rung; dotenv v17 stderr noise;
  hermetic precedence tests). Not re-litigated.
- A7 In-memory wrapper (`secrecy::SecretString`) for the resolved token.
  Genuine hardening with strong adopters (octocrab, kube-client), but R56
  owns source policy, not in-memory representation; the token has exactly
  one consumer (the adapter's header attach); and there is no
  cross-ecosystem agreement story (py/ts have no analogue), so it cannot be
  a shared standard. Deferred as a documented hardening path with a pin.

How the recommended design preserves each principle. S1: no `token` field
in R53's schema (resolving R53's "R56 adding a token" re-verify trigger in
the negative), every R54 layer scanned for the prohibited top-level `token`
key, first hit (nearest scope wins for attribution) raises `RSLB204`/exit 2
with a hint naming `--token-file` and the env var. S2: the only flag tier is
a path, never a value; argv never carries the secret (clig.dev :854-861,
cargo-login stdin precedent, gh `--with-token`). C1: `--token-file` >
env, empty-or-whitespace-only at any tier counts as unset (F242 REUSE,
extended with `trim()` for file reads, proven in the probe); missing token
surfaces as `RSLB401`/4 via the existing require-token boundary (R67; ts
`requireToken` at `config.ts:224-232` is the shape to port); an unreadable
`--token-file` is `RSLB104`/1 (R8.2 "unreadable files", verbatim). C2: the
`mode & 0o077` check (ts `:135` parity) runs on the secret file at load,
once, non-fatally; nothing is checked on the config file because it carries
no secret (py parity: py checks nothing for exactly this reason). P1:
secret extraction is defined over the merged map, so R54's tier count cannot
change secret semantics — per-layer token priority is specified as a
non-concept (MEDIUM composition answer).

Where a different ecosystem needs a different design (Q3, second half).
The permission-check mechanism is genuinely language-bound (Node
`fs.statSync(path).mode` vs `PermissionsExt::mode()` vs Python
`os.stat().st_mode`) — capability agreement, native mechanism. Warning
rendering is pipeline-bound (py's `Config.warnings` list vs ts's injected
`warn` vs rs's warnings vector rendered by R58's eventual pipeline). The
stored-credential tier is scope-bound: whichever repo first ships `auth
login` picks keychain-vs-state-file per R10.1's SHOULD; the template
documents the seam. Two differences are *not* justified and are recorded as
follow-on changes with their rationale (changes to py/ts remain a follow-on
project): (a) ts's file-as-source is accidental drift — D-017(1) applied
the generic chain without the secrets override the org standard requires;
(b) both sources' plain `--token` violates the R5.5 MUST that predates them
(the standard is dated 2026-06-28; ADR-0002 cites only py's own design R8,
and ts's D-016 cites the standard for other rules while missing this one).
One external ideal is a justified non-adoption: clig.dev's "do not read
secrets from env" (:1154-1162) is declined for all three repos because the
org standard explicitly tiers env (R5.4/R10.1), F241 REUSE fixes the env
contract, and cargo (`CARGO_REGISTRY_TOKEN`), gh (`GH_TOKEN`) and 12-factor
all bless env — an org MUST-adjacent practice outranks an external guide's
ideal, and the deviation rationale is this paragraph.

### Recommendation

One stack:

1. `token-source-policy`: config TOML never a token source (py's S1 core);
   two-tier `--token-file <path>` > `<TOOL>_TOKEN` env; stray `token` key
   is fatal `RSLB204`/2 with remedy hint; unreadable token file is
   `RSLB104`/1; missing token is `RSLB401`/4; empty/whitespace-only at any
   tier is unset. No crate.
2. `permission-check`: `std::os::unix::fs::PermissionsExt::mode()`,
   `(mode & 0o077) != 0`, on the `--token-file` only, `#[cfg(unix)]` with a
   `false` no-op fallback; non-fatal. No crate (`rustix 1.1.5` surveyed and
   excluded: a dependency for one `stat`).
3. `warning-channel`: warnings collected once at config-load into
   `Config.warnings` (plus an injected `warn` seam for the binary); library
   prints nothing (R67 layering); the binary renders once through R58's
   pipeline when it lands (assumption, R58 unresolved). No crate.
4. Deferred, not shipped: `keyring 4.2.0` stored-credential tier (adopt
   with an `auth login` surface) and `secrecy 0.10.3` in-memory wrapping
   (adopt if the token gains more than one consumer). Pins and triggers in
   the members.

### Members

#### token-source-policy

##### Landscape

This member decides F239/F240: whether the TOML config file may carry the
token and the resulting precedence chain. Bin map (member slice of the
top-level map): std (`std::env`, `std::fs`) · `keyring`/`secrecy` as the
established secret-handling crates · `cargo-credential-*` helpers and
`zbus` stores as up-and-comers. Authorities: org standard R5.5/R10.1
(binding MUSTs), ADR-0002 (threat model), 12-factor (env-positive),
clig.dev (flag-negative, env-negative ideal), cargo/gh/git (split-file
practice). Practice: cargo and gh implement the recommended shape
(token-file/stdin > env > stored, config never); uv and xh ship plain
secret flags (honestly recorded counter-practice showing the MUST exceeds
current ecosystem habit).

##### Principles and implementation

Implements S1 (standard: config never carries secrets), S2 (standard: no
plain secret flags) and C1 (capability: explicit-intake > env, exit 4 when
absent). Essential behaviors: (1) R53's schema has no `token` field — the
"R56 adding a token" re-verify trigger in R53 resolves negative; (2) every
R54 layer is scanned for a top-level `token` key and the nearest hit raises
`RSLB204`/2 naming file and key, with a hint pointing at `--token-file` and
the env var — loud, not py's silent ignore, per R5.8's SHOULD and R67's
positioning of `RSLB204` for R56's use; (3) `--token-file` reads whole-file,
trims, and treats empty/whitespace-only as unset (F242 parity, proven in
the probe); (4) unreadable token file is `RSLB104`/1; missing token is
`RSLB401`/4. Observable acceptance: a config containing `token = "x"`
fails with code `RSLB204` on stderr and exit 2; `--token-file` pointing at
a 0644 file warns once and still authenticates; `ps` output never contains
the secret. The stray-key fatal (vs py's silent ignore) is this template's
choice, stated so synthesis can overturn it: silent-ignore creates the
"set-but-absent" trap, and R5.8's ❌ example is exactly silent ignoring.

##### Dominant choice

Never-from-config-file (py's S1 core): cargo (`credentials.toml` split),
gh (keychain/file split), git (`.git-credentials` split), 12-factor
(check-in risk) and the org standard (R10.1's stored credential is a
keychain/state-file, not the config TOML) all converge on it. ts stands
alone on the other side with a generic-chain application, not a secrets
argument.

##### Qualified shortlist

`--token-file <path>` > env (recommended); plain `--token <value>` > env
(py verbatim — fails S2, kept as the compatibility runner-up); file as
lowest tier (ts verbatim — fails S1, rejected); dedicated tool-managed
credentials file (needs an `auth login` writer that does not exist —
rejected for the template, natural form of the deferred tier).

##### Excluded by gate

`.env` runtime tier: excluded by binding precedent (ts D-017(5)'s reasoned
omission; R5.1 has no `.env` rung) before any gate is weighed — no figures
collected, and that is the reason. No crate candidate is excluded by a
fitness gate for this member because no crate is shortlisted; `keyring` and
`secrecy` figures are collected under Tradeoffs/Sources as surveyed-but-
deferred, with gate answers there.

##### Up-and-comers

`cargo-credential-*` external helpers (credential storage as a plugin
protocol — the direction cargo itself is moving); `zbus` Secret Service
stores (keyring v1's Linux backend). Neither fits a template today
(plugin host surface; daemon + async runtime), both are watched via the
stored-tier re-verify trigger.

##### Fit for this template

Exact fit: one token consumer (the API adapter), TOML config users copy
(R52/R53/R54), headless CI with no daemon, std-only (zero dependency,
zero MSRV, zero audit surface). The `--token-file` tier composes with
secret managers (`--token-file <(vault read …)`, systemd `LoadCredential`,
Kubernetes service-account files) without the template knowing any of them
— the same composition argument ADR-0002 makes for env.

##### Recommendation

`--token-file <path>` > `<TOOL>_TOKEN` env; no `token` in schema; stray
`token` key is fatal `RSLB204`/2; unreadable token file `RSLB104`/1;
missing token `RSLB401`/4. No crate.

##### Ranked runner-up

py verbatim (plain `--token` > env, silent ignore): one-behavior change
from the recommendation (flag takes a value, stray key ignored). It keeps
S1 and both sources' CLI spelling at the cost of an R5.5 MUST violation
and the set-but-absent trap. If the owner waives R5.5 for template
simplicity (a conformance-note waiver, per the standard's own process),
this is the fallback — not ts's shape, which additionally violates S1.

#### permission-check

##### Landscape

This member decides F245's successor: which file gets the loose-permissions
check and which Rust mechanism performs it (HIGH Q2). Bin map: std
(`PermissionsExt::mode`, `#[cfg(unix)]`) · established: none — no
established crate exists for "warn on loose secret-file mode"; every
surveyed tool hand-rolls one `stat` (cargo, gh, git, ssh) · up-and-comer:
`rustix::fs::stat`/`fstat` (safe POSIX wrapper). Authorities: ts
`config.ts:135` (the `(mode & 0o077) !== 0` shape to preserve), the 1.96.0
std source (floor proof), the executed probe (behavior proof).

##### Principles and implementation

Implements C2 (capability: an overexposed on-disk secret warns at load,
non-fatally). Essential behaviors: (1) the check runs on the `--token-file`
only — never on the config file, which carries no secret (F245-as-written
is not adopted because its precondition is gone; its principle is
transposed to the file that actually carries the secret); (2) exact
predicate `(mode & 0o077) != 0` (ts parity: any group/other read, write or
execute bit); (3) POSIX-only via `#[cfg(unix)]`, with a `false` no-op
fallback so the crate still compiles anywhere — the owner-fixed matrix
(`ubuntu-latest, macos-latest`) is all-POSIX so CI always exercises the
real branch, and no Windows branch exists per F244 OMIT; (4) a metadata
failure degrades to no-warning (the check is best-effort signal, never a
new failure mode — the token file's own readability error is `RSLB104`
already). Observable acceptance: 0600/0400 secret files warn nothing, 0640
and 0644 warn once (proven in the probe for 0600/0644/0400; 0640 follows
from the same bit test).

##### Dominant choice

`std::fs::metadata(path).permissions().mode()` with
`std::os::unix::fs::PermissionsExt`: stable since 1.1.0 (verified at the
1.96.0 tag), zero dependencies, the exact ts semantic in one expression.
Every surveyed production tool checks modes with its platform's native
`stat`, never a helper crate.

##### Qualified shortlist

`PermissionsExt` (recommended); `rustix::fs::stat` (safe, but a
dependency for one `stat` — excluded on fit, figures below for the
record); refusing to read a loose secret file ssh-style (fail-closed
alternative — rejected for the template default, see Tradeoffs).

##### Excluded by gate

Nothing is excluded by a fitness gate: the recommendation is std-only, so
gates 1–6 are answered as inapplicable-with-reason rather than passed —
no license (ships with the toolchain), no MSRV surface beyond `1.1.0 <<
1.96`, no advisory surface, no `unsafe` (safe API over the OS `stat`), no
async coupling, no binary-size/compile-time cost. `rustix` is excluded on
fit (dependency for one call), not on gates: for the record it passes
every gate at crate level (`rustix 1.1.5`, 2026-09-16, rust 1.65,
259,004,169 / 1,157,107,161 downloads, 2109 stars, 101 open issues, no
advisories; license Apache-2.0 WITH LLVM-exception OR Apache-2.0 OR MIT,
metadata only per Q7.B).

##### Up-and-comers

`rustix` (above) — if the template ever needs more POSIX surface
(`openat2`, sealed memfds), the check could move to it; today it would be
the only consumer. Watched, not adopted.

##### Fit for this template

Perfect: one safe std call, no `unsafe`, no dependencies, compiles on the
whole matrix with the real branch always live, testable with
`set_permissions` in-process (as the probe does). A crate here would add
audit surface to satisfy no requirement.

##### Recommendation

`std::os::unix::fs::PermissionsExt::mode()`, `(mode & 0o077) != 0`, on the
`--token-file`, `#[cfg(unix)]` + no-op fallback, non-fatal, metadata
failure degrades to silent. No crate.

##### Ranked runner-up

ssh-style refusal (do not read a group/other-readable secret file): the
local OpenSSH binary contains the `Permissions … are too open` / `bad
permissions` refusal strings (verified via `strings /usr/bin/ssh`; a live
run was blocked by the sandbox having no passwd entry for the uid —
recorded). Refusal is the safer default in theory; warn-and-proceed is
recommended because secret managers, CI workspace mounts and process

user does not control, and a template that bricks those contexts teaches
users to bypass the check. Document the strict variant as the hardening
option.

the secret file (not the config) trades a small amount of ts-literal
fidelity for the honest precondition: warnings about files that carry no
secret train users to ignore warnings.

#### warning-channel

##### Landscape

This member answers the MEDIUM warning question: what mechanism surfaces
the loose-permissions warning, once at load or on every read. Bin map:
std (return a `Vec<String>` on the resolved config — py's
`Config.warnings` shape; an injected `&mut dyn FnMut(&str)` seam — ts's
`warn` callback shape) · established: R58's eventual tracing/logging
pipeline (unresolved — this member assumes its future rendering without
depending on any value) · up-and-comer: none; warning delivery is not a
crate question. Authorities: py `core/config.py` warnings list, ts
`readConfigFile`'s `warn` parameter, R67's layering rule (library writes
to no process stream or file).

##### Principles and implementation

Implements the delivery half of C2. Essential behaviors: (1) the warning
is produced exactly once, at config-load time, when the secret file is
statted — never on every token read, because resolution is pure over
already-loaded values and per-read warnings would spam library consumers
that resolve in a loop; ts warns inside `readConfigFile` (load-time),
which is the parity point; (2) the library returns warnings (a
`warnings: Vec<String>` field on the resolved config, py's shape) and
optionally accepts an injected `warn` callback (ts's seam for the binary
to bridge into its logger) — either way the library itself prints nothing,
per R67 layering; (3) the binary renders each warning once on stderr and
continues with exit 0 unaffected. Observable acceptance: a 0644 secret
file yields exactly one warning line on stderr and a successful run; a
second `token()` read in-process emits nothing new.

##### Dominant choice

Load-time collection into the resolved config (py's `warnings` list):
testable without capturing stderr, no global logger needed, composes with
any R58 pipeline later. ts's injected callback is the same idea from the
caller's side; the recommendation keeps both (field + optional seam).

##### Qualified shortlist

Warnings vector + optional injected callback (recommended); direct
`eprintln!` from the library (rejected — violates R67 layering and is
untestable in-process); the R58 pipeline directly (cannot be selected —
R58 is unresolved; it is the assumed future renderer, recorded as an
assumption with a trigger, not a dependency).

##### Excluded by gate

No crate is involved, so all six gates are inapplicable-with-reason (no
dependency to license/audit/version-gate; rendering cost belongs to R58's
pipeline decision, not this member). Stated, not omitted.

##### Up-and-comers

None. If R58 selects `tracing`, the binary-side bridge is one
`tracing::warn!` call; that is integration, not a candidate.

##### Fit for this template

Exact: keeps the library binary-clean (R67), keeps warnings deterministic
and order-stable for snapshot tests, and leaves R58 free to render
however it lands (text line today, structured event tomorrow) without
reopening R56.

##### Recommendation

`Config.warnings: Vec<String>` populated once at load, plus an optional
injected `warn` seam; binary renders once on stderr; no pipeline crate
selected here. No crate.

##### Ranked runner-up

collect-then-render): simpler by one field, but loses the warnings for
