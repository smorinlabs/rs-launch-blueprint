### Principles and implementation

Shared requirement: CI runner selection that keeps every required check
meaningful on any clone of the template while covering exactly the
owner-fixed OS matrix. Source: py precedent F031 generalized through the
research mandate, then adjudicated against ts's org judgment D-022(1)
and current Rust production practice. Agreement levels:

- Capability (must agree across py, ts, rs): fork-operability — a fresh
  fork with no repository or organization variables set runs every
  required check to a real verdict (pass or fail on the code's merits),
  never to an infra error or a silent skip. Observable acceptance: fork,
  set no variables, open a pull request; every required check reports.
- Standard (must agree; owner-fixed, not this item's to reopen):
  `target-os-matrix = ubuntu-latest, macos-latest` — every runner label
  this item produces resolves to one of these two OS families.
- Capability (must agree within rs): lint-clean workflows — bare
  `actionlint` from the repo root exits 0 (R11's `workflow-lint`
  occupant; R11 revision 6 proved `actionlint` reads its own config, so
  the config is load-bearing input).
- What may vary: the mechanism behind the label (hardcoded literal,
  matrix expression, fleet indirection with public fallback) — each repo
  may choose the cheapest mechanism that preserves the capabilities
  above, and must justify why its mechanism is cheapest for its context.

Architectural alternatives compared before choosing (mechanism is the
architecture here; there are no libraries):

1. Hardcoded labels (ts's shape): `runs-on: ubuntu-latest`,
   `runs-on: ${{ matrix.os }}` under R11's os matrix. Fork-safe by
   construction, zero config surface, the 7-of-7 Rust practice.
2. Repo-variable indirection with public fallback (py's shape):
   `runs-on: ${{ vars.RUNNER_UBUNTU || 'ubuntu-latest' }}`. Fork-safe
   only through the fallback branch, and only if every job repeats the
   expression exactly; buys fleet routing for in-org consumers at the
   cost of a per-job expression plus the `actionlint` strict-`vars`
   coupling (E4 below).
3. Fork-aware conditional on repo identity (uv's shape): `${{
   github.repository_owner == 'astral-sh' && '<fleet-label>' ||
   '<public-label>' }}`. Fork-safe, but bakes one org's name and fleet
   labels into a public template — strictly worse than (2) for a
   template, which is why uv (a product repo, not a template) can carry
   it and rs should not.

HIGH question 1 — does D-022(1) apply equally to rs, or do Rust build
times change the case? It applies equally. Longer Rust builds raise the
absolute value of faster compute, but the rationale turns on who pays
and who configures, not on minutes saved: a public template's default
must serve the consumer with no fleet, no variables, and no budget, and
for that consumer all three mechanisms run on the identical public
label — the indirection buys nothing while costing a per-job expression
on every current and future job (R11's rule adds jobs over time) and
opting the whole repo into strict `vars` checking. The observed Rust
field agrees at every scale, including the slowest-building project
surveyed (uv, which solves speed with hardcoded premium labels and
conditionals, not with `vars` indirection). Rust build times justify
documenting the escape hatch (point `runs-on:` at a faster runner in
your own fork), not adopting the indirection. Recommendation: reject
F031's indirection for rs.

### Recommendation

One stack. Reject the repo-variable runner indirection (ts's shape, per
D-022(1)): every job's `runs-on:` is a hardcoded GitHub-hosted label
(`ubuntu-latest` for single-runner jobs, `${{ matrix.os }}` for R11's
os-matrix `check` job, `macos-latest` wherever R11 names a macOS-only
leg). `.github/actionlint.yaml` carries zero `self-hosted-runner` /
`config-variables` entries and one narrow `paths:` suppression block
covering exactly the workflow files that invoke
`actions/create-github-app-token` with `client-id` (`release-please.yml`
under the current pipeline; `publish.yml` gains an entry only if it
ever invokes the action). No `RUNNER_*` variables are defined or
referenced anywhere.

#### runs-on-selection

##### Landscape

Sub-category: the expression shape of each job's `runs-on:` line. From
the top-level map: first-party literals and matrix expressions;
established hardcoded norm; up-and-comer fleet labels. Candidates found:
(A) hardcoded literal (`ubuntu-latest`, `ubuntu-24.04`,
`ubuntu-26.04`, `macos-latest`); (B) matrix expression (`${{ matrix.os
}}`, serde's `${{matrix.os}}-latest` variant); (C) repo-variable
indirection with public fallback (`${{ vars.RUNNER_UBUNTU ||
'ubuntu-latest' }}`, py fleet-wide across 17 workflow files, e.g. py

`ci.yml:205,318`, `check-lint.yml`); (E) hardcoded third-party label

`namespace-profile-windows-2022-x86-64-16x32`; py's Blacksmith labels as
the values its variables resolve to in-org).

##### Principles and implementation

Must preserve: fork-operability (capability) and the fixed OS matrix
(standard). (A) and (B) preserve fork-operability by construction —
there is nothing to configure. (C) preserves it only through its
fallback branch, which must be repeated exactly on every job, including
jobs added later under R11's slot rule; one job written as bare
`${{ vars.RUNNER_UBUNTU }}` breaks every fork. (D) preserves forks but
bakes a vendor/org identity into a public template. (E) alone fails
fork-operability outright (forks lack the fleet) and fails the fixed
matrix unless each label is proven to resolve to `ubuntu-latest` /
`macos-latest` families — no such proof exists for any rs-adoptable
fleet, and this item found no established Blacksmith-equivalent
precedent of its own for a Rust template. Production usage: (A)+(B) is
the 7-of-7 Rust practice (crates.io, tokio, clap, ripgrep, axum, serde,
plus the Cargo Book guide); (C) is py production; (D)+(E) is uv
production. Maturity favors (A)+(B) overwhelmingly for templates: every
template-shaped project surveyed uses it, while (D)+(E) appear only in
product repos (uv) and org-fleet templates (py).

##### Dominant choice

(A)+(B): hardcoded literal for single-runner jobs, `${{ matrix.os }}`
under an os matrix. Dominant by production count (7/7 Rust projects),
by Rust project authority (Cargo Book CI guide uses (A) in every
example), and by template fitness (zero configuration exists to get
wrong).

##### Qualified shortlist

(A)+(B) hardcoded (recommended); (C) vars indirection with public
fallback (ranked runner-up — production-proven in py, fork-safe via
fallback, pays only for fleet owners); (D) fork-aware conditional
(qualified mechanically — it is fork-safe — but disqualified for
templates on identity-baking grounds; kept in the shortlist to record
that uv's precedent was evaluated and distinguished, not missed).

##### Recommendation

(A)+(B): hardcode every `runs-on:`. Single-runner jobs use
`ubuntu-latest` (or `macos-latest` where R11 names a macOS-only leg);
the compiling matrix job uses `${{ matrix.os }}`. No `vars.*`, no

any workflow file.

##### Ranked runner-up

(C) vars indirection with public fallback, py's exact shape (`${{
vars.RUNNER_<OS> || '<public-label>' }}` per OS family, `RUNNER_WINDOWS`
dropped). Winning condition: the owner stands up a runner fleet for the
template's own repo AND accepts the per-job expression tax plus the
whole-repo strict-`vars` coupling (member 3, E4) — i.e. the template
stops optimizing for the zero-config consumer. P03 measuring a
template-blocking `check` wall clock that only fleet compute fixes
would be evidence toward, but not sufficient for, this condition; the
larger-SKU substitution (Up-and-comers) must be ruled out first.

##### Tradeoffs

(A)+(B) cost nothing to configure, nothing to lint, and nothing to keep
in sync across jobs; their ceiling is public-runner performance, with
larger SKUs as the cheap upgrade. (C) routes in-org runs to a fleet
while keeping forks nominally green, at the cost of: an expression on
every job line (R11's slot rule grows the job count over time); the
strict-`vars` coupling (declaring `config-variables` forces declaring
every `vars.*` repo-wide — E4); a second `actionlint` key to maintain
(F056/F057); and a fork-brittleness mode (a job missing its fallback
branch fails every fork). Speed alone cannot carry (C): on a fork — the
consumer the template must serve first — both shapes run the identical
public label, so (C)'s benefit is zero exactly where the template's
promise matters most.

#### actionlint-runner-labels

##### Landscape

Sub-category: the `self-hosted-runner.labels` key of
`.github/actionlint.yaml` (F056). From the map: the key exists only to
teach actionlint custom labels it cannot know (maintainer docs
`docs/config.md`: labels "added to your self-hosted runners", glob
patterns via `path.Match` supported). Candidates: (A) omit the key
entirely (with the rest of the runner config); (B) declare every custom

maintainer docs.

##### Principles and implementation

Must preserve: lint-clean workflows (capability). The key is pure
overhead unless a custom label appears in the workflow tree: E2 shows a
bare `blacksmith-4vcpu-ubuntu-2404` label fails `[runner-label]` without
it, and E1 shows hardcoded public labels pass without any config file
at all. Under member 1's recommendation no custom label exists, so (A)
preserves the capability with zero surface. If member 1 were ever
reversed, (B) is the idiomatic shape (explicit label inventory, py
production precedent); (C) trades review precision for brevity — a glob
silently accepts labels never audited, so (B) dominates (C) whenever
the label set is small and known, as it always is in a template.

##### Dominant choice

(A) omit the key: dominant by non-need — 4 of 4 surveyed Rust projects
carry no `actionlint.yaml` at all, the maintainer docs call the file
optional, and E1 proves the recommended workflow shape needs nothing.
(The rs file itself still exists for member 4's suppression block; this
key is absent from it.)

##### Qualified shortlist

(A) omit (recommended); (B) literal label inventory (the idiomatic
adopted shape — qualified by py production use and E3's exit-0 proof);
(C) glob pattern (qualified mechanically by maintainer-docs support,
ranked below (B) on audit precision).
