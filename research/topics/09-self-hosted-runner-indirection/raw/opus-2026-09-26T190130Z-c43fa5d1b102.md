### Landscape

**The category this item decides.** Not a crate and not a library. It is the
*runner-selection mechanism* for GitHub Actions jobs: what text sits on each
job's `runs-on:` line, and what `.github/actionlint.yaml` must declare so that
the workflow linter accepts that text without carrying dead entries. Three
ledger rows ride on it: F031 (the indirection itself), F056/F057 (the
linter's runner-label and configuration-variable declarations), and F058 (the
per-file suppression for a known linter false positive on
`actions/create-github-app-token@v3`).

**Is the shared pattern still appropriate in Rust? — HIGH question 1.**
ts's D-022(1) rationale ("Blacksmith explicitly not reused for a public
template") applies to `rs-launch-blueprint` **equally**, and Rust's longer
builds do not change the cost-benefit case for the template, for five
reasons:

1. **The risk is independent of the workload.** GitHub's recommendation is
   about who can put code on the machine, not how long the build takes.
2. **The template is public and GitHub-hosted runners are free for it.**
   Public-repo standard runners are Linux 4 CPU / 16 GB / 14 GB SSD (x64 and
   arm64) and macOS 3 CPU (M1) / 7 GB / 14 GB (arm64), "free and unlimited
   on public repositories" (`supported-github-runners.md`, commit
   `eb8f32b5dd88`, 2026-09-17). The owner pays nothing for A1; A2 as py runs
   it pays a third party.
3. **The generated repositories get no benefit.** Variables are per
   repository or organisation and are not part of a template copy, so every
   downstream repository falls back to `ubuntu-latest`/`macos-latest` under
   A2 anyway (P5). The indirection helps only the template repository
   itself, and `rs-launch-blueprint` has **0** repository variables today
   (`GET /repos/smorinlabs/rs-launch-blueprint/actions/variables`
   `total_count: 0`, live). Adopting A2 would add an expression to every job
   that currently evaluates to the literal it replaces.
4. **Rust build time is attacked elsewhere in this plan.** R11 already gates
   every compiling job behind a `plan` detector and caps cache-bearing job
   ids; R10 owns the dependency cache. Those reduce minutes for every
   adopter; a runner swap helps only whoever pays for it.
5. **Practice agrees.** None of the 12 Rust-ecosystem repositories surveyed
   uses a variable-driven `runs-on:`; the ones that buy speed are
   organisation-funded products that name vendor labels literally.

What *would* change the case: the owner deciding to fund faster runners for
the template repository itself **and** accepting self-hosted-class
execution of fork pull requests, or making the repository private. Neither is
in the inputs; this report does not assume either. No build-time measurement
on 4-CPU public runners versus a paid runner was taken (gap G3); the
recommendation does not rest on one because reasons 1–3 hold at any speed.

**If the indirection were adopted: the idiomatic `actionlint.yaml` shape —
MEDIUM question 4.** Conditional answer, for the record and for the
ranked runner-up:

```yaml
# Only if A2 is adopted. config-variables is a GLOBAL allow-list: every
# vars.* name used by ANY workflow must be listed, not just RUNNER_*.
config-variables:
  - RUNNER_UBUNTU
  - RUNNER_MACOS
  - ANTHROPIC_FEDERATION_RULE_ID   # R18
  - ANTHROPIC_ORGANIZATION_ID      # R18
  - ANTHROPIC_SERVICE_ACCOUNT_ID   # R18 (optional variable)
# NO self-hosted-runner.labels block: labels are checked only when written
# literally in runs-on:, and A2 writes them only in repository settings.
```

Three facts fix that shape, all executed: listing only `RUNNER_*` makes
actionlint reject R18's variables (step 11); a labels block is inert when
every label arrives through an expression (step 2 on py's own tree); and
there is no `RUNNER_WINDOWS` because `windows` is outside
`target-os-matrix`. The labels block is needed only for a job that names a
self-hosted label literally (step 13), which A2 by design never does.

**`create-github-app-token` suppression scope — LOW question 5.** The scope
is a **rule, not a file list**: *one `paths:` entry per workflow file that
contains `uses: actions/create-github-app-token@`, and no other entry.*
Applied to rs today that is `.github/workflows/release-please.yml` only:
F072 inherits the action for release-please auth (`COMMON → REUSE`), and
R21's contributors workflow uses `smorinlabs/contributors-please-action`,
which mints its own installation token from `app-id`/`private-key` and does
not call `create-github-app-token`
(`research/topics/21-contributors-bot-credential-source/DECISION.md:65`).
py's narrower scope matches that rule at its pin; ts's `publish.yml` entry
breaks it — ts `publish.yml` at `cb1cbcb` contains no
`create-github-app-token` step (it authenticates the npm publish through
OIDC `id-token: write`), so the entry is inert, and actionlint never reports
an unused ignore (step 9). If R68 (release binaries, open) later adds a
workflow that invokes the action, the census check adds that file; it is not
added speculatively.

Two further behaviours of that suppression were **executed** and matter for
whoever wires the lint job:

- `paths:` keys match only the bare repository-relative form. `actionlint`
  with no arguments or with `.github/workflows/release-please.yml` honours
  the ignore; `./.github/workflows/release-please.yml` does **not** (step 8).
  ts's comment already warns about this.
- While suppressed, a *typo* in the input name still surfaces
  (`input "client_id" is not defined`, verified in scratch before the
  consolidated script), but a step missing its id input entirely would be
  masked by the "missing input `app-id`" ignore — ts's caveat, accepted as
  the price of a temporary suppression.

**Maturity and dependability.** A1 has no moving parts: GitHub maintains
the labels, and `ubuntu-latest`/`macos-latest` roll forward with GitHub's
image policy (the public table maps `macos-latest` to macOS 26 arm64 on
2026-09-26). A2's dependability depends on an out-of-band setting that is
invisible in review and in the repository's history; org-level variables
of the same name also apply unless shadowed (`variables.md`: "the variable
at the lowest level takes precedence"), so a future org-wide
`RUNNER_UBUNTU` would silently re-route every job of every repo that
carries the expression. Performance: no benchmark was taken; public
runners are 4 CPU Linux / 3 CPU macOS per the docs, and the comparison with
paid runners is gap G3.
