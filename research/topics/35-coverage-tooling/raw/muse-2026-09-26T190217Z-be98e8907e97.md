### Principles and implementation

**Shared requirement and agreement level.** The cross-repo principle for R35, scoped to the divergence analysis, is a *capability + policy* agreement: every launch-blueprint template measures test coverage of its shipped code and blocks merges on a declared threshold. Source: py precedent (coverage.py via pytest-cov with a blocking Codecov check) and ts precedent (Vitest v8 provider with declared thresholds), both aiming at the same observable behavior. What must agree across py/ts/rs: (a) coverage is measured over shipped code on every PR; (b) a declared numeric threshold exists in-repo or in a pinned service config; (c) falling below it fails a required check. What may vary by ecosystem: the collector tool (class B — justified: LLVM source-based vs language-runtime instrumentation are different substrates with no shared low-level value), the exclusion list and report formats (class A — arbitrary settings; values need not match), and — per the two class-F rows — the threshold's home (in-repo flag vs external service config) and the enforcement wiring (blocking vs scaffold). For the class-F rows this report makes a Rust recommendation with transferable rationale for the py/ts follow-on project rather than claiming the split is research-settled.

**Essential behaviors and observable acceptance criteria.** (1) `cargo test` under the template's runner (R32) can be instrumented without changing test code. (2) Scope covers the workspace's lib, bins, and web member with a documented exclusion mechanism. (3) A single in-repo threshold declaration exists. (4) CI fails the PR when line coverage is below it. (5) A human-readable summary prints in logs and a machine-readable artifact (`lcov.info`) is retained from the CI run.

**Architectural alternatives compared before choosing libraries.** (i) LLVM source-based coverage (`-C instrument-coverage` + `llvm-cov`): compiler-inserted counters, source-accurate regions/branches, one instrumented test run, identical pipeline on Linux and macOS. (ii) ptrace/tracing collection (tarpaulin's default engine): no recompilation with instrumentation flags, but Linux-only, slower (trace overhead, repeated runs), and less accurate on optimized/inlined code. (iii) Log-aggregator reporting (grcov): powerful multi-format reporter over profraw/lcov inputs, but a pipeline piece rather than a turnkey cargo command — the template would own the `RUSTFLAGS` + `llvm-profdata` + `grcov` orchestration itself. (iv) External-service gating (Codecov): adds patch-coverage signal and history at the cost of a network dependency, an upload token story, and a second config surface. The recommendation takes (i) for collection, an in-repo local threshold for gating, and no external service in the required path; (iv) is the ranked runner-up as a non-gating informational overlay.

**How the recommended design preserves each principle.** Capability: `cargo llvm-cov --workspace` measures the whole shipped workspace every run. Policy: `--fail-under-lines 80` declares the threshold next to the command that enforces it, so the declaration cannot drift from enforcement the way ts's configured-but-unenforced thresholds did. Agreement level: py keeps its external gate (justified there by patch coverage + history the team already relies on); ts's follow-on is to enforce its in-repo thresholds rather than adopt a service; rs enforces in-repo from day one. All three then satisfy the same observable criteria with ecosystem-native tools.

**Maturity, dependability, performance, integration cost.** 90-day downloads (crates.io API, 2026-09-26): `cargo-llvm-cov` 1,696,594 vs `cargo-tarpaulin` 300,122 vs `grcov` 183,020 — the LLVM wrapper leads the tracing incumbent by 5.7× on recent velocity and the all-time board 7,999,538 vs 3,048,047 vs 2,608,927. All three released in 2026 (0.9.1 on 2026-09-06; 0.37.4 on 2026-09-21; 0.10.7 on 2026-03-03). No open RustSec advisory touches any candidate at current versions (`cargo-llvm-cov`/`cargo-tarpaulin` package pages are 404 = no advisories; `grcov`'s sole listing RUSTSEC-2025-0005 is patched in >0.8.20, retrieved 2026-09-26). Runtime cost is one instrumented `cargo test --workspace` plus merge/report (seconds on a template-sized suite); install cost is the `llvm-tools-preview` component plus either a prebuilt `cargo-llvm-cov` binary or a from-source build. No performance claim rests on unlike benchmarks: the "LLVM is cheaper than ptrace" comparison is architectural (one instrumented run vs traced runs), stated qualitatively per the evidence rules.

**Minimal realistic example.** A workspace with `crates/core` (lib), `src/main.rs` (CLI bin), `crates/web` (service): `cargo llvm-cov --workspace --lcov --output-path lcov.info --fail-under-lines 80` runs the full suite once, writes `lcov.info`, prints the terminal summary, and exits nonzero below 80% lines. Local loop stays coverage-free (`cargo test`, owned by R32); coverage runs on demand (`cargo llvm-cov --html`) and in CI (the gating job).

**Executable acceptance check (planned, not run).** In CI: the coverage job passes on the template's example suite (expected ≥80% lines from day one); a scratch commit deleting half the tests turns the job red with the summary showing the shortfall; restoring the tests turns it green. Locally: `cargo llvm-cov --version` reports the pinned version and `cargo llvm-cov --workspace --lcov` produces a parseable `lcov.info`. No check in this report was executed — this leg performs no toolchain runs; the commands above are the synthesis/empirical-audit runbook.

#### coverage-threshold-and-gate

##### Landscape

Member category: threshold definition (location + values) and CI enforcement wiring — a *pattern* member, not a crate: threshold locations and gate wirings have no versions, downloads, or issue trackers, so crate figures are inapplicable throughout and the evidence is precedent + mechanism instead. Three-bin map of the pattern space: (a) in-repo local gate — the threshold lives next to the command that enforces it (`cargo llvm-cov --fail-under-lines N` failing the CI step); ts's location precedent, py's enforcement precedent combined. (b) External-service gate — the threshold lives in service config (py's `.codecov.yml`: project `target: auto`, patch `80%`) and the service's check blocks the PR. (c) Inert scaffold — thresholds declared but unwired (ts's current state: `vitest.config.ts` thresholds with the coverage CI step commented out). Bin (c) is the anti-pattern: it satisfies neither the capability nor the policy half of the shared principle.

##### Principles and implementation

The divergence analysis classes F136 (location/values) and F137 (enforcement) as F: genuine, still-unresolved design splits where py and ts already differ with no convergence evidence. The research-answerable core: a gate that cannot drift from its declaration. Bin (a) has that property by construction — the flag and the failure are the same process exit code — while bin (b) splits declaration (service config + YAML in repo) from enforcement (a third-party check subject to service outage, token expiry, and fork-PR upload rules), and bin (c) declares without enforcing. Values: the only *enforced* numeric threshold in either source repo is py's 80% (patch); ts's 95/95/90/95 are aspirational-unenforced. This member therefore recommends a single enforced metric, lines ≥ 80, as the day-one gate: it matches the one enforced precedent, passes on template example code from the first commit, and keeps the gate legible (one number, one metric). Raising toward ts's 95s is a follow-on calibration once the example suite sustains it, not day-one config. Branch/function thresholds are explicitly deferred: `llvm-cov` reports regions/branches, but gating one metric well beats gating four metrically-noisily on a template. Local-vs-external token analysis: S_CODECOV_TOKENLESS_ANALYSIS.

##### Dominant choice

The in-repo local gate is the dominant pattern for this template: `--fail-under-lines 80` in the CI coverage step and the mirroring just recipe. It is dominant by fit rather than by headcount — it is the only bin that simultaneously satisfies "declared in-repo" (F136, ts's location precedent and the template's no-secrets constraint) and "actually blocks the PR" (F137, py's enforcement precedent). Every claim about the flag's behavior is README-verified (S_L_FLAGS_REF).

##### Qualified shortlist

- Codecov upload as a *non-gating informational overlay* (tokenless on public repos, S_CODECOV_TOKENLESS_SHORT): qualified because patch coverage and trend history are genuinely useful signals this stack otherwise lacks. Not in the required path: it adds a network dependency and a second config surface to a template whose required checks must pass on forks and offline-mirror CI without secrets.
- Per-metric multi-threshold gating (ts-style lines/functions/branches/statements): qualified as the calibration follow-on once measured example-suite coverage sustains stricter numbers. Not day-one: four thresholds quadruple the ways a template adopter's first PR goes red for reasons unrelated to their change.

##### Excluded by gate

The inert scaffold (bin (c)) is excluded — not by one of the six crate fitness gates, which do not apply to a pattern member, but by the item's principle: a declared-but-unwired threshold fails F137 parity (py blocks; ts merely aspires) and normalizes red-or-absent coverage signal in a template whose job is to model correct CI. ts's commented-out upload step is documented drift to fix in the follow-on project, not a pattern to port.

##### Up-and-comers

None in pattern space. Patch-coverage gating without a SaaS (e.g. diff-aware local gates) has no maintained Rust implementation surfaced in this survey; if one matures it would slot into this member without disturbing the tool member.

##### Fit for this template

The local gate fits the template's constraints exactly: no secret (works on fork PRs, which an external-service gate complicates), deterministic (no third-party check flakiness in the required path), cheap (threshold evaluation is free once the instrumented run exists), and R11-compatible (a single `coverage` job with `needs: plan` and predicate `needs.plan.outputs.code == 'true'`; own job rather than a `check` step because the instrumented build must not share `check`'s `target/`; `ubuntu-latest` only because the line-coverage metric is OS-independent and the tool's own CI proves both runners). The 80-line value fits a template whose example suite is small by design: strict enough to catch an untested module, lenient enough to survive example-code churn.

##### Recommendation

Declare the threshold in-repo and enforce it locally: `--fail-under-lines 80` in the required `coverage` CI job (runner `ubuntu-latest`, `needs: plan`, `if: needs.plan.outputs.code == 'true'`), mirrored in the `Justfile` coverage recipe. Required-check status (blocking the PR) is part of this recommendation: a non-blocking coverage job is bin (c) with extra steps. No `codecov.yml`, no upload token, no external check in the required path.

##### Ranked runner-up

Codecov tokenless upload as a non-required informational step in the same job (S_CODECOV_TOKENLESS_RUNNERUP). Promote to gating only by explicit owner call that also accepts the SaaS dependency for the template's required path; the local `--fail-under-lines` gate stays regardless, so promotion would add patch signal, never replace the project gate.

##### Tradeoffs

Local vs external: determinism, zero secrets, and fork-PR correctness vs patch-coverage signal and historical trends. The template's required path optimizes for the former; the overlay option recovers the latter without weakening the gate. 80 vs 95: day-one green on example code and adopter-friendliness vs ts-strictness; the 80 is a floor with a recorded ratchet plan, not a ceiling. Single metric vs multi: legibility and stability vs granularity; `lcov.info` retains the full data for any future multi-metric gate. Ubuntu-only job vs matrixed: half the instrumented-run cost vs per-OS numbers nobody gates on; the metric does not vary by OS at template scale.
