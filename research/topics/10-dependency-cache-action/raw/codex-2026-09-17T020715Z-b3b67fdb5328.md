### Landscape

This item decides the CI dependency-cache action: reuse Cargo downloads and dependency build outputs between GitHub Actions runs, while Cargo remains the authority for whether an artifact is valid. The first-party/toolchain bin has no Cargo-integrated cache action: the Rust Project's Cargo CI guide and GitHub's Rust starter workflow show build/test setup but no dependency-cache step ([Cargo CI guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html), retrieved 2026-09-16; [starter workflow](https://api.github.com/repos/actions/starter-workflows/contents/ci/rust.yml), retrieved 2026-09-16). `dtolnay/rust-toolchain@v1` is a maintained toolchain installer, not a cache mechanism, so it belongs to R42's out-of-scope provisioning choice ([repository API](https://api.github.com/repos/dtolnay/rust-toolchain), retrieved 2026-09-16). The established-standard bin is GitHub's MIT-licensed `actions/cache@v6`, whose own documentation defines explicit paths, keys, ordered prefix restore keys, and cache scope ([action definition](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), retrieved 2026-09-16; [GitHub dependency-caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), retrieved 2026-09-16). The established Rust-specialist bin also contains `Swatinem/rust-cache@v2`, but its LGPL-3.0 license fails the fixed gate below ([LICENSE](https://api.github.com/repos/Swatinem/rust-cache/contents/LICENSE?ref=v2.9.2), retrieved 2026-09-16). The up-and-comer bin contains `Mozilla-Actions/sccache-action@v0.0.11`; it caches compiler results, not the required Cargo registry/git/target set ([repository API](https://api.github.com/repos/Mozilla-Actions/sccache-action), retrieved 2026-09-16).

Authorities were selected by remit, not familiarity: the Rust Project publishes Cargo's CI guidance; GitHub owns both the cache service and `actions/cache`; each action maintainer publishes its action contract; and the pinned Python and TypeScript workflows establish the source principle ([Cargo guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html), [GitHub docs](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [rust-cache README](https://api.github.com/repos/Swatinem/rust-cache/readme), [pinned py workflow](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/.github/workflows/ci.yml#L85-L89), [pinned ts workflow](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/.github/workflows/ci.yml#L68-L74), all retrieved 2026-09-16). Practice is not selection proof: Tokio (33,164 stars) and Axum (27,156 stars) currently use `Swatinem/rust-cache` in CI, demonstrating that the specialized design is real production practice, while their repository APIs supply the adoption/maintainer-standing evidence ([Tokio API](https://api.github.com/repos/tokio-rs/tokio), [Tokio workflow](https://github.com/tokio-rs/tokio/blob/66e13876a7f0251309d61aef9e9d2821add6f356/.github/workflows/ci.yml), [Axum API](https://api.github.com/repos/tokio-rs/axum), [Axum workflow](https://github.com/tokio-rs/axum/blob/3f46d25e9274d485a99905d3734d37828112bc31/.github/workflows/CI.yml), all retrieved 2026-09-16).

### Principles and implementation

The shared requirement is the F035 capability: CI reuses dependency-fetch and Cargo dependency-build work across runs; agreement is at capability/architectural-pattern level, not at the language-setup-action mechanism ([F035 baseline review](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/BASELINE-REVIEW.md#L309), retrieved 2026-09-16). Python achieves it inside `astral-sh/setup-uv`; TypeScript achieves it through `actions/setup-node` with `cache: 'pnpm'`; Rust has no equivalent integrated toolchain action, so an explicit cache action is an appropriate ecosystem-specific composition ([pinned py CI](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/.github/workflows/ci.yml#L85-L89), [pinned ts CI](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/.github/workflows/ci.yml#L68-L74), [F035 review](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/BASELINE-REVIEW.md#L443), all retrieved 2026-09-16).

`actions/cache@v6` is the fit-preserving design: after R42's toolchain step, cache `~/.cargo/registry`, `~/.cargo/git`, and workspace-root `target`; key it by runner OS, a digest of `rustc -vV`, and all `Cargo.lock`, `Cargo.toml`, and `.cargo/config.toml` files. Use a restore prefix through the identical OS/compiler segment only. The exact key changes on resolved dependencies, manifests/configuration, or compiler identity; the fallback reuses retained downloads and lets Cargo's own fingerprints rebuild incompatible targets. That avoids a never-invalidating lockfile key and avoids discarding every useful artifact after a lockfile edit ([cache action inputs](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), [key matching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-key-matching), both retrieved 2026-09-16). Do not set `save-always`: the action's default post-save condition is `success()`, and its action definition says `save-always` is deprecated ([action definition](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), retrieved 2026-09-16). A minimal realistic future workflow is toolchain setup, a `rustc -vV` digest output, this cache step, then `cargo test --workspace --locked`; it is a proposal, not an executed build.

Observable acceptance criteria are: an unchanged Ubuntu or macOS run receives an exact hit; a `Cargo.lock` change creates a new exact key but can restore same-compiler content; a compiler or OS change cannot restore `target` artifacts from the old compiler/OS; and a failed job does not save a new cache. GitHub documents per-repository cache storage/eviction (10 GB default, seven-day inactivity eviction) rather than an OS-specific quota, so Ubuntu and macOS differ only because the proposed keys intentionally differ; `restore-keys` behavior and save-on-failure behavior are action-wide ([GitHub cache limits](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy), [action definition](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), both retrieved 2026-09-16). GitHub also warns that cache contents are unverified and should contain neither secrets nor untrusted writes; retain default restricted writes for fork PRs ([cache security guidance](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#best-practices-for-using-caches-securely), retrieved 2026-09-16).

### Dominant choice

Choose `actions/cache@v6` (current v6 range; latest observed release v6.1.0) as the explicit Cargo cache action. It passes the fixed license gate, is GitHub-maintained, and exposes the key and path policy this template must own rather than hiding it behind a non-compatible specialist action ([release endpoint](https://api.github.com/repos/actions/cache/releases/latest), [repository endpoint](https://api.github.com/repos/actions/cache), both retrieved 2026-09-16).

### Up-and-comers

`Mozilla-Actions/sccache-action` is the relevant up-and-comer only for a later compiler-cache performance experiment; it must be additive to, not a replacement for, Cargo dependency caching. Its action-only crate figures and RustSec advisory metric are inapplicable for the same reason as `actions/cache`; no performance result is claimed because no comparable workload, instrumentation, cache state, latency, throughput, or storage cost was measured ([repository endpoint](https://api.github.com/repos/Mozilla-Actions/sccache-action), retrieved 2026-09-16).

### Fit for this template

CLI: cache registry/git inputs and `target` so repeat command builds reuse dependencies, while the lockfile plus Cargo fingerprints remain the correctness boundary ([GitHub cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), retrieved 2026-09-16). Library: include `Cargo.toml` in the digest because feature/dependency declarations can change independently of a lockfile; a committed lockfile is still expected for the template's CI reproducibility policy ([Cargo CI guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html), retrieved 2026-09-16). Web service: the identical Cargo workspace and target model applies; cache isolation is by OS and compiler, not application role ([action definition](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), retrieved 2026-09-16). For a future R02 workspace, cache the root `target`; use the globbed lockfile/manifest/config digest so each member contributes without a new action instance ([GitHub cache key matching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-key-matching), retrieved 2026-09-16).

### Recommendation

Adopt `actions/cache@v6` beside, never inside, R42's selected toolchain step. Configure paths `~/.cargo/registry`, `~/.cargo/git`, and `target`; use exact key `cargo-${{ runner.os }}-${{ steps.rustc.outputs.cache-key }}-${{ hashFiles('**/Cargo.lock', '**/Cargo.toml', '**/.cargo/config.toml') }}` and restore prefix `cargo-${{ runner.os }}-${{ steps.rustc.outputs.cache-key }}-`. This preserves the source capability while deliberately changing the unavailable setup-integrated mechanism; the explicit key is a justified native design, not a new shared requirement ([F035 reconciliation](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/BASELINE-REVIEW.md#L443), [cache action contract](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), retrieved 2026-09-16). R20, not R10, chooses whether the rendered action reference is later pinned to the current v6.1.0 commit rather than its major-version range ([research index](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/research/CLAUDE.md), retrieved 2026-09-16).

### Ranked runner-up

`Swatinem/rust-cache@v2` would win only if the owner changes the candidate-license gate to permit LGPL-3.0 GitHub Action code after a separate licensing decision. Its maintained Cargo-aware keying, cleanup, and workspace controls would then reduce template YAML, but that condition is not currently met ([rust-cache README](https://api.github.com/repos/Swatinem/rust-cache/readme), [license](https://api.github.com/repos/Swatinem/rust-cache/contents/LICENSE?ref=v2.9.2), retrieved 2026-09-16).

### Tradeoffs

Against `Swatinem/rust-cache`, the recommendation gives up automatic Cargo metadata pruning, one-week artifact pruning, and action-managed fallback keys; it accepts a small explicit YAML policy because the specialist fails the license gate ([rust-cache README](https://api.github.com/repos/Swatinem/rust-cache/readme), retrieved 2026-09-16). Against `sccache-action`, it gives up remote compiler-result reuse but retains the full requested dependency-cache contract and avoids adding a second cache layer without a measured workload ([sccache action repository](https://api.github.com/repos/Mozilla-Actions/sccache-action), retrieved 2026-09-16). Both choices inherit GitHub cache storage limits and eviction rather than an OS-specific limit ([GitHub cache limits](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#usage-limits-and-eviction-policy), retrieved 2026-09-16).

### Migration implications

P03 should add the cache step to `.github/workflows/ci.yml` immediately after the R42 toolchain-install step; add a preceding step that emits the `rustc -vV` digest; and add no Rust dependency, Cargo feature, or scaffolded cache code. The same step may be placed in each R11-defined job because its key includes job environment inputs and GitHub cache scope is key/version/branch based ([action definition](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), [GitHub cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), retrieved 2026-09-16).

### Validation strategy

Planned, not executed: P03 creates a small locked workspace, runs `cargo test --workspace --locked` twice on each fixed OS, and records an exact `cache-hit` on the second run. It then changes a dependency in `Cargo.lock`, reruns, and expects a new exact key plus a same-compiler prefix restore followed by Cargo rebuilding only what its fingerprints reject. It changes the selected toolchain and expects no target restore because the `rustc -vV` digest changes. Finally it deliberately fails a post-cache Cargo command and verifies that no new cache entry is saved because `actions/cache` uses `post-if: success()` ([action definition](https://api.github.com/repos/actions/cache/contents/action.yml?ref=v6.1.0), [cache key matching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#cache-key-matching), retrieved 2026-09-16). These commands are the empirical acceptance plan; no template, workflow, or build exists or was run in this research item.

### Confidence & re-verify trigger

High confidence in the license-gated recommendation and medium confidence in the unmeasured performance benefit. Re-verify if GitHub changes cache key/scope/eviction semantics, `actions/cache` releases a new major, R20 changes action pinning policy, R42 changes the toolchain invocation so `rustc -vV` is unavailable, or an owner changes the LGPL-3.0 gate; re-measure cache size and hit rate once the real CLI/library/web workspace exists ([GitHub cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), [actions/cache releases](https://api.github.com/repos/actions/cache/releases/latest), retrieved 2026-09-16).
