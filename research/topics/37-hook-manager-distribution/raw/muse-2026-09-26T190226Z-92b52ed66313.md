### Principles and implementation

**Shared requirement and agreement level.** The shared principle, scoped to this item's divergence-analysis rows, is: **define the pre-commit quality suite once in the hook manager's config, enforce it locally on every commit, and re-enforce the identical suite in CI against the whole tree ("define once, enforce twice").** Source: F143/F144/F174 ledger rows plus D-022(1) (ts dual-enforcement structure) and py ADR 0018 (per-check parity intent). Agreement is required at **capability level**: (a) a fresh clone can reach "hooks installed and passing" through one documented setup path; (b) CI runs the same checks the hooks run, so a bypassed or unwired hook cannot merge a violation. Essential behaviors: lefthook version pinned and reproducible; `lefthook install` trigger documented and idempotent; CI re-run covers the whole tree (`--all-files`), not only the diff. What must agree across py/ts/rs: the lefthook tool itself (F142, already common), the parallel pre-commit stage (F146), and the dual-enforcement capability. What may vary: the install channel and the wiring trigger, because these are class-C language-bound mechanics — pnpm's devDependency-plus-`prepare` lifecycle has no Cargo analogue, and Cargo cannot install a Go binary as a dependency.

**Architectural alternatives compared before choosing tools.** (1) Package-manager-scoped install with lifecycle auto-wiring (ts's pattern): impossible in Rust — Cargo has no `prepare` equivalent and no non-crate dependency slot. Rejected as inapplicable, not as inferior. (2) Foreign-runtime global install (`bun install -g`, `npm i -g`): works mechanically but drags a JavaScript runtime into a Rust repo's bootstrap and contradicts R42's bare-executable-on-PATH rule. Rejected. (3) Toolchain provisioner (`mise`/`asdf` version file): centralizes pins but inserts a provisioner R42 explicitly forbids, and every contributor and CI job must first install the provisioner. Rejected. (4) `build.rs` auto-install: runs on every build for every consumer of the library including downstream dependents, mutates state outside `OUT_DIR`, and violates the Cargo Book's build-script contract. Rejected. (5) Explicit setup recipe + pinned direct-download installer script (py's pattern, Bun replaced by a GitHub-release download): one manual step, no foreign runtime, no provisioner, reproducible pin, auditable checksum. Selected.

**How the recommended design preserves each principle.** The pinned script preserves reproducibility (same bytes everywhere, checksum-verified). The explicit `just setup` step preserves the "one documented path to wired hooks" capability; the `just hooks-install` fallback preserves F145's manual re-wire convention. The CI run-all step preserves dual enforcement exactly as D-022(1) intends, placed per R11's accepted structure (below). The class-F disagreement in F174 (ts run-all step vs py per-check jobs) is resolved for Rust in favor of ts's run-all shape because R11's accepted `ci-job-structure` already routes every non-compiling check into the `hygiene` job as an ordered step — one `lefthook run` step reuses the single hook config as the check list instead of duplicating each tool's invocation in YAML, which is precisely the drift the "define once" half of the principle forbids. Rationale for the py/ts follow-on: py's ADR-0018 per-check table duplicates the hook job list in CI configuration; adopting a run-all parity step (as ts already has) would collapse that duplication without changing which tools run. That change is out of scope here; this paragraph supplies its rationale.

**R69 (`web-extra-surface`) effect:** none on manager wiring. R69's accepted value gates `src/web/`, one serve binary, web tests, and later web layers behind the `web` feature. Hook-manager install, `lefthook install`, and the run-all step are feature-agnostic; the only web coupling is a future web-specific hook *job* owned elsewhere, which runs inside the container this item wires. `assumes web-extra-surface` is recorded without behavioral consequence.

**F186 readiness-check content (baseline review).** The hook-toolchain readiness check audits: `lefthook` (this item, presence via `command -v lefthook` per R42's acquisition-channel rule), `just` (recipe runner), plus the hook-job tools R39/R40 select and their invocation per R42. It does **not** audit `bun` or `uv` — those are source-specific runtime tools with no function in a Rust repo. Report-only shape (sibling F181/F185), never aborting `setup` (unlike F182).

**Minimal realistic example.** `lefthook.yml` with a parallel `pre-commit` stage (jobs owned by R38–R41 reference their tools as bare executables); `scripts/install-lefthook.sh` pinning `LEFTHOOK_VERSION=2.1.14`, downloading the `x86_64-unknown` / `aarch64` release asset matching `uname -s -m`, verifying sha256, installing to `~/.local/bin` (or `$CARGO_HOME/bin` when on PATH); `Justfile` recipes `setup` (depends on `hooks-install`) and `hooks-install` (runs installer when `command -v lefthook` fails or version mismatches, then `lefthook install`); CI `hygiene` job step running the installer plus `lefthook run pre-commit --all-files`.

**Executable acceptance check (planned, not run — no empirical engine in this leg):** on a fresh clone on ubuntu-latest and macos-latest, `just setup` exits 0; `git commit` triggers the `pre-commit` stage; `lefthook run pre-commit --all-files` exits 0 on a clean tree and nonzero when a seeded violation (e.g. trailing whitespace) is introduced; the CI `hygiene` job fails on the seeded violation and passes after removal. No check was executed in this research leg; execution belongs to synthesis/empirical audit.

No `BASELINE-REVIEW:` challenge: F186's ADOPT capability is retained with derived content as recorded above; no ledger change is proposed.

#### CI hook-suite re-run step (F174 hygiene step)

##### Landscape

This member is a CI pattern, not a package: no crates.io figures, GitHub figures, RustSec entries, or download counts apply. The pattern landscape has two precedents: ts's run-all step (`pnpm exec lefthook run pre-commit --all-files` inside the `ci` job, `.github/workflows/ci.yml:106`, D-022(1)) and py's per-check parity (ADR 0018: each tool mapped to its own CI job, no literal hook-suite re-run). The deciding authority is R11's accepted `ci-job-structure` (quoted in run `inputs/parameters.json`): tiered jobs partitioned by whether a check compiles Rust; non-compiling checks are ordered steps of the cheap `hygiene` job (no cache, no `needs` edge); compiling checks are steps of the matrix `check` job. A hook-suite re-run executes formatters/linters/scanners but compiles nothing itself, so R11's rule places it unambiguously.

##### Principles and implementation

The step preserves the "enforce twice" half of the shared principle: CI executes the identical `lefthook.yml` job list against the whole tree, so the hook config remains the single source of truth for which checks exist. Implementation: the `hygiene` job gains two ordered steps — (1) run `scripts/install-lefthook.sh` (same pin as local; fail-closed, `--locked`-equivalent hermeticity via checksum), (2) `lefthook run pre-commit --all-files` (optionally `--no-auto-install` to guarantee CI never mutates hook state). No `lefthook install` in CI: `lefthook run` does not require installed shims. Whole-tree (`--all-files`) rather than diff-scoped, because the hygiene job has no path-gating `needs` edge by design (R11: formatter failures must report even when the compile tier is skipped).

##### Dominant choice

ts's run-all shape placed as an ordered step of R11's `hygiene` job. This resolves the class-F disagreement for Rust: run-all wins over per-check jobs because duplicating each hook job's invocation in workflow YAML would create a second check list that drifts from `lefthook.yml`, violating "define once". R39/R40's hook-job tools must therefore be invocable in the hygiene job's environment (their problem to solve within their items; this step only shells out to the manager).

##### Qualified shortlist

A dedicated no-cache `hooks-parity` job (needs: plan, positive predicate) is qualified only if the hook suite ever needs an environment hygiene cannot provide (e.g. a secret-bearing scanner that must not share a job with untrusted-PR steps) — currently no such need is evidenced, and R11's ceiling of roughly six cache-bearing job ids plus its "non-compiling check is a step of hygiene" rule both argue against spending a job id here. Diff-scoped `lefthook run` (no `--all-files`) is not qualified: it reintroduces exactly the skip-gating hazard R11's detector design rejects.

##### Excluded by gate

py's per-check-job mirror (one CI job per hook tool): excluded by R11's accepted structure — non-compiling checks do not get their own jobs, and each new job id consumes cache-budget and required-check surface. A matrix-leg placement inside `check`: excluded — the suite compiles nothing, and matrixing it over `target-os-matrix` would burn compile-runner minutes for byte-identical verdicts (formatters/linters used here are platform-independent; any platform-sensitive check belongs in `check` on its own merits, decided by its owning item).

##### Up-and-comers

lefthook's `--all-files` output formats and JUnit reporters for check-run annotations are worth adopting for failure readability once the step exists; they change presentation, not placement. Monitor only.

##### Fit for this template

All six fitness gates are inapplicable-as-crates and answered as a pattern: no new license surface (MIT lefthook binary, already covered); no MSRV contribution; no RustSec surface; OS matrix satisfied because the step runs in `hygiene` on ubuntu-latest (R11: single-job non-compiling workflows land on ubuntu-latest) with the installer script covering macOS for local parity; no features/async coupling; negligible CI-time cost (one binary download, cached between runs) and zero compile-time cost. `unsafe` posture: inapplicable.

##### Recommendation

Add the install-plus-`lefthook run pre-commit --all-files` step pair to the `hygiene` job in `.github/workflows/ci.yml`, consuming R11's accepted structure unchanged.

##### Ranked runner-up

A standalone `hooks-parity` job behind the `code` detector output, reserved for the day a hook job cannot run inside `hygiene`; adopt only with a recorded reason and a job-id budget check against R11's ceiling.

##### Tradeoffs

One run-all step gives one pass/fail verdict for the whole suite rather than per-tool annotations — coarser failure attribution than py's per-check jobs, but zero config duplication and one obvious place to look. Attribution is recoverable via lefthook's per-job output and (later) JUnit annotations without changing placement. The step also makes `hygiene` depend on the hook-job tools being installed in that job — R39/R40 must keep their tools CI-installable, a constraint this item imposes but does not itself satisfy.
