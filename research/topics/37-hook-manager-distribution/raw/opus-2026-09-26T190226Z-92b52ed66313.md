### Principles and implementation

**Shared requirement, source and agreement level.** DIVERGENCE-ANALYSIS classifies R37 as class C
(`docs/port/DIVERGENCE-ANALYSIS.md:153`): D-020(1) records that npm/pnpm "can list a precompiled binary as a
devDependency and auto-run a lifecycle hook on install; uv and Cargo have no such path". The principle both
source repositories implement is:

> The hook manager is a pinned development tool acquired through the repository's declared tool channel;
> one documented step on a fresh clone activates the hooks; a hook never silently passes because its
> tooling is absent; and CI, which is the authority, re-checks what the hooks check so that a bypassed hook
> (`git commit --no-verify`) cannot land unchecked.

The agreement level is **capability plus policy**: a pinned version, exactly one declared activation step,
fail-closed behaviour when the binary is missing, and CI parity with the hook suite. The mechanism is **not**
an agreement point; each ecosystem realises it with its own acquisition channel.

**What must agree across py, ts and rs, and what may vary.**

**Cross-repository evidence: justified differences versus drift.**

- **ts auto-wiring is a justified ecosystem difference.** `package.json:36` `"prepare": "lefthook install"`
  plus `package.json:54` `"lefthook": "^2.1.10"` ride pnpm's lifecycle. Cargo has no lifecycle hook that runs
  on `cargo build` or `cargo fetch` other than build scripts, and the Cargo book says build scripts "should
  not modify any files outside of" `OUT_DIR` (`build-scripts.md:88-89`). So an automatic trigger has no
  sanctioned Cargo analogue, and the explicit step is the Rust-native realisation of the same capability.
  One weakness in ts: the caret range `^2.1.10` is a floor, not an exact pin; the lockfile pins it.

  GitHub-release Darwin binaries". The release listings contradict it at py's own pin and at the current

**Recommended design and how it preserves each principle.**

1. *Pinned, declared-channel acquisition.* The `Justfile` tool table gains
   `gh:evilmartians/lefthook@v2.1.14`, installed by R42's generic `install-tool` recipe through its second spec
   form as `ubi --project evilmartians/lefthook --tag v2.1.14 --in "${CARGO_HOME:-$HOME/.cargo}/bin"`.
   `ubi` itself is the crates.io entry `ubi-cli@0.12.0` in layer 2 (`GET
   https://crates.io/api/v1/crates/ubi-cli/0.12.0`: `bin_names: ["ubi"]`; the crate named `ubi` has
   `bin_names: []`). `lefthook.yml` sets `min_version: 2.1.14` so an older binary refuses to run (check T5),
   and `just setup` asserts `lefthook version` equals the pin, the same shape as R38's
   `committed --version` assertion (`R38 DECISION.md:168`).
2. *One activation step.* `just setup` (the F182 bootstrap) ends with `just hooks-install`, whose body is
   `lefthook install`. After that, lefthook's default auto-install re-syncs `.git/hooks` whenever
   `lefthook.yml` changes and any hook runs (check T6), and `lefthook check-install` exits 1 on a stale or
   absent wiring (checks T1, T7).
3. *Never silently pass.* `assert_lefthook_installed: true` in `lefthook.yml`. Without it, a hook whose binary
   has disappeared prints `Can't find lefthook in PATH` and exits 0; with it, the hook exits 1 (check T8).
4. *CI parity.* A `hygiene` step runs `lefthook run pre-commit --all-files --no-auto-install --no-tty
   --fail-on-changes` with `LEFTHOOK_EXCLUDE=compiles`. Every pre-commit job that compiles Rust carries
   `tags: [compiles]` and has its CI counterpart as an ordered step of R11's `check` job.

##### Principles and implementation

The principle is "one exact pin in one authoritative place, installed by the repository's declared tool
channel, with the same binary used locally and in CI". R42 already fixed the channel: a single tool table,
a generic `install-tool` recipe, crates.io tools via `cargo binstall --locked --no-confirm`, and release-only
tools via `ubi`. lefthook is release-only, so it is the first occupant of layer 4, which R42 predicted
("R37, R39 or R40 selects a tool not published on crates.io, which activates layer 4 for the first time",
`R42 DECISION.md:470`). Implementation: tool-table entry `gh:evilmartians/lefthook@v2.1.14` →
`ubi --project evilmartians/lefthook --tag v2.1.14 --in "${CARGO_HOME:-$HOME/.cargo}/bin"`. The install
directory is chosen deliberately: R42's invocation rule requires a bare executable resolved on `PATH`, and
`$CARGO_HOME/bin` is already on `PATH` for every rustup user and is where `cargo binstall` places layer-2
tools. `ubi`'s own default, `./bin`, is not on `PATH` (`ubi` README, `--in` row: "Defaults to `./bin`").
Version guard in depth: `min_version: 2.1.14` in `lefthook.yml` refuses older binaries at run time (check T5);
`just setup` asserts the exact version; the tool table is the only place the number is written besides
`min_version`.

##### Dominant choice

There is no dominant Rust-ecosystem channel for a non-crate binary: the practice survey found biome, oxc and
rolldown installing crates via `cargo binstall` and never a release-only binary, and 0 of 17 projects using
lefthook. Within this template the dominant choice is fixed by R42: `ubi` for release-only tools.

##### Principles and implementation

The principle is "one documented step activates hooks on a fresh clone, and hooks never silently pass".
Cargo offers no sanctioned automatic trigger, so the step is explicit: `just setup` runs `install-tools`,
then `hooks-install` (`lefthook install`), then the exact-version assertion. Three lefthook settings make the
explicit step robust. `assert_lefthook_installed: true` turns a vanished binary from exit 0 into exit 1 (T8).
Default auto-install keeps `.git/hooks` synchronised with later `lefthook.yml` edits (T6). `lefthook
check-install` gives the doctor (F186) and CI a machine-readable wired/stale signal (T1, T2, T7). One side
effect must be named: because auto-install is the default, the F175 recipe `just hooks-run` would wire hooks
as a side effect, so it carries `--no-auto-install`, and so does the CI step.

The generated hook is also worth knowing: `lefthook install` writes a `.git/hooks/pre-commit` that tries
`$LEFTHOOK_BIN`, then `lefthook` on `PATH`, then the absolute path of the binary that installed it (observed:
`/opt/homebrew/bin/lefthook`), then a chain of `node_modules`, `go tool`, `bundle exec`, `pnpm`, `uv run`,
`mise exec` and `devbox run` fallbacks. Without `assert_lefthook_installed` the final branch only echoes
`Can't find lefthook in PATH`.

##### Dominant choice

Explicit, documented, one-time command — 4 of 17 surveyed projects, including the Rust compiler itself; no
surveyed project wires hooks from `build.rs`.

##### Principles and implementation

The principle is "CI is the authority and catches a bypassed hook". R11 constrains the form: a check that
compiles nothing is a step of `hygiene`, and a check that compiles is an ordered step of `check`
(`R11 DECISION.md:278`); `cargo fmt --check` is already "lifted into the no-compile `hygiene` job because it
compiles nothing" (`:267`), so `hygiene` carries `rustfmt`. The hook suite may contain a compiling job
(clippy or `cargo check`, depending on R30's tier). Running it inside `hygiene` would compile in the job R11
keeps compile-free. So compiling jobs are tagged `compiles`, excluded from the `hygiene` re-run with
`LEFTHOOK_EXCLUDE=compiles`, and their commands appear as steps of `check` — the same division ruff uses with
`SKIP=rustfmt`. The step passes `--no-auto-install` (a CI checkout needs no hooks; T4 left `check-install`
at 1), `--no-tty`, and `--fail-on-changes` (a fixing job that rewrites files fails CI instead of passing
silently; T9 exit 0 versus T10 exit 1). Scope is the pre-commit stage only: `commit-msg` cannot run over
files and is re-checked by R38's range job; pre-push jobs belong to R39 (secret range scan, CI in R17) and R32
(opt-in tests).

##### Dominant choice

A single run-all step (ts; ruff). The per-check parity table (py) is the minority pattern, and its own ADR
records the manual-sync cost.

##### Qualified shortlist

1. One `hygiene` step, compiling jobs excluded by tag (selected).
2. The same step without exclusion, valid only while no pre-commit job compiles (for example if R30 keeps
   clippy at pre-push); the tag is kept anyway so a later compiling job cannot silently move compilation into
   `hygiene`.

##### Excluded by gate

- Whole suite inside `check` — R11 partition: it would put non-compiling checks behind the compile tier and
  duplicate them across both matrix legs.
- Its own job — R11: "a check that compiles nothing is a step of `hygiene`".
- Hosted pre-commit.ci — built for the pre-commit framework, not lefthook.
- Per-check parity only (py) — principle gate: no mechanical guarantee that a newly added hook job is
  mirrored in CI (ADR 0018 `:16-18`, `:122-123`).
- Crate gates 2, 5, 6: inapplicable — no crate is added; lefthook is a prebuilt Go binary on both runners.

##### Up-and-comers

A drift guard that fails CI when a `compiles`-tagged job has no identical command among `check`'s steps. It
could be built from `lefthook dump` output and the workflow file. No maintained implementation was found;
it is proposed, not specified, and its owner (plausibly R15's drift check) is not decided here.

##### Fit for this template

The web feature (R69) adds compiling checks that R11 already places in `check`; it adds nothing to the
non-compiling pre-commit re-run. The step runs on `ubuntu-latest` only, as `hygiene` does; the hook suite's
macOS behaviour is exercised locally by contributors, and every compiling job still runs on both runners in
`check`.

##### Recommendation

In R11's `hygiene` job: `just install-tool gh:evilmartians/lefthook@v2.1.14`, then
`lefthook run pre-commit --all-files --no-auto-install --no-tty --fail-on-changes` with
`LEFTHOOK_EXCLUDE=compiles` and `GITHUB_TOKEN` exported for `ubi`. Every compiling pre-commit job carries
`tags: [compiles]` and has its command as a step of `check`.

##### Ranked runner-up

Per-check CI steps with a parity table (py ADR 0018). It wins only if lefthook's `--all-files` semantics stop
matching per-file hook semantics for a job that matters (for example a job whose command cannot accept the
full file list), because then the run-all step would no longer mean "what the hook checks".
