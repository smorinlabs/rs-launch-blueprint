### Principles and implementation

Shared requirement (source: py precedent + ledger F307/F312/F332/F333; agreement level: capability + standard). The principle is a machine-checkable API contract: the web service's OpenAPI document is generated from the code, post-processed so documented errors match the runtime envelope, curated so generated-client names are stable, committed as a reviewable file, kept fresh by a staleness test, and gated in CI against breaking changes. What must agree: a committed OpenAPI 3.x JSON snapshot exists, regenerates deterministically from the `web`-gated code, carries stable operation ids, documents the R70 envelope, and CI fails on breaking drift versus the base branch. What may vary: the generator crate, the snapshot path, the export mechanism, and whether the CI job is standalone or folded into `ci.yml` (R11 owns placement).

Architectural alternatives compared before choosing libraries. Code-first (annotate handlers, generate spec) versus design-first (hand-write spec, generate server stubs): code-first wins because the template's value is a working service whose docs cannot drift — py already chose code-first, and the Rust design-first stub generators are immature. Runtime-served spec versus committed snapshot: the committed snapshot wins because R83 (contract fuzzing) and R84 (typed clients) both consume a file, and reviewable diffs are the point; a served `/openapi.json` endpoint remains a compatible optional extra. Same-language differ versus `oasdiff`: `oasdiff` wins because no Rust-native differ is maintained, CI-runnable as an action, and gate-passing (see member 3).

Recommended design preserving each principle: `utoipa 6` + `utoipa-axum 0.3` generate the spec from axum routes; a `utoipa::Modify` implementation injects the R70 envelope schema and rewrites default error responses (mirrors py's `original_openapi` wrap); per-route `operation_id = "…"` attributes curate stable ids (mirrors py's `_operation_id()`); a `#[cfg(feature = "web")]` library function returns the `OpenApi` value, a test re-serializes it and diffs `docs/api/openapi.json` (mirrors py's snapshot test, including `info.version` normalization), a `just export-openapi` recipe regenerates via an example target; `oasdiff/oasdiff-action/breaking@v0.1.17` gates PRs on the snapshot diff (same tool as py, newer tag). R70's envelope shape is open, so the `Modify` implementation reads the schema from R70's module rather than hardcoding it — no block on R70. No `BASELINE-REVIEW:` findings: no recorded baseline is challenged.

Minimal realistic example: two axum routes (one success + one error path) with `operation_id`s, the `Modify` pass replacing the default 422/4xx schema with a placeholder problem object, `cargo test --features web` asserting snapshot equality, and `just export-openapi` rewriting the file. Proposed acceptance check (planned, not executed by this leg): build the example on the 1.96 floor, run the staleness test green, hand-edit the snapshot and watch it fail, run `oasdiff breaking` against a fixture with a removed operation and watch it fail. Reference implementations: utoipa's own axum examples in `juhaku/utoipa` (same repo as the crates, released in lockstep) and the shuttle/mistral.rs adopters above.

### Recommendation

One stack: `utoipa 6.0.0` + `utoipa-axum 0.3.0` for generation with a `Modify` post-processing pass and per-route `operation_id` attributes; committed `docs/api/openapi.json` with a regenerating staleness test and a `just export-openapi` recipe backed by a `--features web` example target; `oasdiff/oasdiff-action/breaking@v0.1.17` (SHA-pinned per R20) as the CI breaking-change check, designed as a tool invocation R11's `ci.yml` can host. Adopt the pipeline — py's principle survives the port.

#### snapshot-staleness-test

##### Landscape

Bin map for the snapshot/staleness mechanism. First-party: none — no Cargo-native snapshot file exists. Established: the hand-rolled regenerate-and-diff test (serialize at test time, compare against a committed file, normalize volatile fields), used across ecosystems and exactly py's `test_openapi_snapshot.py:30` shape. Up-and-comers: none identified for OpenAPI snapshots; the general Rust snapshot-test crate (`insta`) is adjacent but solves a different problem (inline UI snapshots, not a consumable contract file). No new crate is required: the mechanism reuses member 1's `OpenApi` type plus `serde_json`, already in the tree via R69.

##### Principles and implementation

Principle (F332): the generated spec is a committed, reviewable contract that cannot silently drift from the code. Essential behaviors: (a) one library function is the single source of the document; (b) the committed file byte-matches a fresh serialization under a documented normalization (`info.version` pinned to a constant, like py's `SNAPSHOT_VERSION`, since the package version churns independently); (c) the test failure message tells the developer the exact regeneration command; (d) regeneration is a one-command Justfile recipe. Export mechanism comparison: an `examples/export-openapi.rs` target run as `cargo run --example export-openapi --features web` beats a `build.rs` (build scripts run implicitly, cannot fail CI on drift, and complicate caching/MSRV), beats a serve-binary subcommand (R69 freezes the serve CLI surface to `-hVvq --config --debug`), and beats a second binary target (a whole target for a dev-only task). Determinism: `utoipa::openapi::OpenApi` serializes via serde in struct order with `BTreeMap`-ordered paths, so pretty-printed JSON is stable byte-for-byte; the acceptance check asserts regeneration idempotence.

##### Dominant choice

Committed `docs/api/openapi.json` + `tests/web/test_openapi_snapshot.rs` (gated `#![cfg(feature = "web")]` per R69) + `just export-openapi` → `cargo run --locked --features web --example export-openapi`. Crate figures: inapplicable — no new dependency; the mechanism uses `utoipa::openapi::OpenApi` (member 1) and `serde_json` (already required by axum). Test logic mirrors py: load committed file, regenerate via the library function, set `generated["info"]["version"] = SNAPSHOT_VERSION`, compare, and on mismatch print the diff with the recipe invocation. The example target shares the library function, so test and recipe cannot disagree.

##### Qualified shortlist

`insta`-style snapshot assertion as the comparison engine inside the same test (keeps the committed-file contract, swaps hand-rolled diff output for `insta::assert_json_snapshot!`). Not preferred: it adds a dev-dependency and its own snapshot directory conventions for what is otherwise a ten-line file comparison, and R33's snapshot-testing decision (resolved) scopes `insta` to UI-ish snapshots, not contract files.

##### Excluded by gate

Build-script generation (`build.rs` writing the spec at compile time): excluded — violates the principle (generated files are not reviewable diffs; drift cannot fail CI) and complicates gates 2/6 (build scripts run on every platform/toolchain, widening MSRV and compile-time surface for zero benefit). Serve-binary `export-openapi` subcommand: excluded — contradicts R69's accepted CLI surface, which this item must assume, not relitigate.

##### Up-and-comers

None identified: the regenerate-and-diff test is a stable pattern, not an evolving library space. Revisit only if a maintained crate offering committed-file contract testing with diff output appears.

##### Fit for this template

Zero new dependencies, zero runtime cost, works identically on ubuntu + macos (pure file I/O + serde), feature-gated exactly like the rest of the web surface, and produces the file R83/R84 consume. The `docs/api/openapi.json` path mirrors py, keeping cross-implementation familiarity — the one place familiarity is legitimate evidence, since R83/R84 and the docs tree key on the path.

##### Recommendation

The dominant choice above: `docs/api/openapi.json`, web-gated regenerating test with `info.version` normalization, `just export-openapi` via an example target.

The `info.version` normalization hides real version drift by design — accepted because package version bumps must not rewrite the contract; the breaking-change check (member 3) is the drift detector, not the version string.

#### breaking-change-detection

##### Landscape

Bin map for OpenAPI breaking-change detection runnable in CI. First-party: none. Established industry standard, cross-language: `oasdiff` (Go binary, repo `oasdiff/oasdiff`, stars 1,387, pushed 2026-09-21, 48 open issues; latest release v1.32.1, 2026-09-15) with its GitHub Action (`oasdiff/oasdiff-action`, stars 65, pushed 2026-09-15, latest tag v0.1.17) — the same tool py pins at `breaking@v0.1.6`. Rust-native hopefuls, all immature: `schemadoc-diff` 0.1.20 (last release 2023-07-13, no repo listed, 1,505 / 6 downloads), `rusty-schema-diff` 0.1.1 (2024-12-11, license `non-standard`, 1,709 / 6 downloads), `brake` 2026.9.3 (released 2026-09-19, 119 downloads, 0 stars, `rust-version` 1.98.1). Authorities: GitHub releases/tags APIs for currency, crates.io for the Rust candidates' vitality, py's `api-contract.yml:44` for the invocation shape.

##### Principles and implementation

Principle (F333): incompatible API changes fail CI before merge, with the base branch as the reference. Essential behaviors: (a) compare base-branch snapshot vs PR snapshot; (b) classify changes into breaking / non-breaking per OpenAPI semantics (removed operations, narrowed schemas, removed enum values, new required fields); (c) run only when the snapshot changed (or unconditionally with a trivial pass — equivalent outcomes); (d) placement-agnostic invocation R11's `ci.yml` can host. `oasdiff` implements exactly this as a language-agnostic JSON differ: it never sees Rust, only `docs/api/openapi.json` at two revisions, so the Rust port inherits py's proven semantics rather than re-implementing them. The Rust candidates each fail a gate or the maturity bar (below); none ships a GitHub Action, so each would also need a custom `cargo install` + wrapper step — slower CI, more maintenance, no benefit. Performance: `oasdiff` diffs two local files in well under a second; no benchmark is needed because the workload (one file pair, CI) states its own budget, and no unlike-benchmark comparison is made.

##### Dominant choice

`oasdiff/oasdiff-action/breaking@v0.1.17` (py pins v0.1.6; v0.1.17 is the newest tag at retrieval, released alongside oasdiff v1.32.1 on 2026-09-15). Figures: action repo 65 stars, not archived, pushed 2026-09-15; oasdiff proper 1,387 stars, pushed 2026-09-21, 48 open issues. Crate-figure gates: inapplicable in the Rust-crate sense — `oasdiff` is a Go binary consumed as a prebuilt GitHub Action, adding zero entries to `Cargo.toml`/`Cargo.lock`, zero MSRV surface, zero compile time, and zero `unsafe`. The applicable gates are restated: license (oasdiff is Apache-2.0 — compatible with the template's `MIT OR Apache-2.0` since it is a CI tool, not linked code); no RustSec surface (not a Rust dependency); platform (the action runs on `ubuntu-latest`, the same runner py uses; R11 places non-compiling checks on ubuntu or in `hygiene`). Pin the action to its commit SHA per R20's pinning policy at synthesis time. Invocation compares the base and head blobs of `docs/api/openapi.json`; on non-PR events (push to main) compare `before→after` or trivially pass when no base exists — the check must never fail a push it cannot evaluate.

##### Qualified shortlist

None qualified. `schemadoc-diff` is the least-bad Rust-native option (Apache-2.0, real breaking-change detector) but is `at-risk`: no repository listed, no release since 2023-07-13, 6 downloads in 90 days — concrete staleness signals — and it ships no GitHub Action, so adopting it means owning a wrapper around a dormant 0.1 library. It stays a re-verify candidate, not a shortlist member.

##### Excluded by gate

`brake` 2026.9.3 (MIT, 119 downloads, 0 stars, repo `grahambrooks/brake` pushed 2026-09-25): excluded by gate 2 — declared `rust-version` 1.98.1 exceeds the R69 floor of 1.96 — and by maturity (seven days old, no users, no action). `rusty-schema-diff` 0.1.1 (1,709 / 6 downloads, 2024-12-11): excluded by gate 1 — published license is the non-SPDX string `non-standard`, incompatible with the `MIT OR Apache-2.0` requirement. `schemadoc-diff`: excluded as above (at-risk + no CI distribution). ##### Fit for this template
