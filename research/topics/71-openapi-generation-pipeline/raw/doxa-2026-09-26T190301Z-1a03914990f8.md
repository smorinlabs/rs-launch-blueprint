### Principles and implementation

**Shared requirement:** the public HTTP contract must be generated from the same route and data-type definitions as the runtime, normalized by one explicit contract policy, and then treated as a versioned consumer artifact rather than ephemeral documentation.

| Agreement level | Must agree | May vary |
|---|---|---|
| **Capability** | Generate an OpenAPI document; represent R70’s runtime error envelope; expose stable operation IDs; export a committed artifact; detect stale and breaking changes. | Documentation UI, endpoint path serving the document, YAML versus additional JSON presentation. |
| **Standard** | OpenAPI 3.1 JSON at `docs/api/openapi.json`; unique `operationId` values; problem responses use R70’s media type and schema. | Exact R70 fields, status mapping, and extension members. |
| **Architectural pattern** | One pure `openapi_document()` builder is used by runtime serving, export, and tests. Post-processing occurs before every consumer sees the document. | Framework-specific raw-document source and router adapter. |
| **Policy** | Operation IDs are explicit compatibility identifiers; the committed artifact is reviewable; CI compares the base-branch artifact to the proposed artifact. | Whether the check is in a dedicated workflow or a shared job, owned by R11. |

The OpenAPI specification says `operationId` must be unique, and Utoipa supports an explicit per-route `operation_id`; otherwise it defaults to the handler function name. Explicit values are therefore preferable because Rust function/module refactors should not rename generated-client methods. ([spec.openapis.org](https://spec.openapis.org/oas/v3.1.1.html))

**Architectural alternatives**

| Alternative | Result |
|---|---|
| Handwritten/schema-first OpenAPI | Strong artifact control but duplicates Rust route/type declarations and raises drift risk. Reject for this template unless a future decision makes the OpenAPI file the primary source of server generation. |
| Framework-native generator only | Excellent when the selected framework owns both routing and OpenAPI, but prematurely binds R71 to R69. Conditional runner-up. |
| Code-first generator plus typed normalization | **Selected.** Preserves framework flexibility and directly implements the Python principle using Rust’s typed model. |
| Serialize to arbitrary JSON and patch paths | Viable fallback but loses compile-time model assistance and makes OpenAPI-version migrations more fragile. |
| Export from a running server with `curl` | Reject: depends on process startup, environment, ports, and middleware; less deterministic than a pure builder. |
| Write the snapshot from `build.rs` | Reject: build scripts should not modify tracked source files and would create surprising Cargo rebuild and cross-compilation behavior. |
| Test-only snapshots managed solely by `insta` | Useful for library internals—Utoipa itself uses `insta 1.47` in development—but the R71 file is a product artifact consumed by R83/R84, so an explicit path and exporter are clearer. ([docs.rs](https://docs.rs/crate/utoipa/latest/source/Cargo.toml)) |

**Recommended composition**

1. Each route carries an explicit, lower-snake-case operation ID such as `widgets_get` or `widgets_create`.
2. R70’s runtime problem type also derives `utoipa::ToSchema`.
3. `ApiDoc::openapi()` produces the raw document.
4. A project-owned `ContractPolicy` applies typed mutations through Utoipa’s mutable `OpenApi` model/`Modify` facility:
   - registers R70’s problem schema and reusable response;
   - replaces or adds framework validation responses;
   - sets `application/problem+json`;
   - validates operation-ID presence and uniqueness;
   - fixes stable document metadata.
5. Runtime serving, export, and staleness testing all call the same builder.
6. A dedicated binary writes canonical, pretty JSON with one trailing newline.
7. CI first proves freshness, then runs `oasdiff` against the base branch’s committed file.

Utoipa explicitly supports modification of generated documents both through direct mutable types and its `Modify` trait. ([github.com](https://github.com/juhaku/utoipa))

**Minimal implementation shape**

```toml
[dependencies]
serde_json = "1"
utoipa = { version = "6.0.0", default-features = false, features = ["macros"] }

# Enabled only by the binding selected in R69:

```

The current binding releases are `utoipa-axum 0.3.0` and `utoipa-actix-web 0.2.0`. ([docs.rs](https://docs.rs/crate/utoipa-axum/latest))

```rust
#[derive(serde::Serialize, utoipa::ToSchema)]
pub struct ProblemDetails {
    // Exact fields are owned by R70.
}

#[utoipa::path(
    get,
    path = "/v1/widgets/{id}",
    operation_id = "widgets_get",
    responses(
        (status = 200, body = Widget),
        // Raw/default validation documentation may be replaced by ContractPolicy.
    )
)]
async fn get_widget(/* ... */) {
    // ...
}

#[derive(utoipa::OpenApi)]
#[openapi(
    paths(get_widget),
    components(schemas(Widget, ProblemDetails))
)]
struct ApiDoc;

pub fn openapi_document() -> utoipa::openapi::OpenApi {
    let mut document = ApiDoc::openapi();

    // Project-owned typed traversal over document.paths and responses.
    ContractPolicy::from_r70().apply(&mut document);

    assert_operation_ids_are_present_and_unique(&document);
    document.info.version = API_CONTRACT_VERSION.to_owned();

    document
}

pub fn openapi_json() -> String {
    let mut json =
        serde_json::to_string_pretty(&openapi_document()).expect("OpenAPI is serializable");
    json.push('\n');
    json
}
```

`ContractPolicy` should not hard-code “422”. It should receive the status/response selectors established by R70 and the framework adapter established by R69. That keeps R71 independent of the still-open error mapping.

The exporter should be a dedicated, feature-gated binary:

```text
cargo run --locked --features web --bin export-openapi -- docs/api/openapi.json
```

This is preferable to a public user-facing CLI command because it does not enlarge the template application’s supported CLI interface. An `xtask` is the ranked runner-up if repository automation later grows beyond a few commands.

**Observable acceptance criteria**

1. Every operation has a nonempty, unique ID matching the project naming policy.
2. Renaming a Rust function or module without changing its explicit operation ID does not alter the snapshot.
3. Every validation response selected by R69/R70 references R70’s problem schema and advertises its runtime media type.
4. A malformed runtime request returns the documented status, content type, and required problem fields.
5. Exporting twice from the same commit produces identical bytes.
6. `cargo test` fails after changing a route/schema without regenerating `docs/api/openapi.json`.
7. `oasdiff breaking --fail-on WARN` fails for a removed operation, newly required input, narrowed response, or other incompatible fixture.
8. An operation-ID mutation is tested empirically. If Oasdiff does not classify it at `WARN` or stronger, add a small base-versus-head operation-ID map comparator.
9. The same checks pass on `ubuntu-latest` and `macos-latest`.
10. The lockfile passes the configured MSRV, `cargo audit`, and the project’s unsafe-code policy.

**Performance assessment**

This decision is not request-throughput-sensitive if the document is built once at startup or lazily cached. The relevant costs are proc-macro compilation, one-time document construction, serialization, and optional documentation assets. Utoipa’s current docs.rs build reports a 496.4 kB package and a 15-second documentation build, but docs.rs timings are not comparable application benchmarks and were not used to claim it is fastest. Avoiding Swagger UI crates prevents embedded assets and build-script work from entering the default web binary. ([docs.rs](https://docs.rs/crate/utoipa/latest?utm_source=openai))

The implementation benchmark should use a representative fixture—approximately the eventual template route/schema count—with `cargo build --timings`, one-time generation timed with `Instant`, peak RSS measured by the OS runner, and release-binary size recorded before and after the dependency. No performance experiment was executed during this research.

- an `xtask`;
- `build.rs`;
- exporting from a live HTTP endpoint.

A direct file comparison plus dedicated binary is the simplest pattern matching the artifact’s role. VelesDB provides current practice evidence for committed OpenAPI files regenerated and checked in CI. ([ithub.global.ssl.fastly.net](https://ithub.global.ssl.fastly.net/cyberlife-coder/VelesDB/actions/runs/30244501136/workflow?utm_source=openai))

##### Principles and implementation

The snapshot is not merely a test fixture. It is a reviewed, version-controlled product artifact consumed by R83 and R84. Therefore:

- its path must be stable and obvious;
- its bytes must be deterministic;
- it must be regenerable without starting the service;
- tests must not silently update it;
- runtime and snapshot must use the same builder;
- unrelated package version changes should not modify it.

##### Dominant choice

Use a library function plus a dedicated binary and direct integration test. This relies only on `serde_json`, the standard library, and the selected generator.

##### Qualified shortlist

- **Dedicated binary:** selected for the initial template.
- **Workspace `xtask`:** qualified if the repository gains several code-generation or release tasks.
- **`insta`:** qualified for internal component/schema unit snapshots, but not as the owner of `docs/api/openapi.json`.

##### Excluded by gate

- **`build.rs`:** rejected because generation would have repository side effects during ordinary builds.
- **Live endpoint export:** rejected because it requires server startup and environment configuration.
- **Only uncommitted runtime schema:** fails F332 and provides no reviewable input to R83/R84.
- **Only a `.snap` file:** fails the stable consumer-path requirement.

##### Up-and-comers

An `xtask` may become the better automation shell if R83 and R84 later add more generated artifacts. It should call the same library function rather than duplicate generation.

##### Fit for this template

A dedicated binary fits the CLI/library/service shape cleanly:

- the library owns generation;
- the web service serves it;
- the internal binary writes it;
- the public CLI remains unchanged;
- tests compare it.

##### Recommendation

Commit exactly:

```text
docs/api/openapi.json
```

Add:

```text
src/bin/export-openapi.rs
tests/web/openapi_contract.rs
```

And:

```makefile
export-openapi:
    cargo run --locked --features web --bin export-openapi -- docs/api/openapi.json
```

The serializer must produce pretty JSON and exactly one final newline.

##### Ranked runner-up

A workspace `xtask` command:

```text
cargo xtask export-openapi
```

Use it only if R11 or later generation tasks justify another workspace package.

##### Tradeoffs

- Direct string equality can produce a large assertion diff. A custom first-difference message may improve usability without introducing a snapshot dependency.
- Canonical formatting changes from `serde_json` or Utoipa can create review noise; this is acceptable because dependency-driven contract changes should be reviewed.
- The exporter adds another binary target, but it is feature-gated and not distributed as the product CLI.

##### Parameters

- `owns snapshot-path = docs/api/openapi.json`
- `owns export-mechanism = dedicated Cargo binary`
- `owns staleness-mechanism = generated-byte equality integration test`
- `assumes R69:web-extra-surface = enabled for export and tests`
- `assumes R83/R84 input = docs/api/openapi.json`
- `CONFLICT: none`

##### Migration implications

- Introduce `API_CONTRACT_VERSION`.
- Ensure package version is not substituted automatically into `info.version`.
- Add deterministic serializer and exporter.
- Add the committed initial artifact.
- Add a Justfile recipe.
- Update contributor documentation with the regeneration command.

#### oasdiff 1.23.0 and base-branch compatibility gate

##### Landscape

No Rust-native OpenAPI compatibility checker with comparable current rule breadth, CI integration, and production evidence was established. OpenAPI compatibility is language-neutral, so the implementation language of the server is not a reason to replace Oasdiff.

Oasdiff supports local CLI execution, OpenAPI 3.0/3.1 comparison, hundreds of classified change checks, and an official GitHub Action. Version 1.23.0 expanded the rule catalog to approximately 500 change kinds. ([github.com](https://github.com/oasdiff/oasdiff?utm_source=openai))

##### Principles and implementation

The comparison must use:

- **base:** the committed snapshot from the pull request’s base branch;
- **revision:** the committed snapshot from `HEAD`;
- **threshold:** `WARN`, so definite and potential consumer breakage fail;
- **input:** files, not live endpoints;
- **scope:** only public OpenAPI contract changes.

This keeps CI independent of whether the schema was produced by Python, Rust, or another language.

##### Dominant choice

Use the Oasdiff CLI as the canonical semantic engine. The official action may wrap the same check, but local reproduction must remain possible through the CLI.

##### Qualified shortlist

1. **Oasdiff 1.23.0 CLI** — selected canonical invocation.
2. **`oasdiff/oasdiff-action/breaking@v0`** — qualified CI wrapper; resolve the selected tagged release to an immutable commit SHA in actual workflow YAML.
3. A containerized Oasdiff invocation — acceptable on Ubuntu, but less suitable as the cross-platform local command.

##### Excluded by gate

- Textual JSON diffs: detect formatting, not semantic compatibility.
- A custom Rust comparator: too easy to miss OpenAPI compatibility rules.
- Comparing regenerated base code: unnecessarily requires building an old revision and its toolchain.
- Unpinned action from `main`: unreleased behavior and weaker supply-chain reproducibility.

##### Up-and-comers

Oasdiff’s continuing OpenAPI 3.2 work should be monitored, but OpenAPI 3.1 is the compatibility target for this decision. ([github.com](https://github.com/oasdiff/oasdiff?utm_source=openai))

##### Fit for this template

- It consumes the same committed file as R83 and R84.
- It is unaffected by the selected Rust framework.
- Its step can be placed in either a dedicated workflow or a shared job.
- Prebuilt releases support Linux and macOS; Windows is also available but not required. ([github.com](https://github.com/oasdiff/oasdiff?utm_source=openai))

##### Recommendation

Canonical command:

```bash
oasdiff breaking \
  --fail-on WARN \
  "$RUNNER_TEMP/openapi.base.json" \
  docs/api/openapi.json
```

Prepare the base file with Git rather than building the base branch:

```bash
git fetch --no-tags --depth=1 origin "$BASE_REF"
git show "origin/$BASE_REF:docs/api/openapi.json" \
  > "$RUNNER_TEMP/openapi.base.json"
```

Also run:

```bash
oasdiff validate docs/api/openapi.json
```

The official action’s current quick start supports equivalent `base`, `revision`, and `fail-on: WARN` inputs. ([github.com](https://github.com/oasdiff/oasdiff-action?utm_source=openai))

##### Ranked runner-up

Use the official action directly:

```yaml
- uses: oasdiff/oasdiff-action/breaking@<immutable-sha>
  with:
    base: origin/${{ github.base_ref }}:docs/api/openapi.json
    revision: HEAD:docs/api/openapi.json
    fail-on: WARN
```

This is operationally simpler, but the exact action release and bundled engine must be recorded.

##### Tradeoffs

- Adds a non-Rust CI binary.
- Rule updates can alter classifications, so the engine must be version-pinned.
- `WARN` can surface ambiguous changes requiring human review.
- Operation-ID change handling must be proved with a mutation fixture rather than assumed.

##### Parameters

- `owns compatibility-engine = oasdiff 1.23.0`
- `owns compatibility-threshold = WARN`
- `owns comparison-base = pull-request base branch committed snapshot`
- `assumes R11:ci-job-structure = unresolved; invocation is topology-neutral`
- `CONFLICT: none`

##### Migration implications

- Add an Oasdiff installation/pinning step or pinned official action.
- Fetch the PR base branch.
- Handle the case where the base branch has no OpenAPI file as initial contract introduction rather than breakage.
- Apply a path filter if R11 supports it, but keep staleness testing in ordinary Rust CI.
- Upload or print the Oasdiff report on failure.
