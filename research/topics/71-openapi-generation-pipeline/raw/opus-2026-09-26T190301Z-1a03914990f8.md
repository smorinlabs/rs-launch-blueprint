### Landscape

**Category this item decides.** The *API-contract pipeline* for the optional `web` surface:
(1) how an OpenAPI document is derived from the Rust service code, (2) how that document is
corrected so it describes what the runtime actually returns (the error envelope, F307),
(3) how operation identities are kept stable (F312), (4) how the document is committed and
kept honest by a test (F332), and (5) how a pull request that breaks the contract is caught
(F333). It is a bundle: two crates for generation, two in-repo patterns, one test crate, one
external tool.

**Where Rust needs a different design (and why that is justified, not drift).**

1. **F307 is an insertion, not a rewrite.** FastAPI auto-documents a `422 HTTPValidationError`
   on every operation with inputs; py rewrites it. axum documents nothing: extractor rejections
   are undeclared and, at runtime, `text/plain` (observed in the probe:
   `GET /v1/projects/not-a-number` → `400`, `content-type = "text/plain; charset=utf-8"`).
   utoipa therefore has no default error schema to rewrite. The Rust pass *adds* the problem
   response for each input-taking operation. The runtime half — mapping axum rejections into
   the envelope — is R70's; this item's pass is what makes the document promise it.
2. **The pass must run on the merged document.** utoipa's `Modify` trait on `#[derive(OpenApi)]`
   runs inside `ApiDoc::openapi()`, **before** `utoipa-axum` merges route paths. Observed: a
   modifier recording `doc.paths.paths.len()` saw **0** (probe test
   `doc_level_modifier_runs_before_routes_are_merged`). The correction is therefore a plain
   function over the `utoipa::openapi::OpenApi` returned by `OpenApiRouter::split_for_parts()` —
   the exact analogue of py's "call AFTER all routers are included" docstring.
3. **The regenerator is the test, not a binary.** R49 fixes exactly one `[[bin]]` with
   `autobins = false`; R69 fixes the `web` feature to gate exactly four things and gives the
   `<app>-serve` binary only the required global CLI core. A `cargo run --bin export-openapi`
   target or an `export-openapi` subcommand would each break a consumed decision. The idiomatic
   Rust answer that fits is *the staleness test regenerates on demand*:
   `EXPECTORATE=overwrite cargo test --features web --test openapi`, wrapped by a Justfile
   recipe `export-openapi` (R42: bare invocation, no runner prefix).
4. **The snapshot's path moves out of `docs/`.** R11's detector skips the compiling `check` job
   when every changed path is on its skip-list, and `docs/` is a skip-list directory entry. A PR
   that hand-edits only `docs/api/openapi.json` would skip `check` — the job that runs the
   staleness test — and merge a lying contract. Placing the file at repository root under
   `openapi/` (not on the skip-list, so `code` fails closed to `true`; not in R49's `include`
   allow-list, so it is not packaged) keeps the staleness test on every PR that touches it.
   Oxide's `omicron` uses the same root `openapi/` convention. This is a justified departure
   from py's `docs/api/` placement.
5. **The breaking check is a step, not a path-triggered workflow.** R11 forbids trigger-level
   `paths` filters (they leave required checks Pending) and puts non-compiling checks in
   `hygiene` on `ubuntu-latest`. py's `on: pull_request: paths:` shape does not transfer; the
   step must pass trivially when base and head documents are identical, and it must obtain the
   base document itself (`git show "$BASE_SHA:openapi/<name>.json"`).

### Recommendation

**Adopt the full pipeline — all four rows — as one stack of six members, all gated behind R69's
`web` feature (dev-only members are `[dev-dependencies]` used from `#![cfg(feature = "web")]` tests):**

1. **`utoipa` 6.0.0** (`utoipa-gen` 6.0.1 via its `macros` feature) — code-first OpenAPI 3.1.0
   generation; optional dependency under `web`.
2. **`utoipa-axum` 0.3.0** — `OpenApiRouter` + `routes!` so axum routes and documented paths come
   from one declaration; optional dependency under `web`.
3. **Problem-response declaration pass** (in-repo pattern, ~30 lines in `src/web/openapi.rs`) —
   runs on the document returned by `split_for_parts()`, inserts the R70 envelope schema and a
   `400` `application/problem+json` response on every input-taking operation (F307).
4. **Curated operation ids** (in-repo pattern) — explicit `operation_id = "<tag>-<name>"` on every
   `#[utoipa::path]`, enforced by a test asserting presence, uniqueness and the `<tag>-` form (F312).
5. **`expectorate` 1.3.0** (dev-dependency) — the committed-snapshot staleness test at
   `openapi/<package>.json`; regenerated by `EXPECTORATE=overwrite cargo test --features web --test openapi`
   behind a `just export-openapi` recipe (F332).
6. **`oasdiff` v1.32.1** (Go binary, not a crate) — `oasdiff breaking <base> <head> --fail-on ERR
   --err-ignore openapi/breaking-accepted.txt` as a step R11 places in `hygiene` (F333).

Runner-ups: `aide` for members 1–2; a utoipa post-pass that computes `<tag>-<fn>` (py's literal

### Members

#### utoipa

##### Landscape
Code-first generation crates for Rust (three-bin map above): `utoipa` (framework-agnostic,
established), `aide` (axum-native, up-and-comer), `oasgen` (quiet), and framework-bound ones
(`poem-openapi`, `dropshot`, `paperclip`, `apistos`, `rocket_okapi`). `utoipa` is the only
framework-agnostic generator with established adoption.

##### Principles and implementation
Realizes the "code is the source of truth" half of F332 and supplies the typed document that F307
and F312 operate on. Handlers carry `#[utoipa::path(...)]`; types derive `ToSchema`; an
`#[derive(OpenApi)]` root carries `info`, `tags` and shared components. The generated
`utoipa::openapi::OpenApi` is an ordinary mutable struct (`paths.paths: BTreeMap<String, PathItem>`,
`PathItem.get/put/post/...: Option<Operation>`, `Operation.responses.responses: BTreeMap<String, RefOr<Response>>`),
which is what makes a typed post-generation pass possible. Key order in the committed file is
deterministic because the test round-trips through `serde_json::Value`, whose object type is a
`BTreeMap` while `serde_json`'s `preserve_order` feature is off (observed: `Problem.properties` came
out alphabetical, `detail, status, title, type`, not in declaration order). utoipa itself has
`preserve_order`/`preserve_path_order` features; neither is enabled here.

#### Problem-response declaration pass (F307)

##### Landscape
Ways to make the document describe the runtime error envelope: (a) annotate every handler's
`responses(...)` by hand; (b) utoipa `Modify` on the doc root; (c) a function over the merged
`OpenApi` after `split_for_parts()`; (d) a JSON-level rewrite of the serialized document;
(e) `IntoResponses` derive on a shared error type referenced from each path.

##### Principles and implementation
Principle: the contract never advertises an error shape the runtime does not send (py
`problems.py:97–103` docstring: "generated clients would parse the wrong shape"). In axum there is
no framework-default error schema to rewrite; framework rejections (`Path` → 400, observed in the probe; `Query` 400 and `Json` 400/415/422 per axum's
`JsonRejection` variants are from memory of axum's docs, not re-fetched this leg) are simply undocumented. The pass:

```rust
pub fn declare_problem_responses(doc: &mut OpenApi) {
    for item in doc.paths.paths.values_mut() {
        for op in [&mut item.get, &mut item.put, &mut item.post, &mut item.delete, &mut item.patch]
            .into_iter().flatten()
        {
            let takes_input = op.parameters.as_ref().is_some_and(|p| !p.is_empty())
                || op.request_body.is_some();
            if takes_input {
                op.responses.responses.entry("400".into()).or_insert_with(|| RefOr::T(
                    ResponseBuilder::new().description("Invalid request (RFC 9457)")
                        .content(PROBLEM_CONTENT_TYPE, ContentBuilder::new()
                            .schema(Some(Ref::from_schema_name("Problem"))).build())
                        .build()));
            }
        }
    }
}
```

`Problem` is registered once via `components(schemas(Problem))` on the root. In the template, the
set of statuses (400 always; 415/422 for operations with a JSON `requestBody`) is derived from
R70's rejection mapping, which is open; the probe uses 400 only. Handler-specific errors (404 etc.)
are declared in the handler's own `responses(...)` with `content_type = "application/problem+json"`.

##### Dominant choice
Option (c), a function over the merged document — the direct analogue of py's
`openapi_with_problems()` wrapper. Crate figures are **inapplicable**: this member is ~30 lines of
template code using `utoipa`'s public builders; its dependability is `utoipa`'s (member 1).

##### Qualified shortlist
(c) post-merge function — recommended. (a) per-handler annotation only — correct but relies on
every author remembering the framework's rejection statuses. (e) `IntoResponses` shared type —
tidy for handler errors, still per-handler.

##### Excluded by gate
(b) utoipa `Modify` on the `#[derive(OpenApi)]` root — **excluded by observed behaviour**: it runs
inside `ApiDoc::openapi()`, before `utoipa-axum` merges paths; the probe's modifier saw **0**
paths. (d) JSON-level rewrite — loses type checking for no gain. Numbered gates 1–6 are
inapplicable to an in-repo pattern (no license, MSRV, advisory, OS or feature surface of its own
beyond `utoipa`'s), stated here rather than omitted.

##### Up-and-comers
None; no crate specializes in "problem+json OpenAPI injection" for axum with meaningful adoption
(`problem_details` uses `utoipa-axum` only as a dev-dependency, per `/reverse_dependencies`).

##### Fit for this template
Good: keeps R70's envelope type (whatever it becomes) as the single schema source via
`ToSchema`, and needs no knowledge of R70 beyond "which statuses do rejections produce".

##### Recommendation
Adopt (c) in `src/web/openapi.rs`, called from `build_router` immediately after
`split_for_parts()`. Guard it with the test `every_input_taking_operation_documents_problem_400`
(and a 415/422 sibling once R70 lands its JSON-body rejection mapping).

##### Ranked runner-up
(a)+(e): declare problem responses per handler through a shared `IntoResponses` error type,
without a global pass.

##### Tradeoffs
A global pass can over-declare (an operation whose input cannot actually fail extraction still
gets a 400). That is the conservative direction for clients. It also means the document promises
problem+json before R70 makes it true: observed in the probe, the runtime still answered
`text/plain`. That gap is R70's to close and should be asserted by an R70/R83 runtime test.

##### Parameters
None owned or consumed; depends on R70's envelope (related, not a registry dependency).

##### Migration implications
`src/web/openapi.rs`: `PROBLEM_CONTENT_TYPE`, `declare_problem_responses`; root `ApiDoc` registers
`Problem`. `tests/openapi.rs` gains the declaration test.

##### Validation strategy
Executed: `every_input_taking_operation_documents_problem_400` passed; committed probe document
shows `/v1/projects/{id}` `get` responses `['200', '400', '404']` and `/v1/projects` `['200']`;
`components.schemas` = `['Problem', 'Project']`. Planned: runtime test (R70/R83) that a malformed
path parameter yields `content-type: application/problem+json`.

##### Confidence & re-verify trigger
High on mechanism; medium on the exact status set until R70 is accepted. Re-verify when R70's
decision lands or when axum changes rejection statuses.

##### Sources
py `b55b8c26:src/py_launch_blueprint/web/problems.py:97-136`; probe `/tmp/r71-probe/src/web/mod.rs`,
`tests/openapi.rs`; utoipa builders per `utoipa-6.0.0/src/openapi/` (local registry source).

#### Curated operation ids (F312)

##### Landscape
Mechanisms: (a) explicit `operation_id = "..."` on each `#[utoipa::path]`; (b) utoipa's default
(the handler function name) plus a post-pass computing `<tag>-<fn>` (py's `_operation_id`
equivalent); (c) aide's `op.id(...)` transform; (d) leave defaults.

##### Principles and implementation
Principle: operation ids are a public name — R84's generated client derives method names from
them — so they change only by deliberate, reviewed edit. py derives `<tag>-<function-name>`
(`app.py:77-80`), which is stable only as long as function names are. In Rust, (a) decouples the
public name from the private function name entirely: renaming a handler cannot rename the
operation (criterion A4). Enforcement is a test, not a rewrite:

```rust
#[test]
fn operation_ids_are_present_and_unique() { /* every op has operationId; ids unique */ }
// template adds: each id starts with its first tag + "-", so a forgotten attribute
// (default = bare fn name, no hyphen) fails the build.
```

The probe verified utoipa's default is the bare function name: the uncurated handler
`list_projects` produced `list_projects` before the probe's pass prefixed it to
`projects-list_projects`.

##### Dominant choice
(a) explicit attribute + conformance test. Crate figures **inapplicable** (in-repo pattern on
`utoipa`'s `operation_id` attribute).

##### Qualified shortlist
(a) explicit attribute — recommended. (b) default + `<tag>-<fn>` post-pass — faithful to py, zero
annotation burden, but a handler rename silently renames the operation (caught only by the
snapshot diff and oasdiff).

##### Excluded by gate
(d) defaults — fails A3's `<tag>-` form and A4. Numbered gates 1–6 inapplicable to an in-repo
pattern (stated, not omitted).

##### Up-and-comers
None.

##### Fit for this template
Good; ids stay byte-compatible with py's convention (`projects-list_projects`,
`projects-get_project`, `ops-healthz`, `ops-readyz`), which keeps cross-language client parity if
the owner ever wants it.

##### Recommendation
Every `#[utoipa::path]` carries `tag = "<tag>"` and `operation_id = "<tag>-<name>"`;
`tests/openapi.rs` asserts presence, uniqueness and the `<first tag>-` prefix.

##### Ranked runner-up
(b) py-literal post-pass `curate_operation_ids` (the probe's variant), if the owner prefers zero
per-route annotation.

##### Tradeoffs
(a) costs one attribute per route and duplicates the tag; (b) costs nothing per route but ties
public ids to private function names. A rename under (a) is an explicit, visible edit that oasdiff
reports as an operation-id change.

##### Parameters
None.

##### Migration implications
All handlers in `src/web/**` gain `operation_id`; `tests/openapi.rs` gains the conformance test.

##### Validation strategy
Executed: `operation_ids_are_present_and_unique` passed; snapshot ids `projects-list_projects`,
`projects-get_project`. Planned: a deliberately missing attribute fails the `<tag>-` prefix
assertion.

##### Confidence & re-verify trigger
High. Re-verify when R84 selects its client generator (confirm it keys method names on
`operationId`).

##### Sources
py `b55b8c26:src/py_launch_blueprint/web/app.py:77-80,119`; py `docs/api/openapi.json` operation
ids; probe `tests/openapi.rs`. 2026-09-26.

#### expectorate

##### Landscape
Rust committed-expected-output tools: `insta` (`.snap` files with a YAML header; R33's choice for
CLI help), `expectorate` (plain file, `EXPECTORATE=overwrite`), `snapbox` (plain file via
`snapbox::file!`, `SNAPSHOTS=overwrite`; Cargo's own), `goldenfile`, and a hand-rolled
`std::fs` compare.

##### Principles and implementation
F332 needs a snapshot that is **itself the contract artifact**: R83, R84 and oasdiff must read it
as plain OpenAPI JSON at a path the template chooses. `insta`'s ordinary `.snap` format prefixes a
YAML metadata header, so that file is not a valid OpenAPI document. insta 1.48.0 does offer
`assert_binary_snapshot!`, which I probed: it writes the payload as a plain sidecar
`tests/snapshots/insta_bin__openapi.snap.json` (3,081 bytes) next to a metadata file
`tests/snapshots/insta_bin__openapi.snap` (`snapshot_kind: binary`, `extension: json`). The sidecar
is consumable, but its path is derived from the test module and name, it always has a metadata
twin, and the macro's own doc comment (`src/macros.rs:390-398`) marks it "(Experimental) … we may
make incompatible changes for the next couple of versions after 1.41" — too unstable a contract
for a file two other items consume. `expectorate::assert_contents(path, &text)` compares against a plain file, prints a
unified diff on mismatch, and rewrites the file atomically when `EXPECTORATE=overwrite` is set —
test and regenerator in one (answers the MEDIUM question given R49/R69's no-extra-binary
constraints). `info.version` is normalized to `"0.0.0"` before compare (py's `SNAPSHOT_VERSION`),
while the test first asserts the runtime document carries `CARGO_PKG_VERSION` (criterion A7).

#### oasdiff

##### Landscape

##### Principles and implementation
Principle F333: base-vs-head contract comparison fails the PR on ERR-level breaks (A9), with a
reviewed escape hatch for intended breaks (A10: `--err-ignore <file>`, documented in
`docs/BREAKING-CHANGES.md` lines 119–122). Invocation designed to be hosted by either R11
placement:

```bash
set -euo pipefail
snap=openapi/rs-launch-blueprint.json
base_sha="${BASE_SHA:?}"          # pull_request.base.sha, or merge_group base / push 'before'
if git cat-file -e "$base_sha:$snap" 2>/dev/null; then
  git show "$base_sha:$snap" > base-openapi.json
else                               # first PR introducing the snapshot
  printf '%s' '{"openapi":"3.1.0","info":{"title":"x","version":"0"},"paths":{}}' > base-openapi.json
fi
oasdiff breaking base-openapi.json "$snap" --fail-on ERR --err-ignore openapi/breaking-accepted.txt
```

produce no findings and exit 0.
