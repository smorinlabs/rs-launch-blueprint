## Decision

**Adopt a synchronous, blocking execution model for the library crate and the CLI binary, and confine async to R69's optional `web` feature.** The driven-I/O port and every function that reaches it are ordinary `fn` that block the calling thread; the CLI entry point is `fn main() -> ExitCode` with no executor anywhere in the default dependency tree; when — and only when — the `web` feature is on, axum's `async fn` handlers reach the same synchronous port through `tokio::task::spawn_blocking`.

This is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). It records what this research found and what it recommends; P03 builds the template and its CI proves the recommendation. A decision that does not survive implementation is revised against this recorded research, not researched again from scratch. What P03 must validate is listed under `## Engines`.

One stack:

|---|---|---|

### Principles and implementation

**Shared requirement, its source and agreement level.** Every inbound front end — the CLI, and the optional web service — reaches one use-case layer, which reaches the outside world through the driven-I/O port R01 defines; the template must build and test on `ubuntu-latest` and `macos-latest` at an MSRV floor of stable minus two minor versions. The execution model is the *mechanism* by which that requirement is met, not the requirement itself. Source: `docs/port/COMMONALITY.md` rows F016 and F022 (check C01). **Agreement level: mechanism — Rust decides alone.** The two source repositories do not agree and neither answer is portable. py is sync end-to-end because CPython's blocking `requests` is its ecosystem default, and its web tier bridges into FastAPI's async handling through a threadpool; the prompt's `## Context` records the evidence at the py pin (`src/py_launch_blueprint/core/adapters/py_api.py:38`, `import requests`; `src/py_launch_blueprint/web/routers/projects.py:25`, "Handlers are sync (``def``) because ``ProjectsService`` uses ``requests``; FastAPI runs them in its threadpool"). ts is async end-to-end because JavaScript has no blocking I/O to choose (`src/router.ts:182`, `export async function runCli`; `src/lib/api.ts:108`, `async function request`), and the prompt records that `TS_PORT_DECISIONS.md` has no entry choosing async — "there was no sync option to reject". What transfers is py's *shape*, a synchronous core with a bridged async web tier, which is a real architectural pattern; ts's *absence* of a choice is not evidence for one. Both pins are quoted from the prompt's `## Context` and from the Opus raw's reading of them; this synthesis did not re-open either source repository, and says so rather than implying a fresh read.

**What must agree, and what may vary.** Must agree across py, ts and rs: that one use-case layer serves both front ends, and that the web tier is a thin adapter over it. May vary: whether the functions in that layer block.

   (b) **"The web feature pays the tokio cost regardless" is true only of builds that turn the web feature on.** The prompt frames the template as "CLI-first" with "most invocations … a single HTTP round-trip" (`inputs/prompt.md` line 32), and the web surface is off by default (F017 `ADOPT`; R69's `web-extra-surface`). Under alternative A the default build carries no runtime: check T06 measures 38 default crates and no `tokio` in R69 revision 10's shape. Check V07 puts Muse's recommended core into that same shape and finds `tokio v1.53.1` in the root package's **default** tree, with 106 default crates. Muse calls its cost "one-off and bounded" (line 137). It is bounded, but it is not one-off: it recurs in every default build of every consumer of the template, including consumers that never enable `web`. That recurring cost is criterion 1, and criterion 1 is the property that separates A from B.

   (c) **The "two I/O models" objection (lines 175 and 178) is real in kind but small in extent.** Muse's shared requirement is that "the template consumer extending the CLI must meet exactly one spelling of I/O" (lines 98–99). Under A that consumer meets exactly one spelling, `fn`. The `async fn` spelling appears only in the axum handlers, which are `async fn` under Muse's design too. Under R69 revision 10 those handlers live in the optional member `crates/web` (check T04). The line between the two spellings is therefore a crate boundary the owner has already drawn, not a line through the core. At that boundary A adds one `spawn_blocking` wrapper per handler, which check C14 exercises end to end. B instead changes every port method, service method, adapter and test, and the CLI entry point, as Muse's own migration list shows (lines 611–625). Muse's criterion 1 forbids `spawn_blocking` outside the composition root and the binaries (lines 114–117). That criterion encodes Muse's answer rather than testing it, so it is not adopted. **One part of the objection is conceded.** FastAPI's threadpool bridge is automatic; Rust's is written at each call site. A handler that calls the blocking port without `spawn_blocking` compiles cleanly and blocks a runtime worker thread. Nothing in this decision's evidence detects that mistake. It is recorded under `**Unproven, and stated as such.**` and added to what P03 must validate.

   (d) **Muse's no-`CONFLICT:` reading (line 601) is true against R69 revision 10 and false against revision 9, the revision Muse cites.** Muse took R69 revision 9 as its authority (line 47). In that form, Muse's non-optional `tokio` beside `web = ["dep:axum", "dep:tokio"]` is a manifest error (check V08, the same diagnostic as C07), so a `CONFLICT:` line would have been required. In revision 10, which the owner has accepted, Muse's core parses (check V07), and Muse's reading agrees with this decision's own revision-10 restatement of alternative B. Under revision 10, B's remaining cost is criterion 1, which point (b) prices.

   *What Muse adds that this decision had not established.* Four things, each recorded rather than argued away.
   - **A production reference implementation for alternative B.** `rust-lang/crates.io` pins `async-trait =0.1.92`, `axum =0.8.9`, `reqwest =0.13.5` and `tokio =1.53.1` in one workspace (check V09). No repository was found shipping `ureq` and `axum` together, so the reference-implementation gap is now asymmetric, and it runs against A. crates.io is a permanently running web service, which is the workload that row R05-1 distinguishes from this template's default build. It shows that B composes at these versions; it does not show that B fits a CLI-first template.
   - **A CLI-first adopter of alternative C's entry shape.** `rust-lang/rustup` keeps a synchronous `fn main` and drives an explicit multi-thread `tokio` runtime through `block_on` (check V09). Alternative C is rejected here because a library that exposes only `block_on` wrappers cannot be called from its own web feature. rustup has no web feature, so it is not a counter-example to that ground.
   - **The source reading behind Opus's documentation discrepancy.** `reqwest::blocking`'s in-runtime guard is compiled only under `debug_assertions` (check V10). The documented panic therefore fires in debug builds and not in release builds. This strengthens alternative E's rejection and does not bear on A.
   - **Independent corroboration of alternative E's rejection.** Muse measured `reqwest::blocking` carrying `tokio v1.53.1` (115 packages by Muse's method; 85 by this decision's, check V05), which is the "sync API without the sync dependency profile" ground in the alternatives table.

2. **"Bridging is not a first-class pattern" (Perplexity, Gemini) against "the bridge is one documented wrapper" (Opus).** Perplexity's objection is specific: sync-first "often requires explicit use of `tokio::task::spawn_blocking` … which comes with additional complexity and potential performance pitfalls if overused". The complexity half is answered by execution: check C14 runs the whole bridge — `rt.block_on(async { spawn_blocking(fetch).await })` — and gets a result byte-identical to the direct blocking call, with one wrapper per handler and no second public surface. The performance half is **conceded as unmeasured**: no latency, throughput or blocking-pool-saturation figure was produced by any engine or by this synthesis, and "if overused" is a real hazard for a web surface under concurrency. Opus cites tokio's `max_blocking_threads` default of 512 from `docs.rs/tokio/1.53.1/tokio/runtime/struct.Builder.html`; that figure was **not re-verified here** and is carried as Opus's. This is listed below as something P03 must measure.

3. **OpenAI's ranked runner-up contradicts its own policy line.** OpenAI names `ureq` 3.4.2 "the strongest blocking alternative" and offers it as the runner-up "but only if the owner changes the complete architecture to synchronous CLI, core, and web execution … It is not recommended behind Axum's handlers", and it writes an acceptance criterion that "the primary HTTP path contains no `reqwest::blocking`, `ureq`, `spawn_blocking`, or `block_in_place`". The premise is that a blocking client behind axum needs a sync-first *server* too. Check C14 falsifies that premise directly: `ureq` 3.4.2 ran inside a tokio multi-thread runtime through `spawn_blocking` and returned the same 559 bytes as the direct call. OpenAI's criterion is a policy assertion, not a finding, and it is not adopted.

4. **What the three Doxa providers reject under the name "mixed" is alternative C, not alternative A.** Perplexity's "mixed design" is explicitly "a sync CLI while using an async web service … the CLI can call into async library functions by blocking on a runtime using `tokio::runtime::Runtime::block_on`", and it rejects it because "the core library may need to offer both sync and async variants of its I/O functions". That is Opus's alternative C and Opus rejects it on the same ground. **Opus and Doxa agree on C and disagree only on A against B**, which narrows the disagreement considerably and is the reason this decision states A and B as the only live pair. Muse does not evaluate C as a library design; it offers C's entry shape only as rustup's CLI-entry alternative (see the label table above), so it leaves the same pair live.

5. **Intra-Doxa disagreement on the CLI runtime flavour** (recorded because it shows the async branch is not itself settled): OpenAI specifies `#[tokio::main(flavor = "current_thread")] async fn main`; Gemini specifies the current-thread scheduler for the CLI and the multi-threaded one for the web layer; Perplexity specifies `#[tokio::main]` with "the multi-threaded executor (or current-thread variant if desired)". Nothing settles this here, because the recommendation removes the question from the CLI entirely.

6. **Agreement across all five engine bodies** (Opus, the three Doxa providers and Muse), worth recording because it is the part that is not contested: `tokio` is the dominant Rust runtime and the only realistic one for axum, and the standard library ships no executor, so any async choice is also a third-party-runtime choice. Muse states the same at `raw/muse.md` lines 142–146 and 152–157. Muse's acceptance criterion that the tree hold exactly one async runtime (line 125) is also met by alternative A, whose only runtime is R69's `tokio` inside the web feature. **Version precision is not shared, and the difference is an evidence-quality signal** (check C18): Opus, OpenAI and Muse all pin all four crates, Muse at `tokio 1.53.1`, `reqwest 0.13.5`, `ureq 3.4.2` and `axum 0.8.9` (lines 30 and 233–235; OpenAI's body carries `1.53.1` 18 times, `0.13.5` 14, `0.8.9` 17, `3.4.2` 4); Gemini names `1.53.1` and `0.13.5` once each and no `ureq` or `axum` version; Perplexity pins none of the three client and runtime versions at all. Where a version *is* named it agrees, and check C15 confirms all four are the newest non-yanked releases. `async-std` is excluded by Opus and by Muse on its RustSec unmaintained advisory (Muse cites `RUSTSEC-2025-0052`, line 295) and flagged as discontinued by Perplexity; Gemini and OpenAI mention it without that label.

**Unproven, and stated as such.**

- **No Linux execution happened.** Every check above ran on macOS 26.4 `aarch64-apple-darwin`. The `ubuntu-latest` leg of fitness gate 4 rests on the projects' own CI matrices as reported by Opus, not on an execution here. P03's CI closes this.
- **`ureq`'s macOS leg rests on one local run.** Check C17 confirms from `ureq` 3.4.2's own workflow that it runs seven `ubuntu-latest` jobs and no macOS job, so gate 4's macOS answer for `ureq` is check C14's single execution on one machine, not a CI signal from the project.
- **No latency, throughput, memory or requests-per-second figure is claimed by this decision.** None was measured by any engine. In particular, the cost of the `spawn_blocking` bridge under concurrency is unmeasured, and tokio's blocking-pool bound is carried from Opus's docs.rs citation without re-verification.
- **Binary sizes are Opus's, not reproduced here.** So are the maintenance-rubric figures for the sync-first web frameworks (alternative D), the practice-survey manifests read at each project's default branch, the download and reverse-dependency counts, and the observation that `reqwest::blocking` did **not** panic inside a runtime despite its own documentation saying it would. Muse reported the same behaviour on a release build and traced it to source; check V10 confirms at tag `v0.13.5` that the guard is compiled only under `debug_assertions`. This decision still does not rely on it in either direction. Muse's own figures (binary sizes, build seconds, maintenance and responsiveness figures) are likewise Muse's; only its package counts were re-derived here (check V05).
- **The reference-implementation gap is asymmetric, and it runs against the recommendation.** Alternative B has a production reference implementation at these exact versions, `rust-lang/crates.io` (check V09), which is a permanently running web service rather than a CLI-first template. Alternative A has none.
- **A handler that forgets `spawn_blocking` is not detected.** It compiles cleanly and blocks a `tokio` worker thread for the length of the upstream call. This is the one hazard in Muse's "per-callsite bridge" objection that this decision concedes (`## Engines`, disagreement 1, point (c)); P03 item 9 below is the check that must catch it.
- **No survey of `cargo-generate` CLI templates was run** by any engine or by this synthesis. How such templates handle the sync/async boundary when they also ship a library crate is therefore unknown. The closing probe is named in the `### Principles and implementation` paragraph on how CLI templates and `clap`'s examples handle the boundary, and the gap does not bear on the choice.
- **No third-party repository shipping `ureq` and `axum` together was found.** The compatibility claim rests on the resolved-and-built matrix (C10–C13) and the executed bridge (C14).
- **Build seconds are single runs on a shared, loaded machine** and are informational only; the assertion is the ordering.

**What P03 must validate**, since this decision is a proposal and not an implementation:

1. `cargo tree -i tokio -e normal` must fail and `cargo tree -i tokio -e normal --features web` must succeed **against the real template** — the single command that distinguishes this decision from its runner-up (criterion 1).
2. `cargo test` and `cargo test --features web` green on `ubuntu-latest` and `macos-latest`, which supplies the Linux leg this synthesis could not (criteria 9 and the first unproven row).
3. The library's public surface carries no `async fn` and no `impl Future`, checked with R04's selected gate (criterion 8).
4. An integration test that boots the `web` router on an ephemeral port, issues a real request, and asserts the body decodes into the library's own type and matches the CLI's rendering — R01's acceptance criterion for one service serving both front ends.
5. A concurrency measurement of the `spawn_blocking` bridge under load, with the workload, the runtime flavour, the blocking-pool bound and the observed latency all stated. This is the one substantive objection the Doxa providers raised that this synthesis could not answer with evidence.
6. An adapter test against a local HTTP fixture asserting the `ureq::Agent` sends the expected headers and honours its timeout — the py/ts request-wrapper principle.
7. `cargo deny check advisories` against a pinned RustSec database, continuously (gate 3), which is also the mechanism that would fire the `ureq` advisory re-verify trigger.
8. A `compile_fail` doctest pinning criterion 3, so a future contributor cannot quietly put a native `async fn` on the port.
9. A test that fails when a web handler calls the blocking port outside `spawn_blocking` — for example, handlers exercised on a `current_thread` runtime against a port fake that blocks, asserting that a concurrent request still completes — so Muse's forgotten-bridge hazard (disagreement 1, point (c)) is caught by CI rather than by review. The mechanism is P03's to choose; this decision names the property, not the tool.
