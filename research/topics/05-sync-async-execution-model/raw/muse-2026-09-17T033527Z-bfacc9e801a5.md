### Principles and implementation

**Shared requirement.** One execution model must cover the CLI entry point, the core
use case's driven-I/O calls, and the optional web feature's handlers: any I/O the
core performs must be invocable from all three front ends without a per-callsite
bridging discipline, and the template consumer extending the CLI must meet exactly
one spelling of I/O (`fn` or `async fn`), not both.

- *HIGH — sync-blocking vs async core cost.* Measured on this host (rustc 1.98.0,

  structural (second model + bridge, next question). Ergonomics: async colors
  every I/O signature `async fn` and the entry point `#[tokio::main]` (or the

- *MEDIUM — CLI entry-point ergonomics.* Two documented patterns, both verified at

##### Principles and implementation
The runtime member must satisfy: (1) drive the recommended HTTP client's async API
(`reqwest` async is built on `tokio::net`/`tokio::time`, non-optional per its
manifest); (2) be the *same* runtime R69's `axum` web feature uses, so the
feature-on tree holds one executor; (3) run the CLI's single-round-trip workload
without mandatory heavyweight features (`tokio`'s `default = []`, "Include nothing
by default", `tokio/Cargo.toml` at tag `tokio-1.53.1`). `tokio 1.53.1` meets all
three: `crates.io` and `rustup` run it in production, its feature flags let the
core take only `rt-multi-thread, macros` while reqwest adds `net, time` and R69's
web adds `signal, sync`. `smol` meets (3) but fails (1)/(2) — it cannot drive
`reqwest` async or `axum`, so adopting it alongside R69 means two runtimes.

##### Fit for this template
`tokio` is the only runtime that satisfies the one-model principle together with

single round-trip — negligible against one HTTP call's latency, and the
`rt-multi-thread, macros` core feature set keeps the always-on tree minimal

`tokio = "1.53.1"` with features `rt-multi-thread, macros` on the core crate's

##### Principles and implementation
The client member must satisfy: (1) speak the runtime member's model natively —
async for `tokio`, with no bridging; (2) cover redirects, TLS with platform roots,
and JSON bodies, the three behaviors the template's driven adapter needs; (3) keep
default features pure-Rust and cross-platform (`reqwest` 0.13 defaults:
`default-tls` = `rustls` on aws-lc-rs, `charset`, `http2`, `system-proxy`;
`reqwest/Cargo.toml` `[features]`, tag `v0.13.5`). Async `reqwest 0.13.5` meets all
three and is the API the ecosystem's HTTP code is written against (29,725 reverse
deps; `crates.io` pins `=0.13.5` with `gzip, json, stream`). `ureq 3.4.2` meets
(2)/(3) in a sync spelling (`#![forbid(unsafe_code)]`, `ureq/src/lib.rs:524`) at
one quarter the tree — and is the right client for a sync core, which this report
rejects on model unity, not on `ureq`'s merits.

##### Fit for this template
Async `reqwest` is the only client native to both halves of the template: the core
calls it with `.await` and the axum handlers call the same service the same way —
no `spawn_blocking`, no second client. Its `rustls`-by-default TLS keeps the tree
free of system TLS libraries on both OS legs, and `crates.io` proves the exact pin
under production load. The `blocking` facade is rejected *within* this member:
measured at 115 packages including tokio, it charges the full async dependency
cost for sync spelling — and the release-build probe (below) showed its documented
"will panic" guard is `#[cfg(debug_assertions)]`-only, so the misuse fails loudly
in debug and silently parks a worker in release.

##### Recommendation
`reqwest = { version = "0.13.5", features = ["json"] }` (default features on:
`rustls` TLS, `http2`, `charset`, `system-proxy`), async API only. The `blocking`
feature stays off; if a future sync-only consumer appears, it gets its own
deliberate decision, not a quiet feature flip.
