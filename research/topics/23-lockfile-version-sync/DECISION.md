## Decision

**Yes: the release commit must also bump `Cargo.lock`, and the mechanism is release-please's native Rust strategy — `"release-type": "rust"` in `release-please-config.json` — not an `extra-files` jsonpath entry.** The template commits the root `Cargo.lock`, relies on `--locked` on its CI cargo invocations to make the sync enforced (how and where that guard is wired — hook, CI step or job — is owned by R41 `lockfile-freshness-check`, still open), and `extra-files` carries no `Cargo.lock` object. Version: `googleapis/release-please-action` v5.0.0 (already pinned by F063), whose `package.json` declares `"release-please": "^17.6.0"`; the implementation executed here is release-please **17.11.2**, the version npm resolves from that range (retrieved 2026-09-05). Rust is therefore py-shaped on the *principle* (the lockfile records the root package's own version, so it is part of the release transaction) and differs from py only in the *updater*: py needs a generic TOML jsonpath because `release-type: python` knows nothing about `uv.lock`; `release-type: rust` schedules its own `CargoLock` updater for `Cargo.lock` unconditionally.

### Principles and implementation

**Shared requirement and agreement level.** A release PR is one complete version transaction: every committed file that encodes the package's own version — the manifest, release-please's version record, and the lockfile *when the lockfile records the root package's version* — changes in the same commit, so no PR revision, CI run or reviewer ever sees the manifest ahead of the lockfile, and no follow-up "sync" commit exists. The level is **architectural pattern with a policy-level acceptance rule**: what is shared is the completeness of the release commit, not the updater syntax. Evidence in both source repos at their pinned revisions (read from the local clones on 2026-09-05): py `release-please-config.json:16-20` at `b08bccf` — an `extra-files` entry `{"type": "toml", "path": "uv.lock", "jsonpath": "$.package[?(@.source && @.source.editable && @.source.editable.value=='.')].version"}`; ts `.github/workflows/release-please.yml:27-30` at `cb1cbcb` — "pnpm-lock.yaml does not encode the root project's own version. The generated release commit is therefore complete as-is: do not add a post-creation lock synchronization commit, which would expose an inconsistent intermediate PR revision to CI and automated reviewers." The two sources agree on the rule and differ only in lockfile schema, which `docs/port/DIVERGENCE-ANALYSIS.md:107` classes as C (language-bound mechanic, `harmonize: no`) and `docs/port/OWNER-REVIEW.md:65` accepts as written. `Cargo.lock` is py-shaped: each workspace member is a `[[package]]` record with its own `name` and `version` (fixture case S1 recorded `name = "demo-single"` / `version = "0.1.0"`; a workspace has one root lockfile — Cargo workspaces reference, retrieved 2026-09-05 by `raw/codex.md`).

**Essential behaviors** (any design must do all six):

1. `Cargo.toml` `[package] version` stays the single source of truth (F063).
2. The release PR updates `Cargo.toml`, `.release-please-manifest.json`, `CHANGELOG.md` and the root `Cargo.lock` entry of every released member in one commit. The installed strategy does this unconditionally: `strategies/rust.js:108-112` ends `buildUpdates` with `updates.push({ path: this.addPath('Cargo.lock'), createIfMissing: false, updater: new cargo_lock_1.CargoLock(versionsMap) })` after the `CargoToml` updates (release-please 17.11.2, `node_modules/release-please/build/src`).
3. `CargoLock.updateContent` parses the lockfile, matches `[[package]]` entries by `name` against the versions map, and replaces only their `version` values, preserving everything else (`updaters/rust/cargo-lock.js:41-59`). Its output is byte-identical to what `cargo update -w` writes (case S9).
4. CI proves the committed lock is consistent by passing `--locked` to its cargo invocations (R41 decides the wiring; this item only relies on the property); cargo refuses a stale lock with `error: cannot update the lock file … because --locked was passed to prevent this` and exit 101 (case S2, for `cargo build` and `cargo metadata`).
5. A meta-test asserts the copies cargo does not police: `.release-please-manifest.json` ↔ `Cargo.toml`, and that `release-please-config.json` selects `release-type: rust` with no `Cargo.lock` `extra-files` writer (cases S1, S3, S4; `single/tests/version_consistency.rs`). The fixture also keeps `cargo_lock_entry_matches_cargo_toml` deliberately, as the S3 demonstration that such an assertion cannot fail under cargo; the template may keep it (harmless, always passes) or drop it — it is not the guard.
6. In a multi-crate workspace, intra-workspace path dependencies that carry a `version = "…"` requirement are bumped together with the member (`CargoToml`'s versions-map loop, `updaters/rust/cargo-toml.js:42-62`; case S6e), because a bumped member makes a `^old` requirement unsatisfiable (case S7).

**What must agree and what may vary.** Must agree across py, ts and rs: the release PR is complete as generated; every file that encodes the root version is in it; CI proves the result consistent. May vary: whether the lockfile is in the set (ts: no, `pnpm-lock.yaml` has no root version field; py and rs: yes) and the updater that edits it (py: generic TOML jsonpath; rs: the Rust strategy's `CargoLock`).

**Architecture alternatives compared** (before any mechanism was chosen, per owner amendment A5):

- (A) *Native Rust strategy.* `release-type: rust` at the package path; the strategy discovers the package name from `Cargo.toml` and schedules `CargoToml` + `CargoLock` (behavior 2). One writer per file, no per-member configuration, package-aware matching. **Selected.**
- (B) *Generic TOML `extra-files` jsonpath on `Cargo.lock`* (py's shape). Works, but only as `$.package[?(@.name.value=="<crate>")].version`: `GenericToml` parses through release-please's `TaggedTOMLParser` (`util/toml-edit.js:63`), so every scalar is a `{value}` node and py's `.editable.value` is not decoration. The natural path silently changes nothing — a warning and exit 0 (S5a) — so a mistyped entry is caught only by `--locked` in CI later. With (A) present it is a second writer of the same file (per the comment at `github.js:616-620`, `buildChangeSet` merges duplicate updates for one path via `mergeUpdates` — read, not executed — so the two writers would be merged rather than conflict; it is redundant) and needs one expression per released member. **Runner-up.**
- (C) *Post-PR CI step that runs `cargo update -w` and pushes.* Produces the same bytes as (A) (S9) but as a second commit after the PR opens — exactly the intermediate inconsistent revision ts's comment forbids — and needs a write-capable token on the release workflow. **Excluded** by the completeness rule.
- (D) *Do not commit `Cargo.lock`* (the historical library convention), so there is nothing to sync. **Excluded**: the template ships a CLI and a web service, application artifacts whose CI and release builds must resolve one graph; `--locked` presupposes a committed lock; Cargo's FAQ recommends committing when in doubt (retrieved 2026-09-05 by `raw/codex.md`).
- (E) *release-plz or cargo-release.* Rust-native release managers that also update `Cargo.lock`. **Out of scope**: the release manager is settled (F063, F066, F073) and the prompt asks only whether `Cargo.lock` is one of its targets.

**Why the selected design preserves each principle.** Completeness: behavior 2 puts the lock change in the same update set as the manifest (S4). Single source of truth: `CargoLock` copies the version the strategy computed for `Cargo.toml`; nothing is hand-edited (S9 shows it equals cargo's own output). Enforcement: `--locked` turns any drift, from any cause, into a CI failure (S2, S3); R41 owns where that flag is applied. No new dependency: release-please is a GitHub Action (Apache-2.0, `node_modules/release-please/package.json` and `LICENSE`; `engines.node >= 22.0.0`) that never enters the crate graph, so binary size, compile time, MSRV, `unsafe` and RustSec posture are unaffected.

**Fitness gates** (pattern item; crate metrics `inapplicable` — no crate or dependency tree is selected; the prompt requires the reason stated): 1 license — release-please is Apache-2.0, compatible with the fixed `MIT OR Apache-2.0` and never redistributed with the template; 2 MSRV — inapplicable to a Node action; the cargo side of the pattern was executed at the policy floor 1.96.0 and refused at 1.91.1 (S8); 3 advisories and `unsafe` — inapplicable (no crate); 4 OS matrix — the action runs on GitHub's runner; the cargo side was executed on macOS 26.4 arm64 and Linux is planned (`--locked` semantics are platform-independent Cargo behavior; ubuntu run not executed here); 5 features and async coupling — inapplicable; 6 binary size and compile time — none in the template; the release workflow pays the action's Node start-up per run.
