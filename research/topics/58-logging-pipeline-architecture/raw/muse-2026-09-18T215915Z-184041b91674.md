### Principles and implementation

Shared requirement (source: py logging pipeline F250–F254/F262–F263/F274 + owner direction 2026-09-04 "best practices and principles from the Python logging ... for both TypeScript and Rust", `docs/port/OWNER-REVIEW.md`): structured, useful diagnostics that (a) render human-friendly on a TTY and JSON when piped (F250), (b) carry structured key/value fields (F251), (c) redact secret-bearing keys (F252), (d) optionally correlate OTel trace/span IDs behind an optional dependency (F253/F304), (e) resolve level as explicit `--log-level` flag/env, then config default, ahead of `-q`/`-v` (F274), (f) reconfigure idempotently touching only owned state (F262), (g) share one engine across CLI and web profiles with per-front-end policy (F263).

Agreement level: architectural pattern for the pipeline shape (layered subscriber composition with per-layer filtering) + policy for the redaction key list and the level-precedence order + capability for JSON/human switching and OTel correlation. Exact crate versions, field names beyond the redaction list, and web-profile defaults may vary. No new `BASELINE-REVIEW:` finding: F304's reclassification under this item (optional OTel feature boundary inside the `web` surface R69 defines, integration owned by R78, working OTel web example mandatory) is accepted as recorded; this answer gates the bridge behind an optional Cargo feature without making the web example optional.

Architectural alternatives compared: (1) `tracing` span/event model + `tracing-subscriber` `Layer` stack (recommended): contextual spans subsume py's processor-added context; `fmt` layer natively switches JSON vs human rendering; per-layer `Filter` gives front-end profiles; `reload::Layer` gives owned-handle reconfiguration; `tracing-opentelemetry` layer adds OTel correlation. (2) `log` records + `env_logger`/`log4rs`: flat records with no span context, printf-style formatting, no native JSON (env_logger gained JSON late and thinly), global logger set-once with no reload story — fails F250/F251/F262 without hand-rolled scaffolding that re-implements (1). (3) Hand-rolled leveled writer (ts D-018(1)): fails every required behavior; rejected. (4) `slog`: structured and fast but its maintainer has declared it feature-frozen in favor of `tracing` (see member notes), so new-template adoption is unjustifiable.

How the recommended design preserves each principle: F250 — `fmt` layer with `.json()` selected when `stderr` is not a TTY (`std::io::IsTerminal`, std since 1.70, no crate needed); F251 — events with structured fields replace the structlog chain; F252 — a small template-owned redacting `Layer` (a `field::Visit` implementation comparing key names against the `SENSITIVE_KEY_PARTS` policy list) wraps the `fmt` layer, so redaction applies to every sink including OTel; F253/F304 — `tracing-opentelemetry::OpenTelemetryLayer` added only under Cargo feature `otel`, mirroring py's soft-imported extra; F274 — a template-owned resolver implements flag/env > config > `-v`/`-q` precedence and feeds an `EnvFilter`/level directive (this item owns precedence only; `-v` counting stays with R60/cli-ux); F262 — the global default subscriber is installed once; reconfiguration goes through `reload::Handle`s the pipeline owns, so nothing foreign is torn down (migration risk noted below: this differs from py's handler-flag sweep and must be documented); F263 — one `Registry` composes the CLI layer stack; the web profile is a second stack sharing the same constructors plus JSON-default and the OTel layer — "one pipeline, two profiles" holds whether R69 ships a web surface or not.

Maturity, dependability, performance, integration cost: `tracing`/`tracing-subscriber` are the tokio-project standard with 872M/624M all-time downloads and releases within the last 9 months; `log`-ecosystem interop is first-class both directions (`tracing-log`, `log` features on emitters). Representative performance: `tracing`'s scoped dispatcher and per-callsite `Interest` caching keep disabled events near a single atomic load (maintainer design; no new benchmark run for this item — workload-specific numbers are R-independent and no absolute-fastest claim is made). Integration cost is one small module plus a redaction visitor (~150 lines), versus re-implementing JSON/levels/reload on `env_logger`.

Minimal realistic example: `src/logging.rs` exposing `init(LoggingConfig) -> Result<ReloadHandles, InitError>` where `LoggingConfig { level_override: Option<Level>, config_default: Level, verbosity: i8, json: AutoOrBool }`; CLI calls it once at startup, web profile calls `init_web` sharing constructors. Executable acceptance check: planned (see `### Validation strategy`); none executed by this worker.

### Recommendation

One stack: `tracing` 0.1 (emission API for lib + CLI + web) + `tracing-subscriber` 0.3 with features `fmt`, `json`, `ansi`, `env-filter`, `registry`, `reload`, `tracing-log` (pipeline: TTY-aware human/JSON rendering, level filtering, reloadable owned handles, `log`-record capture) + `tracing-opentelemetry` 0.34 behind optional Cargo feature `otel` (span/event correlation and export) + a template-owned redacting `Layer` implementing the F252 sensitive-key policy. Library code emits events/spans only and never installs a global subscriber.

##### Principles and implementation

`tracing` is the emission half of the pattern: `event!`/`span!`/`#[instrument]` macros produce structured, contextual diagnostics in library and application code alike, replacing py's structlog call sites (F251) and ts's stringly `createLogger` lines. The scoped-dispatcher design is what makes library-host ownership (F262) total: libraries emit through whatever subscriber the host installed and carry zero global state of their own. Default features (`GET /api/v1/crates/tracing/0.1.44`, `features.default`, 2026-09-25): `["std", "attributes"]` — no async runtime, no I/O; `valuable`, `log-always`, `max_level_*`/`release_max_level_*` are opt-in. Compile-time cost is small (macros + `tracing-core`); binary cost is negligible when disabled via max-level features. `unsafe` posture: contains `unsafe` (global dispatcher, `valuable` internals where enabled) inside the audited tokio codebase; no soundness advisory open (RUSTSEC-2023-0078 patched in ≥0.1.40; current 0.1.44 unaffected — https://rustsec.org/advisories/RUSTSEC-2023-0078.html, retrieved 2026-09-25).
