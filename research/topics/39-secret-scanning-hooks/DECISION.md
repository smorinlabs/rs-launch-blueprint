### Principles and implementation

**The shared requirement.** No credential reaches a shared remote from a developer machine without having been scanned. Scanning happens at the earliest cheap point (the commit) and again at the last local point before publication (the push). Every suppression is explicit, reviewable in version control, and no broader than the false positive it suppresses. Source: py's precedent as recorded in the prompt (py `lefthook.yml:73` and `:156`, `.gitleaks.toml:10`, `.gitleaksignore:1`; ledger rows F163–F166, `DIVERGENT`, origin `py-only`), tested against the maintainer's current documentation and against executed behaviour.

**Agreement level: policy plus tool and files.** The scanner is a language-agnostic executable; nothing in Python, TypeScript or Rust changes its cost or behaviour at a git hook. So the evidence supports one shared low-level value across all three repositories, not merely a shared capability:

| Must agree across py, ts, rs | May vary |
|---|---|
| the scanner and its pinned version | the hook manager's syntax for declaring the two jobs (R37) |
| the two command lines | the provisioning mechanism (R42 in rs; py keeps its own installer until its follow-on) |
| the `.gitleaks.toml` content | |
| the `.gitleaksignore` header and entry format | |

ts's absence of any secret scanner is a missing capability, not a justified ecosystem difference (both legs checked the ts checkout: `raw/muse.md:25`, `raw/opus.md:113-115`; **carried**, the ts repository is outside this synthesis's read scope). Changing py and ts is a follow-on project; this decision supplies the rationale in `BASELINE-REVIEW` form below.

**The tool.** gitleaks is the most-adopted dedicated scanner (29,499 stars, `SRC9`), its maintainer ships the exact staged-tier hook entry this decision uses (`gitleaks git --pre-commit --redact --staged --verbose`, `SRC15`), its default rule set has 222 rules (`SRC16`), and every behaviour above executed on 8.30.1. **Its maintenance state is `at-risk`, not dormant:** the README opens with "Gitleaks is feature complete. I'm not merging new features into Gitleaks. Future releases will be security patches only. I'm shifting my focus to [Betterleaks]" (`snapshots/gitleaks-README.md:12`, `SRC1`); the newest release is v8.30.1 of 2026-03-21, six months before retrieval (`SRC2`, `SRC3`); the eight newest default-branch commits are Dependabot bumps and their merges (`SRC4`, `SRC5`). It is not dormant: there are 0 repository security advisories (`SRC6`), security patches are promised, and the binary runs. **Why keep it despite `at-risk`:** the durable asset is the file format, not the binary. Betterleaks, from gitleaks' original author (`snapshots/betterleaks-README.md:7`, `SRC26`), reads `.betterleaks.toml` then `.gitleaks.toml` (`snapshots/betterleaks-root.go:285`, `SRC28`), `.betterleaksignore` then `.gitleaksignore` (`:297`, `SRC29`), and translates legacy allowlists (`snapshots/betterleaks-translate_filters.go:20`, `SRC30`). A template that writes gitleaks-format files therefore keeps a one-pin switch; the reverse does not hold. Betterleaks is not the pick today because it is 7.7 months old (created 2026-02-03, `SRC23`), changed its filter language from CEL to Expr within that time (`snapshots/betterleaks-README.md:92`, `SRC27`), and could not be executed here (release assets are not a named endpoint). A frozen gitleaks command line and rule set suits a template that ships exact command lines; the cost is that no new token formats arrive after 2026-03-21, which the re-verify trigger bounds.

**The pre-push range.** py's shape resolves a base (`@{u}`, else `origin/HEAD`, else `origin/main`, else warn and exit 0) and scans `<base>..HEAD`. Executed side by side with the recommended expression (`review/evidence/r39-range.sh`):

| Scenario | py-shape | recommended | Evidence |
|---|---|---|---|
| feature branch with upstream, leak on `HEAD` | blocks | blocks | `R1a`, `R1b` |
| `git push origin other` while on a clean `main` | **passes; the real push delivers the leaking branch to the remote** | blocks; remote lacks the ref | `R2a`, `R2d`, `R2e` vs `R2c`, `R2f`, `R2g` |
| new branch, no upstream (`@{u}` exits 128) | blocks via the `origin/HEAD` fallback | blocks | `R3a`–`R3c` |
| first push to an empty remote | **warns and exits 0** | blocks the real push | `R4a`, `R4b` vs `R4c`–`R4e` |
| detached `HEAD` | — | covered because `HEAD` is in the expression (0 commits without it, 1 with it) | `R7a`–`R7c` |
| a stash holding a token | — | not scanned (`refs/stash` is outside `--branches`/`--tags`) | `R6` |
| leak on a **different** unpushed branch, clean push | — | **blocks the clean push** | `R11a` |
| leak already pushed to a **second remote** (`fork`) with hooks bypassed, then `git push origin` | — | **passes; origin receives it** (0 commits scanned) | `R15a`–`R15c` |

The last row is the accepted cost: the flagged content is a real leak that has not been published, and the price buys a hook with no script and no stdin coupling. The stdin-exact form (`<local-sha> --not --remotes` per ref read from `githooks(5)` stdin) removes that over-scan (`R12a`) and still blocks the leaking branch (`R12b`, `R12c`); it is the ranked runner-up, chosen if R37's manager forwards pre-push stdin and the owner wants per-ref scoping. Residual gaps of the recommended form, neither of which py's shape or the stdin-exact runner-up closes: a push of an explicit object name that no branch, tag or `HEAD` reaches; and a commit already reachable from **any** remote-tracking ref, including a second remote such as a personal fork, is excluded even when the push targets a different remote (`R15b`, `R15c`; named by neither leg). Narrowing the exclusion to the destination remote, `--not --remotes=<remote>`, closes the second gap (`R15d`); git passes that remote's name to the `pre-push` hook as its first argument, so the narrowing is available only if R37's manager forwards hook arguments.

**The allowlist.** Every exemption is a blind spot, so the baseline ships none. The default global allowlist already covers the config file itself (`snapshots/gitleaks-default-config-v8.30.1.toml:25`, `SRC20b`) and other ecosystems' lockfiles; it has no `Cargo.lock` entry (`SRC20c`), and a real 592-line Rust lockfile produces no finding (`C6`). The commented example shows the narrow form for the first real false positive: `targetRules`, `condition = "AND"`, a fixture path and a value prefix together (`C7a`–`C7e`). Its prefix is `^fixture-`, not the `^test-only-` in Opus's example (`raw/opus.md:270`), because the default `generic-api-key` rule never flags a value beginning `test-only-` (`C7f`), so that example would exempt nothing. `.gitleaks.toml` as shipped (`review/evidence/proposed/gitleaks.toml`, sha256 `8dad313ef2f6f9f823a457d17bed43baaf9fe5d0674b0d16e5b018262e8a0443`):

```toml
# .gitleaks.toml — read by gitleaks >= 8.25 and by Betterleaks (legacy-format compatible).
title = "rs-launch-blueprint secret-scanning rules"

# Start from the scanner's maintained default rule set. It already ignores its own
# config file and the AWS documentation example keys (rule allowlist `.+EXAMPLE$`).
[extend]
useDefault = true

# No path or regex exemptions ship by default. Add one only for a real false positive,
# scoped as narrowly as possible, for example:
# [[allowlists]]
# description = "Fake credentials used by the web service's config-parsing tests"
# targetRules = ["generic-api-key"]
# condition = "AND"
# paths = ['''^crates/web/tests/fixtures/''']
# regexes = ['''^fixture-''']
```

The example's `crates/web/tests/fixtures/` path is illustrative; R02 owns the crate layout.

```text
# .gitleaksignore — per-finding suppressions, one fingerprint per line.
# Pattern or path exemptions belong in .gitleaks.toml, not here.
#
# Prefer, in order:
#   1. an inline `gitleaks:allow` comment on a deliberate fake in a new change;
#   2. a commit-form fingerprint  <commit-sha>:<path>:<rule-id>:<line>  for a finding

#   3. a path-form fingerprint   <path>:<rule-id>:<line>  only when (1) is impossible;

#   gitleaks git --no-banner --redact --config .gitleaks.toml -v --log-opts="<range>" .
```
