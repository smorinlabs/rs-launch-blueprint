### Principles and implementation

**Shared requirement.**

- *Source.* py `lefthook.yml:73` and `:156` at the pin. The owner disposition is class D, harmonize
  yes (`docs/port/OWNER-REVIEW.md:266`, 2026-09-04). The owner clarification of 2026-09-04 asks
  for the shared principle and its agreement level.
- *The requirement.* **No credential reaches a shared remote from a developer machine without
  having been scanned. Scanning happens at the earliest cheap point and again at the last local
  point before publication. Every suppression is explicit, reviewable in version control, and as
  narrow as the false positive it suppresses.**
- *Agreement level.* **Policy plus tool.** The divergence is an omission in ts that is not bound
  to TypeScript (`docs/port/DIVERGENCE-ANALYSIS.md:163`: "gitleaks is a standalone,
  language-agnostic Go binary, so its absence in ts is not explained by TypeScript-specific
  mechanics"). Nothing in the Rust, Python or TypeScript ecosystems changes the tradeoff, so the
  evidence supports **one tool, one config file and one pair of hook command lines across all
  three repositories.** That value is recommended because the evidence supports it, not because
  py already uses it.

**Why the hook tier and the CI tier use different tools.** The two tiers answer different
questions:

- The **hook tier** asks whether this change *looks like* it contains a credential. It must be
  offline, fast and deterministic. It must also flag credentials that cannot be verified, such as
  private keys, credentials for internal services, and tokens that are not yet live.
- The **CI tier** (R17) asks whether a *live* credential has reached the remote. `--only-verified`
  keeps its false-positive rate near zero.

py already runs this split: gitleaks in hooks, and TruffleHog in `.github/workflows/secret-scan.yml`
(R17 `DECISION.md`, assertions `01a`–`01c`). Probe 3 T3 and T4 show why the split is needed. With
`--results=verified`, TruffleHog reports **0** findings for a never-issued `ghp_` token that
gitleaks blocks, and TruffleHog did not report the private key at all.

**Why gitleaks now, despite `at-risk`.** The durable asset in this item is the **config and
suppression format**, not the binary. Betterleaks reads both gitleaks files and translates the
legacy allowlist schema. So a template that writes only gitleaks-format files keeps the option to
switch at the cost of one pin and one executable name. The reverse is not true: a
Betterleaks-only Expr config is unreadable by gitleaks.

At the hook tier, a frozen command line and rule set is an advantage, not a defect. The template
ships exact command lines, and gitleaks has promised not to change them. Betterleaks, by contrast,
changed its filter language from CEL to Expr within its first 7 months ("Previously this logic was
implemented in CEL; existing CEL-shaped configs are still accepted for compatibility",
`README.md`). It shipped three releases in eight days in August 2026. This leg also could not execute it.

The cost of the choice is a **frozen detection rule set**: 222 rules at v8.30.1, and no new token
formats after 2026-03-21. R17's actively maintained CI scanner partly offsets that for live
credentials. The re-verify trigger below makes the switch condition explicit rather than leaving
it to drift.

**Minimal realistic example.** These are the files the template ships. Hook-manager syntax is
R37's. The two command lines are what any manager runs.

```toml
# .gitleaks.toml — read by gitleaks >= 8.25 and by Betterleaks (legacy-format compatible).
title = "rs-launch-blueprint secret-scanning rules"

# Start from the scanner's maintained default rule set. It already ignores its own
# config file and the AWS documentation example keys (rule allowlist `.+EXAMPLE$`).
[extend]
useDefault = true

# No path or regex exemptions ship by default. Add one only for a real false positive,
# scoped as narrowly as possible, for example:
# [[allowlists]]
# description = "Fake credentials used by the web service's config-parsing tests"
# targetRules = ["generic-api-key"]
# condition = "AND"
# paths = ['''^crates/web/tests/fixtures/''']
# regexes = ['''^test-only-''']
```

```text
# .gitleaksignore — per-finding suppressions, one fingerprint per line.
# Pattern or path exemptions belong in .gitleaks.toml, not here.
#
# Prefer, in order:
#   1. an inline `gitleaks:allow` comment on a deliberate fake in a new change;
#   2. a commit-form fingerprint  <commit-sha>:<path>:<rule-id>:<line>  for a finding
#      already in history (it suppresses that one commit's occurrence only);
#   3. a path-form fingerprint   <path>:<rule-id>:<line>  only when (1) is impossible;
#      it suppresses that line in every commit and at both hook tiers.
# Precede every entry with a one-line comment saying what it is and why it is safe.
# To obtain a fingerprint:
#   gitleaks git --no-banner --redact --config .gitleaks.toml -v --log-opts="<range>" .
```

```sh
# pre-commit job (manager-neutral command line)
gitleaks git --pre-commit --staged --no-banner --redact --config .gitleaks.toml .

# pre-push job (manager-neutral command line; reads no stdin)
gitleaks git --no-banner --redact --config .gitleaks.toml --log-opts="--branches --tags HEAD --not --remotes" .
```

**How the example composes.** The two jobs run the same binary with the same `--config`. Both
read `.gitleaksignore` from the scan target (`-i` defaults to `.`). The pre-push log expression
selects every commit reachable from a local branch, a local tag or `HEAD` that is not reachable
from any remote-tracking ref. That set is a superset of what any `git push` from this clone can
publish, except an explicitly named object that no branch, tag or `HEAD` reaches.

The expression needs no wrapper script and no stdin parsing, and it fails in the safe direction:

- **Stale remote-tracking refs** make the set larger (over-scan), not smaller.
- **A first push to an empty remote** scans the whole local history, which is correct.
- **Nothing unpushed** gives an empty set, which exits `0` correctly.
- **Stashes are excluded**, because `refs/stash` is not under `--branches` or `--tags`.

#### Staged pre-commit job (F163)

##### Landscape
The mechanisms found are:

- the scanner's own staged mode (`gitleaks git --pre-commit --staged`; `betterleaks git --pre-commit --staged`; `kingfisher scan --staged`);
- a file-list scan of `git diff --cached --name-only`, as ripsecrets and TruffleHog `filesystem` do;
- a wrapper script, as py's `scripts/check-gitleaks.sh --staged` does.

Crate figures are `inapplicable`: this member is a hook job, not a crate. Practice: 0 of 22 Rust
projects run one. py runs it (`lefthook.yml:72-73`). ts has none.

##### Principles and implementation
The job must read the **index**. A file-list scan reads working-tree files, so a partially staged
file is judged on content that is not being committed. Probe 1 §04 shows `--staged` passes when
the staged version is clean even though the working tree holds a secret. That is correct: the
secret is not being committed. The opposite case, a secret staged and then scrubbed from the
working tree, is caught only by an index read.

##### Dominant choice
The scanner's native staged mode.

##### Qualified shortlist
1. The direct command line.
2. A wrapper script like py's. A wrapper adds a presence check with a friendlier message, but the
   hook already fails closed without one (probe 1 §14b: `gitleaks: command not found` blocks).

reads the working tree, not the index. The deprecated `gitleaks protect --staged` is excluded on
support: it is hidden since v8.19.0. Numbered gates 1–6 are `inapplicable` to a hook command line;
they are answered for the scanner under member 1.

##### Up-and-comers
Betterleaks' identical `git --pre-commit --staged`.

##### Fit for this template

34.1ms" (probe 1 §01), 0.05 s process wall time (§15).

##### Recommendation
`gitleaks git --pre-commit --staged --no-banner --redact --config .gitleaks.toml .`

##### Ranked runner-up

##### Tradeoffs

##### Migration implications

#### Pre-push range job (F164)

##### Landscape
Mechanisms found:

- (a) `@{u}..HEAD` with fallbacks (py);
- (b) parsing `pre-push` stdin per ref (`githooks(5)`) with `<local-sha> --not --remotes`;
- (c) a stdin-free `--branches --tags HEAD --not --remotes`;
- (d) no local range tier; rely on CI.

Crate figures are `inapplicable`: this member is a hook job, not a crate. Practice: 0 of 22 Rust
projects. py runs (a).

##### Principles and implementation
The job must scan every commit that the push can publish and that is not already public, without
needing an upstream. git's contract (`githooks(5)`): the hook receives
`<local-ref> SP <local-object-name> SP <remote-ref> SP <remote-object-name> LF` per ref. A non-zero
exit makes "git push … abort without pushing anything".

(b) follows that contract exactly. It needs a script, and the manager must forward stdin
(lefthook's mechanism for this is R37's to decide). (c) needs neither. It scans a superset of (b)
that is bounded by unpushed local work. Its one residual gap is a push of an explicit object name
that no branch, tag or `HEAD` reaches.

##### Dominant choice
No ecosystem convention exists. py's (a) is the only precedent, and it fails B2 twice: probe 4 P1
shows a non-`HEAD` push scanned as 0 commits, and the script's fallback exits `0`.

##### Qualified shortlist
1. (c) stdin-free: executed in probe 4 P2/P3, probe 5 and probe 6.
2. (b) stdin-exact: executed in probe 1 §14.

##### Excluded by gate
- (a), excluded on correctness; evidence in the F164 `BASELINE-REVIEW` line.
- (d), excluded because it loses B2 before publication.

Numbered gates 1–6 are `inapplicable` to a git log expression.

##### Up-and-comers
None specific. Betterleaks accepts the same `--log-opts`.

##### Fit for this template
Contributors push feature branches that have no upstream on their first push; py's form skips or
falls back in exactly that case. (c) needs no upstream.

##### Recommendation
`gitleaks git --no-banner --redact --config .gitleaks.toml --log-opts="--branches --tags HEAD --not --remotes" .`

##### Ranked runner-up
(b), the stdin-exact script. Choose it if R37's manager forwards stdin and the owner wants exact
per-ref scoping. It closes the explicit-object-name gap.

##### Tradeoffs
(c) can block a push because of a leak on a *different* unpushed local branch. That is a
false-positive block of this push, but the flagged content is still a real leak. The trade is to
accept that over-scan in return for having no script and no stdin coupling.

None owned.

##### Migration implications
One pre-push job entry in the R37 hook config. No `scripts/` file.

1. From a clean `main`, create branch `other` with a `--no-verify` leak commit.
2. `git push origin other` must exit non-zero, and the remote must not have `other`.
3. Drop the leak commit; the push must then exit `0`.
4. From a detached `HEAD`, the scanned commit count must include `HEAD`.

##### Confidence & re-verify trigger
Medium-high. Re-verify if R37 selects a manager whose pre-push job runs outside the repository
root. The scan target `.` must be the repository root, because probe 2 H shows that `gitleaks git`
outside a repository exits `0` after scanning 0 commits.

#### Allowlist configuration `.gitleaks.toml` (F165)

##### Landscape
Configuration surfaces found:

- gitleaks `[extend] useDefault` plus `[[allowlists]]` (with `targetRules` and `condition`) since
  v8.25.0;
- Betterleaks Expr `prefilter`/`filter`, which also accepts the legacy gitleaks schema;
- Kingfisher YAML rules;
- ripsecrets `.secretsignore`.

Crate figures are `inapplicable`: this member is a config file, not a crate. py's file: singular
`[allowlist]` with four path patterns (`docs/.*`, `.*\.md$`, and two `.github` template paths) and
two AWS example regexes.

##### Principles and implementation
Every exemption must be narrower than the false positive it suppresses, because an exemption is a
blind spot for real secrets. Two observations follow from the default rule set:

- Its global allowlist already covers lockfiles of other ecosystems, binary and asset files, and
  the config file itself (the `gitleaks\.toml` path). Cargo's `Cargo.lock` is not in that list,
  yet it produced no findings (probe 4 P5).
- The AWS documentation example keys already pass under the default rules (probe 1 §11).

The template therefore has no known false positive to exempt at baseline.

##### Dominant choice
Extend the scanner's defaults. Do not replace them.

##### Qualified shortlist
1. Build fresh: `useDefault = true` and no exemptions. Executed in probe 1 §12, second case.
2. Port py's file.

##### Excluded by gate

#### Fingerprint-suppression file `.gitleaksignore` (F166)

##### Landscape
Per-finding suppression surfaces found:

- gitleaks `.gitleaksignore`, which the README flags as experimental ("Note: this feature is
  experimental and is subject to change in the future");
- inline `gitleaks:allow`;
- a report used as a baseline (`--baseline-path`);
- Betterleaks `.betterleaksignore`, which falls back to `.gitleaksignore`;
- the Kingfisher baseline YAML;
- ripsecrets `[secrets]`, which stores literal secrets.

Crate figures are `inapplicable`: this member is a plain-text file, not a crate.

##### Principles and implementation
A suppression must name one finding and must not contain the secret. gitleaks fingerprints take
two forms, and they behave differently (probe 2):

| Form | Example shape | Suppresses | Evidence |
|---|---|---|---|
| Commit-form | `<commit-sha>:<path>:<rule>:<line>` | That one commit's occurrence, at the range tier only | E passes; F still blocks a re-staged copy |
| Path-form | `<path>:<rule>:<line>` | That path and line in **every** commit and at **both** tiers | B and C pass; G blocks once the line moves |

##### Dominant choice
Ship the file empty, with its instructional header, as py does.

##### Qualified shortlist
1. The empty file with a header documenting the preference order.
2. A `--baseline-path` report file. It is heavier and not needed for a new repository that has no
   history of findings.

##### Excluded by gate
- Pre-populating the file is excluded: the template has no findings to suppress.
- ripsecrets-style literal lists are excluded: they commit the secret itself.

Numbered gates 1–6 are `inapplicable` to a plain-text file.

##### Up-and-comers
Betterleaks reads this file as a fallback, so the format survives a switch.

##### Fit for this template
Template users inherit the file. The header is the only guidance they get, so it must name
supported commands and both forms.

##### Recommendation
An empty file with the header given in the minimal realistic example. The header recommends
inline `gitleaks:allow` first, then commit-form, then path-form.

##### Ranked runner-up
py's file verbatim. Its instruction names the deprecated `gitleaks detect` and does not mention
the two forms.

##### Tradeoffs
The file format is marked experimental upstream. Because gitleaks is frozen, that marking is
unlikely to be acted on in gitleaks itself, and Betterleaks already reads the file.
