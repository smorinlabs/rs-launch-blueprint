### Landscape

Category: language-agnostic secret scanning at git-hook tiers for a Rust template — a staged pre-commit scan, a pre-push commit-range scan, a path/pattern allowlist config, and a per-finding fingerprint-suppression file.

Three-bin map of the Rust field:

- Built-in or first-party toolchain: none. The Rust toolchain (cargo/rustc) ships no secret scanner, and no RFC, working-group output, or annual-survey result proposes one. GitHub platform-side secret scanning and push protection exist but are hosting-platform features, not template-shipped hook tiers, so they are out of this item's scope (complementary, not a substitute).
- Established industry standard: gitleaks (Go binary, MIT), trufflehog (Go binary, AGPL-3.0), git-secrets (shell/AWK, Apache-2.0), detect-secrets (Python, Apache-2.0). All are language-agnostic; none is Rust-specific.
- Up-and-comer: Kingfisher (Rust-built binary, Apache-2.0, MongoDB) and ripsecrets (Rust binary and crate, MIT, single maintainer). Nosey Parker (Rust, Praetorian) would sit here but its repository is archived, so it is excluded.

Every shortlisted candidate comes from this map: gitleaks, trufflehog, git-secrets, detect-secrets, Kingfisher, ripsecrets. Nosey Parker is carried only as an excluded-by-gate record.

### Principles and implementation

Shared requirement: no secret committed to a working tree may reach shared history unnoticed. Source: py precedent (ITM-001 staged scan, ITM-002 range scan, ITM-004/ITM-005 allowlist/suppression split, ADR-02 two-layer coverage) tested against current maintainer docs and the Rust field above. Agreement level: capability plus policy. All three blueprints must agree that (a) every commit passes a staged-diff secret scan, (b) every push passes a range scan covering commits that bypassed the staged hook (`--no-verify`, imported history), (c) pattern/path exemptions live in a reviewed config file while per-finding exemptions live in a separate fingerprint file, and (d) CI re-scans with a verifying scanner as a second layer. The low-level value (gitleaks at both hook tiers) is shared between py and rs not by inheritance but because the evidence supports the same tradeoff in both ecosystems: the tool is a language-agnostic single binary, so its install cost, rule breadth, and hook ergonomics are identical for a Python and a Rust template, and no Rust-native alternative matches its hook-tier story (member evidence below). ts carries no secret scanning at any tier (verified by grep over workflow/config/script files in the ts checkout on 2026-09-26: zero matches for gitleaks, trufflehog, or detect-secrets); that is a missing capability, not a justified ecosystem difference, and a follow-on project should close it with the same two-tier shape. This answer supplies the rationale; it changes no py or ts file.

Essential behaviors: (1) the staged scan fails the commit when a fixture secret is staged and passes a clean tree; (2) the range scan derives its base from the upstream tracking branch with a documented fallback (remote default branch) and a loud skip only when no ref exists; (3) the allowlist narrows by path for prose plus named regexes for known example keys, extends (never replaces) the default rule set; (4) the suppression file holds fingerprints only, ships empty, and every entry carries a rationale comment; (5) scanner output redacts secrets from logs. Observable acceptance criteria: stage a canonical AWS example key outside an allowlisted path and the pre-commit job exits non-zero naming the rule; commit with `--no-verify` and the pre-push job exits non-zero on the same fixture; move the fixture under `docs/` and both jobs pass; add the finding's fingerprint plus rationale to the suppression file and both jobs pass with the fixture restored.

Architectural alternatives compared before choosing libraries. Hook-tier local scanning versus CI-only versus platform push protection: CI-only and push protection both let the secret enter local history (and, for CI-only, the pushed branch) before detection, which fails essential behavior (1); py's ADR-02 two-layer rationale stands — hooks prevent, CI catches. Pattern-rule scanning (gitleaks default set) versus verified-only (trufflehog `--only-verified`) versus entropy/probability (ripsecrets): the hook tier needs instant, offline, broad-pattern feedback on the diff, which is the pattern-rule shape; verified-only needs network calls to live providers from every developer commit (slow, exfiltrates candidates) and misses unverified-but-real secrets, so it belongs in CI (where R17 already puts it), not in hooks. Wrapper script versus direct hook commands: the range tier needs base-resolution fallback logic no single gitleaks flag expresses (py's `@{u}`-then-`origin/HEAD`-then-`origin/main` chain with loud skip), and one entry point serves hooks, CI, and manual runs; the wrapper is kept, with its inner commands modernized to maintained syntax. Fingerprint suppression versus baseline files (detect-secrets) versus inline comments: fingerprints survive file moves better than line-based baselines and keep exemptions reviewable in one file rather than scattered as comments; retained.

How the recommended design preserves each principle: two hook jobs preserve (a) and (b); the `[[allowlists]]` config preserves (c-config); the empty-shipped `.gitleaksignore` preserves (c-suppression); R17's TruffleHog CI workflow (referenced, not re-decided) preserves (d). The one justified cross-ecosystem difference from py is config syntax, not tooling: py's global `[allowlist]` table was replaced by `[[allowlists]]` in gitleaks v8.25.0 (README, retrieved 2026-09-26; no backwards-compatibility statement is given for the global table, unlike the rule-level rename), so rs ships the new syntax at its newer pin while py stays on its working pin until its own review cadence moves it.

Maturity, dependability, performance, integration cost: gitleaks 29,497 stars with pushes 3 days before retrieval is the dependability anchor; its staged/range modes are the maintainer-documented hook path. Representative performance was not benchmarked in this leg (no execution route for binary benchmarks; workload-sensitive claims from unlike suites are not compared, per the prompt) — the qualitative ordering from the tools' own architectures is ripsecrets fastest/narrowest, gitleaks fast/broad, trufflehog slowest at hooks because verification is network-bound; Kingfisher's published benchmark claims (Vectorscan engine, lowest runtime across its suite) are vendor-run and treated as a lead, not a verdict. Integration cost is lowest for gitleaks: one pinned binary plus two text files, zero Cargo dependency-tree impact.

Minimal realistic example: a template checkout with `scripts/check-gitleaks.sh`, `scripts/install-gitleaks.sh`, `.gitleaks.toml` (`[extend] useDefault = true` plus one `[[allowlists]]` table), `.gitleaksignore` (comments only), and two hook jobs invoking the wrapper with `--staged` and `--range`. Executable acceptance check (PROPOSED, not run): `printf 'AKIAIOSFODNN7EXAMPLE\n' > src/fixtures_key && git add src/fixtures_key && scripts/check-gitleaks.sh --staged` must exit 1 naming the AWS rule; `git commit --no-verify -m x` then `scripts/check-gitleaks.sh --range` must exit 1 on the same finding; adding the printed fingerprint to `.gitleaksignore` must flip both to exit 0. No `BASELINE-REVIEW:` finding: no ledger classification is challenged (F163–F166 remain `DIVERGENT`, `py-only` as statements about py/ts; rs adoption extends coverage without reclassifying the sources).

### Recommendation

One stack: gitleaks v8.30.1 as a SHA256-pinned release binary installed by `scripts/install-gitleaks.sh`; `scripts/check-gitleaks.sh --staged` running `gitleaks git --pre-commit --redact --staged --config .gitleaks.toml` and `--range` running `gitleaks git --redact --config .gitleaks.toml --log-opts="<base>..HEAD"` with py's upstream-fallback base resolution; `.gitleaks.toml` extending defaults with one `[[allowlists]]` table (docs/Markdown/template paths plus the two AWS example-key regexes); `.gitleaksignore` shipped empty-with-comments; no new CI job — the second layer is R17's accepted TruffleHog CLI workflow in a separate file.

##### Principles and implementation
The tool must serve essential behaviors (1), (2), and (5): staged-diff blocking, commit-range scanning with a resolvable base, and redacted output — offline, in well under a commit's patience budget, with a default rule set broad enough for a CLI plus library plus web service (cloud keys, private keys, generic high-entropy strings, web tokens). Gitleaks meets all three natively: `git --pre-commit --staged` (its own `.pre-commit-hooks.yaml` entry), `git --log-opts="<base>..HEAD"` (README range example), `--redact`, `[extend] useDefault = true` defaults, `.gitleaksignore` fingerprints. TruffleHog meets the range shape (`git file://. --since-commit/--branch`, `--fail`, exit 183 on findings) but its hook story centers on verification, which needs network egress to providers from every commit. Kingfisher meets the staged shape (`scan . --staged`, pre-commit deployment doc) with hundreds of built-in rules plus optional validation, mapping, and revocation — a SOC workflow whose extra surface is inert weight at the hook tier. Ripsecrets is explicitly pre-commit-shaped (`--install-pre-commit`, file-list args, `.secretsignore`) and local-only by design, but has no range mode, no fingerprint file, and a probability-rule set narrower than gitleaks defaults. Git-secrets is hook-shaped but AWS-pattern-centric with user-written patterns for the rest and no default breadth. Detect-secrets is baseline-file-shaped (line-anchored baselines, Python runtime dependency) rather than diff-and-fingerprint-shaped.

Gitleaks: the most-starred (29,497) dedicated secret scanner with a maintainer-documented staged-plus-range hook path, a default rule set extended (not replaced) by config, redaction, and fingerprint suppression — and the exact tool py already runs at both tiers, so cross-ecosystem evidence and precedent converge rather than compete.

#### two-tier-hook-invocation

##### Landscape
Invocation-pattern bin, not a tool bin. Candidates: (a) wrapper script with two modes (`scripts/check-gitleaks.sh --staged|--range`, py precedent at `b55b8c26364c`); (b) direct hook commands (`gitleaks git --pre-commit --redact --staged`, `gitleaks git --log-opts="<base>..HEAD"`, from the maintainer's `.pre-commit-hooks.yaml` and README range example, retrieved 2026-09-26); (c) legacy direct commands (`gitleaks protect --staged`, `gitleaks detect --log-opts=...` — what py's wrapper currently shells out to, deprecated since v8.19.0 but still available per the README); (d) manager-native file passing (`{staged_files}` interpolation, the shape R37's hook manager may offer — R37 is open, so this is a branch, not a candidate). Authority is the maintainer's own hook file for (b), py's working wrapper for (a), and the README deprecation notice for (c).

##### Principles and implementation
The invocation must preserve essential behaviors (1), (2), and (5) across whatever manager R37 selects: fail the commit on a staged secret, resolve a push base that covers bypassed commits, and redact output. The staged tier is expressible as one direct command (candidate b, exactly the maintainer's hook entry plus `--config`). The range tier is not: deriving `<base>` needs `git rev-parse --abbrev-ref --symbolic-full-name '@{u}'` with fallback to `origin/HEAD` then `origin/main` plus a loud skip when no ref resolves (py's ADR-0018 logic) — shell logic no gitleaks flag performs. Hence a wrapper is required for the range tier regardless, and using it for both tiers keeps one entry point for hooks, manual runs, and any CI reuse, one place for `--config/--redact/--no-banner` uniformity, and one PASS/FAIL reporting shape. The wrapper's inner commands move from (c) to (b): the README states `detect`/`protect` were deprecated in v8.19.0, remain available but hidden, and may break (maintainers ask for issues if they do) — pinning a fresh 8.30.1 while shelling to deprecated verbs would start life on a removal path.

##### Dominant choice
Wrapper script (candidate a) with modern `git`-mode inner commands (candidate b): py's proven structure with the maintainer's current verbs.

##### Qualified shortlist
Direct hook commands for the staged tier only (candidate b without a wrapper): viable if R37's manager makes one-liners cleanly reviewable, but it splits the two tiers across two mechanisms for no benefit. Legacy verbs inside the wrapper (candidate c): works at both py's 8.27.2 pin and 8.30.1 today, carried strictly as a fallback if `git --pre-commit --staged` misbehaves at implementation time.

##### Excluded by gate
No invocation candidate fails a fitness gate; the gates constrain tool artifacts (license, MSRV, advisories, OS matrix, features, size), and a shell wrapper plus documented flags presents no artifact in any of those dimensions. All six gates are recorded `inapplicable` for this member with that reason. (R37's manager, when chosen, must run `bash`/`sh` wrappers on both fixed runners — a constraint handed to R37, not decided here.)

##### Up-and-comers
Manager-native file passing (candidate d): if R37 selects a manager with `{staged_files}`-style interpolation, the staged job could become a direct `gitleaks git --pre-commit --staged` line with no wrapper involvement. This is a live branch pending R37, not a recommendation; the wrapper remains for the range tier either way.

##### Fit for this template
The template's hook jobs (inside R37's manager file, whatever it is) become two one-line jobs — `run: scripts/check-gitleaks.sh --staged` at pre-commit, `run: scripts/check-gitleaks.sh --range` at pre-push — mirroring py's `lefthook.yml` jobs. The wrapper is POSIX-leaning bash (`set -euo pipefail`, `git rev-parse`, no GNU-only flags in py's version), portable to both fixed runners; macOS ships bash 3.2, so the port must avoid associative arrays and other bash-4-isms (py's script already does — carried as an implementation note, verified by reading, not by execution).

##### Recommendation
Port py's `scripts/check-gitleaks.sh` with identical structure, usage text, base-resolution fallback chain, and PASS/FAIL/WARN reporting, replacing the two inner commands with `gitleaks git --pre-commit --redact --staged --config .gitleaks.toml --no-banner` and `gitleaks git --redact --config .gitleaks.toml --no-banner --log-opts="<base>..HEAD"`.

##### Ranked runner-up
Keep py's inner commands verbatim (`protect --staged`, `detect --log-opts`): zero behavioral delta from a proven implementation, at the cost of building on verbs the maintainer has deprecated and hidden. It becomes the recommendation only if the `git`-mode commands fail their implementation-time validation.
