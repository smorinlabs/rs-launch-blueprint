### Landscape
Category: application-owned directory resolution. The first-party bin is Rust `std` (`std::env` plus `Path`), which can read and validate an override but does not model the XDG set; `std::env::home_dir` is stable and explicitly points callers to XDG on Unix and `LOCALAPPDATA`/`APPDATA` on Windows. [Rust std `home_dir`](https://doc.rust-lang.org/std/env/fn.home_dir.html) (retrieved 2026-09-16). The established-standard bin is the XDG Base Directory Specification, whose separate data, config, state, and cache bases have distinct purposes and whose values must be absolute. [XDG specification](https://specifications.freedesktop.org/basedir/latest/) (retrieved 2026-09-16). Shortlisted Rust realizations are `xdg` 3.0.0 (literal XDG), `directories` 6.0.0 (native OS conventions), and `etcetera` 0.11.0 (explicit XDG/native strategies). [xdg docs](https://docs.rs/xdg/3.0.0/xdg/) (retrieved 2026-09-16); [directories docs](https://docs.rs/directories/6.0.0/directories/) (retrieved 2026-09-16); [etcetera docs](https://docs.rs/etcetera/0.11.0/etcetera/) (retrieved 2026-09-16).

The Rust project/Cargo reference is authoritative for `rust-version` semantics, and the freedesktop specification is authoritative for XDG semantics; maintainer docs and published crate artifacts are authoritative for each crate's API and declared MSRV. [Cargo rust-version reference](https://doc.rust-lang.org/cargo/reference/rust-version.html) (retrieved 2026-09-16); [crates.io API, etcetera 0.11.0 artifact](https://crates.io/api/v1/crates/etcetera/0.11.0/download) (retrieved 2026-09-16). ### Principles and implementation
The shared requirement is capability-level, not an inherited four-function policy: resolve only application storage locations that a concrete feature needs, honor the XDG meaning where an XDG location is chosen, and keep resolution testable and centralized. The XDG specification distinguishes persistent user data, persistent/recoverable state such as logs/history, and regenerable cache; it does not require every application to use all of them. [XDG specification](https://specifications.freedesktop.org/basedir/latest/) (retrieved 2026-09-16). The Python pin implements config/data/state/cache and sends its default log to state; the TypeScript pin supplies only config. [Python pin](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/src/py_launch_blueprint/core/paths.py) (retrieved 2026-09-16); [TypeScript pin](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/src/lib/xdg-paths.ts) (retrieved 2026-09-16).

What must agree is intentional classification and a single tested resolver per required location; what may vary is the number of locations and the Rust representation. A config-only Rust template preserves the capability because neither R59 nor R67 has selected a disk sink; introducing data/cache/state before a consumer exists invents a public contract. The alternative full-set architecture is viable: `etcetera`'s `AppStrategy` exposes config/data/cache/state methods and selects XDG on Linux and macOS, but that is a contingent future mechanism, not proof that the template needs all four now. [etcetera docs](https://docs.rs/etcetera/0.11.0/etcetera/) (retrieved 2026-09-16); [etcetera source artifact](https://crates.io/api/v1/crates/etcetera/0.11.0/download) (retrieved 2026-09-16).

No representative latency, throughput, allocation, binary-size, or compile-time benchmark was run: this is one startup-time path calculation, and no source provides comparable workload evidence. The proposed minimal realistic example is a CLI and web composition that both receive the same config resolver, while a file sink and crash sink are disabled; the proposed acceptance check is listed below and was not executed. [R57 ledger context](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/docs/port/COMMONALITY.md) (retrieved 2026-09-16).

BASELINE-REVIEW: F249 — resolve storage locations by their demonstrated lifecycle, not by py's four-accessor shape — keep R57 config-only until R59 or R67 selects persistent disk output; the pinned TypeScript implementation has config only, F249 itself makes data/state/cache contingent on R59/R67, and the XDG specification makes the directory roles distinct. [F249 ledger](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/docs/port/COMMONALITY.md) (retrieved 2026-09-16); [XDG specification](https://specifications.freedesktop.org/basedir/latest/) (retrieved 2026-09-16).

### Dominant choice
Config-only now: R57 adds **zero** data/state/cache accessor functions and no directory crate. R54 remains the owner of the config directory and its XDG override behavior; R59 and R67 must each name an actual persistent artifact before asking R57 to add a state location. This limits the paths module's additional public surface to zero rather than prematurely promising three paths. [F249 ledger](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/docs/port/COMMONALITY.md) (retrieved 2026-09-16); [F247 baseline review](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/docs/port/BASELINE-REVIEW.md) (retrieved 2026-09-16).

### Fit for this template
CLI: config-only has no file, database, history, or cache requirement in the current template, so three extra accessors have no caller. Library: no extra accessors avoid exporting process-environment policy before a library feature needs it. Web: the optional web feature has no local persistence requirement, so it inherits the same absence rather than gaining filesystem coupling. These are present-state conclusions; R59's file sink and R67's crash record are the explicit re-evaluation consumers. [R57 prompt context](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/research/topics/57-xdg-directory-set/prompts/xdg-directory-set.prompt.md) (retrieved 2026-09-16); [F249 ledger](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/docs/port/COMMONALITY.md) (retrieved 2026-09-16).

### Recommendation
Adopt the config-only shape now. Do not add `data_dir`, `state_dir`, or `cache_dir`; do not add `etcetera`, `xdg`, or `directories` for R57. This is a proposed P02 decision, not an implementation result. If R59 or R67 selects a persistent default file, reopen R57 and choose `etcetera` 0.11.0 only after a fresh RustSec result and an MSRV lockfile check; construct one internal `AppPaths` value and expose only the demanded method, rather than copying Python free functions. `AppStrategy` is the maintained structured Rust precedent; its methods separate the app identity from directory selection. [etcetera docs](https://docs.rs/etcetera/0.11.0/etcetera/) (retrieved 2026-09-16); [Cargo MSRV reference](https://doc.rust-lang.org/cargo/reference/rust-version.html) (retrieved 2026-09-16).

### Ranked runner-up
`etcetera` 0.11.0 with `choose_app_strategy` is the runner-up. It wins only if R59 or R67 requires a persistent state file on both Ubuntu and macOS, the next evidence check confirms advisory-free dependencies under the declared MSRV, and the implementation accepts XDG-on-macOS semantics. It is not selected merely because its download/adopter figures are high. [etcetera docs](https://docs.rs/etcetera/0.11.0/etcetera/) (retrieved 2026-09-16); [CI](https://github.com/lunacookies/etcetera/blob/master/.github/workflows/ci.yaml) (retrieved 2026-09-16).

### Tradeoffs
The recommendation gives up Python-style ready-made data/cache/state paths and future log-sink convenience in exchange for no unused dependency, no uncalled public API, and no premature disk-persistence policy. It gives up `etcetera`'s cross-platform strategy choice; that cost is accepted because Windows is outside the fixed target matrix and no state consumer exists. It rejects `xdg`'s exact literal XDG semantics because its current CI evidence does not cover macOS, and rejects `directories`' native mappings because they do not provide state on macOS. [etcetera source artifact](https://crates.io/api/v1/crates/etcetera/0.11.0/download) (retrieved 2026-09-16); [xdg CI](https://github.com/whitequark/rust-xdg/blob/main/.github/workflows/ci.yml) (retrieved 2026-09-16); [directories docs](https://docs.rs/directories/6.0.0/directories/) (retrieved 2026-09-16).

### Migration implications
P03 makes no R57-driven file change now: R54's eventual config resolver remains the only directory concern, and no `paths` data/state/cache accessor or Cargo dependency is introduced. If the runner-up condition occurs, the later change is limited to the paths module selected by R02, its `Cargo.toml`, and focused tests that inject the environment; R59 or R67 owns the caller and file behavior. This is a proposed change map because the Rust template does not yet exist. ### Validation strategy
Planned, not executed: `cargo test --locked paths::tests` under Ubuntu and macOS must prove that the config resolver remains R54-owned and that no data/state/cache accessor is exported; `cargo tree -e normal` must show no R57 directory crate. If R59/R67 triggers the runner-up, planned checks are `cargo test --locked paths::tests::xdg_state` with absolute, empty, and relative XDG values, plus `cargo test --locked --all-features` on both target OSes; expected behavior is one app-namespaced state path only where the chosen sink needs it. The XDG specification requires ignoring relative values, while F247's config-specific acceptance stays with R54. [XDG specification](https://specifications.freedesktop.org/basedir/latest/) (retrieved 2026-09-16); [F247/F249 ledger](https://github.com/smorinlabs/rs-launch-blueprint/blob/79fe776c853c19dd2dee3ee9b947c83297c5e343/docs/port/COMMONALITY.md) (retrieved 2026-09-16).
