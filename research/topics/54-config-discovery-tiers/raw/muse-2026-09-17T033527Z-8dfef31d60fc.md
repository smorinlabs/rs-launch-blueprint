### Landscape

Category: layered CLI configuration discovery and composition — three
sub-decisions: (a) resolving per-user and system config directories,
(b) composing ordered file layers into one merged document, (c) discovering
a project-local config file. One stack is recommended; every shortlisted
candidate comes from the map below.

Three-bin map. Built-in / first-party toolchain: `std::env` (`var_os`,
`split_paths`), `std::path::Path::ancestors`, `toml::Table` merge by hand
(`toml` crate itself is R52's); `std::env::home_dir` is deprecated and not
usable. Established industry standard: `etcetera 0.11.0` (strategy-based
base/app directories, XDG on Linux and macOS), `xdg 3.0.0` (pure XDG
implementation, enumerates `XDG_CONFIG_DIRS`), `config 0.15.x`
(`config-rs`, layered builder with file/env sources), `figment 0.10.x`

`codeberg.org/dirs/dirs-rs`, already adopted by starship) — too new to be

### Principles and implementation

Shared requirement and agreement level. Configuration resolves through
ordered scopes with a documented winner per key; a nearer scope beats a
farther one; an explicit `--config` path replaces discovery instead of
joining it. Source: owner CLI Design Standard R5.1/R5.2 (MUST) above py-only
precedent per the research mandate; py
(`src/py_launch_blueprint/core/config.py:124-140`, `paths.py:108-131`) and
ts D-017(1) (canonical chain "`TOML `<tool>_config.toml>` … with cli-standards
R5.1 precedence (flags > TOOL_* env > project > user > system > defaults)")
are evidence for the same chain.

| # | Principle | Agreement level | Must agree across py/ts/rs | May vary per ecosystem |
|---|---|---|---|---|
| P1 | Six-level precedence: flags > TOOL_* env > project file > user file > system files > built-in defaults | **standard, one order for all three repos** (R5.1 MUST) | the order and that it is documented verbatim | how each layer is parsed |
| P2 | Merge rule: tables merge recursively, scalars and arrays replace, nearer scope wins | **standard** (R5.1 MUST default; MAY deviate only with documentation) | the default rule; any deviation documented | depth of implementation (py merges one section level, equal to recursive for a two-level schema) |
| P3 | `--config` replaces the project/user/system file chain; flags and env still layer above, defaults below | **architectural pattern** (R5.2 MUST; F233 REUSE, not re-decided) | the collapse behavior | none |
| P4 | User config honors `XDG_CONFIG_HOME` on ubuntu and macOS, ignored when empty; system search honors `XDG_CONFIG_DIRS` defaulting to `/etc/xdg` | **capability + standard paths** (R5.2/R5.3, F247 REUSE constraint) | observable behavior incl. empty-ignored | native macOS fallback shape (R5.3 permits `~/Library/Application Support`, but XDG is the canonical reference and py/ts already use `~/.config` on all platforms) |
| P5 | Project discovery finds the nearest project config walking up from cwd and stops at a repo/workspace boundary | **architectural pattern** (R5.2 SHOULD) | nearest-wins + boundary stop | marker set (`.git`, `Cargo.toml`, `go.mod`, `package.json`, `pyproject.toml` baseline) and filename |

Essential behaviors. (1) Discovery yields an ordered layer list, lowest
precedence first: system files (each `$XDG_CONFIG_DIRS/<tool>/<tool>_config.toml`,
earlier dir wins), user file (`$XDG_CONFIG_HOME/<tool>/<tool>_config.toml`),
project file (nearest `.<tool>/<tool>_config.toml` walking up). (2) Missing
files are skipped silently (tolerance of *present-but-bad* layers is R55's).
(3) The user path doubles as the `config set` write target (py
`_discovery_paths` returns `(target, layers)`; write-back is why file-only
read libraries fail this template). (4) Flags and curated `TOOL_*` env layer
above whatever files resolve; `--config` (or its env alias) collapses the
file list to one entry. (5) Relative or empty XDG overrides are ignored,
falling back to defaults (py `paths.py:65-75` absoluteness check; preserved
by the recommended crate's own validation — see member 1).

Observable acceptance criteria. AC1: with distinct keys in system, user and
project files, the effective config holds all three and a key set in two
holds the nearer value. AC2: nested tables merge key-wise; an array in a
nearer file replaces the farther array wholesale. AC3: `--config other.toml`
makes system/user/project files unread-for-effect while a flag and a
`TOOL_*` env var still override `other.toml`. AC4: `XDG_CONFIG_HOME` set to
an absolute path relocates the user file on ubuntu and macOS; empty or
relative values keep `~/.config/<tool>/`. AC5: project config resolves from
a subdirectory to the nearest `.<tool>/` dir and never escapes a `.git` /
`Cargo.toml` boundary. AC6: every tier is exercised by tests that fail if
any tier is dropped (no single-tier test may stand in for the chain).

Architectural alternatives compared before choosing libraries. A1 — one
layering crate (`config-rs` or `figment`) for files+env+merge: rejected.
`config-rs` cannot write values back ("this library can not be used to write
changed configuration values back to the configuration file(s)!",
`rust-cli/config-rs` README), which the `config set` write target needs;
its default features pull every format plus `async`, and per-layer error
identity (which R55's tolerance rules need) is not its model. `figment`'s
`merge` semantics match P2 (incoming replaces, maps merge —
`figment-0.10.19/src/figment.rs:292` docs), but its last release is
2024-05-17, it orbits Rocket rather than CLIs, and neither crate discovers
system/project tiers — both still need the directory answers below. A2 —
`etcetera` for user dirs + `xdg` for system enumeration + custom merge:
rejected as two crates where one plus ten lines suffices (see member
reports). A3 — all custom including the user tier (ts D-017(3)'s ~30-line
`xdg-paths` shape): rejected for Rust, where `etcetera` is the established,
adopted, zero-logic answer and hand-rolling home-directory lookup reintroduces
platform bugs. A4 — **chosen**: `etcetera` user tier + hand-rolled
`XDG_CONFIG_DIRS` parse + hand-rolled `ancestors()` walk-up with boundary
stop + hand-rolled recursive `toml::Table` merge. Each piece is the smallest
unit its ecosystem offers, and the composition mirrors ruff (etcetera user
settings + ancestors project discovery) and Cargo (custom hierarchical merge)
in production.

How the design preserves each principle. P1/P2: the layer list is built in
precedence order and folded through one documented merge function; the merge
rule is asserted per key-origin in tests. P3: retained REUSE, implemented as
control flow (`if config_file: layers = [explicit]`), unchanged from both
sources. P4: `etcetera`'s XDG strategy is selected on Linux *and* macOS
(`choose_base_strategy` uses XDG on both; verified by execution on macOS,
see Validation) and ignores non-absolute overrides; the system parse keeps
only absolute entries with `/etc/xdg` default — py parity line for line.
P5: walk-up with boundary stop implements the R5.2 SHOULD that py's
cwd-only lookup (`project_config_file`, no parent search) does not; this is
a deliberate py-divergence licensed by the mandate (py-only origin, standard
outranks source detail) and matches ts D-017(1)'s stated canonical chain.

Where ecosystems justifiably differ. The directory fallback on macOS stays
XDG (`~/.config/<tool>`) rather than the native
`~/Library/Application Support`: R5.3 permits native paths but names XDG
canonical, and both sources already ship `~/.config` on all platforms, so
uniformity here preserves P4 instead of breaking it. Env handling stays
curated (`TOOL_*` subset per R5.4), never config-rs-style full-prefix
auto-binding — a policy difference, not a library gap.

### Recommendation

One stack: `etcetera = "0.11.0"` for the user tier
(`choose_base_strategy`, XDG on Linux and macOS, joined with the tool name
ruff-style); a ~10-line `std::env::split_paths` parse of `XDG_CONFIG_DIRS`
(default `/etc/xdg`, absolute entries only) for the system tier; a
hand-rolled `Path::ancestors()` walk-up for `.<tool>/<tool>_config.toml`
with `.git`/`Cargo.toml` boundary stop for the project tier; a hand-rolled
recursive `toml::Table` merge (tables recurse, arrays/scalars replace) for
composition; the `--config` env alias as a plain parser env binding
(flag > env automatic, contingent on R60 selecting clap). Precedence
flags > env > project > user > system > defaults; `--config` collapses the
file chain (F233, retained).

#### layer-composition

##### Landscape

Sub-category: folding ordered TOML file layers into one merged document
per P2. Bins: built-in — hand-rolled `toml::Table` recursion (zero new
deps; `toml` itself is R52's); established — `config 0.15.x`
(`config-rs`, 115.0M all-time / 18.6M 90-day downloads, stars 3211),
`figment 0.10.x` (39.1M / 10.3M, stars 913); up-and-comer — none found
that covers file tiers (env-only helpers are out of category). Shortlist
from this map: custom merge (recommendation), `config-rs` and `figment`
(evaluated alternatives with full figures below).

##### Principles and implementation

Must satisfy P1/P2: ordered fold, tables recurse, arrays/scalars replace,
nearer wins — plus the template's write target (the user path stays
available for `config set`) and per-layer error identity for R55's
tolerance rules. The custom merge is ~15 lines over the TOML crate R52
selects (shape executed in `/tmp/r54check/src/lib.rs:merge_toml`). Why not
a crate: `config-rs` documents "this library can not be used to write
changed configuration values back to the configuration file(s)!"
(README), its default features enable every format plus `async`
(`config-0.15.26/Cargo.toml:[features]`, default = toml, json, yaml, ini,
ron, json5, convert-case, async), and its builder surfaces whole-build
errors rather than per-layer ones; `figment`'s `merge` matches P2
(`figment-0.10.19/src/figment.rs:292` docs: incoming replaces, maps
merge) but its last release is 2024-05-17 with last push 2024-09-13, it
orbits Rocket (`Env::prefixed("CARGO_")` is its README's own example),
and it still needs the directory/walk-up answers. Reference
implementations for custom composition: Cargo's hierarchical config merge
(Rust project publication, Sources) and py's own `settings_from_layers`
(one-level section merge, equal to recursive for this schema). Both
alternatives pass the fitness gates (MIT OR Apache-2.0; config rust 1.88
≤ 1.96; no `unsafe` in either `src/` by grep; no RustSec advisories;
figment builds green on docs.rs Sep 2026) — the rejection is fit, not
gates: neither discovers tiers, one cannot write back, and both cost more
dependency weight than 15 lines (config's normal tree includes winnow,
indexmap-optional, and per-format crates; figment pulls pear/uncased/toml
even before providers).

##### Dominant choice

No dominant crate for *template-shaped* file-tier composition: `config-rs`
dominates 12-factor app config (env-heavy, write-never), which is a
different use case; production CLIs with file tiers (Cargo, ruff) merge by
hand. Fit-over-abstract-best therefore picks custom here.

`config 0.15.26` (active: released 2026-09-21, maintainer epage answering

##### Up-and-comers

##### Fit for this template

##### Recommendation

Custom recursive `toml::Table` merge in the library crate (pattern, not a
new crate dependency).

##### Ranked runner-up

(P2 rule, per-layer errors, origin tracking) is first-class. `config-rs`
rents a maintained merge plus env/format machinery the template must then
constrain (features off, write path around it, errors adapted for R55).
`figment` rents merge with the smallest API but the quietest maintenance.

#### project-discovery

##### Landscape

Sub-category: finding the nearest project-local config walking up from
cwd with a repo-boundary stop (P5). Bins: built-in — hand-rolled
`Path::ancestors()` loop (the entire map); established — none (no crate
owns this; Cargo and ruff both hand-roll); up-and-comer — none (niche
helpers `find-up`/`locate-project` named but not shortlisted: no adoption
evidence in surveyed projects). The shortlist is the pattern alone.

##### Principles and implementation

Must satisfy P5: nearest `.<tool>/<tool>_config.toml` walking up from
cwd, stop after the first directory containing `.git` or a workspace
marker, else filesystem root. The practice evidence is unanimous: ruff's
`find_settings_toml` (`crates/ruff_workspace/src/pyproject.rs:109-117`,
`for directory in path.as_ref().ancestors()`), ruff's
`find_fallback_target_version` (same idiom, :147), and Cargo's
current-dir-plus-all-parents probing (Cargo reference). A crate cannot
improve on this: the logic is a loop, a join, an `is_file` check and a
boundary test (~20 lines, executed in `/tmp/r54check/src/lib.rs`).
Boundary markers follow the R5.2 non-exhaustive baseline (`.git`,
`Cargo.toml`, `go.mod`, `package.json`, `pyproject.toml`); the scratch
check implements `.git` + `Cargo.toml` and P03 extends the list. This
walk-up deliberately supersedes py's cwd-only `project_config_file`
(py-only origin; standard outranks source detail) and realizes the chain
ts D-017(1) names but never implemented. Pattern member: crate figures
do not apply; fitness gates 1–6 are vacuous (no new dependency, no
`unsafe`, no features, no async, std-only so MSRV is the toolchain's own
and both target OSes share the code path).

##### Dominant choice

The `ancestors()` loop itself — dominant by production use (Cargo, ruff),
not by crate download count.

##### Up-and-comers

None in this sub-category.

##### Fit for this template

Exact: pure function of `(start_dir, tool_name)` returning
`Option<PathBuf>`; injectable start dir makes tests hermetic (tempdir
fixtures, no cwd dependence); shared by CLI, library and web service;
boundary stop prevents surprising config pickup outside the repo.

##### Recommendation

Hand-rolled `Path::ancestors()` walk-up with boundary stop (pattern, no
crate).

##### Ranked runner-up

py-parity cwd-only lookup (`./<tool>_config.toml` + dotfile preference):
ranks second only as the minimal-diff option. Rejected because R5.2's
walk-up SHOULD outranks the py-only source detail and subdirectory
invocation (the common IDE/terminal case) would silently lose project
config.

##### Tradeoffs

Walk-up can surprise when a parent dir holds a stale config — the
boundary stop and `--show-origin` (R5.7) are the mitigations. cwd-only is
simpler and py-identical but violates the SHOULD and breaks subdirectory
use. No dependency is added either way.

a `pub const ErrorCode::ALL` lists every member and a pinned-row test enforces append-only. **Exit taxonomy** (`#[repr(u8)] enum Exit` → `std::process::ExitCode`, per the org CLI Design Standard R6.1, org-locked, unchanged from ts D-016(2)): `0` success, `1` generic runtime error, `2` usage/parse error, `3` not found, `4` auth required, `5` conflict, `130` SIGINT, `143` SIGTERM; unlisted failures collapse to `1`. **Initial catalog rows** (hundreds digit = exit code for the `1xx`–`5xx` blocks; `RSLB000` is the UNEXPECTED sentinel): `RSLB000` unexpected → 1; `RSLB101` I/O → 1; `RSLB102` transport (DNS/connect/timeout/TLS) → 1; `RSLB103` remote-API failure → 1; `RSLB104` config layer unreadable → 1; `RSLB201` usage/parse (including the CLI parser's own errors) → 2; `RSLB202` config document unparsable → 2; `RSLB203` config value invalid → 2 (**this template's choice, not derived from the standard — see `## Engines`, Disagreement 4**); `RSLB204` secret supplied through a prohibited channel → 2 (**likewise this template's choice; the standard assigns secrets no exit code**); `RSLB205` required non-auth input or consent missing because prompting is disabled or unavailable — `--no-input`, no TTY, or closed stdin — → 2; `RSLB301` resource not found → 3; `RSLB401` credentials absent → 4; `RSLB402` credentials rejected → 4; `RSLB501` conflict/precondition failed → 5; `RSLB901` SIGINT → 130; `RSLB902` SIGTERM → 143; `RSLB903` prompt interrupted by Ctrl-C → 130 (a closed prompt stdin is **not** this code: it is required input that prompting cannot supply, so it is `RSLB205`/2 — see `## Engines`, Disagreement 4). **Envelope** — a single stderr JSON object `{"error":{"code","message","hint"?}}`; `hint` is an optional structured string field carried beside `code` and `message`, omitted (not `null`) when absent and rendered as its own line in human output — its Rust return type is P03's choice and must be able to name the offending input per R7.6, so a borrowed-or-owned string is expected rather than a `&'static str`; stdout stays byte-empty on the error path. This item defines exactly those three keys and defines no trace, cause-array or diagnostic field; R7.8 permits further documented fields, and any such field is a separate addition owned by the item that needs it. What a *stack trace* may do is deliberately absent from this contract: it is F301's, and F301's acceptance criteria are an open owner question (see `## Decision`). **Broken pipe** — a `BrokenPipe` result on the *result* stream ends the process at `0`, silently, with no envelope; a `BrokenPipe` while writing an already-selected error envelope to stderr retains the original application exit status rather than overriding it; a `BrokenPipe` on any other application stream is `RSLB101`/1; no `SIGPIPE` handler is installed and `println!`/`print!` are lint-denied in binary crates. **Boundary precedence** — signal → broken pipe → domain downcast → unexpected; `main` returns `ExitCode` and does not call `process::exit` on the error path; all streams are flushed before exit on every path including signal. **Crash record** — CLI surface only, UNEXPECTED class only, an injected best-effort sink writing `0600` newline-delimited JSON with timestamp, version, PID, code and sanitized cause chain and never argv, environment, headers, tokens or config contents; a write failure never changes the envelope or the exit code; **the location is not decided here and the default sink is a no-op until R57 answers**. **Layering** — `thiserror` in the library crate, `anyhow` (`>= 1.0.103`) in binary crates only; the library crate must not depend on `anyhow`, must install no signal handler or panic hook, and must write to no process stream or file.
