### Principles and implementation

Shared requirement (source: owner amendment 2026-09-12, `docs/planning/p02/owner-decisions.md` §4; restated as binding constraints in this prompt): both AI-review lanes ship with the template by default with no enable variable of any kind; a lane runs whenever the credential it needs is present; when that credential is absent the lane does not run, does not error, and prints that the key needs setting; a user who does not want a lane deletes its file; both lanes reject bots; and the author-trust test is an `author_association` check, never a write-permission check. Agreement level: capability + policy — py, ts and rs must agree that credential presence (not a flag) gates AI lanes, that absence is a silent skip with a printed reason, that deletion is the opt-out, and that bots are rejected and authors association-checked. What must agree: those six behaviors and their observable acceptance criteria (B4-analogue per lane: unconfigured clone yields a skipped real job, no red check, printed key name; guard-analogues: fork/draft/bot/association rejections skip before scheduling). What may vary: the vendor mechanism, the credential shape, the trigger token, and the permission sets — each ecosystem and vendor pair justifies its own.

Architectural alternatives compared before choosing: (A) first-party exec action + template-authored workflows — RECOMMENDED. `openai/codex-action` at `v1.12` supplies the CLI install, the Responses-API proxy that keeps the key out of the model's environment, the `drop-sudo` privilege reduction, permission profiles, and a genuine write-access backstop; the template supplies the two workflow files, the preflight gate, the guards, the prompts (template-local `prompt-file`), and the comment-posting job. (B) Raw Codex CLI in `run:` steps — rejected: it discards the proxy, the sandbox/safety strategy, and the actor check, and re-implements credential plumbing the vendor already hardened (v1.12 changelog: "Strengthen Linux runner privilege isolation and Responses API proxy credential handling"). (C) Vendor-hosted Codex cloud review — rejected for the template: a hosted App cannot express the owner's credential-presence gate (no secret, no preflight, no delete-to-opt-out inside the template), and its permission/trust surface was not retrievable here (gap G4), so it cannot be verified against the six binding behaviors. (D) Third-party Codex review actions — rejected: the largest has 101 stars and no vendor standing, trust model, or evidence of maintenance; adopting one would trade a verified vendor mechanism for an unverified wrapper.

How the recommended design preserves each principle: credential presence is detected by an always-run preflight job that reads `secrets.OPENAI_API_KEY` into `env` (legal there) and publishes a literal `static`/`none` output the real jobs gate on through `needs` — required, not optional, because every Codex credential path is secret-kind (README: "Store it in `secrets`"), and a job-level `if:` cannot read `secrets` (executed `actionlint` proof, Validation strategy). No federation/variable shape exists here, so the output alphabet is two-valued, simpler than R18's three-valued relay. Bot rejection and the `author_association` prefilter sit on the preflight job as pure `github`-context predicates (executed lint-clean), so rejected events skip before scheduling; the action's internal genuine write check (`src/checkActorPermissions.ts`, `getCollaboratorPermissionLevel`, requires admin/write/maintain) then acts as defence in depth, never as the workflow-level trust test the owner ruled out. Prompts live in template-local files passed via `prompt-file` (repo-pinned, no runtime marketplace fetch — the exposure R18 removed at revision 4 has no equivalent here). Comment posting follows the README's own two-job split (codex job with `contents: read`, post job with `issues: write` + `pull-requests: write`), which also satisfies the action's "run as the last step / separate job" guidance since Codex can overwrite later steps' files (`security.md` lines 76–84).

Minimal realistic example: `.github/workflows/codex-review.yml` (`pull_request: [opened, ready_for_review, reopened]`, fork guard + `draft == false` + both bot checks on the preflight; real job runs checkout, base/head fetch, `openai/codex-action@v1.12` with `permission-profile: ":workspace"` and a template-local review `prompt-file`, then a `needs`-gated post job comments the `final-message`) and `.github/workflows/codex-assistant.yml` (`issue_comment` + `pull_request_review_comment` `[created]` plus R18-mirror `issues`/`pull_request_review` events, `@codex` mention match + association prefilter + both bot checks on the preflight; real job runs the action with the comment body passed through `env:` and posts the reply). Executable acceptance check, proposed (not executed — no GitHub runtime here; empirical audit runs it): create a scratch repo from the template with no credential, open a PR and post `@codex` comments as owner/bot/outsider, and assert the preflight succeeds printing `OPENAI_API_KEY`, both real jobs report `skipped`, and no red check appears; then install a key and assert the lanes run and the bot/outsider events still skip. Distinguished from the executed checks: only the `actionlint` expression/context proofs below were executed.

No `BASELINE-REVIEW:` finding: there is no prior-art baseline for this item (origin `none`), and R18's published configuration was used as the mirror shape without disagreement.

##### Principles and implementation

This member preserves all six binding behaviors, with the trust test at its strictest: the assistant lane is human-invoked on arbitrary threads, so the preflight carries the `author_association` prefilter the owner chose over a write-permission check. Trigger vocabulary (template-invented, stated here; R45 owns whether it appears in the PR template): events `issue_comment: [created]`, `pull_request_review_comment: [created]`, `issues: [opened, assigned]`, `pull_request_review: [submitted]` — mirroring R18's four events exactly so both vendors' assistants are reachable from the same places; mention token `@codex` matched with R18's four-clause `contains(github.event.<comment|review|issue>.body, '@codex')` shape. No collision with the Claude lane's `@claude` trigger: the tokens are substring-distinct (`@codex` appears in no `@claude` match and vice versa), and a comment containing both tokens intentionally invokes both vendors — each lane matches only its own token. Guards on the preflight (all `github`-context, all executed lint-clean on the `issue_comment` fixture): the `@codex` content match, `contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.comment.author_association)` (repeated per event payload like R18), `github.event.sender.type != 'Bot'`, and the per-event author type check (`github.event.comment.user.type != 'Bot'`, etc.).
