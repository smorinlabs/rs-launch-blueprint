### Principles and implementation

**The shared requirement, at the policy level.** *The default test run is fast, hermetic, order-independent and bounded in time. Anything slower, networked or environment-dependent is opt-in. The full suite is the CI gate, and a local pre-push run is available but never forced.* All four legs converge on this principle in substance (`raw/opus.md:119-122`, `raw/muse.md:71-93`, `raw/doxa-openai.normalized.md:50`, `raw/doxa-gemini.normalized.md:21-23`). **How B realises P3 without shuffle, and what it does not do.** pytest-randomly exists to surface a test that passes only because an earlier test left state behind. Under libtest with one thread, such a test passes by alphabetical order (E4a). Under nextest the same test fails on every run, because each test starts in a fresh process (E4b1–E4b3). Coupling through the **file system or a fixed port** is not prevented by processes; E4f shows two tests colliding on one path. The template's rule for that residue is structural: a test that touches the file system uses its own temporary directory, and an in-process web test uses R69's `tower::ServiceExt::oneshot` or binds port 0. **The seeded-random-order capability is not available on stable Rust in any first-party or established tool; the principle is preserved by a different mechanism.** **Partitioned execution order, the HIGH question's second half:** nextest natively shards a run with `--partition slice:m/n`, `--partition hash:m/n` and the still-supported but deprecated `--partition count:m/n` (nextest `partitioning.md:8`, `partitioning.md:31`, `partitioning.md:55`, `partitioning.md:63` at tag `cargo-nextest-0.9.146`; E12a–E12e); sharding splits one run's tests into buckets across machines and assigns them deterministically, hashed buckets by binary ID and test name (`partitioning.md:57`, E12d), so it does not randomise order and does not realise F124; it is not adopted, because how many jobs and runners a test run spans is job and runner topology, which belongs to R11.

[profile.default]

[profile.ci]
fail-fast = false

Every key parsed without a warning or unknown-key line (E2h). `nextest-version` is read and satisfied (E2x, E2x2). `profile.ci` runs the feature-on suite (E2y, E2y2) and inherits `default`'s terminating timeout and its `slow::` override: with the default shrunk to 1 s, a hang under `--profile ci` is reported `TIMEOUT` and exits 100, and the 1.2 s `slow::` test still passes (E3p–E3t). The shipped default `slow-timeout` has **no** `terminate-after` and only marks a test slow (E9e, E3a–E3b2), so the explicit `terminate-after = 2` is load-bearing: the hung test is reported `TIMEOUT [60.003s]` and the run exits 100 (E3h–E3k). The `slow::` override matches module-path names: with the default shrunk to 1 s, a 1.2 s `slow::` test passes and a 1.2 s test outside `slow::` times out (E6g0–E6g2). `retries = 0` is the shipped default, written out so a flaky test is never masked. No `default-filter` is set; the class exclusion is carried by `#[ignore]` (M5). No experimental feature is enabled.

**Local scope (revision 2).** `just test` is the **feature-on** suite, and so is the opt-in pre-push job that runs it. The `test` and `test-all` recipes pass `--features web` to the nextest step and to the doc-test step alike, so the local default suite runs the web tier and the doc examples inside the gated `src/web/` tree. Executed: with `RS_PROJECTS_PREPUSH_TESTS=1` the hook runs `6 tests run: 6 passed, 2 skipped`, including the web tier's `serve_binary_starts` (E8e, E8e2); a doc example on `web::health` runs under the recipe's `cargo test --doc --locked --features web` (E8f2, E8f3) and does not run under a feature-off `cargo test --doc --locked` (E8f4, E8f5); `just test-all` runs 8 of 8 (E6t). Runner-up: a feature-off `just test` plus a named `test-web` recipe, rejected because the hook's "full suite" (F173) would then skip the web tier unless the job ran both recipes.

Cargo builds every binary target before the integration tests. That removes the need for ts's staleness-aware rebuild. A binary with `required-features` is skipped when its feature is off, and `CARGO_BIN_EXE_<name>` is then unset (handed over by R49, `research/topics/49-build-target-declaration/DECISION.md:727-731`).
