### Landscape

This item decides the Rust **typed-config semantic-validation layer** after TOML parsing, not a TOML parser or a failure policy. The built-in/first-party bin is Rust types plus `serde` `Deserialize` attributes and custom deserializers; Serde documents typed derives and container/field attributes, but not a general aggregate semantic-validator API ([Serde derive](https://serde.rs/derive.html), [attributes](https://serde.rs/attributes.html); retrieved 2026-09-17). The established-industry-standard bin is `validator` 0.21, whose maintained documentation supplies derive-based field, nested, custom, and struct-level validation with `ValidationErrors` ([validator 0.21 README](https://crates.io/api/v1/crates/validator/0.21.0/download); retrieved 2026-09-17). The up-and-comer bin is `garde` 0.23: its maintained repository documents derive rules, nesting, custom/contextual rules, and a `Report` that aggregates errors ([garde v0.23.0 README](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/README.md), [validation implementation](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs); retrieved 2026-09-17). `validify` and `deserr` are adjacent alternatives, respectively transform-plus-validate and custom deserialization, rather than the narrow post-deserialization schema layer ([validify registry record](https://crates.io/api/v1/crates/validify), [deserr registry record](https://crates.io/api/v1/crates/deserr); retrieved 2026-09-17).

Authority is therefore diverse but scoped: the Rust project’s Cargo reference establishes `rust-version` dependency selection behavior ([Cargo rust-version reference](https://doc.rust-lang.org/cargo/reference/rust-version.html); retrieved 2026-09-17); Serde is the de facto Rust serialization project and its docs define the structural layer ([Serde](https://serde.rs/derive.html); retrieved 2026-09-17); crate maintainers define their validator behavior in their released source; crates.io and authenticated GitHub REST provide the required registry and repository figures. Practice evidence is narrower than popularity suggests: `axum-valid` 0.25.0 is a maintained Axum adapter that exposes both `garde` and `validator` features, showing current web-edge interoperability but not an endorsement for config files ([axum-valid 0.25.0 registry metadata](https://crates.io/api/v1/crates/axum-valid/versions), [reverse-dependency response for garde](https://crates.io/api/v1/crates/garde/reverse_dependencies?per_page=5); retrieved 2026-09-17). I found no maintained, well-known end-user Rust CLI whose public configuration implementation is a complete reference for Garde; that production-adopter evidence is a gap, not a claim of absence.

### Principles and implementation

The shared requirement is F229’s architectural pattern: validate parsed config against a typed schema before any value is used. It is agreement at the architectural-pattern level, not agreement on Pydantic, Zod, Serde, or another library ([ledger F229](../../../../../docs/port/COMMONALITY.md), [baseline review F229](../../../../../docs/port/BASELINE-REVIEW.md); retrieved 2026-09-17). At their pinned commits, Python uses Pydantic `BaseModel` plus literal fields and TypeScript uses Zod’s `safeParse`, including `limit: z.number().int().positive()` ([Python pin `b08bccf`: settings.py](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/src/py_launch_blueprint/core/settings.py), [TypeScript pin `cb1cbcb`: config.ts](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/src/lib/config.ts); retrieved 2026-09-17).

`Deserialize` plus Rust enums and optional `#[serde(deny_unknown_fields)]` covers structural types, closed literal-like sets, and unknown-key policy, but a signed integer still accepts zero or negative values unless an explicit check is added ([Serde container attributes](https://serde.rs/container-attrs.html), [baseline review F229](../../../../../docs/port/BASELINE-REVIEW.md); retrieved 2026-09-17). Serde custom deserializers could encode every semantic rule, but they stop at the first deserialization failure and spread policy across field adapters; a hand-written post-parse collector could aggregate errors, but would reimplement an established validation abstraction. `garde::Validate` instead sends every field rule into one `Report`, whose entries carry paths and errors; it supports range, length, nested, conditional, custom, and self/context-aware rules ([garde validation implementation](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs), [garde error report](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/error.rs), [garde rule reference](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/README.md); retrieved 2026-09-17).

Use one `Config` data type with `Deserialize` for R52’s output and `garde::Validate` for semantic rules. R52 may deserialize TOML directly into it, or convert its parsed value into it; no intermediate `toml::Value` is required by Garde. Immediately call `config.validate()` before resolving or consuming fields. This preserves the shared principle while using Rust’s structural types natively. A malformed TOML value or wrong Rust type still fails during deserialization before Garde runs; Garde aggregates all semantic errors only after structure succeeds. That is a deliberate diagnostic boundary, not full Zod aggregate parity, and R55 decides how either class is tolerated ([garde validation implementation](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs), [R52/R55/R56 scope in binding prompt](../inputs/prompt.md); retrieved 2026-09-17).

Minimal proposed shape, not implemented or run:

```rust
#[derive(serde::Deserialize, garde::Validate)]
struct Config {
    #[garde(length(min = 1))]
    workspace: Option<String>,
    #[garde(range(min = 1))]
    limit: Option<u32>,
}
```

`Option<u32>` makes type errors Serde errors and `range(min = 1)` makes `0` a report entry; closed choices should be Rust enums. The shown code does not settle R55’s unknown-key or recovery policy, R56’s token field, or R52’s parser selection ([garde rules](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/README.md), [binding scope](../inputs/prompt.md); retrieved 2026-09-17).

BASELINE-REVIEW: F229 — configuration is validated before use — retain the pattern and layer Garde semantic validation after Serde structural decoding; require representative rejected values — Serde alone admits a signed integer that TypeScript rejects with `.positive()`; affected items R53, R52, R55 ([baseline review F229](../../../../../docs/port/BASELINE-REVIEW.md), [TypeScript pin](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/src/lib/config.ts); retrieved 2026-09-17).

### Dominant choice

`serde = "1.0"` for structural decoding plus `garde = { version = "0.23.0", default-features = false, features = ["derive"] }` for semantic validation. Garde 0.23.0 declares MSRV 1.87, dual MIT/Apache-2.0 licensing, no default feature set, and an opt-in derive macro; the proposed feature set has no async-runtime coupling ([garde v0.23.0 manifest](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/Cargo.toml), [workspace manifest](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/Cargo.toml); retrieved 2026-09-17). Pin exactly `0.23.0` for the first template release because this is a pre-1.0 crate; later compatible updates require the re-verification trigger below.

### Up-and-comers

Garde is the relevant up-and-comer: its 0.23.0 release, 1.87 declared MSRV, dual license, and minimal opt-in features make it technically suitable, but its 898 stars and unresolved recent issues make it less adoption-proven than Validator ([Garde registry](https://crates.io/api/v1/crates/garde), [Garde repository](https://api.github.com/repos/jprochazk/garde); retrieved 2026-09-17). `validify` is also small and newer in ecosystem position, but the missing MSRV declaration prevents it from advancing beyond this bin ([validify versions](https://crates.io/api/v1/crates/validify/versions); retrieved 2026-09-17).

### Fit for this template

CLI: Garde produces one path-addressed semantic report that the CLI can render after R67 chooses its error envelope; this is closer to Zod’s field-oriented diagnostics than a first-failure custom deserializer ([Garde `Report`](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/error.rs); retrieved 2026-09-17). Library: keep `Config` and its `garde::Report`-returning validation public only if R4’s API decision permits it; callers otherwise receive the project error type, avoiding a parser dependency in the public contract ([Garde `Validate`](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs); retrieved 2026-09-17). Web: no async runtime is coupled to the chosen features; an HTTP adapter may map the same report to a response, and `axum-valid` demonstrates separate optional Garde integration without making it necessary for file config ([Garde manifest](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/Cargo.toml), [axum-valid metadata](https://crates.io/api/v1/crates/axum-valid/versions); retrieved 2026-09-17).

### Recommendation

Adopt `serde = "1.0"` plus exactly `garde = { version = "0.23.0", default-features = false, features = ["derive"] }`. Use Rust enums for closed choices and Garde attributes/custom rules for semantic constraints such as positive limits, then call `Validate::validate` immediately after R52 completes typed decoding. This is the smallest documented mechanism that preserves F229 and provides aggregate semantic diagnostics ([Serde derive](https://serde.rs/derive.html), [Garde validate implementation](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs); retrieved 2026-09-17). It is conditional, not fully accepted, until P03 proves it on both owner-required operating systems and checks the resolved lockfile with the supported MSRV and advisory tooling; upstream does not provide macOS CI evidence ([owner parameters](../../../../../docs/port/PARAMETERS.md), [Garde CI](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/.github/workflows/ci.yml); retrieved 2026-09-17).

### Ranked runner-up

`validator = { version = "0.21.0", features = ["derive"] }` is the runner-up. It wins if P03 needs its established `ValidationErrors` map shape, especially its explicit struct-level validator that can run even when field errors exist, or if a macOS acceptance run reveals a Garde defect ([validator 0.21 README](https://crates.io/api/v1/crates/validator/0.21.0/download); retrieved 2026-09-17).

### Tradeoffs

Against Validator, Garde gives up much larger download history, stars, and a more familiar error-map ecosystem; the cost is accepted because Garde’s flat path/error `Report`, explicit aggregate contract, self/context access, and smaller selected feature set fit a small config schema ([Garde sources](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs), [Validator README](https://crates.io/api/v1/crates/validator/0.21.0/download); retrieved 2026-09-17). Against Serde-only custom deserializers, it adds a proc macro and runtime dependency; the cost is accepted because semantic rules remain visible beside fields and aggregate instead of dispersing into first-failure adapters ([Serde attributes](https://serde.rs/attributes.html), [Garde README](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/README.md); retrieved 2026-09-17). No comparable authoritative benchmark for small TOML config validation was found, so no throughput, latency, allocation, binary-size, or compile-time winner is claimed; a future benchmark must state fixture size, rule count, toolchain, feature set, wall latency, throughput, and RSS before changing this fit-based choice.

### Parameters

owns none. assumes `msrv-policy = stable minus 2 minor versions, raised only in a minor release, declared as rust-version in Cargo.toml and tested in CI`; Garde’s declared 1.87 is below the project floor but its resolved dependency tree still requires P03 verification ([fixed parameter registry](../../../../../docs/port/PARAMETERS.md), [Garde workspace manifest](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/Cargo.toml); retrieved 2026-09-17). assumes `target-os-matrix = ubuntu-latest, macos-latest`; Garde is not yet evidenced on macOS upstream, so P03 must execute the acceptance test there ([fixed parameter registry](../../../../../docs/port/PARAMETERS.md), [Garde CI](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/.github/workflows/ci.yml); retrieved 2026-09-17). assumes R67 maps the structured validation report to its error taxonomy; R55 selects fail-versus-recover behavior; R56 decides whether a token appears; R52 owns TOML parsing ([binding prompt](../inputs/prompt.md); retrieved 2026-09-17). No `CONFLICT:` is emitted.

### Migration implications

Planned P03 changes only: `Cargo.toml` adds the exact Garde dependency alongside Serde; `src/config/schema.rs` defines the `Deserialize + Validate` config model, enums, and semantic attributes; `src/config/load.rs` invokes validation immediately after R52’s typed decode and hands the result to R55/R67; `tests/config_validation.rs` proves accepted and rejected fixtures. The Rust template does not yet exist, so no file was created, scaffolded, or compiled by this research run ([repository README](../../../../../README.md), [binding prompt](../inputs/prompt.md); retrieved 2026-09-17).

### Validation strategy

Planned, not executed: run `cargo test --locked --test config_validation` on both `ubuntu-latest` and `macos-latest`; one fixture must deserialize and validate, one must reject `limit = 0`, one must reject an invalid enum value, and one must prove two semantic-invalid fields appear in one `garde::Report` through `Report::iter()` ([Garde report API](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/error.rs); retrieved 2026-09-17). Run `cargo test --locked` with the project MSRV and then `cargo audit` against the generated lockfile; expected results are a passing matrix and no applicable advisory, while a deserialization type mismatch may be a single Serde error rather than an aggregate report ([Cargo MSRV reference](https://doc.rust-lang.org/cargo/reference/rust-version.html), [RustSec package URL](https://rustsec.org/packages/garde.html); retrieved 2026-09-17). Add a test after R55 settles unknown keys and recovery, rather than selecting `deny_unknown_fields` here ([binding prompt](../inputs/prompt.md); retrieved 2026-09-17).

### Confidence & re-verify trigger

Medium confidence in the mechanism and low-to-medium confidence in its maintenance/portability proof. Re-verify before implementation, on any Garde 0.23.x or 0.24 release, if a RustSec advisory appears, if the resolved lockfile raises the MSRV, if Ubuntu/macOS acceptance differs, or if R55 requires aggregate reporting of structural type errors as well as semantic errors. The last condition would reopen the architectural comparison because direct Serde-to-struct decoding is intentionally first-failure for structure ([Garde validation implementation](https://raw.githubusercontent.com/jprochazk/garde/v0.23.0/garde/src/validate.rs), [Serde derive](https://serde.rs/derive.html); retrieved 2026-09-17).
