# R11 — CI workflow job structure (bundle)

**Purpose.** This raw answer chooses the GitHub Actions topology for the planned
Rust CLI, library, and optional web-service template. It does not choose
formatter, linter, typechecker, test harness, coverage, docs tool, cache action,
aggregate status, or boundary/SCA gate. Those remain with R10, R02, R12, R13,
R27/R28/R30/R32/R35, R71, and R82.

**Status.** This is a research proposal, not a built workflow. The source,
registry, and syntax checks below ran on 2026-09-20. No target-template
workflow, hosted runner, cache rate, or cross-platform Rust command ran because
the template has not been built. Model identity: **GPT-5 Codex**; this session
does not expose a more specific deployment snapshot.

### Landscape

The category is GitHub Actions job topology plus conditional job scheduling. It
decides whether a capability is a separate job or a sequential shared-job step,
and whether an unaffected PR can skip the capability. No candidate here is a
Rust crate. Therefore crates.io 90-day/all-time downloads, RustSec advisories,
Cargo dependency MSRV, `unsafe`, binary size, and Cargo compile-time figures
are **inapplicable**. The applicable costs are runner startup, cache
restore/save, cold-cache compilation, maintenance, and PR feedback latency.
[S1] [S4]

The pinned precedents genuinely diverge. Py has `changes`, path-gated
per-capability jobs, and a separate `lint.yml`. Ts runs format, lint, typecheck,
test, docs, build, and the hook suite as steps in one `ci` job. Neither proves
Rust fitness. [S9]

### Principles and implementation

The three repos should agree at the **capability and architectural-pattern**
level, not on a shared workflow-file count, action, or job count.

| Principle | Agreement level | Essential behavior | Observable acceptance criterion |
|---|---|---|---|
| Required CI remains reportable | Capability/standard | An optimization cannot suppress the required workflow and leave its check pending. | A docs-only PR creates the workflow and reports the R12-selected final required status; R12 later defines how skipped jobs aggregate. [S1] [S2] |
| Independent validation gives independent feedback | Architectural pattern | A job contains a capability with a distinct result, OS matrix, permission boundary, or input set. | A test failure is visible without waiting for formatter/docs/build steps in a shared runner. [S1] [S2] |
| Work skips only when semantic inputs are unaffected | Policy implemented by a pattern | A detector emits named Boolean outputs; downstream jobs read them through `needs`. | A docs-only PR has `base=false` and `web_affected=false`; source or workflow edits make the relevant output true. [S3] [S6] |
| Optional web validation stays correct | Capability | R69's web adapter consumes shared core types, so core or manifest changes can break `--features web`. | Web-feature tests run on both fixed OSes for base or web changes; a web-only edit may skip base-only tests. [L1] [L2] |

Py's shell detector and ts's single Node job remain ecosystem-specific
implementations. Rust needs named capability jobs because its current-stable OS
matrix, separate MSRV check, optional web feature, and separately owned gates
have different inputs and cost profiles. This does not require py or ts changes.
[S5] [S9] [S11] [S12] [S13]

**Cache finding.** R10 remains open, so this answer does not select a cache
action. A future R10 cache can reduce downloads and restore Cargo artifacts
across runs. It cannot make jobs share one live `target/` directory: each
GitHub job has its own virtual-machine runner, while a cache restores prior
files. GitHub documents artifacts, rather than caches, for passing files
between jobs. Put the R10-selected cache step in every Cargo-consuming job. Do
not add a target-directory artifact pipeline unless a target-template benchmark
shows that transfer cost wins. [S1] [S4]

A shared job reuses one live workspace but serializes feedback and combines OS,
permission, and skip scopes. Dedicated jobs duplicate setup on a cold/missed
cache but expose independent results and start matrices in parallel. A hybrid
that groups only same-input fast checks is a future option, but no target
workload measurement justifies it now. The proposed Rust architecture is one
`ci.yml` with named jobs, not a separate Rust `lint.yml`. [S1] [S4] [S9]

**Minimal graph.** On `pull_request`, `changes` emits `base` and
`web_affected`. The base matrix needs `base`. The web matrix needs
`web_affected = base OR web-only`. On `push` and `merge_group`, both outputs
are forced true, so detector classification cannot bypass mainline or
merge-queue validation. `actionlint` parsed that graph. It did not execute an
Action or Rust command. [S6] [S7]

### Recommendation

Adopt one `.github/workflows/ci.yml` with **named independently runnable
capability jobs**, an always-created `changes` job for pull requests, and
`dorny/paths-filter` v4 behavior pinned under R20's action-pinning policy.

1. `changes` uses only the pull-request filtering path, has `contents: read`
   and `pull-requests: read`, and exports `base` and `web_affected` through
   `needs`. `push` and `merge_group` force both true.
2. Each selected capability gets its own job: format, lint, typecheck, test,
   MSRV, docs, build/smoke, coverage, and any R02/R13/R71/R82-owned gate. Tool
   choice remains with the owning item.
3. Current-stable base and web-feature tests each matrix over
   `ubuntu-latest, macos-latest`. A separate `msrv` job verifies the declared
   floor. Its OS scope stays an owner decision.
4. `base` covers manifest, lockfile, shared source, base tests, build inputs,
   Rust toolchain configuration, and workflow files. `web_affected` is `base`
   plus `src/web/**`, the serve-binary source, and web tests.
5. Docs and cheap independently meaningful checks are not hidden behind the
   heavy-job gate. R12 alone decides the aggregate required-status job.

Cache selection may change measured cost, not job isolation. Reconsider a hybrid
only if a built-template benchmark proves that runner concurrency serializes the
jobs and consolidation materially improves PR wall time without losing a useful
individual result. That evidence does not exist. [S1] [S4]

### Members

#### GitHub Actions capability-job topology

##### Landscape

This member is a pattern, not a crate. Crate downloads, release, RustSec,
dependency-tree MSRV, `unsafe`, default features, binary size, and Cargo compile
metrics are inapplicable. The candidates are native job semantics, dedicated
jobs, a shared sequential job, and a measured hybrid. [S1] [S9]

##### Principles and implementation

Use a job when a capability has an independent result, runner matrix, permission
boundary, or skip condition. Use `needs` only for a real dependency, such as
detector output or the aggregate R12 may add. GitHub runs independent jobs in
parallel and each job on its own runner; sequential steps retain one workspace.
[S1] [S2] [S4]

##### Dominant choice

Use one `ci.yml` containing named capability jobs. Every Cargo-consuming job
installs the selected toolchain, invokes R10's future cache mechanism, and runs
the command owned by its item. Base and web test jobs use the fixed two-OS
matrix.

##### Qualified shortlist

| Candidate | Pattern figures and maintenance | Production evidence | Trade-off |
|---|---|---|---|
| Dedicated capability jobs | First-party semantics; no crate figures apply | crates.io, Tokio, and clap use separate jobs; Tokio and clap cache per job. [S11] [S12] [S13] | Extra startup/cold-cache work; parallel, readable feedback and independent matrices. |
| One shared sequential job | First-party semantics; no crate figures apply | Pinned ts `ci.yml`. [S9] | Reuses one live workspace; serial feedback and mixed scope. |
| Hybrid same-input fast checks | First-party semantics; no crate figures apply | crates.io groups some lint/doc work; Cargo shows a distinct warnings job. [S5] [S11] | May lower setup but needs a measured grouping rule. |

##### Excluded by gate

No candidate fails a license, MSRV, RustSec, `unsafe`, binary-size, or compile
crate gate because there is no crate. The shared job is excluded by **template
fit**: it cannot independently express the OS matrix, optional web surface, and
separately owned gates without recreating manual step conditions. [S1] [L1]

##### Up-and-comers

No up-and-comer is selected. A composite action or reusable workflow could
reduce YAML later, but cannot remove the runner isolation that creates the
topology trade-off. [S1]

##### Fit for this template

**CLI:** format, lint, typecheck, packaging, and command-smoke results remain
readable. **Library:** base tests verify both supported OSes without coupling to
web-only work. **Web:** the `web` feature gets a distinct matrix whenever its
adapter or shared core can change. [L1] [S5]

##### Recommendation

Choose named capability jobs in one workflow. Do not create Rust `lint.yml`
only to mirror py. Do not decide R02, R13, or R12; leave named job slots for
their owners.

##### Ranked runner-up

A hybrid that groups only fast checks with identical paths, permissions,
toolchain, and OS requirements. It wins only after a target-template benchmark
shows setup and restore dominate PR wall time and separate names add no
operational value. That condition is unproven. [S1] [S4]

##### Tradeoffs

Dedicated jobs spend more hosted-runner setup and can recompile after cache
misses. They gain parallel feedback, separate matrices/permissions, and direct
failure attribution. A shared job gains live-workspace reuse but loses those
boundaries. A hybrid lowers some overhead but adds an ongoing classification
rule for every check. [S1] [S4]

##### Parameters

This member implements the top-level `owns ci-job-structure` value. It assumes
the fixed OS matrix and MSRV policy copied verbatim below. It does not change
`web-extra-surface` or select R10's cache action.

##### Migration implications

Create `.github/workflows/ci.yml` with named jobs and a shared setup convention.
Do not create `.github/workflows/lint.yml` by default. Insert each later item's
command only into its named job. Keep aggregate status logic under R12.

#### Pull-request path-filtered conditional gating

##### Landscape

This member is a GitHub Actions pattern plus an action, not a Rust crate. Crate
downloads, release, RustSec, MSRV, `unsafe`, binary size, and Cargo compile
figures are inapplicable. The alternatives are native workflow filters, a
maintained detector action, and a hand-written `git diff` detector. [S2] [S6]

##### Principles and implementation

Keep the workflow present on every PR. The `changes` job maps a detector step's
string output into named job outputs. Downstream jobs declare `needs: changes`
and compare the output with `'true'`. On `pull_request`, `dorny/paths-filter`
reads the PR file list through the REST API and requires `pull-requests: read`.
Its documented example composes output and `needs` in this form. Its default
`list-files: none` avoids passing attacker-controlled filenames into a shell.
[S3] [S6] [S7]

##### Dominant choice

Use `dorny/paths-filter` v4 behavior in one `changes` job for `pull_request`
only. Pin production usage under R20. The researched v4.0.3 tag resolves to
`ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d`. Force outputs true on `push` and
`merge_group`.

##### Qualified shortlist

| Candidate | Required pattern fields | Maintenance and figures | Fitness result |
|---|---|---|---|
| `dorny/paths-filter` v4.0.3 | Job outputs, `needs`, `if`, `pull-requests: read`; Node 24 action; default `list-files: none` | 2026-09-20 API: 3,339 stars, `archived=false`, `pushed_at=2026-08-05T12:20:34Z`, MIT; latest v4.0.3 released 2026-08-05; 20 open issues; ten newest issues have a 3.016-day median maintainer response and one unanswered. State: active. [S7] [S8] | Pass. No Cargo dependency, MSRV/RustSec, or binary-size effect. Detector runs on Ubuntu; capability matrices validate both target OSes. |
| Hand-written `git diff` | Checkout history, event/base handling, shell-safe filename handling, tests for PR/push/merge-group | Repository code; no third-party release or crate figures | Fits only if policy disallows an action and the project accepts full event/filename testing. Pinned py proves feasibility, not lower maintenance. [S9] |

##### Excluded by gate

Native `on.pull_request.paths` / `paths-ignore` is excluded by the required
status gate. It filters the whole workflow. GitHub says a path-filtered skipped
workflow leaves its checks `Pending`, blocking a PR that requires them. It
cannot provide this job-output topology. [S2]

##### Up-and-comers

No up-and-comer is selected. crates.io's `tj-actions/changed-files` is evidence
that a changed-file architecture is used in production, not evidence that a
broader action is better for two Boolean categories. [S11]

##### Fit for this template

**CLI:** `base` covers command, library, manifest, lockfile, build, toolchain,
and workflow edits. **Library:** base changes run base and web-feature tests
because shared types can break the adapter. **Web:** `web_affected` also covers
`src/web/**`, the serve binary source, and R69 web tests. A web-only edit can
skip base-only tests. R71/R82 must later add their declared inputs
conservatively. [L1] [L2]

##### Recommendation

Use two positive outputs, not a fragile `docs_only` negation:

~~~yaml
base: source, manifest, lockfile, base tests, build/toolchain, and workflow inputs
web_affected: base inputs plus src/web/**, serve-binary source, and web tests
~~~

The intended relationship is `web_affected = base OR web-only`. Thus a core
change cannot skip `--features web`. Only a docs-only PR skips both heavy
matrices. Keep production filters in reviewed YAML, not an untested shell regex.
[L1] [S6] [S7]

##### Ranked runner-up

The runner-up is the pinned py-style `git diff` detector. It wins only if R20
or a security policy forbids the maintained action and the project accepts tests
for every event, base ref, shallow-history case, and attacker-controlled
filename case. No evidence establishes that restriction. [S6] [S9]

##### Tradeoffs

`dorny/paths-filter` adds a third-party JavaScript action and a read-only PR
permission. It reduces custom diff/glob maintenance, supports the required
output form, and avoids checkout for PR filtering. A hand-written detector
removes the action but owns its edge cases. Native filters are simpler but fail
the required-status constraint. [S2] [S6]

##### Parameters

This member implements the path-gating part of `owns ci-job-structure`. It uses
R69's web path keys without changing the consumed value. `Cargo.toml`,
`Cargo.lock`, and workflow files are safe additional triggers because they can
change feature resolution or the graph; they do not redefine `web`.

##### Migration implications

Add `changes` and reviewed filters to `.github/workflows/ci.yml`. Give only
that job `pull-requests: read`. Make the R69 web-test job depend on
`web_affected`. Keep filters adjacent to the workflow until they require a
dedicated reviewed filter file.
