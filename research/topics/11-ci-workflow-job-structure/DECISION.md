## Decision

**Status.** This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). `rs-launch-blueprint` has no `.github/` tree, no Rust source and no Cargo manifest today. P02 is research; P03 builds the template and its CI proves or disproves what is recorded here. Nothing below has run on a GitHub-hosted runner: no workflow was dispatched, no cache was written, no check was required. A recommendation that does not survive implementation is **revised against this recorded research**, not researched again from scratch.

**Recommendation — one stack: the named pattern `plan-gated compile-tier CI`.** Checks are partitioned into GitHub Actions jobs by **whether they compile Rust**, never by which check they are, inside one `.github/workflows/ci.yml`. Among this decision's own additions, it adds **no third-party action beyond the one R10 selected**. Actions may still enter through slots other items fill: R04's `cargo-semver-checks-action` and `taiki-e/install-action` are examples. Six job ids in three tiers hang off one always-run detector:

```
plan          tier 0  always      ubuntu-latest  no toolchain, no cache, 4 literal outputs
 |
 |-- hygiene        tier 1  always (no needs edge)   the checks that compile nothing, R29's and R20's slots, R82's link check
 |-- workflow-lint  tier 1  if workflows == 'true'   the workflow-file lint; workflows holds its whole input
 |-- check          tier 2  if code == 'true'        matrix over os; 7 cargo steps, each under !cancelled()
 |-- msrv-floor     tier 2  if code == 'true'        the rust-version floor, its own toolchain
 `-- install-smoke  tier 2  if code == 'true'        R50's recipe, web leg as a step gated on web
```

Triggers are `pull_request` and `push` restricted to `main`, plus `merge_group`. The file declares `permissions: {}` at workflow level with a per-job re-grant whose scopes are R08's, and workflow-level `concurrency` with `cancel-in-progress: true` keyed to the pull-request number or, when there is none, the commit sha. Every gated job reads the detector through `needs: plan` and a **positive** `== 'true'` predicate. `ci.yml` carries **no** `on.<event>.paths` or `paths-ignore` filter of any kind. **Every detector output that gates a compile fails closed**: a path nobody anticipated runs the gate rather than skipping it, and no skip-list entry matches a file any package contains. Since revision 5 the first half is structural: `code` and `web` start `true` and turn `false` only on proof that every changed path is skippable, every path test reads the whole list rather than a pipe, and the diff lists the source side of every rename. ### Landscape, and the alternatives compared before any tool

**The category.** This is not a crate decision. It is the *shape of a CI job graph* and the *mechanism by which a run scopes itself to what changed*: which jobs exist in `.github/workflows/ci.yml`, what `needs:` edges join them, and how a detector makes heavy jobs skip on a pull request that cannot affect them. Everything inside a step — which formatter, which linter, which test runner — belongs to another item and is treated here as a **slot**: a named job or step position with a stated rule for filling it.

**Bin 1 — built-in or first-party.** `jobs.<job_id>.needs`, `jobs.<job_id>.if`, `jobs.<job_id>.outputs`, step-level `if:` with the `cancelled()` status function, `on.<event>.paths`/`paths-ignore`, `concurrency` with `cancel-in-progress`, `strategy.matrix`; Cargo's own `-p` / `--workspace` / `--features` / `--locked` scoping; and `git diff --name-only <base>...HEAD` in a `run:` step, which needs `actions/checkout` with `fetch-depth: 0`. Every primitive this recommendation is built from is in this bin.

**Bin 2 — established industry standard.** Four patterns. (a) A hand-rolled detector job publishing literal `true`/`false` outputs consumed through `needs` by positive predicates — what `py-launch-blueprint` does at its source pin (`S20b`–`S20d`). (b) `dorny/paths-filter`, the long-standing third-party detector action: 3,340 stars, not archived, latest release v4.0.3 on 2026-08-05, 20 open issues, maintainer median first response 3.016 days over the ten newest issues with 1 unanswered, no GitHub advisory, adopters sentry.io and web.dev named by the maintainer (`S1`–`S9`). Maintenance state **active**. (c) One job per check, near-universal in library repositories: `clap-rs/clap` keeps `test`, `check`, `docs`, `rustfmt` and `clippy` as separate jobs (`S12a`), `tokio-rs/tokio` has 43 rust-cache steps across its jobs (`S11d`). (d) One aggregate job that all others feed — **R12's**, named only because its correctness constrains what this file may emit.

### Principles and implementation

**The shared requirement, its source, and the level at which agreement is required.** Ledger rows F038 and F040 state the capability: *every quality gate reports as a check a branch-protection rule can require, and a pull request pays only for the gates its change can affect.* The level at which `py-launch-blueprint`, `ts-launch-blueprint` and `rs-launch-blueprint` must agree is **capability plus policy**, not mechanism. The Codex leg reaches the same level independently: the repositories "should agree at the **capability and architectural-pattern** level, not on a shared workflow-file count, action, or job count" (`raw/codex-…md:52-53`).

| Must agree — capability and policy | May vary — ecosystem-local |
|---|---|
| Every gate reports a check branch protection can require | How many jobs the gates occupy, and what they are named |
| A pull request that cannot affect a gate does not pay for it | Which paths make a gate skippable, and how they are detected |
| **A pull request that *can* affect a gate always pays for it** — a detector fails closed | — this row is new in revision 2; see the `web` correction below |
| A skipped gate still **reports**, and reports success | — a policy rather than a free choice, for the reason quoted below |
| The floor language version is proven in CI (`msrv-policy`) | Whether the floor is a matrix leg or its own job — **this item**, settled above |
| Every runner in `target-os-matrix` runs the gates that are OS-sensitive | Which gates are OS-sensitive |

**Missing capability versus justified ecosystem difference, classified per repository, because this decision supplies the rationale for the py and ts follow-on.** **`ts-launch-blueprint` has a missing capability, not a justified difference.** At its source pin its gating shape is one `ci` job (plus an advisory `bun-lane` job with `continue-on-error: true`, no `needs:` edge and no detector, `S22a`–`S22c`), so a docs-only pull request pays the whole check sequence. Closing it would take the same device this decision recommends, since the constraint that forces a detector **job** rather than a trigger filter is the platform's and not Rust's. **`py-launch-blueprint`'s per-check job split is a justified ecosystem difference**: per-job startup is cheap in Python, whereas in Rust the same shape duplicates the **dominant** cost — one dependency compile per job per runner. **py's detector is also the one precedent whose polarity this decision shares**: a hand-rolled skip-list that fails closed (`S20b`, `S20c`), with an always-run lint job that has no `needs:` edge (`S20e`).

**The constraint that turns "a skipped gate still reports" into policy, quoted rather than summarised.** GitHub's troubleshooting page for required status checks tabulates the two kinds of skip as **different outcomes** (`P1a`, `P1b`, asserted offline against the committed snapshot):

> | A workflow is skipped by path filtering, branch filtering, or a commit message | Associated checks stay in a "Pending" state and block merging | Avoid requiring workflows that can be skipped. |
> | A job is skipped by a conditional | The job reports "Success" | |

The same page states that "Successful check statuses are `success`, `skipped`, and `neutral`" (`P1c`), and the reusable it embeds says outright (`P1d`):

> You should not use path or branch filtering to skip workflow runs if the workflow is required to pass before merging.

That answers the prompt's LOW question about `on.push.paths`: a trigger-level path filter on `ci.yml` would make a docs-only pull request **unmergeable** the moment R12 makes any check in that file required. `P1e` is the negative control on `P1b`. The Codex leg excludes native path filters on the same ground (`raw/codex-…md:266-269`).

**Two further platform facts fix the detector's shape.** "If a job fails or is skipped, all jobs that need it are skipped unless the jobs use a conditional expression that causes the job to continue" (`P2a`). And the `needs` context carries `outputs` per dependency; the documentation's worked example shows a non-successful job with `"outputs": {}` — an **empty map** (`P3a`, `P3b`).

**With the platform's default status check, those two facts fix what the predicate's polarity does and does not protect — corrected in revision 4 (audit F1).** A gate reads `needs.plan.outputs.<key> == 'true'`, never `!= 'false'`. The expressions page at the same pinned `github/docs` commit says: "A default status check of `success()` is applied unless you include one of these functions" (`R4-S1`). None of the fixture's five conditions that read `plan`'s outputs — four job-level, one step-level — contains a status function (`R4-L1`). **So when `plan` fails or is skipped, every gated job is skipped, whichever polarity its predicate uses.** Revisions 1 to 3 said the negated form "runs the heavy job" in that case; for this file that was false. Revision 1's `r11-platform-docs.sh` still prints that inference in `P3b`'s pass message; the script is kept byte-identical, and the fact it asserts, an empty outputs map, stands.

**Where the two polarities do differ, the positive form is the one that skips.** There are exactly two such cases. (a) A consumer adds `always()` or `!cancelled()` and so opts out of skip propagation. (b) `plan` succeeds without writing the key the consumer reads, for example through a misspelled output name. In both, `'' == 'true'` is false, so the positive gate skips, while `'' != 'false'` is true, so the negated gate runs. By the asymmetry in the next paragraph, skipping a required quality gate on missing information is the fail-open direction. R18 and R86 adopted the positive rule for a credential gate, where skipping on missing information is the safe direction; this decision does not inherit their reason, only their form. **The positive form is kept for three reasons.** (1) **Consistency.** R18 revision 6 found the negated form a bug in its own draft (`I21`), R86 carries the same rule (`I20`), the maintainer's own `dorny/paths-filter` example uses it (`S6e`), and so do all three engines' reference examples; one convention across a template's workflow files is worth more than a difference confined to (a) and (b). (2) **Case (b) is caught by lint on the consumer side and by the detector cases on the producer side**: `actionlint` exits 1 on a misspelled relayed output (`NC1`); an `out` call in the bash body that misspells or skips a key `outputs:` still declares is invisible to lint, because `$GITHUB_OUTPUT` writes are untyped, and is caught only because every detector case asserts all four outputs (revision 5, audit O1). (3) **Case (a) is excluded by rule rather than by polarity.** A consumer that opts out of skip propagation runs after `plan` has failed, when `plan`'s outputs carry no information; such a consumer must read `needs.plan.result`, never `plan`'s outputs, as its condition. R12's aggregate is the one expected consumer of this kind, and its row below says so.

**Neither polarity makes a failed detector fail closed; a required check must.** A failed `plan` — for example `git diff` exiting non-zero on an unreachable `BASE_SHA` under `set -euo pipefail` — skips `workflow-lint`, `check`, `msrv-floor` and `install-smoke` (`P2a`), and `skipped` is a successful check status (`P1c`). The vendor page tabulates the Success report only for a job skipped by a conditional (`P1b`); this decision assumes the same for a job skipped by a failed dependency, the unsafe assumption, and P03 observes it. Those required checks would therefore go green unless `plan`'s own failure is itself required or aggregated. **This decision hands the constraint on without deciding which way it is met:** either `plan` is itself a required check, or, if R12 chooses an aggregate, the aggregate includes `plan` in its `needs:` and treats `plan`'s `failure` or `cancelled` result as failure. The choice is R12's. P03 validates the outcome: a forced `plan` failure must leave the pull request unmergeable (criterion 13).

**`actionlint` 1.7.12 accepts the negated form silently** — revision 1's `NC2`, **re-run on the current fixture**, `ci.candidate.r2.yml` (check IDs and file names keep their revision-2 names), at `R2-L5`: every `== 'true'` rewritten to `!= 'false'` — eight occurrences on eight lines, five of them live job or step conditions and three slot comments, none of which carries two — exit 0, zero diagnostics. Revision 6's fixture had ten occurrences on nine lines, with four slot comments, one of which carried two (`R7-L2`); revision 7's F1 change removed that line. The linter *does* catch a misspelled output name (`NC1`), a `needs` edge to a missing job (`NC4`) and a job condition reading `secrets` (`NC3`). The `plan` job is structurally the same device as R18's and R86's `credential-preflight` job (`I20`, `I21`), which the owner chose on 2026-09-11 (`I22`); `NC3` is why both must be **jobs** rather than job conditions, since a job-level `if:` may not read `secrets` (`P4a`). All three engines' reference examples use positive predicates, and so does the maintainer's own `dorny/paths-filter` example (`S6e`).

**The detector fails closed, and revision 2 extends that from `code` to `web`.** A detector can err in two directions. **Failing open** means a change that can break a gate is classified as unable to, so the gate skips and reports Success — a false green. **Failing closed** means a change that cannot break a gate is classified as able to, so the gate runs needlessly — wasted minutes. The capability row "a pull request that cannot affect a gate does not pay for it" is a cost preference; the row "a skipped gate reports success" makes every fail-open error a **false pass on a required check**. So the asymmetry is a policy: **every output that gates a compiling or web-surface job is written as the negation of a skip-list, never as an allow-list.** Revision 1 applied that to `code` and not to `web` (see the table below).

**The same premise covers the gates that compile nothing (revision 6, audit F2).** Revisions 2 to 5 stated the conclusion only for compiling and web-surface gates, and gave no reason for that limit. There is none: a skipped non-compiling gate also reports Success. A required check therefore fails open if its key can read `false` while the change touches its input. What differs is cost, and cost selects the form rather than an exemption. A non-compiling check is cheap to run, so its default is **no path gate**: it is a step of `hygiene`, which has no `needs:` edge and runs on every pull request. A path gate on a job that compiles nothing is allowed only when the key's pattern **contains the whole input of every check in that job, by construction**. A check whose input another item declares, and may later widen, is never path-gated. Four consequences follow in the fixture:

**The path list includes the source side of every rename (revision 5, audit F2).** `git diff` detects renames by default, and `--name-only` then prints only the destination. So revision 4's line reported `git mv src/foo.rs docs/foo.rs` as `docs/foo.rs` alone, and its body gave `code=false` on a change that leaves `src/lib.rs` naming a missing module (`R5-D7`). **Why the web surface does not get its own compile job — the prompt's MEDIUM question.** R02's owner-accepted revision 2 (`I100`) recommends a four-package workspace — the root facade, `crates/core`, `crates/cli`, and the optional `crates/web` (`I02`) — and its check **B3** executed the governing fact: "a **workspace-scoped** build compiles the web member with the feature off" (`I01`). **Is skip-gating worth its maintenance cost — the prompt's second HIGH question.** (1) **There is no cheap no-op compile in CI.** R02's `B3` means a workspace-scoped command compiles the optional web member whatever the diff, and every pull-request job starts cold before a cache restore. ### Slots this decision leaves open, and the rule each consumer inherits

Every row is a *slot*: a job id, a `needs` edge and a gating predicate this item fixes, with the contents left to the named item. The partition rule is one sentence: **a check that compiles nothing is a step of `hygiene`, or its own cheap job behind a path gate only when that gate's key contains the whole input of every check in the job; a check that compiles what `check` already compiles is an ordered step of `check`, under `!cancelled()`; and a check needing its own toolchain, its own runner, or a `target/` it must not share becomes its own job with `needs: plan` and a positive predicate, counted against a ceiling of roughly six cache-bearing job ids per runner.** Any new detector key a consumer asks for is written as the negation of a skip-list.
