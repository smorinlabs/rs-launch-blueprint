### Landscape

**The category this item decides.** This is not a crate choice. It is a
*workflow-file policy* for two GitHub Actions settings in every file under
`.github/workflows/`:

1. **Checkout credential persistence** — the `persist-credentials` input of
   `actions/checkout`. When it is left at its default (`true`), the job's
   `GITHUB_TOKEN` (the per-job token GitHub issues to a workflow run) is written to
   disk so that later `git` commands in the job are authenticated. Ledger row F029.
2. **Permission-declaration shape** — whether every workflow declares
   `permissions: {}` at the top level (all `GITHUB_TOKEN` scopes set to `none`) and
   re-grants scopes per job, including the contributors-bot workflow. Ledger row
   F030. The pattern itself is F028 (`COMMON → REUSE`), inherited and not reopened.

A third concern follows from the value test: **mechanical enforcement**, so that
the stated policy and per-file conformance cannot drift apart.

### Principles and implementation

**The shared requirement, its source and its agreement level.** The principle is
**least privilege for the workflow token, applied by default rather than by
demonstrated need**. Its sources are GitHub's secure-use page (least privilege) and
zizmor's two audits (the concrete rules). It is agreed at the **policy** level:
every repository in the family states the same rule and enforces it mechanically.
Nothing in it is language-specific. A GitHub Actions workflow has the same token
model whether the job runs `cargo`, `uv` or `pnpm`, so the low-level values
(`permissions: {}`, `persist-credentials: false`) can and should be identical
across py, ts and rs. This is the rare case where the evidence supports the same
low-level value in every ecosystem.

**Essential behaviors.**

- **B1.** No workflow grants any scope at the top level. Every token scope a job
  holds is visible in that job's own `permissions:` block.
- **B2.** No checkout step leaves a reusable credential on disk unless a named
  later step needs it.
- **B3.** An exception to B2 is explicit (`persist-credentials: true`) and carries
  an inline reason. An exception is never an omission.
- **B4.** B1–B3 are checked by CI, so a new workflow or a new job cannot silently
  regress them.

**Observable acceptance criteria.**

1. `bash scripts/check-workflow-permissions.sh` exits 0 on the conforming tree
   (**executed**, P0 below).
2. The same script exits 1 and names the file when a workflow declares any
   top-level grant other than `{}` (**executed**, NC2 and NC3).
3. The same script exits 1 and names the line when `persist-credentials: true`
   lacks a trailing reason comment (**executed**, NC4a). It exits 0 when the comment
   is present (**executed**, NC4b).
4. `zizmor .github/`, R20's existing invocation at the default persona, exits
   non-zero (exit 12, "highest finding is low") when a checkout omits
   `persist-credentials` (**proposed**. The logic was read in `artipacked.rs:122-141`
   and severity in `:76-92`, and was mirrored by the scratch instrument in NC1. It
   was not executed with zizmor.)
5. `actionlint` exits 0 on every one of those negative cases (**executed**). This
   proves the lint gate alone is not the enforcement.

**What must agree and what may vary.** B1–B4 must agree across all three repos.
What may vary is the enforcement plumbing. py and ts would add the same
language-free shell script and the same zizmor step, so in practice nothing
varies. No ecosystem difference is justified here. The py/ts differences are
drift, classified below.

**Architectural alternatives compared (before any tool).**

| Alternative | F029 (credential persistence) | F030 (bot workflow) | Verdict |
|---|---|---|---|
| **A. Uniform default-deny.** `false` on every checkout; `{}` on every workflow; exceptions explicit and commented | ts's intent, zizmor's rule, 235/237 in the tooled Rust group | ts's shape | **recommended** |
| B. Risk-scoped. `false` only where a risk is demonstrated; top-level grants allowed for small fixed sets | py's actual state (1 of 32 checkouts) | py's shape | rejected: "demonstrated risk" has no check. It left py with 31 unset checkouts and 7 non-`{}` files |
| C. Platform default only. Rely on the repository's "read-only default token" setting and checkout v6's `$RUNNER_TEMP` storage | no per-file setting | no per-file setting | rejected: the setting is invisible to a reader of the file. **Why A holds for F029 — the HIGH question on breadth.** The cost of `false` on a
job that never pushes is one line and zero behavior. The benefit is that any step
in the job can no longer find a token on disk. That covers a compromised
third-party action, a compromised build script, a malicious `build.rs` of a
dependency under `cargo test`, and an `upload-artifact` of the workspace. The v6
`$RUNNER_TEMP` move narrows only the last route (artifact upload of the checkout
directory). It does nothing for a hostile step running in the same job, which can
read `$RUNNER_TEMP` as easily as `.git/config`. That is why zizmor v1.17+ lowers
the severity for v6+ to `Low` when no dangerous upload exists, but still reports it
(`artipacked.rs:76-92`). The "narrow" rule's premise, that a risk must be
demonstrated per workflow, inverts the burden. A reviewer cannot show that a
dependency's build script is benign. A reviewer can show that no step pushes.

**Why A holds for F030 — the HIGH question on the bot workflow.** py's shape
(`update-contributors.yml:11-14`, three writes at top level, one job) and ts's
shape (`update-contributors.yml:56` `{}`, re-granted at `:61-64`) grant **the same
effective token today**. The three authorities read py's shape differently:

- zizmor reports each top-level `write` as `High`, but demotes the finding to the
  **pedantic** persona when "the workflow has only one job"
  (`excessive_permissions.rs:79-90`). The finding therefore does not appear at the
  default persona that R20's step runs.
- ghalint's `job_permissions` policy explicitly exempts a single-job workflow with
  top-level `permissions` (`docs/policies/001.md`, exception 2).
- Scorecard awards its highest score only when the top level is read-only. It
  names the failure mode: a job added later inherits the grant "because of human
  error".

So the honest answer is: **equally auditable today, not equally robust to growth,
and only the uniform shape is enforceable by one rule with no exceptions.** NC3
below executes the growth case. A second job appended to py's shape (a
realistic addition, such as linting the generated file) silently holds
`contents`, `pull-requests` and `issues` write. Nothing in `actionlint` flags it.
zizmor would flag it at the default persona only because the job count crossed
one: with more than one job, and the original job carrying no block of its own,
the top-level writes are no longer demoted to pedantic (`excessive_permissions.rs:63-90`). Under shape A, the same second job holds no scope until
someone writes one. A "small fixed set" is not a stable property of a file that
adopters of a template will edit.

**The MEDIUM question — where `false` breaks a legitimate step.** Two real breakage
classes have primary evidence.

1. **A later step pushes with the checkout token.** `clap-rs/clap`
   `template.yml:31-49` checks out with `persist-credentials: true # to push the
   branch and create PR` and then runs `git push`. The rule's answer is B3: an
   explicit, commented `true`.
2. **A later step fetches from a private repository.** ts `publish.yml:76-79`
   records that with `persist-credentials: false`, "git [is] unauthenticated — on
   a private repo a fetch here dies with 'could not read Username' (v0.1.2's
   publish failed exactly so)". ts's fix was structural: `fetch-depth: 0` at
   checkout, then no re-fetch. The template should carry the same rule as a
   comment where it applies: *fetch everything at checkout, never re-fetch
   afterwards*.

**Is either class present in the rs template?** Each planned workflow was checked.

- **`ci.yml` (R11).** It fetches `fetch-depth: 0` in `plan` and never re-fetches.
  R11's owned value already states "after actions/checkout with fetch-depth 0 and
  persist-credentials false" (R11 `DECISION.md:320`).
- **`release-please.yml`.** It has no checkout. release-please works through the
  API with its own token (py `release-please.yml:55`, ts `:79`).
- **`publish.yml`.** Its verify job needs history (full fetch at checkout, as ts).
  Its publish job uses crates.io Trusted Publishing through OIDC (`id-token:
  write`), not git.
- **The contributors bot.** `smorinlabs/contributors-please-action` at `v1.3.9`
  (tag commit `3c6dbff9ef21190aa1f63b3c400ed4f0ab404ac1`) does not use the checkout
  credential. Before pushing, it runs `git remote set-url origin` with a URL whose
  user is `x-access-token` and whose password is its own App or PAT token
  (`src/index.ts:588-616` at `v1.3.9`, **read**, not executed). The checkout token
  is therefore unnecessary, and `false` is correct.
- **Open question for that action.** It is unverified whether a persisted checkout
  credential (stored, per this leg's unverified understanding, as an HTTP
  `extraheader`) would take precedence
  over the action's URL credential. If it does, the default `true` would make an
  App-configured bot push as `GITHUB_TOKEN`, and that push would not trigger CI on
  the bot pull request. That would be a further reason for `false`. It is recorded
  as a P03 live check, not asserted.

So **no rs template workflow needs `true`** today. The exception path exists for
adopters.

**The LOW question — mechanical enforcement.** Yes, and most of it is already in the
tree through R20.

- **`persist-credentials`.** zizmor's `artipacked` audit fires at the default
  persona for an unset input. It is silent for `false`, and reports explicit `true`
  only at the `auditor` persona (`artipacked.rs:127-141`). That is exactly B2 +
  B3's "explicit exception" half. R20's step (`zizmor .github/`, prebuilt binary,
  default persona, non-SARIF, so a finding is a non-zero exit per
  `docs/usage.md:563-579`) therefore already enforces B2.
- **Two caveats.** (a) With R20's `"actions/*": ref-pin`, `actions/checkout@v7` is
  a tag. zizmor parses it offline as v6+, so the finding is `Low`, and a
  `min-severity` of `medium` or above in `zizmor.yml` or the invocation would
  silence it. The template must not set one. (b) Running with `--format=sarif`
  suppresses the non-zero exit codes (`docs/usage.md:597`), so SARIF-mode wiring
  would turn the gate into a report.
- **Top-level `{}`.** zizmor does **not** enforce B1 at the default persona for a
  single-job workflow (see F030 above). R20 already rejected
  `--persona=pedantic` as a global sensitivity switch that imports unrelated
  failures (R20 `DECISION.md:124-130`). The rest of the rule is carried by a
  repository-local script of about 20 lines. It is the same kind of check as R20's
  comment-grammar script: a text check with no network and no token.

```yaml
name: Update Contributors
on:
  schedule:
    - cron: '17 6 * * 1'
  workflow_dispatch:
# Deny-all baseline (F028), no exception for the bot workflow (F030).
permissions: {}
jobs:
  update-contributors:
    runs-on: ubuntu-latest
    permissions:
      contents: write # commit CONTRIBUTORS.md to the bot branch
      pull-requests: write # open or update the bot pull request
      issues: write # apply the pull request label (labels are an issues-API scope)
    steps:
      - uses: actions/checkout@v7
```

The per-scope comments satisfy zizmor's `undocumented-permissions` audit
(`docs/audits.md:2004-2047`, pedantic-only, and it exempts `contents: read`) at no
cost. The enforcement script:

```bash
#!/usr/bin/env bash
# R08 policy check. zizmor (R20's step) enforces persist-credentials on every
# checkout; this script enforces the two rules zizmor's default persona does not:
#   1. every workflow declares top-level `permissions: {}` (F028/F030);
#   2. every `persist-credentials: true` carries an inline reason comment.
set -euo pipefail
shopt -s nullglob
fail=0
files=(.github/workflows/*.yml .github/workflows/*.yaml)
for f in "${files[@]}"; do
  if ! grep -Eq '^permissions:[[:space:]]*\{\}[[:space:]]*(#.*)?$' "$f"; then
    echo "$f: top-level permissions is not {}"
    fail=1
  fi
  while IFS= read -r hit; do
    echo "$f:$hit: persist-credentials: true without a reason comment"
    fail=1
  done < <(grep -En 'persist-credentials:[[:space:]]*"?true"?[[:space:]]*$' "$f" | cut -d: -f1)
done
[ "${#files[@]}" -gt 0 ] || { echo "no workflow files found"; exit 2; }
exit "$fail"
```

#### checkout credential-persistence breadth

##### Landscape
This member decides F029: how many `actions/checkout` steps set

(only where a risk is demonstrated), and platform-default (rely on v6 storage).

##### Principles and implementation
Least privilege by default. A credential is removed unless a named step needs it,
because a reviewer can prove "no step pushes" but cannot prove "no step is
hostile". v6's storage move narrows artifact leakage only. It does not stop a
compromised step in the same job, which is why zizmor still reports v6+ at `Low`
(`artipacked.rs:76-92`). Implementation: one `with:` line per checkout. Where a job
needs history, fetch it at checkout (`fetch-depth: 0`) and never re-fetch. This is
ts's lesson from `publish.yml:76-79`.

#### permission-declaration uniformity

##### Landscape
This member decides F030: whether every workflow, the contributors bot included,

top-level `{}`, a new job starts with nothing.
