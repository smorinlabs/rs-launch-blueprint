- *Reproduction (P1, P3a, P3b at cargo 1.98.0; P4 at cargo 1.96.0 from `rustup which --toolchain 1.96.0 cargo`; all 2026-09-09T06:06–06:10Z).* Fresh repository from the fixture, initial commit, hook installed. Observed on both toolchains: `bash scripts/check-cargo-lock.sh` exit 0 (Cargo reached, no diagnostic); guarded `git commit` exit 0, the orphan entry committed; `bash scripts/check-cargo-lock.sh --all` on the committed tree exit 0; direct `cargo metadata --locked`, `cargo check --workspace --locked`, `cargo update --workspace --locked` (`Locking 0 packages`) and `cargo generate-lockfile --locked` all exit 0 with the lock unchanged; an unlocked `cargo metadata --format-version=1` then rewrites the lock (`+0 −7`, the `r41-web` block); a subsequent lock-only commit of that churn is accepted by the hook (trigger fires, parity holds, `--locked` passes). Controls that the decision's cases already cover behave as stated: removing the registry edge `anyhow` from `crates/cli` (P2a) → 101; removing the path edge `r41-core` from `crates/web` (P3c) → 101 on all four commands; renaming the member package `r41-web` → `r41-web2` (P3d) → 101. The false pass is therefore confined to a path package that leaves the workspace while no remaining member depends on it.
- *Mechanism (P8, primary source).* `rust-lang/cargo` master `e7506208…`, retrieved 2026-09-09T06:11:32Z (the files have moved since the paths in older write-ups): `src/resolver/encode.rs:196-200` — when a lockfile package has no `source` and no matching path package is found, "We failed to find a local package in the workspace. It must have been removed and should be ignored." and the entry is skipped; `src/ops/lockfile.rs:210-228` — under `--locked` (`!lock_update_allowed()`), `are_equal_lockfiles` compares `into_resolve(old) == into_resolve(new)`, so the orphan is invisible and `write_pkg_lockfile` returns before the `cannot update the lock file` bail at `:56-65`. Without `--locked`, the line comparison at `:212` differs and the file is rewritten. The behavior is platform-independent Cargo logic; one macOS run per toolchain is sufficient evidence and no Linux gap is implied.
- *py precedent (P7).* A two-member uv workspace (`packages/r41core`, `packages/r41web`), `uv lock` then `uv lock --check` exit 0; delete `packages/r41web` and leave `uv.lock`: `uv lock --check` exit 1 with `error: The lockfile at uv.lock needs to be updated, but --check was provided.`; unlocked `uv lock` removes the `r41web` entry. uv 0.11.29, 2026-09-09T06:10:27Z. The hook py runs (`uv-lock-check`) would refuse this commit; the Rust design accepts it.

## Assessment

Revision 2 repairs everything the first judgment audit asked for: the packaging false refusal is fixed by the smallest possible change and covered by executed regression cases on both OS families at the floor and current stable, the parity guard is now described as a Rust-native strengthening rather than a shared behavior, the `.cargo/config.toml` trigger is exercised, and the empirical auditor independently reproduced all 108 checks on both legs. The verdict is nevertheless **reject**, for one reason that no party saw: the decision equates Cargo's `--locked` with `uv lock --check` and writes that equivalence into the settled row's guarantees, but Cargo's lockfile parser silently drops path packages that have left the workspace, so a leaf workspace-member removal — the template's most natural first edit by a user who drops the web service — passes the hook, passes `--all`, passes every runner-up, and surfaces later as unexplained lock churn that the hook also accepts, while py's hook refuses the same edit. This is reproduced with the decision's own fixture at both toolchains, traced to Cargo's own source, and undisclosed anywhere in the decision. The fix is bounded: disclose and narrow, or change the design, and in either case compare the one alternative that delivers the `uv lock --check` semantic and add the regression case. The pattern, tier, trigger set, parity guard and command ranking survive unchanged; with the revision described in F1 and the controller items O2–O4, I expect revision 3 to be approvable without further research.
