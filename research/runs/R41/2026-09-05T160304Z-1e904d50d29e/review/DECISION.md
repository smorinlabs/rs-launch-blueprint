**Yes — as a recommendation for P03 to implement: `rs-launch-blueprint` adopts a conditional pre-commit lockfile-freshness check. The pattern is *conditional conservative resolve with an index-parity guard and a post-resolve lockfile comparison*; the mechanism is the first-party toolchain command `cargo update --workspace` run *without* `--locked`, once per workspace root in the repository and from that root's own directory, followed by a Git comparison of every `Cargo.lock` against the index and a restore, wrapped by a repository-local script (`scripts/check-cargo-lock.sh` is the proposed name; P03 writes it). No third-party crate or tool is added and there is no version to pin beyond the workspace's own `rust-version`.** The test the check makes is the one py's `uv lock --check` makes — "would the lockfile change after a resolution?" (`https://docs.astral.sh/uv/reference/cli/`, `uv lock --check`: "Asserts that the uv.lock would remain unchanged after a resolution. If the lockfile is missing or needs to be updated, uv will exit with an error", retrieved 2026-09-09) — not Cargo's `--locked`, which revision 2 used and which is *not* that test: Cargo's lockfile parser silently drops a `[[package]]` entry for a path package that is no longer in the workspace (`src/resolver/encode.rs:196-200` at `rust-lang/cargo` `e7506208ff1b7f01062e410c419f95628dfdb31b`: "We failed to find a local package in the workspace. It must have been removed and should be ignored.", retrieved 2026-09-09T06:28Z), and `--locked` then compares the *parsed* old and new resolves rather than the file contents (`src/ops/lockfile.rs:210-230`, `are_equal_lockfiles`: line equality first, then, only when lock updates are not allowed, `into_resolve(old) == into_resolve(new)`), so removing a leaf workspace member leaves an orphan entry that every `--locked` command accepts with exit 0 and the next unlocked Cargo run silently prunes (cases E1a–E1d, E2a, E3c below; `uv lock --check` refuses the analogous uv-workspace removal with exit 1 per the r2 judgment audit's probe P7). Without `--locked`, Cargo writes the lockfile exactly when its text would differ (`src/ops/lockfile.rs:45-52`, `write_pkg_lockfile`: "If the lock file contents haven't changed so don't rewrite it"), so "the file changed after the resolve" is precisely "the lockfile would change". The check runs at pre-commit only when a Cargo resolution input is staged — any `Cargo.toml` or `Cargo.lock` in the repository, or a `.cargo/config` / `.cargo/config.toml`, including staged deletions — and, before it invokes Cargo, refuses the commit while any such input differs between the Git index and the worktree or exists untracked and not Git-ignored, so a repaired-but-unstaged lockfile cannot make a broken commit pass; Git-ignored paths, where Cargo's own build output lives, are never scanned. It then runs `cargo update --workspace` — documented as "Attempt to update only packages defined in the workspace. Other packages are updated only if they don't already exist in the lockfile. This option is useful for updating Cargo.lock after you've changed version numbers in Cargo.toml" (`https://doc.rust-lang.org/cargo/commands/cargo-update.html`, retrieved 2026-09-09) — for **each workspace root in the repository**, because one such command resolves one workspace and Cargo lets a repository hold independent workspaces beneath its top level (a package with its own `[workspace]` table, or one listed in the top-level `workspace.exclude`; `https://doc.rust-lang.org/cargo/reference/workspaces.html`, retrieved 2026-09-09T07:18Z, and the r3 empirical audit's reproduction). Roots are the tracked top-level `Cargo.toml`, plus every other tracked `Cargo.toml` that declares a `[workspace]` table or sits beside a tracked `Cargo.lock` *and* that Cargo itself reports as its own workspace root (`cargo locate-project --workspace --manifest-path`); candidates Cargo rejects — a non-member package under another workspace, a vendored crate with its own lock, an unparsable template manifest — are skipped with one summary note, because Cargo cannot resolve them from there either ("current package believes it's in a workspace when it's not" — a synthesizer probe of 2026-09-09, not retained, since the sketch discards `locate-project` stderr; G0 records the consequence: `locate-project` is asked about `vendored/foo/Cargo.toml` and no resolve is issued for it). A single-workspace repository, the template's shape, therefore runs no extra Cargo process (A4). Each root is resolved *from its own directory*, because Cargo "looks for configuration files in the current directory and all parent directories" (`https://doc.rust-lang.org/cargo/reference/config.html`, "Hierarchical structure", retrieved 2026-09-10T01:11Z), not from `--manifest-path`: a nested root's own `.cargo/config*` — which the trigger set includes because such a file can redirect sources and patch dependencies — and the configs of its parent directories therefore apply to the check exactly as they apply to the developer's `cargo update --workspace` in that directory (H1, H2; the r4 judgment audit's F1). A `.cargo/config*` *below* a workspace root (inside a member directory) is not applied — Cargo reads it only for commands run inside that directory — and the check must report it (H4); a root whose `Cargo.lock` is Git-ignored and untracked is not resolved, so nothing is written there (H3). The check refuses with exit 1 if any `Cargo.lock` now differs from the index or was created, printing Cargo's own change summary (`Adding …`, `Removing …`, `Updating …`, `Downgrading …`) and the `git diff --stat`, then restores the lockfile from the index so a refusal never leaves the worktree modified. Cargo's own failures (manifest errors, cache or network errors) keep Cargo's diagnostic and Cargo's exit status (101), distinct from a stale lock. The same check's `--all` mode runs unconditionally for a clean CI checkout, where nothing is staged and the conditional trigger would otherwise skip. This is py-shaped on the principle and on the semantic — py's `uv-lock-check` job runs `uv lock --check` whenever `pyproject.toml` or `uv.lock` is staged; ts has no equivalent job — and Rust-specific in the mechanism, because Cargo has no `--check`-style flag and its `--locked` flag tests a weaker property. What this decision fixes is the pattern, the behaviors an implementation must have and the edge cases it must handle; the executable form is P03's work, and the script written in this run (`review/empirical/fixture/scripts/check-cargo-lock.sh`) is an illustrative sketch that established the findings below, not code this decision ships.

### Principles and implementation

**Shared requirement, source and agreement level.** A dependency-manifest edit that would change the lockfile must not be committed without the matching lockfile change, and the developer must learn this before the push round-trip, at a cost small enough to run on every commit. Agreement is at the **capability and policy level** — catch the drift locally before the push, and keep routine feedback cheap — not at the command level; but the *concrete requirement* py realizes is `uv lock --check`'s "the lockfile would change, so refuse", and this decision delivers that concrete requirement rather than the narrower "the parsed resolve differs" that Cargo's `--locked` delivers (spec §2: a concrete requirement is not silently weakened into a vague goal). A third behavior, evaluating exactly what Git will commit (the index-parity guard), is required of the Rust design by the hazard reproduced in case B5a; it is not shared with py, whose hook has no such guard, and it is listed under what may vary below. The sources: py realizes it with `uv lock --check` (`lefthook.yml:126-131` at `b08bccfb55d05f15e46a83b52c5660b1881d19f5`, read by `raw/codex.md` via `git show` on 2026-09-05), ts never adopted a lockfile check (`lefthook.yml` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00` has format, size, lint, typecheck, commit-message and pre-push test jobs only; `TS_PORT_DECISIONS.md` discusses lockfile/CI policy without such a hook), and the ledger records the pair as `py-only` / `DIVERGENT`. The Rust ecosystem has the underlying property natively but split across two behaviors: Cargo's resolver preserves an existing lockfile whenever it still satisfies the manifests (`https://doc.rust-lang.org/cargo/reference/resolver.html`, retrieved 2026-09-05) and writes it only when its contents would change (`src/ops/lockfile.rs:45-52`, above); Cargo's `--locked` flag makes a resolving command exit 101 instead of writing, but tests parsed-resolve equality, not file equality (`src/ops/lockfile.rs:210-230`). The Cargo team's guidance recommends committing lockfiles for applications and, since 2023, for libraries too (`https://blog.rust-lang.org/2023/08/29/committing-lockfiles/`, 2023-08-29, retrieved 2026-09-05). Scope relative to py: `uv lock --check` resolves one project workspace, and py's job runs it once at the root (`glob: "{pyproject.toml,uv.lock}"`, `run: uv lock --check`), so py's guarantee is single-workspace; Cargo permits independent workspaces beneath a repository's top level (the Cargo workspaces reference: "All path dependencies residing in the workspace directory automatically become members", "The exclude key can be used to prevent paths from being included in a workspace", and Cargo's refusal to treat a non-member, non-excluded package under a workspace as its own project — the captured `believes it's in a workspace when it's not` error), and a template user may add one (a `cargo fuzz`-style directory with its own `[workspace]` table, an excluded tool crate), so the Rust design checks every workspace root the repository holds rather than only the top-level one; a single-workspace repository behaves exactly as py's does. "Fresh" here means the committed `Cargo.lock` is byte-for-byte what Cargo would write for the committed manifests and configuration after a conservative resolve; it does not mean every dependency is at its newest version (`cargo update --workspace` never upgrades a package that is already in the lockfile — F1 shows it *downgrading* only because the requirement changed).

**Findings this research established.** These are properties of Cargo and of Git's index, not of any one script, and they are what makes the design below the design. Each was surfaced by an audit of an earlier revision of this decision, then reproduced on four toolchain/OS legs (macOS 1.96.0, macOS 1.98.0, Linux 1.96.0, Linux 1.98.1) in `review/evidence/lockfile-freshness-acceptance.r5.log` and `review/evidence/lockfile-freshness-acceptance-linux.r5.log`, and independently rerun by the revision-5 empirical audit (`review/evidence/audit-lockfile-freshness-check-r5.log`). Case identifiers (`E1a`, `G1a`, `H1a`, …) name the assertions in those logs.

1. **`--locked` is not `uv lock --check`: every `--locked` Cargo command accepts a lockfile left stale by the removal of a leaf workspace member.** With `crates/web` dropped from `[workspace].members` and its `[[package]]` entry still in `Cargo.lock`, `cargo metadata --locked` (E1a), `cargo update --workspace --locked` (E1b, printing `Locking 0 packages`), `cargo generate-lockfile --locked` (E1c, a recorded rather than asserted case) and `cargo check --workspace --locked` (E1d) all exit 0 and leave the lockfile untouched; the same holds when the member directory is deleted with `git rm -r` (E2a) and after the stale state is already committed (E3c). An unlocked resolve of that same tree then prunes seven lines (E1h). The mechanism is in Cargo's source at `e7506208ff1b7f01062e410c419f95628dfdb31b`: the lockfile parser drops the orphan entry at parse time (`src/resolver/encode.rs:196-200` — "We failed to find a local package in the workspace. It must have been removed and should be ignored.") and `--locked` compares the *parsed* resolves rather than the file text (`src/ops/lockfile.rs:210-230`, `are_equal_lockfiles`), while an unlocked run writes exactly when the text would differ (`src/ops/lockfile.rs:45-52`, `write_pkg_lockfile` — "If the lock file contents haven't changed so don't rewrite it"). `uv lock --check` refuses the analogous uv-workspace removal with exit 1 (uv 0.11.29, the r2 judgment audit's probe P7). Surfaced by `review/audit-fable.r2.md` F1. **Consequence for any implementation:** the freshness test must compare lockfile *contents* after an unlocked resolve. A `--locked` form delivers a strictly weaker guarantee, and choosing one means disclosing the orphan-entry and normalization gaps as documented limits.

2. **One `cargo update --workspace` resolves one workspace: a single top-level resolve does not see a nested independent workspace.** With a second workspace under `nested/` (its own `[workspace]` table and its own `Cargo.lock`) whose manifest re-requires `anyhow = "=1.0.100"` against a lock at 1.0.104, `cargo update --workspace` run at the repository top level exits 0 and leaves `nested/Cargo.lock` untouched (G1a), as does `cargo metadata --locked` (G1b); the same resolve run inside `nested/` changes that lockfile by two insertions and two deletions (G1e). Cargo permits such a workspace beneath a repository's top level — a package with its own `[workspace]` table, or one listed in the top-level `workspace.exclude` (`https://doc.rust-lang.org/cargo/reference/workspaces.html`, retrieved 2026-09-09T07:18Z) — and refuses to resolve a package that is neither a member nor excluded ("current package believes it's in a workspace when it's not"), which is why membership must be settled by Cargo's own `cargo locate-project --workspace` verdict rather than by a marker heuristic (G2, and alternative (K) below). Surfaced by `review/audit-codex.r3.md` F1. **Consequence for any implementation:** a check that claims to cover every `Cargo.lock` in the repository must discover each workspace root and resolve it separately; a check that resolves only the top level must say so and accept the gap.

3. **Cargo discovers `.cargo/config*` from the current directory, so a per-root resolve must run inside that root.** Cargo "looks for configuration files in the current directory and all parent directories" (`https://doc.rust-lang.org/cargo/reference/config.html`, "Hierarchical structure", retrieved 2026-09-10T01:11Z), not from `--manifest-path`. With a config-level `[patch.crates-io]` in `nested/.cargo/config.toml` redirecting `anyhow` to a path crate, resolving that root as `cargo update --workspace --manifest-path nested/Cargo.toml` from the top level never applies the file, and gives the wrong verdict in both directions: it passes the stale registry-form lockfile (H1a) and it rewrites the correctly patched lockfile that the in-directory resolve produces (H2d). Running the same resolve inside `nested/` inverts both: the stale state is refused (H1b, `Adding anyhow v1.0.104 (<path>)`, ` nested/Cargo.lock | 2 --`) and the repaired state is accepted untouched (H2b). Two boundaries follow and were executed: a `.cargo/config*` *below* a workspace root (inside a member directory) is not applied by a root-directory resolve and must be reported rather than silently ignored (H4a; H4b shows the same resolve run inside that member directory rewriting the root lockfile), and a manifest-level `[patch.crates-io]` at the top level is applied and refused normally (F5). Surfaced by `review/audit-fable.r4.md` F1. **Consequence for any implementation:** each discovered root is resolved with the working directory set to that root, and a config file Cargo would not apply there is disclosed, not assumed away.

A fourth, smaller finding follows from Git rather than Cargo and is kept because it changes the design: no bare Cargo command can evaluate what Git will actually commit, because Cargo reads the worktree. With the repaired lockfile present but unstaged, both `cargo metadata --locked` and `cargo update --workspace` exit 0 (B5a, B5a2) although the commit would be broken. An implementation therefore compares the Cargo resolution inputs between the index and the worktree before it starts Cargo, and refuses on a mismatch (B5b, B7, C3). Surfaced by `review/audit-fable.r1.md` and `raw/codex.md`'s prototype; it is also what makes restoring from the index an exact undo.

**Essential behaviors** — what any implementation must do; all ten. Each was demonstrated by this run's sketch on all four toolchain/OS legs, recorded in `review/evidence/lockfile-freshness-acceptance.r5.log` and `…-linux.r5.log`; P03 re-proves them against the template's own check in the template's own CI:

1. A staged change to the Cargo inputs that would make `Cargo.lock` change is refused, whatever the class of change: a registry edge added (B1, B2), a requirement changed so a locked version no longer satisfies it (F1), a member version bumped (F2), a registry edge removed (F3), a leaf workspace member removed — the orphan-entry case that every `--locked` command accepts — whether the members list alone is edited (E1) or the directory is deleted with `git rm` (E2), a lockfile that Cargo would normalize (E4), a missing lockfile that the resolve would create (E6), and a source change through a manifest-level `[patch.crates-io]` (F5). The check exits 1; `git commit` exits 1; no commit is created.
2. A refusal never modifies the worktree: `Cargo.lock` is restored from the index (sha256 unchanged after every refusal: B1, B2, C2c, E1e, E1f, E2b, E3c2, E4b, F1–F3, F5, and for a nested workspace's lock G1c, G3, H1b) and a lockfile the resolve created is removed (E6a, E6b). This is uv's non-writing `--check` semantic.
3. Staging the repaired lockfile with the manifest makes the commit succeed (B6, E1i, E2e, E3d).
4. A relevant index/worktree mismatch is refused *before* Cargo runs — a repaired lock left unstaged (B5b, B5c), a staged lock with an unstaged manifest (B7), or an untracked, non-ignored manifest in the repository (C3). Git-ignored paths are not scanned, so Cargo's own build output — `target/package/<crate>-<version>/Cargo.toml` and `Cargo.lock` written by `cargo package` verification — does not refuse (D1–D4). B5a and B5a2 show why the guard exists and that it is command-independent: bare `cargo metadata --locked` *and* bare `cargo update --workspace` both pass in that state because Cargo reads the worktree, not the index.
5. A member manifest, the root manifest, the lockfile, a `.cargo/config.toml` and a staged *deletion* of a member manifest all trigger the check (A2, A3, B6, A7, E2b); unrelated commits skip Cargo entirely (C1: `CARGO_BIN=/nonexistent/r41-cargo` and the commit still succeeds with `SKIP: no staged Cargo resolution inputs`). A manifest edit that needs no new resolution (a comment) passes without a lock write (A2, A1b).
6. Failure output distinguishes a stale lock from a Cargo failure: a stale lock shows Cargo's own change summary and the lock diff stat and exits 1 (B1, F1–F3); a Cargo failure keeps Cargo's diagnostic and Cargo's status, 101, with no out-of-date verdict (F4: a malformed member manifest gives `error: key with no value, expected \`=\``, `error: failed to load manifest for workspace member …`, then `FAIL: Cargo lockfile validation could not complete`; script exit 101; `git commit` exit 1; lock unchanged).
7. An unconditional mode exists for CI: `--all` runs Cargo with nothing staged (A4) and catches a stale lock committed past the hook (C2c) and an orphan entry committed past the hook (E3c2), both of which the default mode cannot see (C2b, E3b) and the second of which `cargo metadata --locked` cannot see either (E3c).
8. **What must agree and what may vary.** Must agree across py, ts and rs: a manifest change that would change the lockfile is caught before the push (py: yes; ts: no, and this decision does not follow ts), the check does not write the lockfile, the check is conditional on staged inputs so unrelated commits pay nothing, and CI proves the committed state independently. May vary: the command (`uv lock --check` versus `cargo update --workspace` plus a Git comparison, because Cargo has no non-writing "would change" flag), the number of workspaces checked (py: the one project workspace; rs: every workspace root the repository holds, because Cargo permits nested independent ones), the trigger set (Cargo needs the config files too, because `.cargo/config.toml` can redirect sources and patch dependencies — honoured by resolving each root from its own directory, H1/H2, and reported where Cargo would not apply the file, H4), and the parity policy — py's `uv lock --check` reads the worktree exactly as Cargo does, but py's hook has no parity guard; Rust adds one because the reproduced hazard (B5a, B5a2) is real and because the restore step depends on it (worktree == index for every `Cargo.lock` before Cargo runs is what makes `git checkout -- Cargo.lock` an exact undo).

**Architecture alternatives compared** (before any command was chosen, per owner amendment A5; every discriminator below was executed on all four legs):

- (A) *Conditional conservative unlocked resolve, `cargo update --workspace` run from each workspace root's own directory, plus index-parity guard, post-resolve Git comparison of every `Cargo.lock`, and restore.* Catches every executed change class including the orphan entry (E1, E2, E3) and normalization (E4); no compilation; touches the registry index only when a package must be resolved and never downloads crate archives (A5b: 0 `.crate` files cold; 88-package graph: 0.67–0.70 s cold with 0 archives versus 1.59–1.78 s and 85 archives for locked metadata). Precedent for the write-then-diff shape at CI tier: dfinity/ic `.github/workflows/ci-pr-only.yml:208-245` at `fe38094d061eedc8146b72647779d903e3e83a0f` runs `cargo update --workspace`, then `git add Cargo.lock …` and `git diff --cached --quiet`, failing the PR and showing the diff when the lockfile changed (retrieved 2026-09-09; path-filtered on `**/*.toml` and `**/*.lock`). **Selected.**
- (B) *The same design with `cargo metadata --format-version=1` unlocked as the resolve.* Identical verdicts and identical lock bytes in every executed case (B3e versus B4, E1g, F1–F3: same diff stats; `1c006eed…9125` for both); costs crate-archive downloads when the cache lacks them (A5: 1 archive; 85 on the 88-package graph) and exercises the metadata path the rest of the tooling consumes. **First runner-up.**
- (C) *Conditional `cargo metadata --locked` plus index-parity guard* — revision 2's design. Refuses a stale registry edge (B3c-class; revision 2 B1) but passes the orphan entry in both forms and after a bypass (E1a, E2a, E3c) and passes a lockfile Cargo would normalize (E4a); the narrower guarantee would have to be disclosed as a documented limit. **Rejected**: alternative (A) meets the concrete requirement at the same warm cost and lower cold cost, so accepting the narrower guarantee is not justified by any fitness argument.
- (D) *Conditional `cargo update --workspace --locked` plus the same guard.* clap's dedicated `lockfile` CI job (`https://github.com/clap-rs/clap/blob/master/.github/workflows/ci.yml#L195-L206`, retrieved 2026-09-05) and apache/iceberg-rust (`.github/workflows/ci.yml:75-76` at `4687d265374bf5dc7bd8cd461f3bd46a23864761`, "Check Cargo.lock is up-to-date", retrieved 2026-09-09) run exactly this; refuses the stale registry edge (B3d) but passes the orphan (E1b, `Locking 0 packages`). **Rejected** for the same reason as (C); its command is the one (A) runs, minus the flag that hides the orphan.
- (E) *Locked compilation, `cargo check --locked` or `cargo build --locked`.* Refuses the stale registry edge at resolution time (B3c) but passes the orphan (E1d) and on a fresh lock proceeds to compile: 0.98–1.28 s on macOS (run r5, under host load; 0.82–0.93 s in run r4) and 0.27–0.30 s on Linux for the fixture's 4-package graph (A6), 10.067 s at the floor for the 88-package graph in `raw/codex.md`. **Not selected** as the hook; CI keeps `--locked` on its compiling invocations per R23.
- (F) *Check an isolated snapshot of the staged tree.* Would support partial staging instead of refusing it, but needs a policy for workspace paths, `.cargo` config, symlinks and snapshot cost; no maintained implementation was found by any party. **Not selected**; documented as the extension path if partial staging must be supported.
- (G) *CI or pre-push only.* Avoids all local latency; loses the early failure F171 exists to provide, and the measured local cost does not justify deferring. **Not selected** as the only tier; the CI tier remains as `--all` plus `--locked` invocations.
- (H) *`cargo metadata --locked --no-deps`, `cargo update --locked --dry-run`, `cargo generate-lockfile --locked`.* The first two return 0 on the stale registry edge (B3a, B3b) and are **excluded** as false passes; `--dry-run` cannot see the orphan either, because the orphan is dropped at parse time and detection happens only when Cargo compares the encoded file text on write, which `--dry-run` skips (inferred from `encode.rs:196-200` and the `--dry-run` documentation, "doesn't actually write the lockfile"; not executed on the orphan tree). The third refuses stale locks but by documented operation re-resolves to the latest permitted versions (`https://doc.rust-lang.org/cargo/commands/cargo-generate-lockfile.html`, retrieved 2026-09-05), so it can reject a valid lock merely because newer versions exist, and it too passes the orphan while nothing newer exists (E1c, recorded exit 0); **excluded** as semantically wrong for "fresh".
- (I) *Variant of (A) that leaves the repaired lock on disk instead of restoring it* (the dfinity/ic shape; what lefthook-style `stage_fixed` conventions expect). One fewer developer step, but the hook then modifies a tracked file during `git commit`, departs from uv's non-writing `--check`, and breaks essential behavior 2 that the revision-2 empirical audit verified. **Not selected** here; it is a wiring-time option R37 may take with its own regression case, not a change to the pattern.
- (J) *Limit the guarantee to the top-level workspace* (revision 3's actual behavior, stated honestly). The trigger must stay recursive because the root workspace's members and path dependencies live anywhere beneath it, so a staged change in a nested independent workspace would still fire the hook and run a top-level resolve that cannot see it — the silent false pass the r3 audit reproduced (G1a, G1b) — unless the check also refused on any `Cargo.lock` outside the top-level workspace, which blocks legitimate nested workspaces outright. **Rejected**: the honest form of this option is either a silent gap or a hard block, while discovery costs a single-workspace repository nothing.
- (K) *Discover roots by markers alone* — every tracked `Cargo.toml` with a `[workspace]` table or beside a tracked `Cargo.lock`, resolved without asking Cargo. A vendored or otherwise non-member package carrying its own `Cargo.lock` would then be resolved from inside another workspace, which Cargo refuses ("believes it's in a workspace when it's not"), turning every commit into a Cargo failure; G2 is the discriminator. **Rejected** in favour of validating each nested candidate with `cargo locate-project --workspace`.
- (L) *Ask Cargo about every tracked manifest* (`cargo locate-project --workspace` per `Cargo.toml`, no candidate filter). Correct, but 0.03–0.08 s per manifest on macOS (measured 2026-09-09) — three extra processes for the template, hundreds for a repository that vendors crates. **Rejected** on cost: the candidate rule yields the same roots (the top-level manifest is a root by construction; every other root either declares `[workspace]` or owns a lock) with zero extra processes for one workspace (A4) and one per nested candidate otherwise.
- (M) *Derive the trigger set from Cargo's own member list* (`cargo metadata --no-deps` per commit, or the manifests the top-level root reports) so that a single-workspace guarantee is honest without a recursive glob — the middle option between (J) and discovery. It costs one Cargo process on every guarded commit even for the template's single workspace, and a nested independent workspace is still unchecked, silently, because its manifests are not in the top-level member list. **Rejected**: it is dearer than discovery for the template and weaker for the nested shape.
- (N) *Per-root resolve from the top-level working directory with `--manifest-path`* (revision 4's form). Cargo anchors configuration discovery on the working directory, so a nested root's own `.cargo/config*` is never applied while the instructed remediation, run in that directory, applies it: with a config-level `[patch.crates-io]` the hook refuses the lock its own remediation produces and passes the lock the in-directory resolve would change (H1a, H2d). **Rejected** in favour of `cd <root dir> && cargo update --workspace`, which costs nothing (the top-level root's directory is `.`) and inverts both verdicts correctly on all four legs (H1b, H2b).

**Why the selected design preserves each principle.** Early failure: the check runs inside `git commit` (real `.git/hooks/pre-commit` in every case; `core.hooksPath` verified empty, A0) and a change that would alter the lockfile never becomes a commit (B2, E1f, E2c, F1–F3). The concrete requirement: the comparison is of file contents after Cargo's own write decision, so it is exactly "would the lockfile change" — including the orphan entry (E1–E3) and normalization (E4), which `--locked` misses — for every workspace the repository holds (G1, G3), under that workspace's own configuration context (H1, H2, F5), and it does not refuse on format-version or cross-toolchain grounds (E5, A1b on every leg), on manifests that are not workspace roots (G2), or on a configuration file Cargo would not apply to the root-directory resolve (H4a, reported). Non-writing check: the restore leaves the worktree as it was on every refusal (behavior 2). Intended commit contents: the parity guard makes the check evaluate what Git will commit, not merely what is on disk (B5, B7, C3), which py's hook does not do and which no bare Cargo command can do (B5a, B5a2); it never scans Git-ignored paths, so Cargo's own build output cannot cause a false refusal (D2, D3). Cheap routine feedback: unrelated commits never start Cargo (C1); warm guarded commits cost 0.12–0.14 s on macOS and 0.03 s on Linux for this fixture (0.02–0.03 s of which is the `git grep` / `git ls-files` discovery added in revision 4), the whole script in `--all` mode 0.15–0.19 s on macOS and 0.02–0.03 s on Linux (A4b), and the recommended resolve itself 0.01–0.03 s warm (A1b) or 0.10–0.14 s warm on the 88-package graph — run r4 on an idle host; run r5's macOS legs ran under load (0.33–0.50 s guarded commits, 0.55 s `--all` at the floor, with the no-Cargo skip commit itself at 0.71 s), see Performance. Independent CI proof: `--all` plus `--locked` on CI invocations (C2c, E3c2, B3c). No new dependency: the check needs only Git, Bash and the installed Cargo; MSRV, `unsafe`, RustSec, binary size and compile time of the template are untouched.
