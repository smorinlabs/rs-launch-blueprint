## Decision

**Yes: `rs-launch-blueprint` adopts a conditional pre-commit lockfile-freshness check. The pattern is *conditional Cargo resolution with an index-parity guard*; the mechanism is the first-party toolchain command `cargo metadata --locked --format-version=1` wrapped by a repository-local script, `scripts/check-cargo-lock.sh`. No third-party crate or tool is added and there is no version to pin beyond the workspace's own `rust-version`.** The check runs at pre-commit only when a Cargo resolution input is staged — any `Cargo.toml` or `Cargo.lock` in the repository, or a `.cargo/config` / `.cargo/config.toml` — and, before it invokes Cargo, it refuses the commit while any such input differs between the Git index and the worktree or exists untracked and not Git-ignored, so a repaired-but-unstaged lockfile cannot make a broken commit pass; Git-ignored paths, where Cargo's own build output lives, are never scanned. On failure it keeps Cargo's own diagnostic and appends one remediation line. The same script's `--all` mode runs the check unconditionally for a clean CI checkout, where nothing is staged and the conditional trigger would otherwise skip. This is py-shaped on the principle — py's `uv-lock-check` job runs `uv lock --check` whenever `pyproject.toml` or `uv.lock` is staged; ts has no equivalent job — and Rust-specific in the mechanism, because Cargo has no `--check`-style flag: `--locked` on a fully resolving command is the freshness test, and `cargo metadata` is a compile-free command that performs the full resolution. Two plausible cheaper commands pass on a stale lock and are excluded: `cargo metadata --locked --no-deps` does not resolve the dependency graph, and `cargo update --locked --dry-run` resolves it but exits 0 without writing (both measured below).

### Principles and implementation

**Shared requirement, source and agreement level.** A dependency-manifest edit that changes the resolved graph must not be committed without the matching lockfile change, and the developer must learn this before the push round-trip, at a cost small enough to run on every commit. Agreement is at the **capability and policy level** — catch the drift locally before the push, and keep routine feedback cheap — not at the command level. A third behavior, evaluating exactly what Git will commit (the index-parity guard), is required of the Rust design by the hazard reproduced in case B5a; it is not shared with py, whose hook has no such guard, and it is listed under what may vary below. The sources: py realizes it with `uv lock --check` (`lefthook.yml:126-131` at `b08bccfb55d05f15e46a83b52c5660b1881d19f5`, read by `raw/codex.md` via `git show` on 2026-09-05), ts never adopted a lockfile check (`lefthook.yml` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00` has format, size, lint, typecheck, commit-message and pre-push test jobs only; `TS_PORT_DECISIONS.md` discusses lockfile/CI policy without such a hook), and the ledger records the pair as `py-only` / `DIVERGENT`. The Rust ecosystem has the underlying property natively: Cargo's `--locked` flag makes any resolving command exit 101 instead of rewriting `Cargo.lock` (`https://doc.rust-lang.org/cargo/commands/cargo-metadata.html`, `https://doc.rust-lang.org/cargo/reference/resolver.html`, retrieved 2026-09-05), and the Cargo team's guidance recommends committing lockfiles for applications and, since 2023, for libraries too (`https://blog.rust-lang.org/2023/08/29/committing-lockfiles/`, 2023-08-29, retrieved 2026-09-05). "Fresh" here means Cargo can use the committed resolution for the current manifests; it does not mean every dependency is at its newest version.

**Essential behaviors** (any design must do all seven; each is executed in `review/evidence/lockfile-freshness-acceptance.log` and `…-linux.log`):

1. A staged manifest that requires a different lockfile is refused and the lockfile is not written (B1, B2: exit 101 from the script, exit 1 from `git commit`, `Cargo.lock` sha256 unchanged, no commit created).
2. Staging the repaired lockfile with the manifest makes the commit succeed (B6).
3. A relevant index/worktree mismatch is refused *before* Cargo runs — a repaired lock left unstaged (B5b, B5c), a staged lock with an unstaged manifest (B7), or an untracked, non-ignored manifest in the repository (C3). Git-ignored paths are not scanned, so Cargo's own build output — `target/package/<crate>-<version>/Cargo.toml` and `Cargo.lock` written by `cargo package` verification — does not refuse (D1–D4). B5a shows why the guard exists: bare `cargo metadata --locked` passes in that state because Cargo reads the worktree, not the index.
4. A member manifest, the root manifest, the lockfile and a `.cargo/config.toml` all trigger the check (A2, A3, B6, A7); unrelated commits skip Cargo entirely (C1: `CARGO_BIN=/nonexistent/r41-cargo` and the commit still succeeds with `SKIP: no staged Cargo resolution inputs`). A manifest edit that needs no new resolution (a comment) passes (A2).
5. Failure output keeps Cargo's diagnostic (`error: cannot update the lock file … because --locked was passed to prevent this`) and adds a remediation line that distinguishes a needed lock update from a cache or network failure (B1).
6. An unconditional mode exists for CI: `--all` runs Cargo with nothing staged (A4) and catches a stale lock that was committed past the hook (C2c), which the default mode cannot see (C2b).
7. The command works at the `msrv-policy` floor: every case passes with Cargo/rustc 1.96.0 (stable 1.98 minus two minors) as well as with 1.98.0 (macOS) and 1.98.1 (Linux), and the fixture compiles `--locked` at the floor (A6).

**What must agree and what may vary.** Must agree across py, ts and rs: a manifest change that needs a re-lock is caught before the push (py: yes; ts: no, and this decision does not follow ts), the check is conditional on staged inputs so unrelated commits pay nothing, and CI proves the committed state independently. May vary: the command (`uv lock --check` versus `cargo metadata --locked --format-version=1`), the trigger set (Cargo needs the config files too, because `.cargo/config.toml` can redirect sources and patch dependencies), and the parity policy — py's `uv lock --check` reads the worktree exactly as Cargo does, but py's hook has no parity guard; Rust adds one because the reproduced hazard (B5a) is real.

**Architecture alternatives compared** (before any command was chosen, per owner amendment A5):

- (A) *Conditional `cargo metadata --locked` plus index-parity guard.* Full resolution, no compilation, JSON discarded; Cargo may fetch registry index and crate sources when the lock references packages absent from the cache. **Selected.**
- (B) *Conditional `cargo update --workspace --locked` plus the same guard.* clap's dedicated `lockfile` CI job runs exactly this (`https://github.com/clap-rs/clap/blob/master/.github/workflows/ci.yml#L195-L206`, retrieved 2026-09-05); refuses the stale fixture (B3d) without writing. Its documented semantics are "update workspace members only", which is a consistency check by side effect rather than by definition, and it does not exercise the metadata path the rest of the tooling consumes. **First runner-up.**
- (C) *Locked compilation, `cargo check --locked` or `cargo build --locked`.* Refuses the stale fixture at resolution time (B3c) but on a fresh lock proceeds to compile: 1.07 s / 0.90 s on macOS and 0.28 s / 0.32 s on Linux for the fixture's 4-package graph (A6, run r2, on the unrepaired repository A), 10.067 s at the floor for the 88-package graph in `raw/codex.md`. Adds compiler, build-script and source failures to a freshness check. **Second runner-up**, appropriate only if compilation already belongs in the same hook tier.
- (D) *Check an isolated snapshot of the staged tree.* Would support partial staging instead of refusing it, but needs a policy for workspace paths, `.cargo` config, symlinks and snapshot cost; no maintained implementation was found by any party. **Not selected**; documented as the extension path if partial staging must be supported.
- (E) *CI or pre-push only.* Avoids all local latency; loses the early failure F171 exists to provide, and the measured local cost does not justify deferring. **Not selected** as the only tier; the CI tier remains as `--all` plus `--locked` invocations.
- (F) *`cargo metadata --locked --no-deps`, `cargo update --locked --dry-run`, `cargo generate-lockfile --locked`.* The first two return 0 on the stale fixture (B3a, B3b) and are **excluded** as false passes. The third refuses stale locks but by documented operation re-resolves to the latest permitted versions (`https://doc.rust-lang.org/cargo/commands/cargo-generate-lockfile.html`, retrieved 2026-09-05), so it can reject a valid lock merely because newer versions exist; **excluded** as semantically wrong for "fresh".

**Why the selected design preserves each principle.** Early failure: the check runs inside `git commit` (real `.git/hooks/pre-commit` in every case; `core.hooksPath` verified empty, A0) and a stale manifest never becomes a commit (B2). Intended commit contents: the parity guard makes the check evaluate what Git will commit, not merely what is on disk (B5, B7, C3), which py's hook does not do and which bare `--locked` cannot do (B5a); it never scans Git-ignored paths, so Cargo's own build output cannot cause a false refusal (D2, D3). Cheap routine feedback: unrelated commits never start Cargo (C1); warm guarded commits cost 0.10–0.12 s on macOS and 0.03 s on Linux for this fixture (run r2), and a median 0.277 s / 0.210 s (1.96.0 / 1.98.0) on the report's 88-package workload. Independent CI proof: `--all` plus `--locked` on CI invocations (C2c, B3c). No new dependency: the script uses Git, Bash and the installed Cargo; MSRV, `unsafe`, RustSec, binary size and compile time of the template are untouched.

**Tier conclusion.** Pre-commit, conditional. The warm cost is one to three tenths of a second on a realistic graph and zero for unrelated commits; the cold path costs seconds only when the cache lacks sources, which ordinary project setup (`cargo fetch`, any prior build) prevents. This is the tiering both source repos share (fast staged-file checks at pre-commit, slower full-tree checks later), and it does not remove the later authoritative gate (`--all` and `--locked` in CI).
