## Principle and agreement level

The decision states the shared requirement correctly and at a defensible level. The principle — a dependency-manifest edit that would change the lockfile is caught locally, before the push, at a cost small enough to run on every commit — is sourced to py's `uv-lock-check` job (`lefthook.yml:126-131` at the pinned commit) and to ts's absence of any such job, matching the ledger's `py-only` / `DIVERGENT` row F171. Agreement is placed at the capability and policy level (catch the drift locally; keep routine feedback cheap; CI proves the committed state independently), and the decision is explicit that the *concrete* requirement py realizes is `uv lock --check`'s "would the lockfile change after a resolution" test, which it delivers rather than the narrower parsed-resolve equality that Cargo's `--locked` tests. That is the right reading of spec §2's "do not silently weaken a concrete requirement into a vague goal": the narrowing is neither silent nor adopted, and the two semantics are distinguished from Cargo's own source at a pinned commit (the quoted lines of `encode.rs:196-200`, `lockfile.rs:45-52` and `lockfile.rs:210-230` are verbatim at `e7506208…`, checked 2026-09-09T07:51Z). What must agree and what may vary are separated explicitly; the index-parity guard is correctly labelled a Rust-side addition motivated by a reproduced hazard rather than a shared behavior; the uv quote ("Asserts that the uv.lock would remain unchanged after a resolution") is verbatim on the current uv reference page.

On the question the task puts first — whether per-root discovery preserves the principle at the right level without over-reaching the template's single-workspace shape — the decision's argument holds as far as it goes. py's guarantee is single-workspace because uv resolves one project workspace; Cargo permits independent workspaces beneath a repository top level; the trigger set is necessarily recursive because the root workspace's members live anywhere beneath it; so a top-level-only resolve behind a recursive trigger is either a silent gap or a hard block (alternative J), and Cargo-validated discovery costs a single-workspace repository no Cargo process (A4, A4b: no `cargo locate-project` in the spy log; 0.15–0.19 s macOS / 0.02–0.03 s Linux for the whole `--all` script). That is proportionate: the template pays nothing, and a user who later adds a nested workspace gets the check without touching the hook. The over-reach is elsewhere — not in *whether* nested roots are checked, but in *how* each one is resolved: the r4 design claims the concrete `uv lock --check` semantic for every root, yet resolves nested roots under the top-level's configuration context instead of their own (finding F1 below). For the template's own shape the claim is true; for the nested shape the decision now extends the guarantee to, it is not.

## Findings

**F1 — unresolved (blocks approval). A nested independent workspace's own `.cargo/config.toml` is a trigger input the per-root resolve never applies, so the r4 script gives the wrong verdict in both directions for a nested root whose configuration changes resolution, and the remediation cannot recover the false refusal.** Evidence: probe P1 above, r4 script (sha256 `8c58e171…62c6`) as `.git/hooks/pre-commit` on a copy of the decision's fixture with `nested/` built as G0 builds it; `nested/.cargo/config.toml` carrying a config-level `[patch.crates-io]`; the lock produced by the decision's remediation command inside `nested/` is refused by the script (exit 1) and by the guarded commit (exit 1) at cargo 1.98.0 and at the 1.96.0 floor, and running that remediation again cannot recover it (P1.5: `Locking 0 packages`, lock unchanged, refused again), because the script's resolve — `cargo update --workspace --manifest-path nested/Cargo.toml` from the top level — re-resolves `anyhow` from the registry (P1.4), while the in-directory resolve leaves the lock unchanged (P1.5); the registry-form lock staged with the same config passes (exit 0) although the in-directory conservative resolve changes it (P1.6). Mechanism: `check-cargo-lock.sh:46` fixes the working directory at the top level and `:110` passes only `--manifest-path`; Cargo's configuration reference anchors config discovery on the current directory and its parents (retrieved 2026-09-10T00:56Z). Where the text is contradicted: the F171 row's guarantee ("any `Cargo.lock` of any workspace in the repository change after a conservative resolve is refused"), essential behavior 9 ("every independent workspace root in the repository is resolved and its lockfile compared"), the What-may-vary rationale for triggering on `**/.cargo/config.toml`, and the remediation sentence in the script's `FAIL:` line. The planned-validation entry "behavior with a `.cargo/config.toml` that changes resolution … (A7 shows only that staging one fires the trigger)" and the limits paragraph's "does not isolate … user-level Cargo configuration" do not disclose this: the first is a coverage statement (a class of input was not executed), whereas F1 is a design statement — the per-root resolve runs under a different configuration context than the developer's resolve in that workspace does, whichever inputs are tested — and the second concerns configuration outside the repository, whereas `nested/.cargo/config.toml` is a tracked, triggering input. Classification: a fixable gap, not an owner design question — resolving from each root's own directory (P1.8, one line, top-level root unaffected) inverts both verdicts correctly at both toolchains; the fix needs the script change, a regression case in repository G (a nested root with its own `.cargo/config.toml` `[patch]`, accepted when the in-directory repair is staged, refused otherwise), the per-root timing re-measured, the limits paragraph and re-verify line updated, and a rerun of both legs. If the owner instead prefers to exclude nested-root configuration from the guarantee, that is a narrowing that must be disclosed in the F171 row and the limits paragraph, with P1's case recorded as a documented-limit test — but nothing in the evidence argues for accepting the narrower guarantee when the fix costs one line.

**O1 — wording precision; does not block.** The limits paragraph says the script "transiently writes `Cargo.lock` inside the hook before restoring it", and "one that Git-ignores `Cargo.lock` passes vacuously" is stated for the top-level library case only. Probe P4: a nested `[workspace]` root with `Cargo.lock` in `nested/.gitignore` is committed through the hook (exit 0) and afterwards `nested/Cargo.lock` exists on disk, written by the resolve and neither restored nor removed (it is neither `changed` nor `created` to Git); with `anyhow = "=1.0.100"` staged in `nested/Cargo.toml` the hook exits 0 and the ignored lock is rewritten from 1.0.104 to 1.0.100 and left there. The guarantee is not violated (an ignored lock is not a lockfile in the repository), but the "transiently" sentence is false for ignored locks and the vacuous-pass disclosure should cover nested roots too. A revision 5 can fix this in the same paragraph.

**O2 — revision residue; does not block.** Line 25 ("revision 3 delivers that concrete requirement") and Engines row 7 ("the revision-3 script refusing it", "the revision-3 design tests file equality") name the previous revision as the deliverer of the current semantic. **O3 — alternative-set completeness; does not block.** Between alternative J (limit the guarantee to the top-level workspace, with a recursive trigger that fires on inputs the resolve cannot see) and the selected discovery there is an uncompared middle option: derive the trigger set from Cargo's own member list (`cargo metadata --no-deps`, or the tracked manifests the top-level root reports) so that a single-workspace guarantee is honest without a recursive glob. ## Assessment

Revision 4 is the right design for the item and the text is, with the exceptions above, precise about what it enforces. The principle is stated at the capability and policy level with its py source and the ts divergence; the concrete `uv lock --check` semantic is preserved deliberately rather than weakened; the mechanism is proved from Cargo's own source at a pinned commit and every citation I checked is verbatim; the alternatives are compared on executed discriminators; per-root discovery is proportionate to the template's single-workspace shape because it costs that shape nothing; the empirical audit is consistent with the decision and its evidence hashes and line references are correct; the R23 attribution and the absence of `BASELINE-REVIEW:` and `CONFLICT:` lines are handled as the runbook requires.

I reject on F1 alone. This item has drawn a scope finding in every round because each revision's guarantee sentence reached slightly past what its script did; revision 4's guarantee reaches to "any workspace in the repository" and its script resolves every root under the top-level's configuration context, which is not that workspace's conservative resolve whenever the root carries its own `.cargo/config*` — a file the decision itself puts in the trigger set for exactly the reason that makes the omission matter. The defect is fixable in one line of the script plus a regression case and two sentences of text; it is not a design question for the owner, and I recommend the fix over a disclosed narrowing. The template's own shape is unaffected, so the owner's practical risk is confined to users who add a nested workspace with its own Cargo configuration; that is not a reason to publish a guarantee the script does not keep. O1–O5 are for the synthesizer's revision 5 and do not need owner input.
