## Decision

This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). It records what the research found and what it recommends; P03 builds the template and its CI proves the recommendation. A recommendation that does not survive implementation is revised against this recorded research, not researched again from scratch. What P03 must validate is listed under `## Engines`.

**Recommendation — one stack, entirely first-party, adding no crate and no GitHub Action to the template.** Every element is a command shipped with the Rust toolchain plus a checked-in expectation file; the only external utilities are `diff`, `tar`, `cmp` and `jq`.

1. **Packed-file-set assertion (the Rust analogue of F039).** Per publishable package: `cargo package -p <pkg> --list --no-verify --offline --locked`, output diffed against a checked-in `ci/expected-packed-files.txt`; any addition or removal fails. The expectation must list the entries Cargo synthesizes (`.cargo_vcs_info.json`, `Cargo.lock`, `Cargo.toml`, `Cargo.toml.orig`) as well as the source paths. The changelog read at the pin dates registry-free listing to Cargo 1.94 (`src/doc/src/CHANGELOG.md`, 2026-03-05, PR #16341, "cargo-package: skip registry verification when using `--list`"), so 1.94 is the floor this element implies; the probe exercised `--offline --list` on 1.98 only and tested no earlier toolchain.
2. **Packaged-metadata assertion (the Rust analogue of F078).** Run `cargo package -p <pkg>`; **abort the guard if that command's exit status is nonzero**, then (a) fail on a scoped grep of its stderr for `ignoring (library|binary) … is not included in the published package`, ``ignoring `package.build` `` and `both package.include and package.exclude are specified; the exclude list will be ignored`; (b) extract the `.crate` with `tar` and run `cargo metadata --no-deps --format-version 1` against the *extracted* manifest, diffing a `jq`-normalized `{name, kind}` target projection against a checked-in `ci/expected-packaged-targets.json`; (c) `cmp` the source `Cargo.toml` against the archive's `Cargo.toml.orig`; (d) compute the wider publish-facing projection (`name`, `version`, `description`, `license`, `license_file`, `repository`, `homepage`, `documentation`, `readme`, `keywords`, `categories`, `rust_version`, `edition`, `links`, `publish`, `default_run`) from the *source* manifest and from the *extracted archive* manifest and diff the two — never against a checked-in file, which would carry `version` and break at every release. The target-set diff is the authoritative signal; the stderr grep is the early, human-readable one, and its warning strings are not a stable interface.
3. **`cargo publish -p <pkg> --dry-run --locked`** as the last step of the publish workflow's verify job, immediately before the protected-environment upload. Unlike npm's pack dry run, Cargo's dry run reaches the crates.io index — Opus observed `Updating crates.io index` on its probe; this check did not run the command at all — so the verify job needs outbound network access, a note for R08 (`workflow-permission-hardening`) rather than a conflict here.
4. **`package.include` declared in `Cargo.toml`, never alongside `package.exclude`.** The allowlist makes the shipped set a declared artifact rather than a residue of `.gitignore`, and keeps the expectation file short. Both `LICENSE-MIT` and `LICENSE-APACHE` must appear in it, or the dual license ships without its texts.

**Placement.** Elements 1–4 are bound to the publish workflow's verify job, before the upload — ts's placement for F039/F078, and the placement both engines put the guard at; only Opus adds a second, pull-request copy on top of it. A pull-request copy of element 1 alone is recorded as **recommended hardening, not bound here**: it is feasible (the listing ran offline, without touching a registry, exit 0 — log line 78) and it would turn "we shipped the wrong files" into a review-time diff, but wiring a step into pull-request CI falls inside `ci-job-structure` (R11, unresolved), which R26 does not consume. P03 adds it when R11 fixes the job shape.

**Ledger rows settled:** F039 (`ci-workflows`, ts `.github/workflows/publish.yml:112`) and F078 (`release-versioning`, ts `:199`), bundled in `docs/port/COMMONALITY.md` as one publish-content-verification item. Both ts steps were re-read at the pin (log lines 209–212). `py-launch-blueprint` at its pin has neither (log lines 214–233: its publish workflow carries tag-ancestry, version-match, build, upload and publish steps only), so no `BASELINE-REVIEW:` arises from a challenged source fact.

**Answers to the prompt's questions.** HIGH-1: yes — `cargo package --list` enumerates the exact shipped set, one sorted path per line on stdout with diagnostics on stderr (log lines 236–252), which is a cleaner diff substrate than ts's JSON. HIGH-2: yes, Cargo has a direct analogue of npm's `bin` auto-correction, and **this half of the bundle is an active check, not a documented non-issue** — see `### Principles and implementation`. MEDIUM-3: no, Cargo's defaults are not safer in a way that lowers the guard's value; they are differently leaky (npm ships what is not excluded, Cargo ships what git does not ignore), and the probe's denylist state shipped a stray file. MEDIUM-4: publish-time verify job now, pull-request copy of the cheap half as hardening once R11 lands. LOW-5: no maintained crate or Action wraps this; hand-rolled shell is the ecosystem norm, as it is in ts. `cargo-diet` computes `include` directives and rewrites the manifest, so it cannot be a gate; `cargo-release` does not assert packed content.

### Principles and implementation

**Shared requirement, source, agreement level.** *A publish pipeline must prove, before the irreversible upload, that the artifact contains exactly the intended files and declares exactly the intended package metadata; the packaging tool's own silent normalizations are changes requiring assertion, not trustworthy cleanup.* Source: ts expresses it as two steps of one verify job (F039, F078, `DIVERGENT`, origin `ts-only`, bundled in both rows' Notes); py expresses it nowhere. Agreement is required at the level of **policy plus observable acceptance criteria**, not at the level of a command: `npm pack --dry-run --json` and `cargo package --list` are two instances of one policy.

**The load-bearing finding, verified in the pinned source.** Cargo materializes auto-discovered targets into explicit tables when it packages, and **prunes any target whose source file is not in the packed set, emitting a warning and continuing**. At `rust-lang/cargo` commit `797e8a9bca276c1c9f9f738d2a20f484fa4eea9d` — the commit the installed `cargo 1.98.0 (797e8a9bc 2026-08-05)` reports — the prune helper `prepare_target_for_publish` (`src/cargo/util/toml/mod.rs:3298-3316`) calls ``gctx.shell().warn(format!("ignoring {context} `{name}` as `{}` is not included in the published package", …))?`` and returns `Ok(None)`, dropping the target. It is called for `"library"` (`:3105`), `"binary"` (`:3109`), `"example"` (`:3111`), `"test"` (`:3112`) and `"benchmark"` (`:3114`); `package.build` entries get the same treatment at `:3005`. A second warn-and-continue surface sits in `src/cargo/ops/cargo_package/mod.rs:482-486`: when both `package.include` and `package.exclude` are set, Cargo warns `both package.include and package.exclude are specified; the exclude list will be ignored` and proceeds. The warning severity is deliberate and dated: `src/doc/src/CHANGELOG.md` at that commit, Cargo 1.80 (2024-07-25), "cargo-package: Warn, rather than fail, if a Cargo target is excluded during packaging." (PR #13713). All four citations were read at the pin and are reproduced in the evidence log (lines 10–56).

**Reproduced.** On the probe crate (library plus two binaries), narrowing `include` so `src/bin/rsguard-serve.rs` was not packed made `cargo package` print ``warning: ignoring binary `rsguard-serve` as `src/bin/rsguard-serve.rs` is not included in the published package`` and **exit 0**, producing a `.crate` whose normalized `Cargo.toml` declared only one `[[bin]]` (log lines 124–143). That is ts's F078 hazard — "ship the package WITHOUT its CLI" — reproduced in Cargo, with no exit-code signal. The risk is therefore real and silent by design; the question this item answers is not whether it exists but what asserts it.

**Essential behaviors.** (1) The packed file set is asserted against a checked-in expectation and any difference fails. (2) The packaged manifest's target set is asserted against a checked-in expectation and any difference fails, because a nonzero exit status will not appear. (3) The author manifest survives into the archive unmodified (`Cargo.toml.orig`) while the normalized `Cargo.toml` is compared semantically, never textually — Cargo documents that it rewrites the packed manifest and removes `[patch]`, `[replace]` and `[workspace]`, so a byte-diff of the normalized manifest is the wrong assertion. (4) All of it runs before the upload, in the same workflow, on the same commit.

**Observable acceptance criteria for P03.** (a) A deliberately narrowed `include` that drops a binary fails the publish workflow before the upload step. (b) A stray file added to the repository root fails the guard. (c) The healthy repository passes on `ubuntu-latest` and `macos-latest`. (d) The guard aborts rather than inspecting a stale archive when `cargo package` exits nonzero.

**What must agree; what may vary.** Must agree: the four essential behaviors above, and their placement before the upload. May vary: the expectation file's format, whether the comparison is `diff` or a set comparison, whether a pull-request copy of the file-set half also runs, and which additional publish-facing fields the projection pins.

| Alternative | Why not chosen as primary |

**Fitness gates.** The stack adds no crate, so the crate figures (downloads, last release, stars, open issues, issue responsiveness, adopters) and the dependency-tree gates are `inapplicable` for the selected elements: they are subcommands of the toolchain the template already requires, plus a manifest key that toolchain reads. Recorded per gate: (1) license — no dependency is introduced, so nothing is added to the template's license surface; (2) MSRV — the stack's highest toolchain floor is cargo 1.94 (2026-03-05) for offline `--list`, and cargo 1.80 (2024-07-25) for the warning text, both below the floor the fixed policy implies against current stable; (3) advisories — no crate is adopted, so no RustSec page applies to a selected element, and the stack's `unsafe` exposure in the shipped artifact is zero; (4) platforms — the elements are toolchain commands plus `diff`, `tar`, `cmp` and `jq`; every result here is macOS-only, so Linux is unproven (see `## Engines`); (5) default features and async coupling — `inapplicable`, no crate is compiled against; (6) binary size and compile time — zero added to the template's artifact; the CI cost is the `cargo package` run the publish flow already performs. The gates that excluded the surveyed wrappers are recorded in the row above and in both raw reports.

**Reference implementations.** `PyO3/maturin` runs `["package", "--list", "--allow-dirty", "--manifest-path"]` and parses the result as the authoritative file set for Python source distributions (`src/source_distribution/mod.rs`, Opus-reported at HEAD 2026-09-10) — production evidence that `--list` output is parsed by tools, not only eyeballed. `clap-rs/clap` declares a workspace-level `include` inherited with `include.workspace = true`; `GitoxideLabs/gitoxide` declares `include = ["/src/**/*", "/LICENSE-*"]`. The counter-practice is real: `BurntSushi/ripgrep` uses `exclude`, and `serde` and `tokio` declare neither. Those four adoption facts are Opus-reported at HEAD and were not re-read here.

**Where the Rust design must differ from ts's.** ts parses JSON because npm offers it; Rust's stable output is a sorted plain-text list, so the assertion is a `diff` and is simpler rather than a workaround. ts greps `npm publish --dry-run` stderr for two known auto-correction strings; grepping Cargo's stderr is necessary but not sufficient, because excluding examples, tests or benches from a package is a legitimate design that produces the same warning shape — hence the scoped grep plus an authoritative target-set diff. ts's workflow comment states its dry run "never contacts the registry"; Cargo's `publish --dry-run` reaches the index instead, per Opus's probe observation, which this check did not reproduce.

No `BASELINE-REVIEW:` finding. The recorded source facts for F039 and F078 were confirmed at both pins, and this decision keeps their principle and their publish-time placement.

**Disagreement 1 — does Cargo have a silent-rewrite analogue to npm's `bin` auto-correction?** Codex says no undocumented silent correction exists: Cargo's manifest rewriting is documented, `Cargo.toml.orig` preserves the author's bytes, and the guard should therefore be a projection-equality check with an allowlist of documented transformations. Opus says yes: target pruning drops a target whose source is not packed, warning only. **Settled for Opus by this synthesizer's own reading of the pinned source and by reproduction**: `prepare_target_for_publish` warns and returns `Ok(None)` (`src/cargo/util/toml/mod.rs:3298-3316` at `797e8a9b`), and fault A produced `cargo package` exit 0, the pruning warning, and a packaged manifest missing `[[bin]] rsguard-serve`. Codex executed nothing in this run and did not reach the pruning path; its framing of Q2 as "documented normalization, not silent correction" is incomplete. Q2's half of the bundle is an active check.

**Disagreement 2 — what the metadata assertion should compare.** Opus asserts the target set; Codex asserts a wider publish-facing field projection plus a byte-compare of `Cargo.toml.orig`. **Merged**, because they are complementary and both cheap: the target-set diff is the verified core (it is what the pruning fault moves), and Codex's `Cargo.toml.orig` compare and field projection are adopted with the qualification in `## Empirical check` — executed on the healthy path only, discrimination not demonstrated, workspace inheritance untested, left for P03.

**Disagreement 3 — placement.** Opus recommends the file-set half in pull-request CI *and* the full guard at publish time; Codex recommends publish-time only, arguing that a pull-request copy adds maintenance pressure to every source change. **Settled for Codex's binding, with Opus's finding recorded**: the guard is bound to the publish verify job, matching the source precedent and coupling to nothing unresolved, while the pull-request copy is recorded as recommended hardening because R26 consumes no parameter and wiring a step into pull-request CI belongs to `ci-job-structure` (R11, unresolved), which lists every item that wires a check into CI and does not list R26. Opus's feasibility evidence stands and was reproduced: the listing runs offline without a registry, exit 0.

**Disagreement 4 — source citations.** Opus's Cargo citations (`src/workspace/parser/mod.rs:3116` and neighbours) are from `master`'s current layout and **do not resolve at the pin**: the tree at `797e8a9b` contains no `src/workspace/` path at all, and the same code lives at `src/cargo/util/toml/mod.rs`. The behaviour Opus describes is confirmed; its file and line citations are not portable to the toolchain the template will use. This decision cites the pin.

**Where the engines agree, and it held.** Both recommend `cargo package --list` diffed against a checked-in expectation; both reject the unstable JSON output under the stable-Rust constraint (confirmed, exit 101); both reject wrapper crates and Actions; both place the metadata check before the upload; both report no `CONFLICT:` and no `BASELINE-REVIEW:`. **Unproven, with what would prove it.**

1. **Linux.** Every result in this decision was produced on macOS 26.4 arm64. The fixed `target-os-matrix` includes `ubuntu-latest`, and no evidence for it exists in this run. What proves it: running the healthy pass and both injected faults on an `ubuntu-latest` runner in P03's CI and confirming the same three exit statuses and the same diffs.
2. **A green-path `cargo publish --dry-run`.** Not executed here (the check must not reach a publish endpoint) and not executed by Opus (its probe reached the index, then failed on an unpublished path dependency). What proves it: the verify job at P03's first tagged release, where the version is publishable and the index resolves.
3. **Discrimination of the `Cargo.toml.orig` compare and the wider field projection.** Executed once, healthy, single package. What proves it: P03 injecting a metadata fault (a changed `license` or `version` in a fixture archive) and confirming the projection diff fails, plus one run under the real workspace layout once R02 and R49 land.
4. **The target-set assertion in the addition direction.** Only removal was reproduced here. What proves it: a P03 case that packs a target the expectation does not list.
5. **The include+exclude and `package.build` warnings, and `--workspace --list` concatenation.** Read in the pinned source or taken from Opus, never triggered. What proves it: P03 exercising a manifest with both keys, a build script excluded from the package, and a multi-package workspace listing.
6. **Runner utility availability.** `jq` and `tar` on both GitHub-hosted images is Opus-reported, not re-verified. What proves it: the first CI run of the guard on each runner.
7. **Warning-string stability.** The scoped grep matches prose that Cargo may reword. What proves nothing can silently rot: the target-set diff, which survives wording changes; P03 should treat a grep miss as tolerable and a target diff as fatal.

**Design constraints P03 must carry, each from an observed result.** Abort the guard when `cargo package` exits nonzero, before extracting anything: a failed packaging run leaves the previous `.crate` on disk and an unguarded check reads it and reports the earlier package's targets (row 10). Read the packaged manifest from the `.crate`, never from `target/package/<pkg>-<ver>/`. Loop over publishable packages with `-p`. Keep the guard's own scratch files outside the repository being packaged — this check's first attempt put them inside and Cargo's dirty-tree detection failed the run for the wrong reason, which is exactly how a real guard would produce a false failure. Expectation files are per publishable package, and their contents depend on R02's topology and R49's target names.
