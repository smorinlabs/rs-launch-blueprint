### Principles and implementation

**Shared requirement, its source and agreement level.** One canonical, version-controlled statement of how to work in this repository, discoverable by whichever AI coding tool a contributor happens to use, with no second place where the same policy can drift; and, beside it, a repository-scoped greeting that tells a human what the project is and which commands to run. The first half is F197's principle (`docs/port/COMMONALITY.md:201`, `COMMON → REUSE`), already agreed and not re-decided here. The second half is the owner requirement recorded in the prompt's Context via D-024(6).

Two agreement levels are in play, and conflating them is the error the ts precedent invites:

| Concern | Agreement level | Must agree across py / ts / rs? |
|---|---|---|
| A single canonical instruction file exists and no second file restates its policy | architectural pattern | **Yes** — this is F197, already `COMMON → REUSE` |
| Which vendor rule paths are committed (`.cursor/`, `.windsurf/`, `.devin/`) | policy/mechanism | **No** — it may vary with each repository's contributor tooling and each vendor's current discovery behaviour |
| A repository-scoped welcome greets a human at session start | capability/standard, and an explicit owner requirement | **Yes** for the capability; the mechanism is per-tool |
| Which commands the welcome names | policy/mechanism, derived from F176 (`task-runner tool` = `just`, `COMMON → REUSE`) | **No** — each ecosystem names its own recipes |

That table is why the recommendation is *identical* to py (which ships neither spoke) and a *removal* relative to ts, without either repository being the winner by default: the removal is justified by the vendors' current documentation and by the practice evidence, not by py's agreement. py reached the same shape independently, in commit `fc8d944b7e439bb4e3f19aaf1b2bdf8da4292a57` — "docs(agents): make agents.md canonical; claude.md imports it; drop vendor rule files (#410)", pre-pin (Tier V, `git -C ~/c/py-launch-blueprint show --stat fc8d944`, 2026-09-10).

**Essential behaviours.** These are requirements the template must exhibit, recorded for P03 to prove. None has been observed on the rs template, which does not exist. B1 in particular is a requirement on third-party products, so it stays Tier D until P03 runs the check A5 describes.

- **B1.** A contributor's tool loads the repository's instructions without the contributor configuring anything.
- **B2.** Exactly one place holds a policy statement; every other file either points at it or does not exist.
- **B3.** A human opening a Claude Code session in this repository sees, once, what the project is and which commands to run.
- **B4.** No committed file can silently go stale relative to the commands or paths it names.

**Observable acceptance criteria.** A1 is F197's and is carried here only as the precondition R43 assumes; A2–A4 are R43's, and all four are for P03 to observe on the real template — none has been observed there, because the template does not exist.

- **A1.** `AGENTS.md` exists at the repository root, and `CLAUDE.md` contains an `@AGENTS.md` import and no independent policy statements.
- **A2.** `git ls-files` returns zero paths under `.cursor/`, `.windsurf/` or `.devin/`.
- **A3.** `.claude/settings.json` parses as JSON and `companyAnnouncements` is an array of exactly length 1.
- **A4a.** That single string names the repository and at least one `just` recipe.
- **A4b.** Every `just <recipe>` token the string contains appears in the output of `just --summary`.
- **A5.** Tier P, and not assertable in CI: opening the built template in Cursor, in Devin Desktop and in Devin CLI shows the root `AGENTS.md` in the agent's context; starting Claude Code in it shows the announcement to the human, both on a clean profile and on a profile that already sets `companyAnnouncements` at user or managed scope.

**What must agree versus what may vary.** Must agree: that exactly one file holds policy, that every tool reaches it, and that a human greeting exists. May vary: which vendor paths (if any) a given repository commits, and which recipe names its greeting lists. Naming the same recipe names in all three repositories would be a shared low-level value with no evidence supporting the same tradeoff in all three ecosystems, so this decision does not recommend one.

**Architectural alternatives, compared before any file was chosen.** Four designs are candidates for B1–B3. Each is assessed against the vendors' documented behaviour (Tier D), because none of them can be assessed by execution inside this programme.

| Design | How a vendor tool reaches the instructions | Files committed | Policy sources | Verdict |
|---|---|---|---|---|
| **D1. Hub-only** — root `AGENTS.md` plus `CLAUDE.md` importing it | Cursor, Devin Desktop and Devin CLI each *document* reading root `AGENTS.md` (Tier D); Claude Code documents reading `CLAUDE.md` | 2 | 1 | **Selected** |
| **D2. Hub + thin vendor spokes** (the ts shape) | Same as D1, plus one rule file per vendor whose body re-points at the hub | 2 + n | 1 policy file + n vendor frontmatter contracts | Not selected — the spoke buys nothing D1 lacks, and its own correctness is Tier P |
| **D3. Hub + substantive vendor rules** (the `surrealdb/surrealdb` shape) | Same as D1, plus vendor rules carrying their own content | 2 + n | n + 1 — **violates B2** | Excluded on principle. This is the shape py deliberately removed in `fc8d944` |
| **D4. Hub + nested `AGENTS.md`** for directory-scoped guidance | Cursor documents nested `AGENTS.md` as automatically applied and combined with parent directories; Devin documents a subdirectory `AGENTS.md` as a glob rule with an auto-generated `<directory>/**` pattern | 2 + k, all one format | 1 format, no vendor frontmatter | **Held in reserve.** This is the replacement for a glob-scoped rule file, and the answer to the workspace-shape argument |

D2 versus D1 is the real question, and D1 wins on three grounds, each stated at its own tier.

1. **The spoke instructs a tool to do what its documentation says it already does** (Tier D for the behaviour, Tier V for the documentation text). A body whose entire content is "read `AGENTS.md`" adds no instruction the hub does not already carry.
2. **The spoke is a second frontmatter contract that only the vendor controls, and its correctness is Tier P.** ts's `.cursor/rules/doc-template.mdc` writes `globs` as a YAML sequence (`- "docs/**/*.md"`), while Cursor's current page says "Use `globs` to scope a rule to specific files or directories. Separate multiple patterns with commas"; ts's `.cursor/rules/projectenv.mdc` writes `read rules ./doc-template.mdc` where the documented include form is `@filename`. Both file contents and both documentation strings are Tier V (re-read from the pin and from the live page on 2026-09-10). **Neither is evidence that current Cursor rejects those files** — that would require executing Cursor. They are recorded here exactly as Opus recorded them: *format drift observed against current vendor documentation, not verified by execution.* The point they establish is narrower and more useful than a breakage finding: a spoke's correctness can only ever be settled by running the vendor's product, so it can never be gated in CI, whereas the hub's format has no vendor frontmatter to drift.
3. **The directory-scoping argument is answered by the hub format, on the same documented basis (Tier D).** ts's `.windsurf/rules/justfile-rules.md` uses `trigger: glob` with `globs: Justfile` (Tier V, read from the pin). Both vendors now document nested `AGENTS.md` as providing directory scoping (D4, Tier D). It does not provide *single-file* scoping — but a root-level `Justfile`'s conventions land in the always-on root hub either way, and for a rule of roughly 30 lines the context saved by a glob trigger is negligible against the cost of a second policy source restating conventions F177 and F178 already record as `just`-native.

The one capability D1 gives up is the ability to hand a tool instructions the hub should not contain. The vendor's own current answer to that is a skill, not a rule file: "**To improve coding ability, speed of completion, and lower cost**, we highly recommend **using Skills instead whenever possible**. … **Rules and AGENTS should be kept as small as possible**" (Devin CLI rules page, Tier V, retrieved 2026-09-10). That is the documented escape hatch if a future need appears, and it is not this item's decision.

**Why the announcement is a separate mechanism and not a fourth spoke.** Claude Code exposes two session-start surfaces with different audiences, and they do not substitute for one another (all Tier V for the documentation text, retrieved 2026-09-10):

| Mechanism | Audience | What the documentation says |
|---|---|---|
| `companyAnnouncements` | **Human**, at startup | "Show your organization's announcements to users at startup. When you list more than one, Claude Code picks one at random for each session; on a person's very first launch it shows the first entry." Scope `Any file`; type array of strings; default unset |
| `SessionStart` hook → `additionalContext` | **Agent** | The string "passes … into Claude's context window", wrapped in a system reminder; a successful hook's "stdout is never shown in the transcript"; and the same page directs "For static context that doesn't require a script, use [CLAUDE.md](/docs/en/memory) instead" |

Only the first puts repository-scoped text in front of a human at session start, so the hook is the wrong tool for F199 by Anthropic's own guidance — even though `astral-sh/ruff` and `astral-sh/uv` are maintained Rust reference implementations of the hook path, because both use it for dynamic *agent* context, a different requirement (Tier V: `astral-sh/ruff`'s settings carry `hooks`, `enabledPlugins` and `extraKnownMarketplaces`; `astral-sh/uv`'s carry `hooks`; neither carries `companyAnnouncements`).

**Two documented semantics govern the announcement's shape, and both were re-read.** The settings page states "When you set the same list key … in more than one file, Claude Code combines the lists instead of picking one", exempting four model-list keys (`fallbackModel`, `modelPicker`, `availableModels`, `modelSettings`) of which `companyAnnouncements` is not one; and the reference states the random pick quoted above (Tier V, retrieved 2026-09-10). Chained, they give the consequence that governs the design: for a contributor whose organisation or user settings already set the key, the repository's welcome merges into that pool and is shown roughly one session in N, framed as a company message. The two design responses are (a) keep the repository's array at exactly one entry, so the template never multiplies the pool on its own, and (b) treat the welcome as a convenience and never as the only place a required instruction appears — anything a contributor must know belongs in `AGENTS.md`, which is loaded every session regardless.

**The MEDIUM question — `just` recipes, or `cargo` commands?** Name **`just` recipes**, plus `just --list` as the index; do not name raw `cargo` commands as a parallel vocabulary. Three reasons. F176 fixes `just` as the template's task-runner tool (`docs/port/COMMONALITY.md:180`, `COMMON → REUSE`). R42's resolved `package-manager-invocation` value settles that recipes invoke `cargo` subcommands directly with no provisioner prefix, so `cargo` is precisely the layer *beneath* the one the repository asks a contributor to use; naming it in the welcome teaches past the interface and duplicates the hub's command card in a third place. And a recipe name is checkable where a `cargo` command is not: `just --summary` enumerates recipes, so a welcome that names them can be gated against drift (A4b). The `just --list` pointer is carried from the Codex raw because it costs nothing and it keeps the welcome useful when the recipe set outgrows the string.

**The LOW question — staleness.** The announcement is the one member of this bundle with a real staleness risk, because it hard-codes recipe names P03 has not chosen. That risk is answered by making the check executable (A4b), not by omitting the welcome. The vendor-rule members' staleness risk is the opposite case: it is *not* checkable at all, since only the vendor's product can say whether a rule file still parses and still applies. That asymmetry — checkable drift kept, uncheckable drift removed — is the single principle that decides both halves of this bundle in opposite directions.
