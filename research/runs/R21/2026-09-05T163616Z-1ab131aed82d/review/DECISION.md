### Principles and implementation

**Shared requirement.** The contributors bot must open a pull request that can reach a mergeable state on its own — that is, whose required status checks report a conclusion without a maintainer intervening — using a credential the repository owner provisions once, and it must fail loudly rather than silently when no credential is provisioned.

**Source of the requirement and agreement level.** Ledger rows F060 (`COMMON → REUSE`) and F061 (`DIVERGENT`, this item) at `docs/port/COMMONALITY.md:66-67`; the TypeScript port decision D-022(11) ("branch-sync idempotency, bot commit, PR-not-push"); and the owner direction of 2026-09-04 in `docs/port/OWNER-REVIEW.md` ("For this one, we should model it on what PyLaunch Blueprint does"). The agreement level is **policy**. The mechanism is a YAML input and a repository secret; nothing about Rust, Python or TypeScript changes what a GitHub token can do, so a shared low-level value across py, ts and rs is justified here on evidence rather than taste, and an ecosystem-specific divergence would be accidental drift rather than a justified difference. What must agree across the three repos is the credential **class** — a user- or App-identity token, not the ambient job token. What may vary is the secret's name, whether the App is installed, and the trigger cadence (R07's, out of scope).

**Q1 — the one qualification this decision carries throughout, stated here in full.** No run of `contributors-please-action` with `secrets.GITHUB_TOKEN` supplied as `pat:` was executed by either engine or by this synthesis. Executing one would require creating a credential, registering or installing a GitHub App, and opening a pull request, all of which this programme's research phase forbids and this run's empirical check explicitly declined (log case 11). Every statement below about that configuration *aborting*, *failing at identity lookup*, or *returning `403`* is therefore an inference from two separately verified facts, and is marked **(Q1, predicted)** at each occurrence. The two facts are: the action's PAT path calls bare `GET <apiUrl>/user` with an `Authorization: Bearer` header and throws `GitHub token identity lookup failed: ${response.status}` on any non-ok response (`src/index.ts:432,439` at `3c6dbff9`, read in this run, log case 04); and bare `GET /user` is absent from GitHub's published list of endpoints an installation access token may reach, while `GITHUB_TOKEN` is itself an installation access token (log cases 07 and 08). The prediction is recorded as unproven in `## Engines` with the check that would prove it.

**Why O4 is not adopted, with each ground at exactly its evidence's width.**

1. *B3, documented.* GitHub documents that a `pull_request` event resulting from a `GITHUB_TOKEN`-created or -updated PR produces workflow runs in an approval-required state, cleared only by a writer clicking **Approve workflows to run** (log case 08, and the same carve-out on the `triggering-a-workflow` page Codex cites, log case 09). For a bot whose entire point is to run unattended, that converts every bot PR into a manual step. This ground is established from GitHub's current documentation retrieved in this run; it is not an executed run, and it does *not* say the checks never report.
2. *B1, predicted.* The configuration is expected to abort at credential resolution before any PR is attempted **(Q1, predicted)**.

Ground 1 alone excludes O4. The recommendation therefore does not depend on whether ground 2 is right — a point the Opus raw makes about its own reasoning and this synthesis endorses.

Two further observations that weaken ts's stated rationale without being load-bearing. The ts workflow's header comment at `cb1cbcb2` claims `pat` "uses the workflow's own GITHUB_TOKEN so the template works out of the box with zero extra setup" (quoted verbatim in log case 03). For a fork created in a personal account, GitHub's default is that workflows are **not** allowed to create or approve pull requests, so B2 needs a settings change before "zero extra setup" can hold; for a fork created in an organization, the setting is inherited from the organization and this run establishes nothing about its value (log case 10). Separately, py's own workflow comment at `b08bccfb` documents the sibling failure mode from the other direction — "`[skip ci]` suppresses the pull_request workflows behind main's required checks, leaving the bot PR permanently blocked" (quoted verbatim in log case 02) — which shows the repositories already treat "the bot PR's checks must actually run" as a requirement, not a preference.

This establishes what the suite is *configured* to pass. Whether any PAT lane has actually run, and with what result, depends on that repository's secrets and run history, which cannot be read without an authenticated token and was not read here.

**How the recommended design preserves each principle, and where an ecosystem would need something different.** O1 keeps the App as the preferred short-lived, installation-scoped credential (B4) exactly as both source repos already do, and reserves the long-lived secret for the case the App cannot cover. No ecosystem needs a different design, because no part of the mechanism touches a language toolchain. The Rust template differs only in *which* checks the bot PR must trigger — `cargo fmt --check`, `clippy`, `cargo test` across the fixed `target-os-matrix` — which strengthens B3's importance rather than weakening it, **conditional on P03 or the owner actually making those checks required on the default branch**; the template does not exist yet and this decision does not assume that setting (it is listed for P03 in `## Engines`).

**Landscape, three bins.** *Built-in / first-party*: the ambient `secrets.GITHUB_TOKEN`; the repository/organization setting **Allow GitHub Actions to create and approve pull requests**; `actions/create-github-app-token`. *Established industry standard*: a dedicated fine-grained PAT in a repository secret; App credentials primary with a PAT fallback (the shape both source repos already carry). *Up-and-comer*: first-party App-token minting displacing third-party equivalents — `tibdex/github-app-token`, the former third-party default, is archived (Opus raw, authenticated retrieval 2026-09-10) — and App-only, zero-fallback bot workflows. The two engines agree on the bin *structure* and on which credential class sits in each: `GITHUB_TOKEN` first-party, a dedicated PAT (or App-primary-with-PAT-fallback) the established standard. They differ on the up-and-comer entries — Codex puts the fine-grained-versus-classic PAT distinction there, Opus puts first-party App-token minting and App-only workflows there — and the map above is the union, not a claim that they produced identical bins. Authorities: GitHub Docs (sole authority for `GITHUB_TOKEN` and installation-token semantics, four pages retrieved by this run); the action's own README, `action.yml` and `src/` at the pinned tag (sole authority for what each credential value does in this action, read by this run); `peter-evans/create-pull-request` and `release-plz` as the widely-used community and Rust-native references (carried from the Opus raw).

**Fit for this template, per target shape.** The credential is the same for all three shapes, and that uniformity is part of the argument: nothing about the shape changes what a token can do. What differs is how much the bot PR depends on B3, and all three depend on it. *CLI*: if the default branch carries `cargo fmt --check`, `clippy` and `cargo test` across the fixed matrix as required checks — the conditional stated above, which P03 or the owner settles, not this research — then under O4 each bot PR's runs would wait behind **Approve workflows to run** until a writer clicks it. *Library*: adds semver and docs checks to the same required set, so the dependence on B3 only increases; the library shape also makes the "consumer forks the template" case more common, which is the population that may be unable to install an organization-level App — the argument for keeping a fallback rather than going App-only. *Web service*: adds the heaviest checks (integration, OpenAPI conformance); same conclusion, more strongly, and no web-specific credential requirement, since the bot job never touches the service. Across all three the documentation obligation is identical: one either/or setup step, "install the App **or** set one repository secret".

**Answers to the prompt's remaining questions.** *HIGH (is `GITHUB_TOKEN` sufficient with the declared `permissions:` grants, without any consumer setup step?)* — No, on the documented ground: even where PR creation is permitted, the resulting `pull_request` runs are approval-required (log case 08), and for a personal-account fork PR creation is itself disallowed by default (log case 10). Whether this action would even reach PR creation with that token is **(Q1, predicted)** to be no. *HIGH (what capability does a dedicated PAT provide that `GITHUB_TOKEN` cannot, and does this PR need it?)* — Triggering downstream `pull_request` workflows without an approval gate, and, for this action specifically, resolving a committer identity through `GET /user`. The bot PR needs the former whenever the default branch requires status checks; it does **not** need protected-branch bypass, and the workflow must not grant it. *MEDIUM (security trade-off)* — a long-lived PAT versus the ambient, automatically-scoped, automatically-expiring job token is a real cost, accepted and bounded below. *LOW (does a "zero extra secret" story reduce first-run friction?)* — no adopter-feedback dataset comparing template setup guides was found by either engine, and none is manufactured here; recorded as an evidence gap. What can be said without such a dataset: the ts sentence describes zero setup for a configuration that, for a personal-account fork, needs a repository-settings change regardless (log case 10), so the comparison is one documented step against one documented step plus one undocumented one.

**Tradeoffs — what O1 gives up.** *Versus O2 (App-only).* O1 keeps a long-lived credential in the template's documented setup surface; a fine-grained PAT is owner-scoped and revocable but does not rotate the way an installation token does, and a public template's consumers cannot be assumed to follow least-privilege PAT hygiene. Accepted because the PAT is used only when the App is absent, the recommended grants are three repository-scoped permissions rather than a classic `repo`-scoped token, and the alternative leaves App-less consumers with no working path; bounded further by documenting a machine account and an explicit expiry. *Versus O3.* Nothing material: O3's short-lived token is already what O1's primary App path uses, and O3 cannot serve as the fallback. O1 gives up one indirection layer that would have to be pinned and updated. *Versus O4 (the ts shape).* The literal "zero repository secrets" onboarding sentence — traded for a setup story of one either/or step. This decision does not claim that one step is the *complete* setup for every consumer: the repository's **Allow GitHub Actions to create and approve pull requests** setting is documented as controlling whether `GITHUB_TOKEN` can create and approve pull requests (log case 10), and whether it also constrains a PAT-authored PR was not established here — item 5 of what P03 must validate.
