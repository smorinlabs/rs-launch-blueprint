### Landscape

This item selects a GitHub Actions authentication pattern, not a Rust crate. The field map is: **built-in/first-party** — the repository-scoped, per-run `GITHUB_TOKEN`; **established industry standard** — a GitHub App installation token or a dedicated repository secret containing a fine-grained PAT; **up-and-comer/conditional** — a fine-grained PAT where an existing organization policy or account type cannot use it, leaving a classic PAT as a compatibility fallback. GitHub recommends fine-grained PATs over classic PATs where possible, and directs workflows that need capability unavailable to `GITHUB_TOKEN` to an App installation token or a repository-secret PAT. ### Principles and implementation

The shared requirement is an idempotent contributors update that commits a generated branch and opens or updates a pull request rather than pushing generated content to the default branch. Agreement is at the **architectural-pattern and policy** level: use `contributors-please-action` in `mode: pull-request`, grant only the required `contents`, `pull-requests`, and `issues` writes, prefer an installed GitHub App, and retain a functional fallback for repositories without that App. F060 establishes the shared pull-request pattern; F061 is the unresolved credential-source setting. [F060/F061 ledger, retrieved 2026-09-05](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/COMMONALITY.md) · [`contributors-please-action` v1.3.9 README, retrieved 2026-09-05](https://github.com/smorinlabs/contributors-please-action/blob/3c6dbff9ef21190aa1f63b3c400ed4f0ab404ac1/README.md)

The action documents that App credentials win when both App credentials and `pat` are present, and that `pull-request` mode pushes/updates a bot branch, opens/updates a PR, and labels it. The recommended architecture therefore keeps the App path first and gives `pat` a dedicated, least-privilege fine-grained PAT secret named `CONTRIBUTORS_PLEASE_PAT`. This is not a Rust library choice: Cargo figures, dependency-tree MSRV, RustSec, `unsafe`, feature coupling, binary size, compile time, and Ubuntu/macOS crate CI are **inapplicable** because no crate is selected or introduced. The resulting workflow itself is GitHub-hosted and OS-independent; its configured target matrix remains the fixed `ubuntu-latest, macos-latest`, while this particular scheduled/push job can run on `ubuntu-latest`. [Action credential/mode documentation, retrieved 2026-09-05](https://github.com/smorinlabs/contributors-please-action/blob/3c6dbff9ef21190aa1f63b3c400ed4f0ab404ac1/README.md) · [fixed parameters, retrieved 2026-09-05](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/PARAMETERS.md)

The significant alternatives are not replacement Rust libraries. `GITHUB_TOKEN`, with `contents: write` and `pull-requests: write`, is sufficient to create or update a PR in the repository that runs the workflow. However, GitHub now creates the resulting `pull_request` workflow runs in an approval-required state; a writer must approve them. A GitHub App installation token or PAT instead permits those PR workflows to run automatically. This contributor PR needs that latter capability if required checks are expected to report without a human approval; it does not need protected-branch bypass, and the workflow must not grant it. [GitHub event semantics, retrieved 2026-09-05](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow) · [`create-pull-request` token guidance, retrieved 2026-09-05](https://github.com/peter-evans/create-pull-request/blob/main/README.md)

Minimal realistic example: a workflow with `permissions: {}` at top level, one `contributors-please` job re-granting exactly `contents`, `pull-requests`, and `issues` as `write`; action inputs include App ID/private key and `pat: ${{ secrets.CONTRIBUTORS_PLEASE_PAT }}`, `mode: pull-request`, and generated-file `paths-ignore`. The maintained py workflow is the reference composition. Proposed acceptance: install the App in a disposable repository, then temporarily withhold its credentials and invoke the workflow with the dedicated PAT; assert the action output says the PAT path was selected, one `contributors-please/update` PR exists, and its `pull_request` checks start without manual approval. No live GitHub workflow was run in this research. ### Excluded by gate

No crate candidate exists, so crate license, MSRV, RustSec advisory, `unsafe`, platform, feature, binary-size, and compile-time gates are inapplicable. The ambient-token pattern is excluded as the dominant fallback because it fails the functional gate of autonomous required-check execution after it creates/updates the bot PR: GitHub places resulting `pull_request` workflow runs in approval-required state. ### Up-and-comers

Fine-grained PATs are the preferred PAT form, with one-repository and specific-permission restrictions, but are conditional where organization policy, outside-collaborator status, or an unsupported API capability prevents their use. A classic PAT is then a documented compatibility fallback, not the preferred template instruction; classic PATs can reach all repositories available to their owner and GitHub advises considering `GITHUB_TOKEN` first. ### Recommendation

Model rs-launch-blueprint on py-launch-blueprint: keep App credentials first and set `pat: ${{ secrets.CONTRIBUTORS_PLEASE_PAT }}`. Document a fine-grained, repository-limited PAT with `contents: write`, `pull-requests: write`, and only `issues: write` if the action continues to apply its pending label. State that the secret is required only while the GitHub App is not installed, but that it is intentionally retained so the fallback produces a PR whose checks start automatically. This implements the owner’s direction and avoids treating ts’s zero-secret story as sufficient when its bot PR needs required checks. [owner-reviewed source pattern, retrieved 2026-09-05](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/.github/workflows/update-contributors.yml) · [GitHub token-event behavior, retrieved 2026-09-05](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow)

### Ranked runner-up

`secrets.GITHUB_TOKEN` is the runner-up. It wins only when the template’s explicit priority is first-run, zero-secret setup and maintainers accept approving each generated PR’s `pull_request` workflow runs, or there are no PR checks to run. The declared permissions are sufficient for the PR creation itself, subject to the repository/organization allowing GitHub Actions to create PRs. [`create-pull-request` workflow-permission and token guidance, retrieved 2026-09-05](https://github.com/peter-evans/create-pull-request/blob/main/README.md) · [GitHub event semantics, retrieved 2026-09-05](https://docs.github.com/en/actions/how-tos/writing-workflows/choosing-when-your-workflow-runs/triggering-a-workflow)

### Tradeoffs

The recommended dedicated secret adds consumer setup, secret rotation, and an identity/permission-management obligation. Unlike the automatically provided `GITHUB_TOKEN`, a PAT is tied to its owner; a fine-grained PAT limits that blast radius but still needs expiry and renewal. The gain is automatic bot-PR workflow execution and a fallback that remains usable if the App is not installed. A GitHub App-only design reduces PAT risk further because installation tokens expire after one hour, but it removes the documented fallback and therefore does not satisfy the requested credential-fallback pattern. [GitHub PAT guidance, retrieved 2026-09-05](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/creating-a-personal-access-token) · [GitHub App token lifetime, retrieved 2026-09-05](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
