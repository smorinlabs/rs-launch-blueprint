### Principles and implementation

**Shared requirement.** First-party shipped source must be screened for security-relevant defects beyond what the linter's default rule set catches. Source: py's `bandit` gate (`.github/workflows/lint.yml`, `[tool.bandit]`) and ts's deliberate non-adoption with CodeQL backstop (D-014(5)); owner direction 2026-09-04 ("Make sure there's a security scanner", `docs/port/OWNER-REVIEW.md`). **Agreement level: capability, not a shared tool.** Py and ts already diverge on mechanism, and the owner asked for scanner coverage, not for one scanner everywhere. What must agree: the template's first-party source is screened by an automated security analyzer whose findings gate or report before release. What may vary: the analyzer, its tier, and its configuration.

**Essential behaviors.** B1: the screen covers bandit-mappable defect classes that survive translation into idiomatic Rust. B2: a slow full-tree scan does not block per-commit flow (py's pre-push rationale, F115). B3: findings are actionable at the template's scale (low false-positive cost on a small tree). B4: the screen reproduces in CI on `ubuntu-latest` and `macos-latest`.

**Bandit-class mapping (why the residual is thin).** `eval`/`exec` injection, pickle-style unsafe deserialization, and SQL string-formatting injection have no idiomatic-Rust equivalent (no `eval`, opt-in `serde`, typed query builders); `shell=True` injection is structurally absent because `std::process::Command` executes literal argv without a shell (established in R64's evidence); hardcoded credentials fall to R17's adopted TruffleHog secret scan; `assert`/`try-except-pass` style rules are ordinary clippy territory (R28). What remains for a dedicated first-party scanner — command-argument handling, path traversal, crypto-misuse logic, log injection, lifetime bugs — is exactly what the adopted CodeQL `security-extended` suite already screens at CI (R16 names the Rust delta: `rust/log-injection`, `rust/access-after-lifetime-ended`). No `BASELINE-REVIEW:` finding is emitted: F114/F115 stand as `DIVERGENT`/`py-only`; no inherited mechanism is challenged.

**Architectural alternatives compared.** (1) **No standalone scanner** (recommended): R06 `forbid` proves zero first-party `unsafe` at compile time, assumed R28 clippy covers lint-class rules, adopted R16 CodeQL covers first-party SAST at CI, adopted R17 TruffleHog covers secrets, pending R13 covers the dependency tree. Zero new moving parts. (2) **`cargo-geiger`**: counts `unsafe` in first-party code and dependencies — but first-party output is definitionally empty under R06 `forbid` (the compiler rejects what geiger would count), and R06 already records geiger as out of scope for the unsafe mechanism (citing open issue `geiger-rs/cargo-geiger#539`, which reports geiger does not recognize the `[lints]`-table form) — still `open` as of 2026-09-26 (created 2025-04-11, 3 comments; [issue](https://api.github.com/repos/geiger-rs/cargo-geiger/issues/539), retrieved 2026-09-26). Its dependency-tree census belongs to R13's SCA lane, not to F114. (3) **Semgrep**: a real AST scanner with Rust support, but a second SAST engine alongside adopted CodeQL, distributed outside Cargo (no crates.io crate), with Rust rule depth now verified: the community ruleset holds exactly 10 Rust security rules (`rust/lang/security/`: args, args-os, current-exe, insecure-hashes, reqwest-accept-invalid, reqwest-set-sensitive, rustls-dangerous, ssl-verify-none, temp-dir, unsafe-usage — each a `.yml` rule plus a `.rs` test, and `rust/lang` contains no other directory; [listing](https://api.github.com/repos/semgrep/semgrep-rules/contents/rust/lang/security), retrieved 2026-09-26). (4) **SCA tools (`cargo-audit`/`cargo-deny`) as the analogue**: rejected — different threat class (known-vulnerable dependencies vs first-party defects), and R13 owns that lane; adopting them here would pre-empt R13.

**Maturity, dependability, performance, integration cost.** Geiger is maintained (0.13.0 on 2025-08-31, repo pushed 2026-09-14) but functionally vacuous here; Semgrep is maintained (pushed 2026-09-25) but redundant here; Rudra/MIRAI are archived. No workload-matched latency/throughput benchmark for any candidate was found, so no fastest claim is made; scan-speed tiering (F115) is moot with no tool adopted. Integration cost of adoption would be one install plus one CI/hook slot per tool plus ongoing finding triage; integration cost of the recommendation is zero files.

**Minimal realistic example and acceptance check (proposed, not executed).** Fixture: a Cargo workspace whose root sets `[workspace.lints.rust] unsafe_code = "forbid"` (R06's reference shape) plus one seeded `unsafe` block. Expected: `cargo build` fails on the seed (R06 mechanism, already executed by R06); `cargo geiger` on the same tree reports no first-party `unsafe` beyond what the compiler rejected — demonstrating vacuity rather than value; CodeQL `security-extended` per R16's config runs at CI (already executed by R16 against its own fixture). This run executed no fixture: the only executed commands were read-only endpoint GETs and local `rustc/cargo --version` (1.98.1, retrieved 2026-09-26). R16's revision-4 status (proposal to validate in P03) is inherited: template-level composition is unproven until the template exists.

##### Principles and implementation

A bandit analogue would pattern-match first-party source for vulnerability classes. Geiger does something else: it walks the crate and its dependencies counting `unsafe` blocks, functions, traits, impls and macros — an audit-scoping census, not a finding generator. The maintainer states this directly: "This tool is not meant to advise directly whether the code ultimately is truly insecure or not. The purpose of cargo-geiger is to provide statistical input to auditing" ([README](https://api.github.com/repos/geiger-rs/cargo-geiger/contents/README.md), retrieved 2026-09-26), installed by `cargo install --locked cargo-geiger` (or a `vendored-openssl` feature build, or prebuilt binaries) and invoked as bare `cargo geiger` with no config file. Under R06's adopted `forbid`, the first-party half of that census is vacuous: the compiler rejects every `unsafe` block geiger could count, so running geiger over template-owned code can only ever print zero. R06 additionally records geiger as unfit for its mechanism because open issue #539 reports geiger misreads the `[lints]`-table form (`No unsafe usage found, missing #![forbid(unsafe_code)]`) — still `open` as of 2026-09-26 (created 2025-04-11T11:20:51Z, 3 comments; [issue](https://api.github.com/repos/geiger-rs/cargo-geiger/issues/539), retrieved 2026-09-26). Semgrep does match vulnerability patterns over Rust, but as a second SAST engine it duplicates the adopted CodeQL suite's role while adding a non-Cargo distribution (pip/binary) and a separate rule-selection surface (`.semgrep.yml` / registry rulesets); the community Rust security ruleset is exactly 10 rules (`rust/lang/security/`, with `rust/lang` holding nothing else; [listing](https://api.github.com/repos/semgrep/semgrep-rules/contents/rust/lang/security), retrieved 2026-09-26) — real but thin beside Semgrep's first-tier languages. Neither candidate preserves a principle the adopted composition drops: compile-time memory-safety policy (R06), lint-class rules (R28), first-party SAST (R16), secrets (R17) and dependency advisories (R13) each already have an owner.

##### Dominant choice

There is no dominant standalone first-party source security scanner in Rust — that is the finding. The ecosystem's dominant security tooling is dependency-oriented (`cargo-audit`, `cargo-deny`) plus CI-level SAST (CodeQL, adopted by R16) plus clippy built-ins (R28's lane). Geiger's 53,864 recent downloads against audit's 3,546,867 and deny's 1,721,281 (`crate.recent_downloads`, retrieved 2026-09-26) quantifies how little of the ecosystem's security effort flows through a standalone first-party scanner. The dominant choice for this member is therefore the composition, not a tool.
