### Principles and implementation

The shared requirement is **an explicit, safe human decision at a terminal without contaminating machine-readable stdout**.  Its agreement level is an architectural pattern and policy, not a shared crate or identical command result.  F276, F279, and F280 require the three interaction capabilities; F275 requires a common `--no-input` switch; F277 and F278 remain plain mutation flags.  [Ledger F275–F280](../../../../../docs/port/COMMONALITY.md) and [pinned Python confirmation implementation](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/src/py_launch_blueprint/cli/options.py) (retrieved 2026-09-16).

The Rust architecture is: command code performs a `stdin.is_terminal() && stderr.is_terminal()` and `--no-input` gate; a small CLI-only `Prompter` adapter then calls `dialoguer`; library and web-service entry points accept already-decided values and never invoke it.  This avoids coupling an async web runtime to a synchronous terminal UI, preserves stdout for command results, and makes scripted tests substitute a deterministic adapter.  `dialoguer` itself also rejects a nonterminal `Term`, but that error is not an application policy or a usable `--yes` diagnostic.  [Rust `IsTerminal`](https://doc.rust-lang.org/std/io/trait.IsTerminal.html) and [dialoguer `Confirm::interact_on`](https://docs.rs/dialoguer/0.12.0/dialoguer/struct.Confirm.html#method.interact_on) (retrieved 2026-09-16).

The proposed shapes are: `Confirm::new().default(false).interact_opt()` for destructive actions; `Input::<String>::new().default(current).validate_with(...) .interact_text()` for each `config init` value; and `MultiSelect::new().items(display_labels).interact_opt()` followed by index-to-domain-value mapping.  `MultiSelect` intentionally returns indexes rather than `Choice { name, value }` objects, so the adapter owns a parallel `Vec<Choice<T>>`; this preserves the TypeScript name/value principle without putting unstable display text in the domain type.  All three default methods render on stderr, and the `*_on` variants explicitly accept a `console::Term`, satisfying the output-stream requirement.  [dialoguer `Confirm`](https://docs.rs/dialoguer/0.12.0/dialoguer/struct.Confirm.html), [Input](https://docs.rs/dialoguer/0.12.0/dialoguer/struct.Input.html), and [MultiSelect](https://docs.rs/dialoguer/0.12.0/dialoguer/struct.MultiSelect.html) (retrieved 2026-09-16).

The main alternative is no prompt crate.  It avoids a dependency but makes terminal mode, redrawing, key decoding, cancel handling, and validation retry template-owned behavior; that recreates a mature terminal UI surface for three commands.  `inquire` is a credible richer alternative: it returns selected owned values and supports validators, but its default feature set adds crossterm, macros, one-liners, and fuzzy matching, and its normal API uses its internally constructed terminal rather than `dialoguer`'s direct `Term::stderr()` call shape.  [inquire manifest](https://github.com/mikaelmello/inquire/blob/v0.9.4/inquire/Cargo.toml) and [inquire `MultiSelect`](https://docs.rs/inquire/0.9.4/inquire/struct.MultiSelect.html) and [inquire terminal source](https://github.com/mikaelmello/inquire/blob/v0.9.4/inquire/src/terminal/crossterm.rs) (retrieved 2026-09-16).

No like-for-like benchmark was found or run.  Prompt latency is dominated by human input, so no throughput claim follows from download counts; the relevant cost is dependency and compile footprint.  With `default-features = false`, `dialoguer`'s direct dependency is `console`, whereas its default `editor` and `password` features add optional dependencies not needed by this item.  [dialoguer manifest](https://github.com/console-rs/dialoguer/blob/v0.12.0/Cargo.toml) (retrieved 2026-09-16).

BASELINE-REVIEW: F360 — noninteractive commands must not silently widen an interactive choice — replace TypeScript's select-all fallback with refusal unless an explicit documented all-selection flag is supplied; Python already refuses unless `--yes`, while TypeScript selects every fetched project — evidence: [py pin `options.py`](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/src/py_launch_blueprint/cli/options.py), [ts pin `projects.ts`](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/src/commands/projects.ts), and [Divergence Analysis R61](../../../../../docs/port/DIVERGENCE-ANALYSIS.md) (retrieved 2026-09-16).

**Observable acceptance criteria (proposed, not executed).** An interactive CLI renders every prompt to stderr and leaves stdout byte-clean; `--yes` returns before confirmation; `--no-input` or either non-TTY refuses a prompt-required operation with an actionable diagnostic; an empty submitted multi-select is a deliberate no-op; a cancelled prompt is surfaced as a typed adapter error for R67; input validation displays an error and retries; the library and web service have no dependency on `dialoguer`.  The same noninteractive refusal policy should be the future harmonized behavior for py, ts, and rs; it is a follow-on change for py/ts, not a claim about their current implementations.  [R61 prompt](../inputs/prompt.md) and [R67 ledger dependency](../../../../docs/port/COMMONALITY.md) (retrieved 2026-09-16).

Adopt one optional CLI-only dependency: `dialoguer = { version = "0.12.0", default-features = false }`.
