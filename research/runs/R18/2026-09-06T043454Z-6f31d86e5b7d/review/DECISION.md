# R18 — ai-assisted-review-workflows (bundle, Deep) — decision (revision 3, 2026-09-10)

## Decision

**Status.** This decision is a **proposal to be validated in the implementation phase against the real template**. `rs-launch-blueprint` has no `.github/workflows/` tree, no Rust code and no configured credential today; P02 is research and P03 builds the template, and P03's CI is what proves or disproves what is recorded here. A recommendation that does not survive implementation is **revised against this recorded research**, not researched again from scratch. Nothing below claims owner acceptance: the owner has reviewed R01 only.

**Recommendation.** Ship **both** workflows, as **one bundle**, from `anthropics/claude-code-action` at **`v1.0.220`** (annotated tag `020e931323e467e00b803ad64e03410d3796b8f7` → commit `19dda84776b3518d98b8798e591daee763049ed3`, resolved 2026-09-10), **inert by default** in a downstream fork behind a repository variable (the design's intent; that an unconfigured repository yields a `skipped` job rather than a red check is **U2**, unproven here), with `pull-requests: write` on the review job, **workload identity federation** as the credential path, and — new at revision 3 — **an author-trust prefilter on the assistant lane** and **a `draft == false` clause on the review lane**:

| File | Trigger | Job-level guard | Permissions | Action inputs |
|---|---|---|---|---|
| `.github/workflows/claude-code-review.yml` | `pull_request: types: [opened, ready_for_review, reopened]` | `vars.ENABLE_CLAUDE_REVIEW == 'true'` **and** `py`'s fork guard **and** both `py` bot guards, unchanged **and** `github.event.pull_request.draft == false` (**new at revision 3**) | `contents: read`, `pull-requests: write`, `issues: read`, `id-token: write` | three `anthropic_federation_*` identifiers from `vars.*`; `plugin_marketplaces: 'https://github.com/anthropics/claude-code.git'`; `plugins: 'code-review@claude-code-plugins'`; `prompt: '/code-review:code-review … --comment'` |
| `.github/workflows/claude.yml` | `issue_comment: [created]`, `pull_request_review_comment: [created]`, `issues: [opened, assigned]`, `pull_request_review: [submitted]` | `vars.ENABLE_CLAUDE_ASSISTANT == 'true'` **and** `py`'s four-clause `contains(…, '@claude')` condition **and**, on each of those four clauses, `contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.<comment\|review\|issue>.author_association)` (**new at revision 3**) | `contents: write`, `pull-requests: write`, `issues: write`, `id-token: write`, `actions: read` | the same three federation identifiers; `additional_permissions: actions: read`; **no** `prompt:` input (omitting it selects interactive mode — `docs/faq.md` at `v1.0.220`: "**Without `prompt` input**: Runs in interactive mode - waits for @claude mentions in comments", `action-docs-quotes-v1.0.220.log`) |

**Why the assistant lane gains an author-trust prefilter, stated here because it is the security case.** The `vars` enable flag protects a **downstream fork**, where it is unset. It cannot protect the **origin repository**, where it is `true` by construction, the federation identifiers are configured, and strangers can comment on a public template. Upstream issue `anthropics/claude-code-action#1068` — "Default workflow template missing author trust gate — secrets exposed on public repos", open since 2026-03-18, labels `bug`, `documentation`, `area:permissions`, `p1`, author `NONE`, 0 comments, `updated_at` 44 seconds after creation (`issue-1068.log`) — names three exposures of the unprefiltered `if:` and asks for exactly this clause. Revision 2 recorded that issue only as a comment count. Read in full, its three exposures divide as follows against the recommended configuration:

| `#1068`'s exposure | Answered by federation? | Answered by the enable flag on the origin repository? | Answered by the revision-3 prefilter? |
|---|---|---|---|
| The job starts and consumes runner minutes | No | No | **Yes**, for any commenter outside `OWNER`/`MEMBER`/`COLLABORATOR` — **U12**, not observed |
| `secrets.ANTHROPIC_API_KEY` / `secrets.CLAUDE_CODE_OAUTH_TOKEN` reach the runner | **Yes** — there is no such secret under federation | No | Moot under federation |
| An OIDC token is obtainable (`id-token: write`) | **No** | No | **Yes**, same qualification |

The third row is the correction that matters, and it revises a claim `opus` made and revision 2 carried: federation was recorded as a mitigation for `#1068`, and it answers only the second row. `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_URL` are present in the runner environment from the moment a job with `id-token: write` starts, and the 2026-06-01 GMO Flatt Security disclosure describes them as "the credentials required to request that OIDC token, so an attacker who obtains them can replicate the entire token exchange process" — the exchange whose output is a Claude GitHub App installation token with write access to contents, issues, pull requests and workflows (`flatt-disclosure-2026-06-01.log`). Federation changes which credential is worth stealing; it does not remove the one the published chain actually steals. **The prefilter is the only control in this record that acts before the job starts**, which is why it is adopted rather than offered.

**Ranked runner-up, with the conditions under which it wins.** Ship **neither** workflow and publish a documented opt-in recipe instead (the `codex` and `doxa-openai` position). It wins on any of three owner judgements. Two are the ones revision 2 recorded: the owner declines recurring third-party spend on the origin repository, or declines shipping a vendor-AI exemplar inside a public template tree. **The third is added at revision 3 and is the one the judgment audit asked to see argued**: the owner declines the residual prompt-injection exposure of a **write-capable assistant lane on a public repository, reachable from text an OWNER, MEMBER or COLLABORATOR writes** — because a trusted author routinely quotes untrusted content (pasting an issue body, a fork pull request's diff, a stack trace) into a comment, and neither the prefilter nor any action-side check distinguishes a trusted author's own words from untrusted text that author pasted. The researcher who published the chain states the general form of that residual plainly: "The permission model around Claude Code isn't hardened enough to safely handle untrusted input… at the time of writing, I have reported around 50 separate vulnerabilities to Anthropic that allow attackers to bypass the permission system and execute arbitrary commands in Claude Code" (`flatt-disclosure-2026-06-01.log`). That residual is **not** the published chain — see the exposure analysis under fitness gate 3, which finds the recommended configuration outside every phase of it — but it is a live class, and it is an owner risk decision, not an engineering-fitness one.

The runner-up's *other* stated grounds — that a public template cannot supply a downstream consumer's credential, and that an unconfigured fork would get a red check — are what the enable flag is **designed** to answer, and the evidence gathered here supports that design **syntactically, not yet at runtime**. Precisely what the checks establish (see `## Empirical check`, `contexts-availability.log` and `actionlint.log`): a job-level `if:` **may** reference the `vars` and `github` contexts and **may not** reference `secrets`, so both a credential-independent enable flag and an `author_association` prefilter are expressible at the job level at all. Whether an unset variable makes the job **`skipped` rather than failed** is a GitHub *runtime* outcome that no check here executed; it is **U2**. If the owner funds only one member, `claude.yml` alone is more defensible than `claude-code-review.yml` alone on spend, because only the review lane's spend is driven by repository traffic rather than by a human asking — but note that `claude.yml` is also the lane carrying the wider permission grant and the exposure analysed above, so the spend ranking and the security ranking point in opposite directions and the owner is choosing between them.

**Ledger rows settled.** `F051` (AI-assisted PR code review workflow) and `F052` (AI assistant workflow triggered by @mention comments), `docs/port/COMMONALITY.md:57-58`, both `py-only`, both `DIVERGENT`, both bundled to R18. ### Principles and implementation

**Shared requirement, source, agreement level.** The requirement behind `py`'s two files is: *every pull request receives a first-pass automated review before a human reads it, and a maintainer can summon an agent into an issue or review thread without leaving GitHub.* Its source is the `py` implementation at pinned commit `b08bccfb55d05f15e46a83b52c5660b1881d19f5` (both files read verbatim, `source-repos-pinned.log`) plus ledger rows F051/F052.

The agreement level is **policy or mechanism**, the third row of the agreement-level table in the design spec §2 (`docs/superpowers/specs/2026-09-01-rs-port-research-program-design.md`), which defines it as "Any deliberately shared value, protocol detail or tool, with its owner decision or evidence", varying in "Only the aspects outside that agreement; low-level choices can be shared when that level is intentional". The spec presents the three levels **unordered**, and no ranking among them is claimed here. Revision 2 called this level "the weakest of the three levels in `docs/port/README.md`"; that was wrong twice over and is withdrawn — `docs/port/README.md` mentions "agreement level" exactly once, at line 56, in a passing clause about A5 adjudication, and carries no list of the levels and no ranking; and spec §2's definition allows the *narrowest* variation of the three, not the widest.

The assignment is argued from what §2 says rather than from a rank. §2 requires that a policy-or-mechanism agreement carry "its owner decision or evidence". There is no owner decision registering these two workflows as a shared value, and the evidence in `## Context` shows the sources already disagree. Three observations place the requirement at this level rather than at "capability or standard" or "architectural pattern":

1. `ts-launch-blueprint` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00` ships eight workflow files, none AI-related, and zero paths under `.github/` matching `claude` (`source-repos-pinned.log`: the `ls-tree` listing the eight files exits **0**; the `ls-tree … | grep -ci claude` that returns the zero count exits **1**, which for `grep -c` *is* the zero-match result — see check 6). A capability-level or pattern-level agreement would already be violated by one of the three siblings; a policy-or-mechanism agreement without a registered owner decision is exactly what an unmatched sibling looks like.
2. Nothing in the capability is ecosystem-shaped, so there is no architectural pattern whose fitness in Rust could be the thing that must agree. The action reads a diff and posts comments; the diff being Rust changes no mechanism. There is no Rust analogue to select and no Rust idiom to honor.
3. The reviewing entity is a paid third-party service reached with an organization credential. Whether to spend it here needs "its owner decision or evidence" in §2's words, which is precisely why "`py` does it" cannot settle it.

**What must agree; what may vary.** What must agree across `py`, `ts` and `rs` is the **guard contract**, because it is simultaneously a security property and a correctness property and is ecosystem-neutral. It has four clauses, and clause (a) is scoped at revision 3 to the lane it actually binds:

- (a) **The review lane** — the only lane triggered by a `pull_request` event — never runs on a pull request from a fork, on the ground that a fork run cannot obtain the credential and could only fail. That is **a platform runtime behaviour that no check here executed**; the support available is the maintainer's own `.github/workflows/claude-review.yml` at `v1.0.220`, which carries the identical guard with the comment "Skip on fork PRs since they can't mint the OIDC token used for Claude API auth" (`action-source-v1.0.220.log`), plus `py`'s own guard comment recording that the action "aborts on non-human actors … which showed as a **false red check** on the v2.4.1 release PR (#470)" and that "Skipping is a neutral (non-failing) outcome for this non-required job" (`source-repos-pinned.log`) — reference concordance and one field report, not an observed run (see **U3**). Revision 2 stated clause (a) as a property of the whole contract; that was inaccurate against this decision's own fixtures, and revision 3 corrects it. **The assistant lane cannot carry this clause and does not need it**: none of its four events is a `pull_request` event, so `GITHUB_REF` is the default branch, no fork ref is checked out, and the run happens in the base repository with its credentials by design. The assistant lane's fork-adjacent exposure is a *comment* on a fork pull request, which is `#1068`'s case and is answered by clause (d), not by a same-repository test.
- (b) Neither lane runs when either the pull-request author or the run's initiator is a bot.
- (c) No credential is reachable from a run whose content an untrusted contributor controls.
- (d) **New at revision 3.** On a public repository the assistant lane never *starts* for an author outside `OWNER`, `MEMBER` or `COLLABORATOR`. This is a prefilter, not a permission check: `author_association` is not the same predicate as write access, and an organization `MEMBER` without write access passes it and is then refused by the action's own `checkWritePermissions` (read in source, `action-guard-source-v1.0.220.log`). It admits every write-access holder — a repository collaborator reports `COLLABORATOR`, an organization member reports `MEMBER`, the owner reports `OWNER` — so it introduces no false refusal for a legitimate maintainer, and it is defence in depth in front of an authoritative action-side check, never a replacement for it.

What may vary per repository: whether the capability is enabled at all, which events are listened to, which model, and which prompt.

**Architectural alternatives, compared before libraries.** Four architectures can deliver "pull requests get an automated first-pass review"; the choice among them precedes the vendor choice.

| Architecture | Expressed as | Travels through "Use this template"? | Verdict |
|---|---|---|---|
| A. Workflow-file agent (`claude-code-action`, `run-gemini-cli`, `codex-action`) | YAML in `.github/workflows/`, versioned and reviewed like code | **Yes** — the file is tree content | **Chosen.** The only architecture that is itself a template artifact. |
| B. Platform-configured reviewer (GitHub Copilot code review) | repository ruleset plus organization settings | No — repository *state*, not tree content | Rejected on fit: a template that ships nothing cannot transfer the capability, and the value test in the prompt is about two files. |

Inside architecture A, `anthropics/claude-code-action` is selected over `The-PR-Agent/pr-agent`, `google-github-actions/run-gemini-cli` and `openai/codex-action` because it is the only candidate that (i) covers **both** members with one component, one credential and one App installation, (ii) is on a stable `v1` series with **no `v2` tag** among the 287 tag refs returned (`action-release.log`, HTTP 404 and `gh` exit 1 on `git/ref/tags/v2` — the correct result for a ref that does not exist), and (iii) has the maintainer running both shapes against its own repository in a form that can be read at a tag.

**Why the selected design preserves each principle.** Clauses (a) and (b) of the guard contract are carried over from `py` byte-for-byte on the review lane, so they are preserved by construction there, and clause (a) is now scoped to that lane for the reason given above. Clause (c) is preserved by the enable flag downstream and by clause (d) upstream. The two **additions** to `py`'s shape exist because `py`'s guard protects neither a template consumer nor a public origin repository:

*The enable flag, for the consumer.* In a repository created from the template, an internal PR satisfies `head.repo.full_name == github.repository`, so the fork guard passes and the job runs with no credential. The platform bounds the available fix: `jobs.<job_id>.if` may read only `github, needs, vars, inputs`; `secrets` is absent there and from `jobs.<job_id>.steps.if` as well, while it *is* available in `jobs.<job_id>.env` (verified, `contexts-availability.log`, and independently by `actionlint`, which rejects `if: secrets.X != ''` at the job level, `actionlint.log`). A `vars`-gated job is therefore the only single-line mechanism the context table permits at the job level, and its **intended** effect is that both files are inert in every unconfigured downstream repository while the origin repository needs one variable write. That intended effect is a design purpose, not an observed one: the **runtime** outcome — a `skipped` job rather than a failed one — is **U2**. The step-level alternative (`env: HAS_CRED: ${{ secrets.X != '' }}` read by `steps.if`) is legal under the same table; its expected drawback is that a skipped *step* would sit inside a job still reporting green, reading as a passing review that never happened — also a runtime expectation, reasoned from the same table and likewise never executed here.

*The author-trust prefilter, for the origin repository.* `author_association` arrives through the `github` context, which the same context table lists as available in `jobs.<job_id>.if`, so `#1068`'s suggested fix is expressible at the job level; `actionlint` accepts the four-clause form with exit 0 (`actionlint.log`, revision-3 addendum, fixture `candidate-claude.r3.yml`). The clause is written in the exact shape `#1068` asks for, `contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.<payload>.author_association)`, and `doxa-openai` independently asks for "a trusted association prefilter where practicable" (`raw/doxa-openai.normalized.md:388`). What the prefilter does **not** do is stated with it, three times over: it is not a write-access check (clause (d) above); it does not stop the run for an OWNER, MEMBER or COLLABORATOR who pastes untrusted text, which is the residual carried into the runner-up's third condition; and it would **not** have stopped the published chain's Phase 2, whose triggering comment came from a trusted author and whose body was tampered with afterwards — that vector is closed instead by the action's own `isBodySafeToUse` at `v1.0.220`, read in source (`action-guard-source-v1.0.220.log`, G4).

The "neither" case rests on four grounds, which divide two and two. **Two are engineering claims that the recommended design answers syntactically but not yet at runtime**: checks 1, 7 and 12 establish that a job-level `if:` may read `vars` and `github` and may not read `secrets`, so a public template *can* ship a workflow gated on a variable it does not itself set and prefiltered on the commenter's association, imposing no credential on a consumer — but whether an unset variable yields a `skipped` job rather than a red check is **U2**, unproven until P03, and nothing here claims it. **The other two grounds** — that a public template should not carry a vendor-AI exemplar, and that no acceptance criterion requires AI review — are **owner policy**, and are carried as the ranked runner-up. Revision 3 adds a **third** owner-policy ground to the runner-up, and it is the one the judgment audit asked to see argued: the residual prompt-injection exposure of a write-capable assistant lane on a public repository, reachable from trusted-author text that may quote untrusted content. Chosen: **both**, once, consistently across every section. The recommendation did **not** change, and the reason it did not is stated rather than assumed — the phase-by-phase analysis in fitness gate 3 finds the recommended configuration outside every phase of the published chain, the four remediations are present at the pin (three located in source), and clause (d) closes the one exposure that the enable flag structurally could not reach. What changed is that the case is now argued instead of resting on one endpoint. If U2 or U12 fails in P03, the "neither" case regains ground and this decision is revised against this recorded research.
2. **Is the bot guard Rust-specific?** `doxa-gemini` asserts a Rust-specific adjustment and proposes a name denylist containing `dependabot[bot]`, `renovate[bot]` and `release-plz[bot]`. **Settled against it** by check 6: `py`'s guard is *type*-based (`github.event.pull_request.user.type != 'Bot'` and `github.event.sender.type != 'Bot'`), which is name-independent and therefore already catches `release-plz[bot]` and every other bot without enumeration; a denylist is strictly weaker. Check 10 adds a second, independent reason a denylist is the wrong instrument: the action's own `checkWritePermissions` returns `true` for **any** actor whose login ends in `[bot]`, and the refusal lives in `checkHumanActor`, which is likewise type-based — so a name list at the workflow level would be duplicating, in a weaker form, a check that already exists in a stronger form one layer down. The HIGH question in the prompt answers: **`py`'s guard logic ports unchanged; there is no Rust-specific adjustment to make.**
3. **Which version?** `v1.0.217` (codex), `v1.0.219` (doxa-openai), `v1.0.175` (gemini), `@v1` floating (perplexity), `v1.0.220` (opus). Checks 2 and 3 settle it: all three specific tags resolve, each was current at its own retrieval date, `v1.0.220` is current at 2026-09-10, and cadence is ≈ one patch per day — so **no engine was wrong, and every pin is stale within days**. `doxa-openai`'s SHA `5ccc3a35a6367cdb8e6fbd0728287467540ecfe2` is confirmed as the exact commit behind `v1.0.219`. **`doxa-gemini`'s `v1.0.175` is rejected on currency, not on safety, and revision 3 corrects revision 2 here**: gemini's safety argument for it is sound — `v1.0.175` is above the `v1.0.94` at which the S2 chain was fixed and above the `1.0.74` that fixes S1 — and revision 2's refutation of its `v1.0.94` figure compared that figure against a different advisory and a single release's changelog, which was a category error (fitness gate 3). The remaining ground is that `v1.0.175` is `py`'s pin, 45 patch releases behind current, on a component releasing daily. `doxa-perplexity`'s `@v1` is the *form* of a pin, which is **R20**'s decision — but note S1's own guidance that non-pinned references received the fix automatically, and note that `plugin_marketplaces` takes a Git URL with no ref and therefore cannot be pinned at all; both are handed to R20 as evidence.
4. **How to make the workflows inert in a downstream repository?** `doxa-perplexity` proposes an `if` that checks for the presence of the required secret. **Refuted** by check 1 and by `actionlint` in check 7 — and the refutation is **syntactic**: the context table omits `secrets` from `jobs.<job_id>.if`, and `actionlint` rejects the expression with exit 1 and the quoted diagnostic. The proposal is not merely unproven, it is not expressible. `opus`'s `vars`-gated flag is adopted instead; the step-level `env`-relay alternative is legal and is recorded above with its drawback.
5. **Drop `synchronize` from the review trigger?** Only `opus` proposes it; `py`, `gemini` and `perplexity` keep it; `doxa-openai` keeps it too but pairs it with per-PR `concurrency`. It is **adopted, on a structural argument, not a measured one**: `synchronize` is the only trigger that fires per push rather than per state change, and the maintainer's own review workflow listens on `types: [opened]` alone (check 4). No cost figure exists to make this numeric (`#1482`, open). It remains a weak element of this recommendation and is **U6**.
6. **Bundle or two independent decisions?** `doxa-openai` argues independence; `opus` supplies the only actual *argument* either way, and it is a design coupling: dropping `synchronize` removes automatic re-review after a fix-up push, and the replacement is a write-access user typing `@claude please re-review`, which is F052. **That argument holds only if `synchronize` is dropped** — if P03 restores it, the bundling rationale weakens to shared component, credential, App installation, pin and Dependabot surface, which is real but not decisive. `doxa-openai`'s further ask, to split F052's **ledger** decision from F051's, is a controller matter and is routed as a baseline finding rather than answered here.
7. **`issues: [assigned]` in the assistant trigger.** `codex` would drop it ("a template needs an explicit request, not a side effect of triage"); `opus`, `py`, `examples/claude.yml` and the maintainer's own file all keep it. **Kept**, on three-way reference concordance (check 4), and recorded as minor: with `assignee_trigger` unset (`action.yml` at `v1.0.220` gives it no default), the expected consequence is that an `assigned` event only re-evaluates an issue whose body or title already contains `@claude`. That is **reasoned from the input's absent default and the workflow's own `contains(…, '@claude')` condition, not observed**.
8. **Small factual corrections to the raws**, recorded so they are not carried forward: `ts` has **8** workflow files at `cb1cbcb`, not nine (check 6); `releases/latest` returns the floating tag `v1` (published 2025-08-26), so the newest *patch* must be read from the releases list; the maintainer's own workflows use `actions/checkout@v6` while `py` uses `@v7`, and `actions/checkout`'s current release is `v7.0.1` (2026-07-20), so `py` is the more current of the two on that line.
9. **Not surfaced by any engine, found here:** the one published GitHub security advisory for the action, `GHSA-8q5r-mmjf-575q` / `CVE-2026-47751` (check 5). It does not change the recommendation — `v1.0.220` and `py`'s `v1.0.175` are both above the patched `1.0.74` — but it is direct evidence for the fork guard, for `docs/security.md`'s "do not check out an untrusted ref into the workspace root before this action", and for R20's pin-form tradeoff. Revision 3 records that it is **not the whole security history** (fitness gate 3).

**Four trigger and guard objections from `doxa-openai`, adjudicated at revision 3 (JA-05).** All four were raised in `raw/doxa-openai.normalized.md`; revision 2 answered none of them.

10. **Draft double-fire — `opened` plus `ready_for_review` with no `draft` clause. ADOPTED.** `doxa-openai` recommends `draft == false` (`:168-175`). The objection is correct and it contradicts this decision's own bounded-spend rationale: `opus`'s stated ground for the trigger list, "every retained event fires at most once per pull request per state change" (`raw/opus.md:105`), is true of each event and **false of their composition**, because a pull request opened as a draft fires `opened` and then fires `ready_for_review` when it is marked ready — two paid agent sessions for one pull request. With `draft == false`, a draft-opened pull request is skipped at `opened` and reviewed once at `ready_for_review`, and a ready-opened pull request is reviewed once at `opened` and never fires `ready_for_review`; the composition becomes exactly-once. The clause is adopted, lints clean (check 12) and is fixture `candidate-claude-code-review.r3.yml`. **Its basis is reasoned and practice-corroborated, not observed**: the documented `pull_request` activity-type set includes `opened`, `ready_for_review` and `converted_to_draft` (check 11), and `github/docs`' own repository carries six workflow files gating on `pull_request.draft`; no run was executed, so exactly-once firing is **U11**. `doxa-openai`'s companion proposal, per-PR `concurrency` with `cancel-in-progress: true` (`:236-239`), is **declined with reasons**: it exists to cancel superseded runs from a per-push trigger, and with `synchronize` dropped and `draft == false` added, no retained event can fire twice for one pull-request state, so there is nothing for it to cancel. If P03 restores `synchronize` (U6), the concurrency group must be restored with it.
11. **`pull_request_review: [submitted]`. KEPT, with the widening stated.** `doxa-openai` excludes it (`:348`) because it "adds a fourth content surface not requested and makes quoted mentions in review summaries capable of triggering work". Two facts bear on it. First, the objection is right that this **widens the prompt's MEDIUM question**, which names three surfaces — issue comments, PR review comments, issue bodies — and the recommendation ships four plus title matching; revision 2 shipped the widening without noting it, and revision 3 notes it here. Second, `py`, `examples/claude.yml` and the maintainer's own `claude.yml` are character-identical on this event (check 4), and clause (d) now bounds *who* can write into that surface to `OWNER`/`MEMBER`/`COLLABORATOR`, which is the property that makes surface count matter far less than it did before. Kept on that basis. The narrower three-surface list remains a defensible configuration and is the first thing to cut if P03 finds the assistant lane noisy.
12. **Issue-title matching. KEPT.** `doxa-openai` excludes it (`:350`), "only issue bodies are in scope". The clause `contains(github.event.issue.title, '@claude')` is `py`'s, `examples/claude.yml`'s and the maintainer's own, character-identical (check 4). An issue title is authored by the issue author and therefore falls under the same clause-(d) prefilter as the body, so it adds no new author surface — only a second field on the same event. Kept, and recorded as the least load-bearing element of the trigger configuration.
13. **No fork or same-repository clause on the assistant job. THE CONTRACT WAS WRONG, NOT THE FIXTURE.** `doxa-openai` asks for a same-repository preflight on this lane (`:388`, `:416`, `:479`); guard-contract clause (a) at revision 2 read "the job never runs on a pull request from a fork" as a property of the whole contract, while only `candidate-claude-code-review.yml` implements it — and `py`'s own `claude.yml` has no such clause either (check 6). The resolution is that **clause (a) binds the review lane only**, and revision 3 rewrites it that way with the reason: none of the assistant lane's four events is a `pull_request` event, so `GITHUB_REF` is the default branch, no fork ref is checked out, and running in the base repository with base-repository credentials is the design rather than a leak. What `doxa-openai`'s preflight would actually address — the agent *operating on* a fork pull request's contents — is covered by `docs/security.md`'s "do not check out an untrusted ref into the workspace root", which the assistant fixture already satisfies by passing no `ref:` on non-`pull_request` events. The assistant lane's real fork-adjacent exposure is a **comment** on a fork pull request from an untrusted account, which is `#1068`, answered by clause (d).

**Two record gaps closed at revision 3.** `plugin_marketplaces: 'https://github.com/anthropics/claude-code.git'` is now listed in the `## Decision` table's action inputs, where revision 2 omitted it even though `candidate-claude-code-review.yml` carries it and the `plugins` reference cannot resolve without it; and `opus`'s observation that the review lane fetches its plugin from an external marketplace Git URL at run time — "one more moving part and one more trust edge" (`raw/opus.md:589`) — is recorded under reference implementations, with the additional fact that a marketplace URL carries no ref and therefore cannot be pinned, and is handed to **R20** as pin-form evidence.
