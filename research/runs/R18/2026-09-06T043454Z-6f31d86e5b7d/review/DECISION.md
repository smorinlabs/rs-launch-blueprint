### Principles and implementation

**Shared requirement, source, agreement level.** The requirement behind `py`'s two files is: *every pull request receives a first-pass automated review before a human reads it, and a maintainer can summon an agent into an issue or review thread without leaving GitHub.* Its source is the `py` implementation at pinned commit `b08bccfb55d05f15e46a83b52c5660b1881d19f5` (both files read verbatim, `source-repos-pinned.log`) plus ledger rows F051/F052. The agreement level is **policy/mechanism** — the weakest of the three levels in `docs/port/README.md` — for three reasons, each observed rather than assumed:

1. `ts-launch-blueprint` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00` ships eight workflow files, none AI-related, and zero paths under `.github/` matching `claude` (`source-repos-pinned.log`: the `ls-tree` listing the eight files exits **0**; the `ls-tree … | grep -ci claude` that returns the zero count exits **1**, which for `grep -c` *is* the zero-match result — see check 6). Two of the three sibling repositories already disagree; that is only tolerable if the thing they disagree about is a policy choice.
2. Nothing in the capability is ecosystem-shaped. The action reads a diff and posts comments; the diff being Rust changes no mechanism. There is no Rust analogue to select and no Rust idiom to honor.
3. The reviewing entity is a paid third-party service reached with an organization credential. Whether to spend it here is an owner policy question, which is precisely why "`py` does it" cannot settle it.

**What must agree; what may vary.** What must agree across `py`, `ts` and `rs` is the **guard contract**, because it is simultaneously a security property and a correctness property and is ecosystem-neutral: (a) the job never runs on a pull request from a fork, on the ground that a fork run cannot obtain the credential and could only fail — **a platform runtime behaviour that no check here executed**; the support available is the maintainer's own `.github/workflows/claude-review.yml` at `v1.0.220`, which carries the identical guard with the comment "Skip on fork PRs since they can't mint the OIDC token used for Claude API auth" (`action-source-v1.0.220.log`), i.e. reference-implementation concordance plus GitHub's documented fork restrictions, not an observed run (see **U3**); (b) the job never runs when either the pull-request author or the run's initiator is a bot; (c) no credential is reachable from a run whose content an untrusted contributor controls. What may vary per repository: whether the capability is enabled at all, which events are listened to, which model, and which prompt.

**Essential behaviors and observable acceptance criteria.**

| # | Essential behavior | Observable acceptance criterion (P03 proves each) |
|---|---|---|
| B1 | A qualifying pull-request event starts the review job | a human-authored PR in the configured origin repository produces a run with `conclusion: success` |
| B2 | Fork PRs, bot-authored PRs and bot-initiated runs are **skipped, not failed** | `.workflow_runs[0].conclusion == "skipped"` for each of: a fork PR, the release-please PR, a Dependabot PR |
| B3 | A run that starts actually posts its output | `gh api repos/<o>/<r>/issues/<pr>/comments --jq 'length'` ≥ 1; a green job with 0 comments reproduces `anthropics/claude-code-action#1121` |
| B4 | A repository created from the template with no variable set is inert | every PR and every `@claude` comment yields a **skipped** job, never a red check |
| B5 | Only a write-access user can summon the assistant | the same `@claude` comment from a non-write account produces no agent action |
| B6 | The assistant can read CI results | `@claude why did the clippy job fail?` on a red PR yields a reply naming the failing job |

**Architectural alternatives, compared before libraries.** Four architectures can deliver "pull requests get an automated first-pass review"; the choice among them precedes the vendor choice.

| Architecture | Expressed as | Travels through "Use this template"? | Verdict |
|---|---|---|---|
| A. Workflow-file agent (`claude-code-action`, `run-gemini-cli`, `codex-action`) | YAML in `.github/workflows/`, versioned and reviewed like code | **Yes** — the file is tree content | **Chosen.** The only architecture that is itself a template artifact. |
| B. Platform-configured reviewer (GitHub Copilot code review) | repository ruleset plus organization settings | No — repository *state*, not tree content | Rejected on fit: a template that ships nothing cannot transfer the capability, and the value test in the prompt is about two files. |
| C. Hosted third-party review app (PR-Agent as a service, CodeRabbit as an app) | a GitHub App installed on the repository | No | Rejected on the same fit ground, plus a second vendor relationship. |
| D. Self-hosted agent in a generic job | bespoke YAML plus a script | Yes | Rejected on maintenance cost: reimplements diff assembly, comment threading, deduplication and prompt-injection sanitization that A gets from a maintained action. |

Inside architecture A, `anthropics/claude-code-action` is selected over `The-PR-Agent/pr-agent`, `google-github-actions/run-gemini-cli` and `openai/codex-action` because it is the only candidate that (i) covers **both** members with one component, one credential and one App installation, (ii) is on a stable `v1` series with **no `v2` tag** among the 287 tag refs returned (`action-release.log`, HTTP 404 and `gh` exit 1 on `git/ref/tags/v2` — the correct result for a ref that does not exist), and (iii) has the maintainer running both shapes against its own repository in a form that can be read at a tag.

**Why the selected design preserves each principle.** The fork/bot guard is carried over from `py` byte-for-byte, so (a) and (b) are preserved by construction. The one **addition** to `py`'s shape — a repository-variable enable flag — exists because `py`'s guard does not protect a *template consumer*: in a repository created from the template, an internal PR satisfies `head.repo.full_name == github.repository`, so the fork guard passes and the job runs with no credential. The platform bounds the available fix: `jobs.<job_id>.if` may read only `github, needs, vars, inputs`; `secrets` is absent there and from `jobs.<job_id>.steps.if` as well, while it *is* available in `jobs.<job_id>.env` (verified, `contexts-availability.log`, and independently by `actionlint`, which rejects `if: secrets.X != ''` at the job level, `actionlint.log`). A `vars`-gated job is therefore the only single-line mechanism the context table permits at the job level, and its **intended** effect is that both files are inert in every unconfigured downstream repository while the origin repository needs one variable write. That intended effect is a design purpose, not an observed one: the **runtime** outcome — a `skipped` job rather than a failed one — is **U2** below, unproven by this research. (The lint fixture `candidate-claude-code-review.yml` carries an inline comment asserting the same expectation; it is left byte-for-byte as linted, and it too states U2, not a result.) The step-level alternative (`env: HAS_CRED: ${{ secrets.X != '' }}` read by `steps.if`) is legal under the same table; its expected drawback is that a skipped *step* would sit inside a job still reporting green, reading as a passing review that never happened — also a runtime expectation, reasoned from the same table and likewise never executed here.

**Adjudication of both findings — what the evidence supports and what it does not.** Both are **accepted for the `rs` template**, with limits stated because both are security-relevant.

*F051 / `pull-requests: write`.* **Supported:** that `py`'s grant differs from every maintained reference; that the reference configurations which post comments all grant `write`; that a third party reports and a second party independently reproduces a silent no-op under `read`. **Not supported:** that `py`'s own repository currently exhibits the silent failure — no run of `py`'s workflow was inspected, and `py`'s `--comment` flag differs from the reproducer's configuration, which the reproducer describes as lacking `--comment`. **Not established by this research:** the exact mechanism, i.e. whether the job's `pull-requests` grant bounds the Claude GitHub App installation token used for the write, or whether some writes go through the job's own `GITHUB_TOKEN`. `docs/security.md` says only that "The GitHub app receives only a short-lived token scoped specifically to the repository" and that "the token cannot … perform actions beyond the configured permissions", which does not disambiguate the two. The recommendation therefore rests on *concordance with three maintained references plus a reproduced report*, not on a demonstrated causal chain, and B3 above is the check that settles it in P03. Consequence if the finding is wrong: an over-broad grant on the review job, which R08 would then narrow — a strictly smaller failure than a review that silently never posts.

*F051+F052 / workload identity federation.* **Supported:** that federation exists at `v1.0.220`, that it removes the stored credential, that the maintainer uses it in production, and that it adds no permission beyond the `id-token: write` already required. **Two costs, both verified and both material:** `docs/setup.md` requires **admin access to an Anthropic organization** (register an issuer, create a service account, create a federation rule) — a one-time setup each downstream fork owner must repeat, which a `CLAUDE_CODE_OAUTH_TOKEN` produced by `claude setup-token` does not require; and "Inline comment classification (`classify_inline_comments`) currently requires `anthropic_api_key`; with federation it is skipped and unconfirmed inline comments are posted directly" — a behavior change, not merely a credential change. **Not established:** whether `CLAUDE_CODE_OAUTH_TOKEN` (which `docs/setup.md` describes as generated by Pro and Max users with `claude setup-token`) and a federated service-account token bill against the same account, so the finding is recorded as *prefer federation where the owner has an Anthropic organization and is not relying on subscription-backed OAuth*, and the static token stays documented as the supported fallback. `docs/setup.md` also warns: "Do not set `anthropic_api_key` or `claude_code_oauth_token` alongside the federation inputs — a static credential takes precedence and federation will not be used."

**Minimal realistic example and executable acceptance check.** The minimal example is the two files reproduced as lint fixtures at `review/evidence/candidate-claude-code-review.yml` and `review/evidence/candidate-claude.yml`, plus two repository variables. `actionlint` on both exits 0 (`actionlint.log`); that is the whole of what can be executed before the template exists. 5. **Drop `synchronize` from the review trigger?** Only `opus` proposes it; `py`, `gemini` and `perplexity` keep it. It is **adopted, but on a structural argument, not a measured one**: `synchronize` is the only trigger that fires per push rather than per state change, and the maintainer's own review workflow listens on `types: [opened]` alone (check 4). No cost figure exists to make this numeric (`#1482`, open). It is the weakest element of this recommendation and is the first item on the P03 list below.
6. **Bundle or two independent decisions?** `doxa-openai` argues independence; `opus` supplies the only actual *argument* either way, and it is a design coupling rather than a packaging coincidence: dropping `synchronize` removes automatic re-review after a fix-up push, and the replacement is a write-access user typing `@claude please re-review`, which is F052. **That argument holds only if `synchronize` is dropped** — if P03 restores it, the bundling rationale weakens to shared component, credential, App installation, pin and Dependabot surface, which is real but not decisive.
7. **`issues: [assigned]` in the assistant trigger.** `codex` would drop it ("a template needs an explicit request, not a side effect of triage"); `opus`, `py`, `examples/claude.yml` and the maintainer's own file all keep it. Kept, on three-way reference concordance (check 4), and recorded as minor: with `assignee_trigger` unset (`action.yml` at `v1.0.220` gives it no default, `action-source-v1.0.220.log`), the expected consequence is that an `assigned` event only re-evaluates an issue whose body or title already contains `@claude`. That is **reasoned from the input's absent default and the workflow's own `contains(…, '@claude')` condition, not observed** — no run was executed, and no log carries a statement of the action's assignee behaviour.
8. **Small factual corrections to the raws**, recorded so they are not carried forward: `ts` has **8** workflow files at `cb1cbcb`, not nine (check 6); `releases/latest` returns the floating tag `v1` (published 2025-08-26), so the newest *patch* must be read from the releases list, not from `/releases/latest`; the maintainer's own workflows use `actions/checkout@v6` while `py` uses `@v7`, and `actions/checkout`'s current release is `v7.0.1` (2026-07-20), so `py` is the more current of the two on that line.
9. **Not surfaced by any engine, found here:** the one published GitHub security advisory for the action, `GHSA-8q5r-mmjf-575q` / `CVE-2026-47751` (check 5). It does not change the recommendation — both `v1.0.220` and `py`'s `v1.0.175` are above the patched `1.0.74` — but it is direct evidence for the fork guard, for `docs/security.md`'s "do not check out an untrusted ref into the workspace root before this action", and for R20's pin-form tradeoff.
