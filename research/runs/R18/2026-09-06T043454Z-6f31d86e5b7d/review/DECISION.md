# R18 — ai-assisted-review-workflows (bundle, Deep) — decision (revision 5, 2026-09-10)

## Decision

**Status.** This decision is a **proposal to be validated in the implementation phase against the real template**. `rs-launch-blueprint` has no `.github/workflows/` tree, no Rust code and no configured credential today; P02 is research and P03 builds the template, and P03's CI is what proves or disproves what is recorded here. A recommendation that does not survive implementation is **revised against this recorded research**, not researched again from scratch. Nothing below claims owner acceptance: the owner has reviewed R01 only.

**Recommendation — moved at revision 4, and the move is the condition.** Ship **both** workflow files, as **one bundle**, from `anthropics/claude-code-action` at **`v1.0.220`** (annotated tag `020e931323e467e00b803ad64e03410d3796b8f7` → commit `19dda84776b3518d98b8798e591daee763049ed3`, resolved 2026-09-10), **as inert artifacts**, and **do not enable either lane on any public repository — the origin repository included — until the owner has recorded acceptance of the residual named under "What enabling costs the owner" below.** Revisions 1 to 3 recommended shipping both without qualification and treated origin-repository enablement as settled; it is not settled, no owner acceptance is on record (the owner has reviewed R01 only), and revision 4 makes the condition the recommendation rather than a footnote. **If the owner withholds that acceptance, the documented runner-up is what ships**: delete both files and publish the opt-in recipe. Also new at revision 4: **the run-time plugin-marketplace fetch is removed** from the review lane, on evidence read at the tag (see "The unpinned marketplace fetch, adjudicated" below). Carried unchanged from revision 3: `pull-requests: write` on the review job, **workload identity federation** as the credential path, the author-trust prefilter on the assistant lane, and the `draft == false` clause on the review lane. That an unconfigured repository yields a `skipped` job rather than a red check remains **U2**, unproven here.

**Why the assistant lane gains an author-trust prefilter, stated here because it is the security case.** The `vars` enable flag protects a **downstream fork**, where it is unset. It cannot protect the **origin repository**, where it is `true` by construction, the federation identifiers are configured, and strangers can comment on a public template. Upstream issue `anthropics/claude-code-action#1068` — "Default workflow template missing author trust gate — secrets exposed on public repos", open since 2026-03-18, labels `bug`, `documentation`, `area:permissions`, `p1`, author `NONE`, 0 comments, `updated_at` 44 seconds after creation (`issue-1068.log`) — names three exposures of the unprefiltered `if:` and asks for exactly this clause. Revision 2 recorded that issue only as a comment count. Read in full, its three exposures divide as follows against the recommended configuration:

| `#1068`'s exposure | Answered by federation? | Answered by the enable flag on the origin repository? | Answered by the revision-3 prefilter? |
|---|---|---|---|
| The job starts and consumes runner minutes | No | No | **Yes**, for any commenter outside `OWNER`/`MEMBER`/`COLLABORATOR` — **U12**, not observed |
| `secrets.ANTHROPIC_API_KEY` / `secrets.CLAUDE_CODE_OAUTH_TOKEN` reach the runner | **Yes** — there is no such secret under federation | No | Moot under federation |
| An OIDC token is obtainable (`id-token: write`) | **No** | No | **Yes**, same qualification |

The third row is the correction that matters, and it revises a claim `opus` made and revision 2 carried: federation was recorded as a mitigation for `#1068`, and it answers only the second row. `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_URL` are present in the runner environment from the moment a job with `id-token: write` starts, and the 2026-06-01 GMO Flatt Security disclosure describes them as "the credentials required to request that OIDC token, so an attacker who obtains them can replicate the entire token exchange process" — the exchange whose output is a Claude GitHub App installation token with write access to contents, issues, pull requests and workflows (`flatt-disclosure-2026-06-01.log`). Federation changes which credential is worth stealing; it does not remove the one the published chain actually steals. **Scoped at revision 4, because revision 3 overstated it (empirical finding F3).** Revision 3 said the prefilter "is the only control in this record that acts before the job starts". That is wrong as written: the assistant lane's job-level `if:` also carries `vars.ENABLE_CLAUDE_ASSISTANT == 'true'`, and a `vars` clause is pre-job control too. The supported claim is the narrower one: **once the origin repository sets `ENABLE_CLAUDE_ASSISTANT` to `true`, the `author_association` clause is the only actor-trust control that acts before the job is scheduled** — the enable flag is a capability switch, not an actor check, and it is `true` by construction on the repository this decision is about. That is why the prefilter is adopted rather than offered.

**And it is load-bearing for a reason revision 3 did not have, found at revision 4 while correcting F1.** `src/entrypoints/prepare.ts:37` calls `setupGitHubToken()` **before** the write-permission check at `:44` and before either mode calls `checkHumanActor`. `setupGitHubToken()` exchanges the workflow's OIDC token for a Claude GitHub App installation token at `https://api.anthropic.com/api/github/github-app-token-exchange` (`src/github/token.ts:121`). Because the assistant lane passes `additional_permissions`, `parseAdditionalPermissions()` returns a value, so `token.ts:100` sends `DEFAULT_PERMISSIONS` merged with it — `contents: "write"`, `pull_requests: "write"`, `issues: "write"` (`token.ts:69-73`) plus `actions: read`. **A write-capable App installation token is therefore requested before any actor-trust check inside the action returns** (`action-entrypoint-plugins-v1.0.220.log`, E2 and E3). Whether anything attacker-controlled is processed in that window was not traced; that is **U14**. On the review lane `additional_permissions` is unset, `parseAdditionalPermissions()` returns `undefined`, no body is sent, and the resulting permission set is chosen server-side and is **not readable from this source** — recorded as **U17**.

**Ranked runner-up, promoted at revision 4 from "ranked second" to "the default if acceptance is withheld".** Ship **neither** workflow and publish a documented opt-in recipe instead (the `codex` and `doxa-openai` position). It wins on any of three owner judgements, and revision 4 changes its standing rather than its content: because the third condition below is now *live and unresolved* rather than hypothetical, the runner-up is no longer merely an alternative the owner may pick. Two things follow, and they are different: while acceptance is unrecorded the shipped state — two files with their variables unset — is **functionally equivalent** to the runner-up, because nothing runs either way; and if acceptance is **withheld**, the runner-up is what ships, meaning the two files are deleted and only the recipe remains. Two of its three conditions are the ones revision 2 recorded: the owner declines recurring third-party spend on the origin repository, or declines shipping a vendor-AI exemplar inside a public template tree. **The third is added at revision 3 and is the one the judgment audit asked to see argued**: the owner declines the residual prompt-injection exposure of a **write-capable assistant lane on a public repository, reachable from text an OWNER, MEMBER or COLLABORATOR writes** — because a trusted author routinely quotes untrusted content (pasting an issue body, a fork pull request's diff, a stack trace) into a comment, and neither the prefilter nor any action-side check distinguishes a trusted author's own words from untrusted text that author pasted. The researcher who published the chain states the general form of that residual plainly: "The permission model around Claude Code isn't hardened enough to safely handle untrusted input… at the time of writing, I have reported around 50 separate vulnerabilities to Anthropic that allow attackers to bypass the permission system and execute arbitrary commands in Claude Code" (`flatt-disclosure-2026-06-01.log`). That residual is **not** the published chain — see the exposure analysis under fitness gate 3, which finds the recommended configuration outside every phase of it — but it is a live class, and it is an owner risk decision, not an engineering-fitness one.

The runner-up's *other* stated grounds — that a public template cannot supply a downstream consumer's credential, and that an unconfigured fork would get a red check — are what the enable flag is **designed** to answer, and the evidence gathered here supports that design **syntactically, not yet at runtime**. Precisely what the checks establish (see `## Empirical check`, `contexts-availability.log` and `actionlint.log`): a job-level `if:` **may** reference the `vars` and `github` contexts and **may not** reference `secrets`, so both a credential-independent enable flag and an `author_association` prefilter are expressible at the job level at all. Whether an unset variable makes the job **`skipped` rather than failed** is a GitHub *runtime* outcome that no check here executed; it is **U2**. If the owner funds only one member, `claude.yml` alone is more defensible than `claude-code-review.yml` alone on spend, because only the review lane's spend is driven by repository traffic rather than by a human asking — but note that `claude.yml` is also the lane carrying the wider permission grant and the exposure analysed above, so the spend ranking and the security ranking point in opposite directions and the owner is choosing between them.

**What enabling costs the owner, and what an adopter must understand to accept it knowingly.** Two auditors declined to certify shipping this as revision 3 stated it, and the honest answer is not that they were wrong but that revision 3 asked the wrong question. Shipping the **files** and enabling the **capability** are separate acts with separate risk owners, and revision 3 conflated them. Four facts fix the boundary:

1. **The template consumer is not exposed by the files alone.** With `ENABLE_CLAUDE_REVIEW` and `ENABLE_CLAUDE_ASSISTANT` unset — the state of every repository created from the template — no job runs, no credential exists, and no federation identifier is configured. What a stranger receives is two inert files plus a documented enablement decision. That defence rests entirely on **U2**, which is unproven, and if U2 fails a stranger gets a red check instead of an inert file, which is precisely the `codex`/`doxa-openai` objection and a reason the runner-up would then win outright.
2. **The residual is a property of the capability, not of the files.** The runner-up does not remove it; it relocates the decision to adoption time. Anyone who follows the opt-in recipe inherits the same residual, because the residual is what the action does once it is running, not what the template ships.
3. **The residual is not removable by configuration, and it binds both lanes.** A trusted author routinely quotes untrusted content, and no check separates the author's own words from text the author pasted. It is tempting to argue the review lane is safer on `contents: read`; the record does not support that, though it does not refute it either — and the distinction is the honest one. The S2 chain escalates through the **Claude GitHub App installation token**, not through the job's own grants (security-claims table, row 12). For the **assistant** lane that token's request is read in source and is write-capable: `additional_permissions` is set, so `token.ts:100` sends `DEFAULT_PERMISSIONS` merged with it — `contents`/`pull_requests`/`issues` `write`. For the **review** lane no body is sent at all (`token.ts:79-81`, `:115-118`), so the scope is chosen server-side and **is not readable from any source this research can reach** — that is **U17**, and *unknown is not read-only*. What is settled for both lanes is the input side: a pull-request diff written by a write-access author is trusted-author content on exactly the same footing as a comment, so the residual itself binds both. **Treat the review lane as write-capable until U17 says otherwise, rather than assuming it is not.**
4. **The pre-token window is real.** `setupGitHubToken()` runs before every actor-trust check inside the action (above, and E2/E3 in `action-entrypoint-plugins-v1.0.220.log`). The workflow's job-level `if:` is therefore the only control that acts before an App token is requested — and its runtime effect is **U12**, unproven.

Given (1) to (4): the exposure is **argued and bounded** — bounded by the fork guard, the bot guards, the enable flag, the `author_association` prefilter, a pin above both fix versions, and a configuration outside every phase of the published chain — and it is **not eliminated**. Whether a bounded, unremovable exposure on a write-capable lane is acceptable is an owner risk judgement, not an engineering-fitness one, and this decision does not have that judgement on record. So it does not assert one. **An adopter accepting it knowingly must understand five things**, and they are written into the fixture headers because the fixture is what gets copied: that enabling on a public repository accepts an unremovable trusted-author prompt-injection residual; that a write-capable Claude GitHub App installation token is requested before any actor-trust check returns; that `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is **inactive** in this configuration; that the `author_association` clause is a prefilter and not a permission check; and that both the inertness of an unconfigured fork (U2) and the prefilter's effect (U12) are unproven and P03 must prove them before the variable is flipped anywhere public.

### Principles and implementation

**Shared requirement, source, agreement level.** The requirement behind `py`'s two files is: *every pull request receives a first-pass automated review before a human reads it, and a maintainer can summon an agent into an issue or review thread without leaving GitHub.* Its source is the `py` implementation at pinned commit `b08bccfb55d05f15e46a83b52c5660b1881d19f5` (both files read verbatim, `source-repos-pinned.log`) plus ledger rows F051/F052.

The agreement level is **policy or mechanism**, the third row of the agreement-level table in the design spec §2 (`docs/superpowers/specs/2026-09-01-rs-port-research-program-design.md`), which defines it as "Any deliberately shared value, protocol detail or tool, with its owner decision or evidence", varying in "Only the aspects outside that agreement; low-level choices can be shared when that level is intentional". The spec presents the three levels **unordered**, and no ranking among them is claimed here. Revision 2 called this level "the weakest of the three levels in `docs/port/README.md`"; that was wrong twice over and is withdrawn — `docs/port/README.md` mentions "agreement level" exactly once, at line 56, in a passing clause about A5 adjudication, and carries no list of the levels and no ranking; and spec §2's definition allows the *narrowest* variation of the three, not the widest.

The assignment is argued from what §2 says rather than from a rank. §2 requires that a policy-or-mechanism agreement carry "its owner decision or evidence". There is no owner decision registering these two workflows as a shared value, and the evidence in `## Context` shows the sources already disagree. Three observations place the requirement at this level rather than at "capability or standard" or "architectural pattern":

1. `ts-launch-blueprint` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00` ships eight workflow files, none AI-related, and zero paths under `.github/` matching `claude` (`source-repos-pinned.log`: the `ls-tree` listing the eight files exits **0**; the `ls-tree … | grep -ci claude` that returns the zero count exits **1**, which for `grep -c` *is* the zero-match result — see check 6). A capability-level or pattern-level agreement would already be violated by one of the three siblings; a policy-or-mechanism agreement without a registered owner decision is exactly what an unmatched sibling looks like.
2. Nothing in the capability is ecosystem-shaped, so there is no architectural pattern whose fitness in Rust could be the thing that must agree. The action reads a diff and posts comments; the diff being Rust changes no mechanism. There is no Rust analogue to select and no Rust idiom to honor.
3. The reviewing entity is a paid third-party service reached with an organization credential. Whether to spend it here needs "its owner decision or evidence" in §2's words, which is precisely why "`py` does it" cannot settle it.

**What must agree; what may vary.** What must agree across `py`, `ts` and `rs` is the **guard contract**, because it is simultaneously a security property and a correctness property and is ecosystem-neutral. It has four clauses, and clause (a) is scoped at revision 3 to the lane it actually binds:

- (a) **The review lane** — the only lane triggered by a `pull_request` event — never runs on a pull request from a fork, on the ground that a fork run cannot obtain the credential and could only fail. That is **a platform runtime behaviour that no check here executed**; the support available is the maintainer's own `.github/workflows/claude-review.yml` at `v1.0.220`, which carries the identical guard with the comment "Skip on fork PRs since they can't mint the OIDC token used for Claude API auth" (`action-source-v1.0.220.log`), plus `py`'s own guard comment recording that the action "aborts on non-human actors … which showed as a **false red check** on the v2.4.1 release PR (#470)" and that "Skipping is a neutral (non-failing) outcome for this non-required job" (`source-repos-pinned.log`) — reference concordance and one field report, not an observed run (see **U3**). Revision 2 stated clause (a) as a property of the whole contract; that was inaccurate against this decision's own fixtures, and revision 3 corrects it. **The assistant lane cannot carry this clause and does not need it**: none of its four events is a `pull_request` event, so `GITHUB_REF` is the default branch, no fork ref is checked out, and the run happens in the base repository with its credentials by design. The assistant lane's fork-adjacent exposure is a *comment* on a fork pull request, which is `#1068`'s case and is answered by clause (d), not by a same-repository test.
- (b) Neither lane runs when either the pull-request author or the run's initiator is a bot.
- (c) No credential is reachable from a run whose content an untrusted contributor controls.
- (d) **New at revision 3.** On a public repository the assistant lane never *starts* for an author outside `OWNER`, `MEMBER` or `COLLABORATOR`. This is a prefilter, not a permission check: `author_association` is not the same predicate as write access, and an organization `MEMBER` without write access passes it and is then refused by the action's own `checkWritePermissions` — which, **corrected at revision 4**, is called not by either mode but once in the shared entrypoint, `src/entrypoints/prepare.ts:44`, after `setupGitHubToken()` at `:37` (`action-entrypoint-plugins-v1.0.220.log`, E2). It admits every write-access holder — a repository collaborator reports `COLLABORATOR`, an organization member reports `MEMBER`, the owner reports `OWNER` — so it introduces no false refusal for a legitimate maintainer, and it is defence in depth in front of an authoritative action-side check, never a replacement for it.

What may vary per repository: whether the capability is enabled at all, which events are listened to, which model, and which prompt.

Inside architecture A, `anthropics/claude-code-action` is selected over `The-PR-Agent/pr-agent`, `google-github-actions/run-gemini-cli` and `openai/codex-action` because it is the only candidate that (i) covers **both** members with one component, one credential and one App installation, (ii) is on a stable `v1` series with **no `v2` tag** among the 287 tag refs returned (`action-release.log`, HTTP 404 and `gh` exit 1 on `git/ref/tags/v2` — the correct result for a ref that does not exist), and (iii) has the maintainer running both shapes against its own repository in a form that can be read at a tag.

**Why the selected design preserves each principle.** Clauses (a) and (b) of the guard contract are carried over from `py` byte-for-byte on the review lane, so they are preserved by construction there, and clause (a) is now scoped to that lane for the reason given above. Clause (c) is preserved by the enable flag downstream and by clause (d) upstream. The two **additions** to `py`'s shape exist because `py`'s guard protects neither a template consumer nor a public origin repository:

*The enable flag, for the consumer.* In a repository created from the template, an internal PR satisfies `head.repo.full_name == github.repository`, so the fork guard passes and the job runs with no credential. The platform bounds the available fix: `jobs.<job_id>.if` may read only `github, needs, vars, inputs`; `secrets` is absent there and from `jobs.<job_id>.steps.if` as well, while it *is* available in `jobs.<job_id>.env` (verified, `contexts-availability.log`, and independently by `actionlint`, which rejects `if: secrets.X != ''` at the job level, `actionlint.log`). A `vars`-gated job is therefore the only single-line mechanism the context table permits at the job level, and its **intended** effect is that both files are inert in every unconfigured downstream repository while the origin repository needs one variable write. That intended effect is a design purpose, not an observed one: the **runtime** outcome — a `skipped` job rather than a failed one — is **U2**. The step-level alternative (`env: HAS_CRED: ${{ secrets.X != '' }}` read by `steps.if`) is legal under the same table; its expected drawback is that a skipped *step* would sit inside a job still reporting green, reading as a passing review that never happened — also a runtime expectation, reasoned from the same table and likewise never executed here.

*The author-trust prefilter, for the origin repository.* `author_association` arrives through the `github` context, which the same context table lists as available in `jobs.<job_id>.if`, so `#1068`'s suggested fix is expressible at the job level; `actionlint` accepts the four-clause form with exit 0 (`actionlint.log`, revision-3 addendum, fixture `candidate-claude.r3.yml`). The clause is written in the exact shape `#1068` asks for, `contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.<payload>.author_association)`, and `doxa-openai` independently asks for "a trusted association prefilter where practicable" (`raw/doxa-openai.normalized.md:388`). What the prefilter does **not** do is stated with it, three times over: it is not a write-access check (clause (d) above); it does not stop the run for an OWNER, MEMBER or COLLABORATOR who pastes untrusted text, which is the residual carried into the runner-up's third condition; and it would **not** have stopped the published chain's Phase 2, whose triggering comment came from a trusted author and whose body was tampered with afterwards — that vector is closed instead by the action's own `isBodySafeToUse` at `v1.0.220`, read in source (`action-guard-source-v1.0.220.log`, G4).
