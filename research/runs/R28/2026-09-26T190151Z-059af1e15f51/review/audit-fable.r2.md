## Finding 1 — JF-5: the R30 coupling is neither handed off nor mentioned

**Failed claim.** The F109 row, line 23: "`rust-lang.rust-analyzer` alone. It formats with the toolchain's `rustfmt` and supplies type diagnostics itself, so no separate type-checker extension is needed (the ts pattern)". The OVERRIDE, line 96: "`.vscode/settings.json` is `{ "rust-analyzer.check.command": "clippy" }`". The `re-verify:` list, line 136, names R06, R27, R49 and R69 but not R30.

**Evidence.**
- The prompt, `inputs/prompt.md:31`, names R30 as a coupling. It says to "assume R30 has picked a checker (likely `rust-analyzer`'s built-in diagnostics or a `cargo check`-based gate) and recommend the matching editor extension, without re-deciding which checker runs in CI".
- Both legs answer that coupling explicitly. `raw/opus.md:217-219`: "R30 (type-check) — if R30's gate is `cargo check`/clippy, rust-analyzer's `check.command` already runs the same command, so no extra extension is needed". `raw/muse.md:603-605`: the diagnostics rust-analyzer surfaces are "the same command family R30's gate uses — engine owned there".
- The decision drops that statement. It is not in the list of points where the legs agree (line 201), and it is not in the decision's own text.
- The R30 prompt (`topics/30-type-check-gate/prompts/type-check-gate.prompt.md:9`) assigns F107, "single engine serving both CI and editor", to R30. The decision's `check.command = "clippy"` key selects the command the editor's on-save check runs. That is the editor half of F107's question. The decision does not say that this key is an input to R30, or that R30's choice could change it.
- R30 is `open` (`research/CLAUDE.md:36`). R30 publishing a different checker arrangement is therefore a live event that could invalidate F109 or the override. It is not a re-verify trigger.

Revision 2 repaired the same class of omission for R27/F100 (line 113). The R30 coupling, which the same prompt names, remains unaddressed.
