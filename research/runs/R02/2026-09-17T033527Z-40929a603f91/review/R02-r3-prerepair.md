## Decision

**Recommendation — one stack.** A Cargo **root-package workspace** of four packages:

| Package | Directory | Role |
|---|---|---|
| `rs-launch-blueprint` | repository root | the published facade: `[lib] src/lib.rs`, `[[bin]] rslbp`, `[[bin]] rslbp-serve`, the composition root, the production adapter |
| `rs-launch-blueprint-core` | `crates/core/` | models, ports, services, the error catalogue, the shipped `InMemoryProjectsPort`. No CLI or web framework, no HTTP client |
| `rs-launch-blueprint-cli` | `crates/cli/` | the CLI front end. Depends on `core` only |
| `rs-launch-blueprint-web` | `crates/web/` | the web front end, an **optional** dependency of the facade. Depends on `core` only |

with these four enforcement mechanisms and nothing else:

| Mechanism | Settles | Tier |
|---|---|---|
| The crate edge itself — a crate may name only crates listed in its own `Cargo.toml`, and Cargo refuses a reverse edge as a cycle | F003, F004, F005, F007, the adapters half of F006, F021 | every `cargo check`, continuously |
| `cargo-deny` **0.20.2**, invoked `cargo deny --all-features check bans`, configured by a repository-root `deny.toml` `[bans] deny[].wrappers` | F008 | pre-push + CI |
| A per-member `crates/core/clippy.toml` (`disallowed-types`, `disallowed-methods`) with the deny level carried by `[workspace.lints.clippy]`, backed by `cargo check` itself | F009 | the contributor's own edit loop |
| A dependency-free `tests/workspace_edges.rs` in the facade asserting that `cargo metadata --no-deps` produces exactly the intended intra-workspace edge set, plus `crates/core`'s external-dependency allow-list | F010 | wherever `cargo test --workspace` runs |

**Ledger rows settled: F003, F004, F005, F006, F007, F008, F009, F010, F020, F021, F116.**

**Not selected**, each for a stated reason below: a single package with module visibility; an intra-crate layer-contract linter (`boundary` 0.27.0, `cargo-modules` 0.27.0, the ArchUnit ports); a virtual-manifest workspace; an `xtask` architecture checker (`cargo_metadata` 0.23.1, `cargo-depgraph-check` 0.1.0, `dep_graph_rs` 0.2.0); `guppy` 0.18.0 as a custom-lint substrate, excluded on fit because the template's whole edge set is four rows and `serde_json` parses them in twenty lines; `hexser` 0.6.0, an invasive macro and dependency-injection framework that would couple the domain to an external opinionated macro library, which is the opposite of what F004 asks for; `cackle` 0.2.0, which constrains *what a crate may do* (network, filesystem, process) rather than *which crate a member may depend on*, and so answers a different question; and the unused-dependency family `cargo-machete`, `cargo-udeps`, `cargo-shear` and `cargo-hakari`, which find unused or duplicated dependencies and shrink build times and none of which can express "only this member may depend on `axum`".

No `import-linter`/`tach` analogue is adopted, because in Rust the compiler is the analogue — at *crate* granularity only. That qualification is the whole of this item, and it is why the topology and the enforcement are one decision rather than two.

### Principles and implementation

**Shared requirement.** Architectural boundaries are enforced by a machine, not by review. Concretely: the composition root is reachable only from front ends and never from the core (F003); the core never depends on a front end (F004); front ends never depend on each other (F005); the core's own layers stay ordered (F006); no CLI or web framework enters the core, guarded both authoritatively and in a fast local tier (F008, F009); the permitted edges are declared in one readable artifact rather than inferred (F010); and the check runs at a defined place in the hook and CI pipeline (F116).

**Source and agreement level.** `py-launch-blueprint` at pin `b08bccfb` states the principle in its own words — `docs/adr/0017-hexagonal-core-and-boundary-enforcement.md`, "enforce the boundaries mechanically rather than by convention" — and realizes it in five `import-linter` contracts (`pyproject.toml:318-355`), a `tach.toml` module graph, and a subtree-scoped `ruff.toml` banned-api list (`src/py_launch_blueprint/core/ruff.toml:13`). `ts-launch-blueprint` at pin `cb1cbcb` has none of it; `docs/port/DIVERGENCE-ANALYSIS.md:77` records why — "ts's flat `src/` with one front-end and no core/front-end split leaves nothing for these tools to check (consequence of F001)". `DIVERGENCE-ANALYSIS.md:77-79,241` puts F003–F010 and F116 in one item-level bucket, cause class C, `harmonize: partly`; F020 is class C, `harmonize: no`; F021 is class G ("no precedent either side"), `harmonize: no`.

No shared low-level value is recommended. There is no owner requirement for one, and the evidence does not support the same tradeoff in all three ecosystems: Python's checker exists because the language has no compile-time module direction, while Rust's compiler makes the same guarantee stronger and free at the crate edge. The one value worth naming across all three is the **declared-graph artifact** (F010) — py has `tach.toml`, rs gets `cargo metadata --no-deps` plus an assertion test, ts has nothing — and even there the agreement is at capability level, not a shared file format.

**The question the whole item turns on was settled by execution, not by argument.** A one-package crate with `pub mod core_layer;` and `pub(crate) mod cli_layer;`, where `core_layer.rs` contains `use crate::cli_layer::CliThing;` — core reaching upward into the front end, exactly what F004 forbids — **compiles clean** (check `A`, `review/evidence/r02-workspace-probe.log`). This is not a gap in the lints. The Rust Reference defines visibility as who may *name* an item, and `pub(crate)` grants naming rights to the entire crate, including the module that must not have them. For this requirement, module visibility points the wrong way.

On the crate edge the same four violations are build failures (checks `C1`–`C4`): `E0433` for the code tier and `error: cyclic package dependency` from Cargo's own resolution for the manifest tier, before rustc runs.

**F009's mechanism is not a translation of py's; a literal port was ruled out by execution.** py's fast tier works because `ruff` resolves configuration per directory subtree. Clippy does not. Three executed cases decide it: a `clippy.toml` at the **package root** of a single package flagged `src/core_layer.rs` *and* `src/cli_layer.rs`, so it cannot ban a framework in the core without banning it in the CLI (check `D1`); a `clippy.toml` at `src/clippy.toml`, py's nested shape, was **ignored** — zero `disallowed type` diagnostics on code that a package-root file flags, while the crate still compiled, so the zero is not a compile failure (check `D2`); and `crates/core/clippy.toml` under `cargo clippy --workspace` flagged only `crates/core/src/lib.rs` and left the identical use in `crates/cli/src/lib.rs` untouched (check `D3`). F009's capability is available in Rust at *package* granularity and nowhere else, which makes the split a second, independent reason for itself rather than a consequence of the F004 argument.

**F008's configuration, and the one entry that cannot be written.** The `deny.toml` `[bans]` section carries one `deny` entry per framework:

```toml
[bans]
multiple-versions = "warn"
deny = [
  { crate = "axum", wrappers = ["rs-launch-blueprint-web"], reason = "core and the CLI are framework-agnostic (F008)" },
  { crate = "clap", wrappers = ["rs-launch-blueprint-cli", "rs-launch-blueprint"], reason = "argument parsing belongs to the CLI layer and to the serve binary's required global core (F008)" },
]
```

`wrappers` is keyed on the **banned crate** and requires *every direct dependent* in the resolved graph to be listed. This run executed the consequence the Opus raw predicted from reading `src/bans.rs` but could not test: a `tokio` row confined to the web member **fails a clean tree**, because `axum` depends on `tokio` directly and is therefore a second unlisted direct parent (checks `CD4a`, `CD4b`). **`tokio` deliberately has no row.** The mechanism for every crate `wrappers` cannot express is the F010 test's second table — `crates/core`'s external-dependency **allow-list**, keyed on the *protected member* rather than on the banned crate, which handles `tokio` cleanly and also catches a framework nobody thought to ban. The two members are complementary, not redundant. The `clap` row carries two wrappers because R69 puts the `rslbp-serve` binary's required global core on the facade; it needs re-verification once R60's companion crates are known, since a direct dependent such as `clap_complete` must be added to the list or the row dropped.

**Two operational findings that no engine report carries, both executed here.** First, `--all-features` is a **global** flag: `cargo deny check bans --all-features` — the form the Opus and perplexity legs imply — is rejected by the argument parser with `unexpected argument '--all-features' found` (check `CD5a`). Second, and this is why the flag is not optional for this topology: without it the resolved graph holds only the three non-optional packages, and the optional `rs-launch-blueprint-web` member, `axum` and `tokio` are **absent from it entirely** (checks `CD5b`, `CD5c`, `CD5d`). A default-feature run would therefore be checking a graph in which the web surface does not exist. The invocation this decision recommends is `cargo deny --all-features check bans`, in that order.

**A third executed finding corrects a claim about the web feature's reach.** The Opus raw states that with `web` off "`cargo build` does not compile the web member at all (verified)". That is true of a *root-scoped* build (check `B1`) and false of a workspace-scoped one: `cargo build --workspace` with the feature off compiles `rs-launch-blueprint-web` regardless, because **workspace membership, not the root package's feature, decides which members are built** (check `B3`). The optional-dependency edge governs the facade's graph, not the workspace's build set. This matters to R11's job shape and to any hook or CI command written `--workspace`; it does not change the topology, and the feature-gated `rslbp-serve` binary is still skipped by a default build, as `required-features` specifies (check `B4`).
