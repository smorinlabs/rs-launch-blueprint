### Principles and implementation

Shared requirement: the driven adapter must report "not there" and "transport broke" as two distinguishable outcomes of its return contract, and the application service — not the adapter — must decide that absence is a user-facing error. Source: py HEX-12 ("A port method returns `None`/`[]` for legitimate absence ... and raises `APIError` for transport failure. The application service, not the adapter, decides that absence is a user-facing error"), made cross-repo binding by the owner direction of 2026-09-04 ("This is a hex pattern that we've used before in the other repo. It would make sense to have a similar best practice pattern across all three", `docs/port/OWNER-REVIEW.md:231`, overriding the `harmonize: no` label on this Class-F item).

Agreement level: architectural pattern. What must agree across py, ts and rs is the split (adapter reports absence-as-data vs failure-as-error; service judges absence an error) and its observable criteria below. What may vary is the mechanism: py's `X | None` + `raise`, ts's nullable lookup + throw (proposed follow-on), and Rust's `Result<Option<T>, E>` + `ok_or_else` are three ecosystem-appropriate realizations of one principle. No shared low-level value is recommended: no explicit owner requirement and no same-tradeoff-in-all-ecosystems evidence supports one (notably, error-code spellings stay per-repo: `RSLB301` here vs py's `PLBP` catalog, consistent with R67 P1 where the token's spelling may vary).

Essential behaviors and observable acceptance criteria (for P03's template):

1. A lookup-style port method has three distinguishable outcomes: found, absent, broken. Observable: `get` on a missing id returns `Ok(None)`; on a dead transport returns `Err`; tests assert both arms, and assert the arms differ (absence is never `Err`, breakage is never `Ok(None)`).
2. The port error type has no not-found variant. Observable: `grep` for `NotFound` in the port/adapter error enum finds nothing; the enum names transport, I/O and decoding failures only.
3. Absence becomes a domain error at exactly one layer: the service call site. Observable: every `ok_or_else`/`ok_or` producing `NotFound` lives in service (application) modules; adapters contain none.
4. The domain error distinguishes not-found from transport failure as matchable variants feeding R67's catalog (`RSLB301` → 3 vs `RSLB101/102/103` → 1). Observable: a test matches each service outcome to its catalog code and exit.
5. Collection methods have no absence case. Observable: `list_*` returns `Result<Vec<T>, E>`; empty store yields `Ok(vec![])`, never `None`, never `Err`.
6. The contract is documented on the trait. Observable: every lookup-style port method carries a `# Errors` section stating `Err`-means-broken / `Ok(None)`-means-absent (C-FAILURE).

Is the shared pattern still appropriate in Rust? Yes, and the type system makes it cheaper than in py: py's `| None` relies on convention plus a separate `raise` the checker cannot require, while Rust's `Result<Option<T>, E>` forces the caller to handle both channels (`#[must_use]`, exhaustive match, `?`). The `?`-plus-`ok_or_else` call site is one expression versus py's three-line call/check/raise.

### Dominant choice

Honestly split by layer in the ecosystem, so no single shape dominates everywhere: Rust's own transport-adjacent APIs fold absence into the error channel as a distinguished kind (`std::fs` → `ErrorKind::NotFound`, executed in this run), while data-access facades offer the split shape and document absence-expected call sites against it (sqlx `fetch_optional` → `Result<Option<Row>, Error>`). For this template's question — a driven port seam behind which an HTTP/remote transport sits, consumed by an application service that owns the domain error — the applicable dominant is the split shape: the seam in this architecture is py-HEX-12's "adapter reports", not std's "syscall fails", and the maintained reference (sqlx) resolves the same tension the same way. The folded shape is the legitimate dominant only at the raw-transport layer (e.g. inside the HTTP adapter, a 404 response may transiently be an error-typed value before the adapter maps it to `Ok(None)` at the port boundary).

### Recommendation

Adopt the two-channel absence split as the template's port absence-vs-failure contract (F012):

1. Lookup-style port methods (single-resource reads such as `get_project`, `resolve_workspace_gid`) return `Result<Option<T>, PortError>`: `Ok(Some(t))` found, `Ok(None)` legitimately absent, `Err(_)` transport/I/O/decoding broke. `PortError` names transport failures only and has no not-found variant.
2. Collection-style methods (`list_projects`) return `Result<Vec<T>, PortError>`; an empty store is `Ok(vec![])` — no absence case exists for collections.
3. The service converts at the call site with `port.get(id)?.ok_or_else(\|\| DomainError::NotFound { … })?`: `?` (+ `From`) carries the mechanical transport leg, `ok_or_else` states the absence judgment explicitly. The resulting `NotFound` variant feeds R67's stable `RSLB301` → exit 3; transport failures feed `RSLB101/102/103` → exit 1.
4. The domain error is `thiserror`-derived in the library crate per R67 (consumed, not re-selected); it implements `std::error::Error` and is `Send + Sync` (C-GOOD-ERR). Every port method documents the contract in a `# Errors` section (C-FAILURE).
5. HTTP (and any future) adapters map the transport's own absence signal (e.g. status 404, a successful round-trip yielding "not there") to `Ok(None)` at the port boundary — before any status-to-error helper — so the seam never leaks transport-shaped absence.
6. The contract is seam-shape agnostic as required: the signature is identical for a trait method (R01's decided shape, executed here including `Arc<dyn ProjectsPort>` erasure), a generic bound, or an injected function value; only the trait form was executed, the others hold by construction (same `fn` signature).

### Ranked runner-up

Folded domain error: the port returns `Result<T, PortError>` with a `PortError::NotFound { … }` variant, and the service propagates with a single `?` (translating the port error into the domain error wholesale, if at all). Condition under which it wins: P03 implementation evidence shows the service layer never treats absence as anything but an error — i.e. every lookup call site converts identically and no caller branches on "absent but fine" — making the `Option` channel pure ceremony whose per-call-site `ok_or_else` costs more in boilerplate than it buys in explicitness. No such evidence exists now; absence-tolerant call sites (existence checks, upserts, create-if-missing) are foreseeable in a template, so the judgment site should stay visible until proven uniform.

### Tradeoffs

Versus the folded runner-up, the pick gives up single-`?` call sites (each lookup pays one `ok_or_else` combinator) and asks every service author to remember the conversion rather than getting `NotFound` "for free" from the seam. That cost is accepted because: (a) the conversion is the absence judgment the shared principle requires to be visible, and `ok_or_else` keeps it explicit, greppable and unit-testable per call site instead of buried in a `From` impl; (b) `?`-only propagation of a folded error cannot distinguish "judged" from "mechanical" conversions in review; (c) the cost is one expression (cheaper than py's three-line check-and-raise), compiler-checked (`#[must_use]` on both channels), and measured at zero dependencies and zero new build cost. Versus bare `Option<T>` (rejected alt C), the pick pays a `Result` wrapper — accepted because the seam is fallible and breakage must have a channel. Versus ts's inline shape (rejected alt D), the pick pays one more layer of indirection — accepted because the owner made the hex split binding across all three repos.
