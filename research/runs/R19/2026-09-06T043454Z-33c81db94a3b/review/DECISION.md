## Decision

**Adopt the two-entry, catch-all-group Dependabot configuration**: one `.github/dependabot.yml` declaring exactly the ecosystems this template has manifests for — `cargo` and `github-actions` — each with a single wildcard version-update group, a weekly Monday cadence, an explicit 5-day cooldown, the default open-PR budget written out, and one Conventional-Commits prefix contract. py's role taxonomy (`runtime` / `dev-tools` / `lint-and-format` / `test`) is **not** ported, because the `cargo` ecosystem cannot express a development-versus-production distinction at all. ts's `update-types: [minor, patch]` filter is **not** ported to the `cargo` entry, because Dependabot's `minor` is plain SemVer while Cargo's compatibility rule is not, so the filter would present a Cargo-incompatible `0.1 → 0.2` bump inside a group named for low-risk updates. Both rejections are stated at their exact evidential strength — including what remains possible and what was not read — under `### Principles and implementation`; this paragraph is the headline, not the full claim.

This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). It records what the research found and what it recommends; P03 builds the template and its CI proves the recommendation. Dependabot is a hosted service whose behavior is observable only on a live repository, so *no* part of this configuration has been executed — what the empirical check below verifies is the schema, the running implementation behind it, and the live behavior of other people's repositories. `## Engines` lists what P03 must validate and what remains unproven. A decision that does not survive implementation is revised against this recorded research, not researched again from scratch.

Six absences are deliberate, and each is load-bearing: `labels` (Dependabot's own defaults already produce the wanted outcome and a declared string that the consumer's fork lacks is ignored — see `### Principles and implementation`); `groups.<id>.dependency-type` and `commit-message.prefix-development` (neither reaches `cargo`); `cooldown.semver-*-days` (supported for `cargo`, **not** for `github-actions`, so writing it would desymmetrize the two entries); `versioning-strategy` on the `github-actions` entry (not in that key's supported-ecosystem list); and the `npm`/`uv` entries py and ts carry (this template has no JavaScript or Python manifest). `rust-toolchain` — a live ecosystem — is also not declared, for the reason given under *Ecosystem set* below.

### Principles and implementation

**Shared requirement, its source, and the agreement level.** The principle behind both source configurations is: *a repository's dependency and workflow-action versions are refreshed automatically, on a fixed cadence, in a small number of reviewable pull requests that are themselves subject to the repository's own commit contract.* Source: py `.github/dependabot.yml` at pin `b08bccfb` (ecosystems `uv`, `github-actions`, `npm`; four name-keyed groups; `cooldown.default-days: 5`; `labels`; `commit-message` with `prefix: chore`, `prefix-development: chore`, `include: scope`; `open-pull-requests-limit: 5`; `schedule.day: monday`) and ts `.github/dependabot.yml` at pin `cb1cbcb2` (ecosystems `github-actions`, `npm`; one `update-types: [minor, patch]` group per ecosystem; weekly; no cooldown, labels or commit-message key) — both re-read through their pins in this run (evidence log section 12). `docs/port/DIVERGENCE-ANALYSIS.md:103` classifies R19 as class **A**, `harmonize: partly` — "grouping-strategy shape can be one org value; the `cargo` ecosystem key itself is Rust-specific". The agreement level is therefore **policy**: the *shape* of the answer (how many groups, whether routine updates are batched, whether a cooldown exists and how long, whether PRs are identifiable by label, whether bot commits conform to the commit contract) is one org value; the ecosystem keys, and any key whose availability is ecosystem-bound, are necessarily per-repository.

**Essential behaviors any answer must produce.**

1. Every dependency source the repository actually has is declared, and nothing else.
2. Routine version updates arrive batched, on a fixed cadence, in a bounded number of open PRs.
3. A newly published release is not proposed the instant it appears.
4. Security updates are never delayed or batched behind the routine cadence.
5. Every Dependabot commit satisfies the repository's own commit-message contract (`commit-message-convention`, owned by R38).
6. A batched PR cannot land a change that violates a fixed parameter — here the MSRV policy — without CI catching it.

**Why A cannot be ported (capability, not taste).** Dependabot's Cargo package manager registers its production check as a constant:

```ruby
Dependabot::Dependency.register_production_check("cargo", ->(_) { true })
```

read at `dependabot/dependabot-core` commit `1abafc5ca0900334fd970832e9ef43f2afc78233`, path `cargo/lib/dependabot/cargo.rb` (retrieved 2026-09-10, evidence log section 2; the npm package manager registers a non-trivial check at the same layer, section 2b, which is the control). Every Cargo dependency is therefore "production" to Dependabot, whatever manifest table it sits in. Three documented keys follow, and none reaches `cargo`: `groups.<id>.dependency-type` is "Supported by: `bundler`, `composer`, `mix`, `maven`, `npm`, and `pip`"; `commit-message.prefix-development` is "Supported by: `bundler`, `composer`, `mix`, `maven`, `npm`, `pip`, and `uv`"; and `commit-message.include: scope`, which appends "`deps` or `deps-dev`", can only ever append `deps` for a Cargo entry. Both support lists quoted verbatim from the options-reference source, `github/docs` commit `dd75c5f38a14d1c07c3982beddb471a605b142f7`, path `content/code-security/reference/supply-chain-security/dependabot-options-reference.md` (retrieved 2026-09-10, evidence log section 3), rendered at <https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference>. **The precise claim:** py's runtime-versus-dev-tools *predicate* is a capability the Cargo ecosystem does not have. A hand-maintained list of crate *names* could imitate the grouping, and that residue is what the template-fit argument below rejects; what no configuration can recover is the dev/production distinction itself.

**Why A is also wrong for a template (fit).** py's four groups name roughly twenty concrete packages (`click`, `pydantic`, `ruff`, `pytest*`, …) at pin `b08bccfb`. A template's dependency names are the first thing a consumer replaces; the day a consumer swaps one crate for another or drops the web crate, a name-keyed group silently stops matching, and the documented rule "Any outdated dependencies that do not match a rule are updated in individual pull requests" (options-reference source, retrieved 2026-09-10) quietly restores the noise the group existed to remove. A `patterns: ["*"]` group contains no repository-specific string and so cannot rot this way. The three surveyed projects that do keep name-keyed families — servo, nushell, datafusion — each have a versioned crate family (`objc2*`, `polars-*`, `arrow*`) that must move in lockstep; a three-crate template has none.

**Why B is wrong for the `cargo` entry (semantics).** The Cargo book states the compatibility rule as "versions are considered compatible if their left-most non-zero major/minor/patch component is the same", with `0.2.3 := >=0.2.3, <0.3.0` and `1.2.3 := >=1.2.3, <2.0.0` (<https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html>, retrieved 2026-09-10, evidence log section 4). Dependabot's `update-types` offers only "Supported values: `minor`, `patch`, and `major`" — plain SemVer levels (options-reference source, retrieved 2026-09-10, evidence log section 3) — and the open request to add Cargo-aware values spells out the consequence: "a version upgrade from v0.1.0 to v0.2.0 is considered 'incompatible' even though, by typical SemVer standards, it is minor", asking for `cargo-compatible`/`cargo-incompatible` values on `ignore.update-types` and `groups.*.update-types` (`dependabot/dependabot-core` issue **#9681**, state `open`, created 2024-05-06, updated 2026-08-04, 2 comments, read at `GET https://api.github.com/repos/dependabot/dependabot-core/issues/9681`, retrieved 2026-09-10, evidence log section 5). **The precise claim, and its limit:** the documented value set and the open request together establish that Dependabot's `minor` is plain SemVer and has no Cargo-aware variant, so a group labelled "minor and patch" would contain bumps Cargo treats as incompatible. This run did **not** read or execute Dependabot's version-classification code path; `common/lib/dependabot/dependency_group.rb` was read and contains no Cargo-specific rule ("left-most", "cargo" both absent — evidence log section 5), which is corroborating absence, not proof. Pre-1.0 crates are ordinary in a Rust dependency tree, so this is not an edge case. The same filter is harmless on `github-actions`, whose versions are release tags with no 0.x convention; it is dropped there only so both entries carry one house shape.

**Why C preserves each behavior.** Behavior 2: "All updates for dependencies that match a rule are combined in a single pull request", and a wildcard pattern matches every dependency, so nothing falls back to an individual PR through non-match (options-reference source, retrieved 2026-09-10). GitHub's own guidance names this the starting point — "A single wildcard group is the simplest starting point. If you later find you want, say, patch-level and major-version updates handled differently, break the wildcard into more targeted named groups" (<https://github.blog/security/supply-chain-security/tame-dependabot-group-your-updates-slow-the-cadence-keep-security-fast/>, retrieved 2026-09-10, carried over from the Opus raw). Behavior 3 and 4: the platform now applies "a **default cooldown period of 3 days** to version updates, even when `cooldown` is not configured", and "**This default cooldown does not apply to security updates**" (options-reference source, retrieved 2026-09-10, evidence log section 3); `default-days: 5` raises the window to py's recorded value and states the policy where a template consumer will read it. Security PRs are additionally exempt from the PR budget: "_Security update_ pull requests are not subject to this limit and do not count toward it" (same source). Behavior 5: `prefix: "chore"` with `include: "scope"` yields `chore(deps): …`, and `chore` is in R38's eleven-type enum. Behavior 6 is *not* provided by any Dependabot key — see the MSRV paragraph below.

**Two absences argued from evidence rather than from taste.**

*Labels.* `dependabot-core` registers a label per ecosystem — `register_label_details("cargo", name: "rust", …)` and `register_label_details("github_actions", name: "github_actions", …)` — on top of `DEFAULT_DEPENDENCIES_LABEL = "dependencies"` (paths `cargo/lib/dependabot/cargo.rb`, `github_actions/lib/dependabot/github_actions.rb`, `common/lib/dependabot/pull_request_creator/labeler.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log sections 2 and 2c). Those defaults were then observed on live pull requests at `ratatui/ratatui`, which declares no `labels` key: `dependencies+rust` on Cargo PRs and `dependencies+github_actions` on Actions PRs (evidence log section 10, retrieved 2026-09-10). Dependabot "creates these default labels automatically, as necessary in your repository", whereas of a custom label the same page says "If any of these labels is not defined in the repository, it is ignored" (both sentences read verbatim from the pinned options-reference source, evidence log section 16). A template is copied into forks whose label sets the template does not control, so the declared form carries a failure mode the omitted form does not — and py's own file illustrates it: py declares the hyphenated `"github-actions"`, while the default Dependabot creates is the underscored `github_actions`. Acceptance criterion A8 is met by the defaults; the taxonomy belongs in a comment, not in a key. This is the one place where restating a default is *not* safe, which is why `open-pull-requests-limit: 5` and `applies-to: version-updates` — both documented defaults whose effect depends on nothing outside the file — are written out for the reader while `labels` is not.

*`prefix-development` and a `deps-dev` scope.* Both are unavailable for `cargo` (support list above) and could not fire even if accepted, since no Cargo dependency is ever in Dependabot's "Development dependency group". The template's documentation should say so: a Cargo bump always scopes as `(deps)`, never `(deps-dev)`, which is a real loss of information relative to py's `uv` entry and is not recoverable by any key.

**Why the commit-message keys are written rather than inherited.** Dependabot's default is "Commit messages follow similar patterns to those detected in the repository" (pinned options-reference source, evidence log section 16) — a heuristic, not a contract. This run watched the heuristic work: `ratatui/ratatui` declares no `commit-message` key and its Dependabot titles read `build(deps): bump duct from 1.1.1 to 1.1.2` (evidence log section 11, retrieved 2026-09-10). `build` happens to be in R38's enum too, but the heuristic reads a repository's *own* history, which a freshly generated template consumer's repository does not have, and R38's F157 fails the PR when a guess lands outside the enum. **One consequence must be stated rather than glossed:** a grouped subject is long. The live grouped titles observed in this run take two forms — `chore(deps): bump the all-other-cargo-deps group across 1 directory with 6 updates` (datafusion) and `build(deps): bump the rust-dependencies group across 1 directory with 23 updates` (helix), against the shorter `bump the arrow-parquet group with 9 updates` form (evidence log section 7). For this decision's group identifiers, the longer form measures **68 columns** for `cargo` and **77** for `github-actions`, or **60** and **69** under F152's soft-line measurement (to the last space) — all above R38's 50-column header cap. R38's F156 relaxes only the width rules for pull requests opened by `dependabot`, keeping grammar and the type enum enforced, so the configuration is compatible with the commit contract *because of that exemption*, not despite short titles. Those four numbers are arithmetic over the live title format, not an executed `committed` run; A7 is the check that settles it.

**Why `versioning-strategy` is written on the `cargo` entry.** The value restates today's Cargo default, and the implementation says why that default is right here: `RequirementsUpdateStrategy::BumpVersionsIfNecessary`, commented "Cargo resolves to the newest compatible version and a bare version is a caret-equivalent (compatible) requirement, so only raise the requirement when it doesn't already allow the new version. Avoids needless churn and MSRV bumps." (`cargo/lib/dependabot/cargo/update_checker.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log section 6). Cargo also accepts only three of the five documented values — `ALLOWED_UPDATE_STRATEGIES = [LockfileOnly, BumpVersions, BumpVersionsIfNecessary]`, with `check_update_strategy` raising "Unknown update strategy" otherwise (`cargo/lib/dependabot/cargo/update_checker/requirements_updater.rb`, same commit) — so the documented `widen` value is not available to a Cargo entry even though the key's own page lists `widen` generically. The key is not in the `github-actions` support list ("Supported by: `bundler`, `cargo`, `composer`, `helm`, `mix`, `npm`, `pip`, `pub`, and `uv`", evidence log section 3), hence its absence there. Writing it costs one line and pins the behavior the MSRV policy wants; it carries no consumer-repository dependency, unlike the label case.

**The Rust-specific risk no Dependabot key addresses: MSRV.** The fixed `msrv-policy` requires `rust-version` in `Cargo.toml` and an MSRV job in CI. Dependabot does not read `rust-version`: the request to do so is open — `dependabot/dependabot-core` issue **#5423**, created 2022-07-26, updated 2026-01-05, 7 comments (`GET https://api.github.com/repos/dependabot/dependabot-core/issues/5423`, retrieved 2026-09-10, evidence log section 5b). Cargo's own resolver did gain MSRV awareness (`resolver = "3"`, `resolver.incompatible-rust-versions`, with `edition = "2024"` selecting it — <https://doc.rust-lang.org/cargo/reference/resolver.html>, retrieved 2026-09-10, evidence log section 14), so the fixed `rust-edition` puts the resolver in the MSRV-aware mode; that is a mitigation, not a substitute, because Dependabot picks a target version before Cargo resolves. **The guard is the CI MSRV job, and this item does not weaken it.** The template's documentation carries the remediation: a grouped PR that fails the MSRV job is resolved by adding an `ignore` entry for the offending crate, never by relaxing the job.

**Ecosystem set, and the one workspace fact that fixes `directory`.** Of the 14 Rust repositories surveyed by the Opus raw, 11 declare `cargo`, 14 declare `github-actions`, and 0 declare `rust-toolchain`. `cargo` is the only key that reads `Cargo.toml`/`Cargo.lock`; `github-actions` is what keeps R20's SHA-pinned actions fresh, so omitting it strands that policy. `rust-toolchain` is live on github.com and "supports automatic updates for Rust toolchain versions defined in `rust-toolchain.toml` and `rust-toolchain` files" for "Versioned toolchains such as `channel = "1.xx.yy"` and `channel = "1.xx"`" and dated nightly/beta channels (`data/reusables/dependabot/supported-package-managers.md` at `github/docs` commit `dd75c5f3`, retrieved 2026-09-10, evidence log section 15). R42 commits `rust-toolchain.toml` but leaves the `channel` **value** to R27, which is open (`research/topics/42-dev-toolchain-provisioning/DECISION.md:18`), so this entry is deferred rather than declined on principle: it becomes correct the moment R27 fixes a numeric channel. On `directory`, Dependabot's Cargo parser calls `check_rust_workspace_root` and raises "This project is part of a Rust workspace but is not the workspace root" when pointed at a member (`cargo/lib/dependabot/cargo/file_parser.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log section 6b) — so one entry at `/` covers the CLI, library and web-service crates, and a per-crate entry would be an error rather than merely redundant. This constrains P03's manifests: shared versions belong in the workspace-root `[workspace.dependencies]` table, and requirements stay bare/caret rather than `=`-pinned, or `increase-if-necessary` has nothing to do.

**Reference implementations, and what they do and do not prove.** The schema's single implementation is `dependabot/dependabot-core` (MIT; maintenance state **active**: `archived: false` with a same-day `pushed_at`, per the Opus raw's `GET https://api.github.com/repos/dependabot/dependabot-core`, 2026-09-10). It is a hosted service, never linked into the template. The closest *configuration* reference for the recommended shape is `ratatui/ratatui`'s file (two entries, catch-all group each, cooldown, PR limit, `versioning-strategy` on Cargo) — but this run found that repository's configured values are **not in force**, so it is cited as a shape precedent only and never as behavioral evidence (see `## Engines`, disagreement 5). The behavioral references are `cargo-bins/cargo-binstall` and `apache/datafusion`, whose `patterns: ["*"]` Cargo groups were each observed producing a group branch on 2026-09-10 (evidence log section 7). **Performance is not a meaningful axis for this item**: nothing runs on a developer machine or in the template's build, no workload, latency, throughput or resource cost applies, and the cost of a wrong answer is measured in reviewer attention per week, instrumented by the count of open Dependabot PRs.

**Cross-repo follow-on rationale** (this project changes neither source repository): ts should gain a `cooldown` and a `commit-message` prefix to reach the same policy shape; py should either drop its `labels` key or define the hyphenated `github-actions` label in its repository, because the default Dependabot creates is `github_actions` and "If any of these labels is not defined in the repository, it is ignored".

re-verify: 2027-03-10, or earlier on any of: `dependabot-core` implements #9681 (`cargo-compatible`/`cargo-incompatible` update types), which reopens the grouping predicate; `dependabot-core` implements #5423 (`rust-version` awareness), which changes what the CI MSRV job must catch; R27 fixes a numeric `rust-toolchain.toml` channel (add a `rust-toolchain` entry); R51 lands a Dockerfile or R44 a devcontainer (add that ecosystem); GitHub changes the platform default cooldown or renames an ecosystem's default label; P03's first four weeks of Dependabot PRs show the catch-all group is not batching, or that one weekly PR is too large to review.

## Parameters

The prompt's `- owns:` line is empty; this item owns no parameter, so there are no `owns` lines. Its `- consumes:` line is empty; there is no consumed parameter, so there are no consumed-parameter lines.

- assumes msrv-policy = stable minus 2 minor versions, raised only in a minor release, declared as rust-version in Cargo.toml and tested in CI
- assumes rust-edition = 2024
- assumes target-os-matrix = ubuntu-latest, macos-latest
- assumes license = MIT OR Apache-2.0

How each bears on the decision. `msrv-policy` is the parameter this item is least able to protect: Dependabot cannot read `rust-version` (#5423, open), so `versioning-strategy: increase-if-necessary` reduces MSRV-raising manifest churn without eliminating it, and the CI MSRV job stays the guard (acceptance criterion A9). `rust-edition = 2024` matters only because edition 2024 selects Cargo's MSRV-aware resolver, which mitigates the same risk one layer down. `target-os-matrix` is untouched: Dependabot runs on GitHub's infrastructure, not in the template's runner matrix, though every PR it opens is gated by that matrix. `license` is untouched: this item adds no crate to `Cargo.toml`, so nothing enters the dependency tree or the licence graph. No `CONFLICT:` line: neither raw raised one, and the recommendation needs no registered value changed.

Two researched parameters owned elsewhere bear on the decision without being consumed by it, so neither appears above. R38's `commit-message-convention` supplies the type enum that makes `chore(deps): …` grammatical, the 50-column soft-line header cap that a grouped subject exceeds, and the F156 `dependabot` width exemption that makes the long subject acceptable. R11's `ci-job-structure` (still open) decides which job gates a grouped PR; a required check or auto-merge rule keyed on a label must key on `dependencies`, which `dependabot-core` applies as `DEFAULT_DEPENDENCIES_LABEL` to every pull request it opens and which was present on every Dependabot PR sampled in this run, rather than on an ecosystem label.
