## Decision

**Adopt the two-entry, catch-all-group Dependabot configuration**: one `.github/dependabot.yml` declaring exactly the ecosystems this template has manifests for — `cargo` and `github-actions` — each with a single wildcard version-update group, a weekly Monday cadence (carried from py rather than argued from the survey — see *Cadence* below), an explicit 5-day cooldown, the documented default open-PR budget of five written out, and one Conventional-Commits prefix contract. Both numeric keys reach **version updates only**: the pinned options reference states that the `cooldown` option "is only available for _version_ updates, not _security_ updates" and that "_Security update_ pull requests are not subject to this limit and do not count toward it", and the documented default the `5` restates is "If five pull requests with version updates are open, no further pull requests are raised" (`github/docs` commit `dd75c5f38a14d1c07c3982beddb471a605b142f7`, lines 187, 548 and 545, asserted by `review/evidence/r19-check-r5.sh`, retrieved 2026-09-15). py's role taxonomy (`runtime` / `dev-tools` / `lint-and-format` / `test`) is **not** ported, because the `cargo` ecosystem cannot express a development-versus-production distinction at all. ts's `update-types: [minor, patch]` filter is **not** ported to the `cargo` entry either — but for the opposite reason to the one revision 1 gave. Revision 1 claimed the filter would *admit* a Cargo-incompatible `0.1 → 0.2` bump because Dependabot's `minor` is plain SemVer; **that mechanism does not exist**, and the classifier at the very pin revision 1 cited refutes it (`### Principles and implementation`, *Why B is rejected*, and `## Empirical check` sections 5a–5e). Dependabot classifies a Cargo `0.1 → 0.2` bump as `major`, so a `[minor, patch]` group **excludes** it. The filter is rejected because that exclusion, applied to a Rust dependency tree, is dense: every pre-1.0 minor release falls out of the group into an individual pull request, which re-partitions the review load rather than batching it and defeats essential behavior 2. The two rejections rest on different kinds of evidence and are stated separately at their exact evidential strength — the taxonomy rejection on a capability the `cargo` ecosystem does not have, the filter rejection on a volume consequence of a capability it does have — under `### Principles and implementation`; this paragraph is the headline, not the full claim.

This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). It records what the research found and what it recommends; P03 builds the template and its CI proves the recommendation. Dependabot is a hosted service whose behavior is observable only on a live repository, so *no* part of this configuration has been executed — what the empirical check below verifies is the schema, the running implementation behind it, and the live behavior of other people's repositories. `## Engines` lists what P03 must validate and what remains unproven. A decision that does not survive implementation is revised against this recorded research, not researched again from scratch.

      prefix: "chore"
      include: "scope"
    groups:
      github-actions:
        applies-to: version-updates

Six absences are deliberate, and each is load-bearing: `labels` (Dependabot's own defaults already produce the wanted outcome and a declared string that the consumer's fork lacks is ignored — see `### Principles and implementation`); `groups.<id>.dependency-type` and `commit-message.prefix-development` (neither reaches `cargo`); `cooldown.semver-*-days` (supported for `cargo`, **not** for `github-actions`, so writing it would desymmetrize the two entries); `versioning-strategy` on the `github-actions` entry (not in that key's supported-ecosystem list); and the `npm`/`uv` entries py and ts carry (this template has no JavaScript or Python manifest). `rust-toolchain` — a live ecosystem — is also not declared, for the reason given under *Ecosystem set* below.

### Principles and implementation

**Shared requirement, its source, and the agreement level.** The principle behind both source configurations is: *a repository's dependency and workflow-action versions are refreshed automatically, on a fixed cadence, in a small number of reviewable pull requests that are themselves subject to the repository's own commit contract.* Source: py `.github/dependabot.yml` at pin `b08bccfb` (ecosystems `uv`, `github-actions`, `npm`; **six groups**, of which four are the name-keyed `uv` groups this decision declines to port — `runtime`, `dev-tools`, `lint-and-format`, `test` — one is `npm`'s pattern-keyed `@commitlint/*`, and one is the `github-actions` entry's group named `github-actions` whose predicate is `patterns: ["*"]`, the catch-all shape this decision selects; `cooldown.default-days: 5`; `labels`; `commit-message` with `prefix: chore`, `prefix-development: chore`, `include: scope`; `open-pull-requests-limit: 5`; `schedule.day: monday`) and ts `.github/dependabot.yml` at pin `cb1cbcb2` (ecosystems `github-actions`, `npm`; one `update-types: [minor, patch]` group per ecosystem; weekly; no cooldown, labels or commit-message key) — both re-read through their pins in this run (evidence log section 12). `docs/port/DIVERGENCE-ANALYSIS.md:103` classifies R19 as class **A**, `harmonize: partly` — "grouping-strategy shape can be one org value; the `cargo` ecosystem key itself is Rust-specific". The agreement level is therefore **policy**: the *shape* of the answer (how many groups, whether routine updates are batched, whether a cooldown exists and how long, whether PRs are identifiable by label, whether bot commits conform to the commit contract) is one org value; the ecosystem keys, and any key whose availability is ecosystem-bound, are necessarily per-repository.

**Essential behaviors any answer must produce.**

1. Every dependency source the repository actually has is declared, and nothing else.
2. Routine version updates arrive batched, on a fixed cadence, in a bounded number of open PRs.
3. A newly published release is not proposed the instant it appears.
4. Security updates are never delayed or batched behind the routine cadence.
5. Every Dependabot commit satisfies the repository's own commit-message contract (`commit-message-convention`, owned by R38).
6. A batched PR cannot land a change that violates a fixed parameter — here the MSRV policy — without CI catching it.

**Why A cannot be ported (capability, not taste).** Dependabot's Cargo package manager registers its production check as a constant:

```ruby
Dependabot::Dependency.register_production_check("cargo", ->(_) { true })
```

read at `dependabot/dependabot-core` commit `1abafc5ca0900334fd970832e9ef43f2afc78233`, path `cargo/lib/dependabot/cargo.rb` (retrieved 2026-09-10, evidence log section 2; the npm package manager registers a non-trivial check at the same layer, section 2b, which is the control — that one line is cited from the **r3** rerun of 2026-09-12, because the cited r2 log's section 2b is a TLS handshake timeout, as `## Empirical check` records). Every Cargo dependency is therefore "production" to Dependabot, whatever manifest table it sits in. Three documented keys follow, and none reaches `cargo`: `groups.<id>.dependency-type` is "Supported by: `bundler`, `composer`, `mix`, `maven`, `npm`, and `pip`"; `commit-message.prefix-development` is "Supported by: `bundler`, `composer`, `mix`, `maven`, `npm`, `pip`, and `uv`"; and `commit-message.include: scope`, which appends "`deps` or `deps-dev`", can only ever append `deps` for a Cargo entry. Both support lists quoted verbatim from the options-reference source, `github/docs` commit `dd75c5f38a14d1c07c3982beddb471a605b142f7`, path `content/code-security/reference/supply-chain-security/dependabot-options-reference.md` (retrieved 2026-09-10, evidence log section 3), rendered at <https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference>. **The precise claim:** py's runtime-versus-dev-tools *predicate* is a capability the Cargo ecosystem does not have. A hand-maintained list of crate *names* could imitate the grouping, and that residue is what the template-fit argument below rejects; what no configuration can recover is the dev/production distinction itself.

**Why A is also wrong for a template (fit).** py's four `uv` groups name roughly twenty concrete packages (`click`, `pydantic`, `ruff`, `pytest*`, …) at pin `b08bccfb`, and its `npm` group names one more (`@commitlint/*`); its `github-actions` entry, the one whose dependency names py does not control, uses `patterns: ["*"]` instead. A template's dependency names are the first thing a consumer replaces; the day a consumer swaps one crate for another or drops the web crate, a name-keyed group silently stops matching, and the documented rule "Any outdated dependencies that do not match a rule are updated in individual pull requests" (options-reference source, retrieved 2026-09-10) quietly restores the noise the group existed to remove. A `patterns: ["*"]` group contains no repository-specific string and so cannot rot this way. The three surveyed projects that do keep name-keyed families — servo, nushell, datafusion — each have a versioned crate family (`objc2*`, `polars-*`, `arrow*`) that must move in lockstep; a three-crate template has none.

**What the classifier actually does — the correction that forced revision 2.** Revision 1 asserted that Dependabot's `minor` is plain SemVer with no Cargo-aware variant, so a `[minor, patch]` group would *admit* a `0.1 → 0.2` bump. Three files read at `dependabot/dependabot-core` commit `1abafc5ca0900334fd970832e9ef43f2afc78233` — the pin revision 1 itself named — establish the opposite, and each is asserted on by the check (evidence log sections 5a–5c, retrieved 2026-09-10):

1. `cargo/lib/dependabot/cargo/version.rb` defines `Dependabot::Cargo::Version.update_type`, which returns `standard_semver_type(...)` only when `from_major >= 1` and otherwise returns `cargo_pre_1_0_type(...)`. That method reads `return "major" if to_minor > from_minor`, with the preceding branch — `return "major" if from_minor.zero? && (to_minor > from_minor || to_patch > from_patch)` — making any increase breaking for a `0.0.z` version. So the classifier implements Cargo's left-most-non-zero rule directly.
2. `cargo/spec/dependabot/cargo/version_spec.rb` asserts it: `expect(described_class.update_type("0.1.0", "0.2.0")).to eq("major")`, alongside `update_type("0.1.0", "0.1.1")` being `"patch"`.
3. `updater/lib/dependabot/updater/group_update_creation.rb` is the group-update path. `semver_rules_allow_grouping?` begins `return cargo_semver_rules_allow_grouping?(group, dependency, checker) if job.package_manager == "cargo"`, *before* the plain-SemVer branch that other ecosystems take; that path ends in `cargo_update_type_allowed?`, whose test is `group_update_types.include?(actual_update_type)` where `actual_update_type = Dependabot::Cargo::Version.update_type(...)`.

**So a Cargo group declaring `update-types: [minor, patch]` does not admit `0.1 → 0.2`; it excludes it.** The same `Version` class also overrides `ignored_minor_versions` to return `ignored_major_versions` whenever the major component is zero, so `ignore.update-types` is Cargo-aware in the same way — which matters because the MSRV remediation below is an `ignore` entry. The classification landed in commit `2e059329` (pull request **#13349**, "Fix Cargo pre-1.0 semantic versioning classification (0.y.z minor updates as major)", authored 2025-10-21), read from the commit history of `version.rb` *at* the pin, which is deterministic (evidence log section 5d). **Issue #9681 remains open and revision 1 misread its scope**: filed 2024-05-06 — seventeen months before #13349 — it asks for two *additional, explicitly named* values, `cargo-compatible` and `cargo-incompatible`, on `ignore.update-types` and `groups.*.update-types`. Its being open is not evidence that the plain values are SemVer-naive, which is how revision 1 used it (state `open`, created 2024-05-06, updated 2026-08-04, 2 comments, `GET https://api.github.com/repos/dependabot/dependabot-core/issues/9681`, retrieved 2026-09-10, evidence log section 5e). Revision 1 also cited `common/lib/dependabot/dependency_group.rb` containing no Cargo-specific rule as corroborating absence; that was the wrong file — the Cargo rule lives in the two files above — and the citation is withdrawn rather than qualified.

**Why B is nonetheless rejected for the `cargo` entry (volume, not semantics).** With the classification correct, the filter's defect is what it does to the pull-request count. The documented fallback is unchanged: "Any outdated dependencies that do not match a rule are updated in individual pull requests" (options-reference source at `github/docs` commit `dd75c5f3`, retrieved 2026-09-10, evidence log section 3). Under `[minor, patch]` a Cargo group admits 1.x minor and patch bumps and 0.y *patch* bumps, and expels two classes into individual pull requests: every `1.x → 2.x` major, **and every `0.y → 0.(y+1)` release**. Pre-1.0 crates are ordinary rather than exceptional in a Rust dependency tree, so the second class is not a tail case — it is a large, recurring fraction of the weekly churn, and each expelled bump consumes one slot of `open-pull-requests-limit: 5`. The filter therefore re-partitions the review load instead of reducing it, which is precisely the outcome essential behavior 2 exists to prevent. **What B genuinely buys, stated rather than dismissed:** the weekly grouped pull request would contain *only* bumps Cargo itself considers compatible, and every incompatible bump would arrive isolated for individual review. That is a real reviewability gain, and it is the reason alternative D is considered rather than waved past. The filter would be harmless on `github-actions`, whose versions are release tags with no 0.x convention; it is dropped there only so both entries carry one house shape. **The limit of this rejection:** it is an argument about expected pull-request volume for a template whose dependency set P03 has not yet fixed, not a measurement. Nothing here has been executed against a live Dependabot installation; acceptance criteria A3, A4 and A10 are what convert it into a result, and A10 is stated so that its count measures exactly this cost.

**Why D is rejected, and on what terms it returns.** Declaring both `update-types: [minor, patch]` and `update-types: [major]` on one ecosystem leaves no update unmatched, so it recovers B's compatibility separation without B's volume penalty — the objection above does not touch it. It is rejected on three narrower grounds and one general one. First, for Cargo specifically the `major` group is a poor risk signal: because the classifier is Cargo-aware, that group collects every pre-1.0 release alongside genuine `1.x → 2.x` breaks, so a group named for breaking changes would be dominated by routine `0.y` bumps and the separation it advertises would not be the separation a reviewer gets. Second, it doubles the steady-state pull-request count for a three-crate template whose dependency set is small — the condition that makes separation worth its cost is a dependency tree large enough that one weekly pull request is unreviewable, and P03's template is not that. Third, `github-actions` has no 0.x convention, so the same two-group shape partitions the two entries on different meanings, and writing it on only one entry gives up the house symmetry this decision keeps everywhere else. Generally, GitHub's own advice is wildcard-first and treats a targeted split as a response to observed pain rather than a starting position (quoted under *Why C preserves each behavior*), and neither source repository configures the shape. **Why the template's small size counts against D but not in favour of B**, since the two rejections appear to use size in opposite directions. They do not, because the two defects are of different kinds. B's defect is **structural**: whatever the dependency set's size, every expelled bump becomes its own pull request, so B fails essential behavior 2 by construction and a smaller tree only makes the failure cheaper, never absent. D's cost is **proportional**: it batches correctly at every size and merely charges two pull requests a week instead of one, which is worth paying exactly when one weekly pull request has grown unreviewable. Size therefore decides D and not B — and it is the one input to D's rejection that P03 will actually measure, which is why D is recorded as the successor rather than merely dismissed. **The terms of its return are recorded, not left implicit:** if P03's A3 and A10 evidence shows the single weekly grouped pull request is too large or too mixed to review, D is the successor to adopt, and this paragraph is the recorded analysis it is adopted against.

**Why C preserves each behavior.** Behavior 2: "All updates for dependencies that match a rule are combined in a single pull request", and a wildcard pattern matches every dependency, so nothing falls back to an individual PR through non-match (options-reference source, retrieved 2026-09-10). GitHub's own guidance names this the starting point — "A single wildcard group is the simplest starting point. If you later find you want, say, patch-level and major-version updates handled differently, break the wildcard into more targeted named groups" (<https://github.blog/security/supply-chain-security/tame-dependabot-group-your-updates-slow-the-cadence-keep-security-fast/>, retrieved 2026-09-10, carried over from the Opus raw). Behavior 2's *budget* half rests on a documented default rather than on a group predicate: "If five pull requests with version updates are open, no further pull requests are raised until some of those open requests are merged or closed" (pinned options-reference source, **line 545**, asserted at that line number by `review/evidence/r19-check-r5.sh` §3b), which is what makes `open-pull-requests-limit: 5` a restatement of the platform default rather than a new policy. Behavior 3: the platform applies "a **default cooldown period of 3 days** to version updates, even when `cooldown` is not configured" (same source, **line 196**, evidence log section 3, and re-read at that line number by `r19-check-r5.sh` §2d); `default-days: 5` raises the window to py's recorded value and states the policy where a template consumer will read it.

**Behavior 4, and the sentence revisions 1–4 argued it from.** Those revisions supported "Security updates are never delayed or batched behind the routine cadence" with "**This default cooldown does not apply to security updates**". That sentence is true, and the third check reads it verbatim at its §2d — but the pinned source attaches it to the *unconfigured* default at line 196 ("even when `cooldown` is not configured"), and this recommendation **configures** `cooldown`, which puts the file in the other state: the configured branch opens at line 198, "When **`cooldown`** is defined:", and its five numbered steps state no security exemption at all. **The sentence that settles the configured case** is line 187 of the same pinned file, in the `## cooldown` section's own opening paragraph: "The `cooldown` option is only available for _version_ updates, not _security_ updates." The document says the same thing a second way in its section headers: `## cooldown` and `## open-pull-requests-limit` carry only the Version-updates octicon, while `labels`, `groups`, `commit-message` and `versioning-strategy` each carry the Security-updates octicon as well — which is the non-vacuity control that makes the first two headers' omission a real asymmetry rather than a failed match. **The budget carries the same exemption in its own words:** "_Security update_ pull requests are not subject to this limit and do not count toward it. There is no limit on the number of open pull requests for security updates" (line 548). Every read named in this paragraph is at `github/docs` commit `dd75c5f38a14d1c07c3982beddb471a605b142f7`, snapshotted into `review/evidence/github-docs-dd75c5f3/` and asserted by `review/evidence/r19-check-r5.sh` §2a, §2b, §2c, §2d, §3a and §3c (retrieved 2026-09-15). So a security advisory's pull request is exempt from the 5-day cooldown and from the 5-PR budget whether or not either key is written, and acceptance criterion A6 is what observes it on the real template. Behavior 5: `prefix: "chore"` with `include: "scope"` yields `chore(deps): …`, and `chore` is in R38's eleven-type enum. Behavior 6 is *not* provided by any Dependabot key — see the MSRV paragraph below.

**Two absences argued from evidence rather than from taste.**

*Labels.* `dependabot-core` registers a label per ecosystem — `register_label_details("cargo", name: "rust", …)` and `register_label_details("github_actions", name: "github_actions", …)` — on top of `DEFAULT_DEPENDENCIES_LABEL = "dependencies"` (paths `cargo/lib/dependabot/cargo.rb`, `github_actions/lib/dependabot/github_actions.rb`, `common/lib/dependabot/pull_request_creator/labeler.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log sections 2 and 2c). Those defaults were then observed on live pull requests at `ratatui/ratatui`, which declares no `labels` key: `dependencies+rust` on Cargo PRs and `dependencies+github_actions` on Actions PRs (evidence log section 10, retrieved 2026-09-10). Dependabot "creates these default labels automatically, as necessary in your repository", whereas of a custom label the same page says "If any of these labels is not defined in the repository, it is ignored" (both sentences read verbatim from the pinned options-reference source, evidence log section 16). A template is copied into forks whose label sets the template does not control, so the declared form carries a failure mode the omitted form does not — and py's own file illustrates it: py declares the hyphenated `"github-actions"`, while the default Dependabot creates is the underscored `github_actions`. Acceptance criterion A8 is met by the defaults; the taxonomy belongs in a comment, not in a key. This is the one place where restating a default is *not* safe, which is why `open-pull-requests-limit: 5` and `applies-to: version-updates` — both documented defaults whose effect depends on nothing outside the file — are written out for the reader while `labels` is not.

*`prefix-development` and a `deps-dev` scope.* Both are unavailable for `cargo` (support list above) and could not fire even if accepted, since no Cargo dependency is ever in Dependabot's "Development dependency group". The template's documentation should say so: a Cargo bump always scopes as `(deps)`, never `(deps-dev)`, which is a real loss of information relative to py's `uv` entry and is not recoverable by any key.

**Why the commit-message keys are written rather than inherited.** Dependabot's default is "Commit messages follow similar patterns to those detected in the repository" (pinned options-reference source, evidence log section 16) — a heuristic, not a contract. This run watched the heuristic work: `ratatui/ratatui` declares no `commit-message` key and its Dependabot titles read `build(deps): bump duct from 1.1.1 to 1.1.2` (evidence log section 11, retrieved 2026-09-10). `build` happens to be in R38's enum too, but the heuristic reads a repository's *own* history, which a freshly generated template consumer's repository does not have, and R38's F157 fails the PR when a guess lands outside the enum. **One consequence must be stated rather than glossed:** a grouped subject is long. The live grouped titles observed in this run take two forms — `chore(deps): bump the all-other-cargo-deps group across 1 directory with 6 updates` (datafusion) and `build(deps): bump the rust-dependencies group across 1 directory with 23 updates` (helix), against the shorter `bump the arrow-parquet group with 9 updates` form (evidence log section 7). For this decision's group identifiers, the longer form measures **68 columns** for `cargo` and **77** for `github-actions`, or **60** and **69** under F152's soft-line measurement (to the last space) — all above R38's 50-column header cap. R38's F156 relaxes only the width rules for pull requests opened by `dependabot`, keeping grammar and the type enum enforced, so the configuration is compatible with the commit contract *because of that exemption*, not despite short titles. Those four numbers are arithmetic over the live title format, not an executed `committed` run; A7 is the check that settles it.

**Why `versioning-strategy` is written on the `cargo` entry.** The value restates today's Cargo default, and the implementation says why that default is right here: `RequirementsUpdateStrategy::BumpVersionsIfNecessary`, commented "Cargo resolves to the newest compatible version and a bare version is a caret-equivalent (compatible) requirement, so only raise the requirement when it doesn't already allow the new version. Avoids needless churn and MSRV bumps." (`cargo/lib/dependabot/cargo/update_checker.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log section 6). Cargo also accepts only three of the five documented values — `ALLOWED_UPDATE_STRATEGIES = [LockfileOnly, BumpVersions, BumpVersionsIfNecessary]`, with `check_update_strategy` raising "Unknown update strategy" otherwise (`cargo/lib/dependabot/cargo/update_checker/requirements_updater.rb`, same commit) — so the documented `widen` value is not available to a Cargo entry even though the key's own page lists `widen` generically. The key is not in the `github-actions` support list ("Supported by: `bundler`, `cargo`, `composer`, `helm`, `mix`, `npm`, `pip`, `pub`, and `uv`", evidence log section 3), hence its absence there. Writing it costs one line and pins the behavior the MSRV policy wants; it carries no consumer-repository dependency, unlike the label case.

**The Rust-specific risk no Dependabot key addresses: MSRV.** The fixed `msrv-policy` requires `rust-version` in `Cargo.toml` and an MSRV job in CI. **Dependabot does not take `rust-version` into account when it selects the candidate version for a Cargo update, and the mechanism — not an open issue — is what establishes it.** Read at `dependabot/dependabot-core` commit `1abafc5ca0900334fd970832e9ef43f2afc78233`, snapshotted into `review/evidence/dependabot-core-1abafc5c/` and asserted by `review/evidence/r19-check-5f.sh` (log `review/evidence/dependabot-rust-version-pinned.log`, retrieved 2026-09-13; every `§` in this paragraph is a section of *that* script): the hyphenated manifest key `rust-version` occurs **zero** times across all 20 files of `cargo/lib/` (§3b), and the `rust_version` method that does exist, in `cargo/lib/dependabot/cargo/file_parser.rb`, runs `SharedHelpers.run_shell_command("rustc --version")` — it reports the *runner's* toolchain as the ecosystem's language version and never opens the manifest key (§3a). The generic filter that would apply an MSRV, `filter_unsupported_versions(releases, language_version)` in `common/lib/dependabot/package/package_latest_version_finder.rb`, applies `next release unless language_version` as its first per-release guard, so a `nil` language version returns every candidate release unchanged (§2c) — and `cargo/lib/dependabot/cargo/update_checker.rb` calls `latest_version_finder.latest_version` with no argument at all, against a signature that defaults `language_version:` to `nil`, the string `language_version` occurring nowhere in that file (§2a, §2b). **Where that claim stops, stated here and not only in the limits below:** `latest_version` is the crates.io candidate this argument is about, and the sibling `latest_resolvable_version` reaches a version by shelling out to real Cargo — `run_cargo_update_command` runs `cargo update -p #{dependency_spec} -vv`, with **no** `--precise` flag (`cargo/lib/dependabot/cargo/update_checker/version_resolver.rb`, in the same snapshot). What Cargo's own MSRV-aware resolver then does inside that shell-out is not something this check measures, and it is the same thing as the mitigation recorded at the end of this paragraph. **The refinement, which strengthens the point rather than softening it:** Cargo's `package_details_fetcher.rb` *does* capture each crates.io release's published `rust` field as `PackageLanguage#requirement` (§4), so the candidate's own MSRV is recorded and then bypassed — the data is present and the filter is never armed. Issue **#5423** ("Take `rust-version` into account when updating lock file / manifest", open, created 2022-07-26, 7 comments) is the standing request to change this; it is **corroboration, not the ground**, and it is cited from the snapshot `review/evidence/issue-5423.json` retrieved 2026-09-13, because a GitHub issue has no ref to pin (§6). Revision 1 numbered the section that read it `5b`. Cargo's own resolver did gain MSRV awareness (`resolver = "3"`, `resolver.incompatible-rust-versions`, with `edition = "2024"` selecting it — <https://doc.rust-lang.org/cargo/reference/resolver.html>, retrieved 2026-09-10, the **main** check's evidence log section 14), so the fixed `rust-edition` puts the resolver in the MSRV-aware mode; that is a mitigation, not a substitute, because Dependabot picks a target version before Cargo resolves. **The guard is the CI MSRV job, and this item does not weaken it.** The template's documentation carries the remediation: a grouped PR that fails the MSRV job is resolved by adding an `ignore` entry for the offending crate, never by relaxing the job.

**Ecosystem set, and the one workspace fact that fixes `directory`.** Of the 14 Rust repositories surveyed by the Opus raw, 11 declare `cargo`, 14 declare `github-actions`, and 0 declare `rust-toolchain`. `cargo` is the only key that reads `Cargo.toml`/`Cargo.lock`; `github-actions` is what keeps R20's SHA-pinned actions fresh, so omitting it strands that policy — and declaring it with `applies-to: version-updates` is this decision's answer to the version-versus-security-only choice R20 hands over. **One qualification, because R20 records live counter-evidence against the freshness outcome:** that the resulting pull request advances the pinned commit sha *and* its trailing version comment together is R20's acceptance criterion 4 and is **unproven** — `dependabot-core` #7912 and #14716 are open — so "fresh" here means the pin is proposed for update, not that the pin and its label stay in step. See "Relation to R20" under `## Decision` and the unproven list in `## Engines`. `rust-toolchain` is live on github.com and "supports automatic updates for Rust toolchain versions defined in `rust-toolchain.toml` and `rust-toolchain` files" for "Versioned toolchains such as `channel = "1.xx.yy"` and `channel = "1.xx"`" and dated nightly/beta channels (`data/reusables/dependabot/supported-package-managers.md` at `github/docs` commit `dd75c5f3`, retrieved 2026-09-10, evidence log section 15). R42 commits `rust-toolchain.toml` but leaves the `channel` **value** to R27, which is open (`research/topics/42-dev-toolchain-provisioning/DECISION.md:18`), so this entry is deferred rather than declined on principle: it becomes correct the moment R27 fixes a numeric channel. On `directory`, Dependabot's Cargo parser calls `check_rust_workspace_root` and raises "This project is part of a Rust workspace but is not the workspace root" when pointed at a member (`cargo/lib/dependabot/cargo/file_parser.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log section 6b) — so one entry at `/` covers the CLI, library and web-service crates, and a per-crate entry would be an error rather than merely redundant. This constrains P03's manifests: shared versions belong in the workspace-root `[workspace.dependencies]` table, and requirements stay bare/caret rather than `=`-pinned, or `increase-if-necessary` has nothing to do.

**Reference implementations, and what they do and do not prove.** The schema's single implementation is `dependabot/dependabot-core` (MIT; maintenance state **active**: `archived: false` with a same-day `pushed_at`, per the Opus raw's `GET https://api.github.com/repos/dependabot/dependabot-core`, 2026-09-10). Opus: a catch-all `patterns: ["*"]`. **Revision 1 settled this for Opus on a false premise and revision 2 re-settles it, still for Opus, on a different one.** Revision 1 argued that Dependabot's `update-types` are plain SemVer levels, so Codex's file would group a Cargo-incompatible `0.1 → 0.2` bump under a name asserting it is minor; it reached that from the documented value set plus open issue #9681, and explicitly recorded that it had not read the classifier. Revision 2 read it (evidence log sections 5a–5d): `Dependabot::Cargo::Version.update_type` routes pre-1.0 pairs to `cargo_pre_1_0_type`, which returns `"major"` on a `0.y` change; the pinned spec asserts the `0.1.0 → 0.2.0` case; and `semver_rules_allow_grouping?` dispatches `cargo` to a path that admits an update only when the group's declared types contain that computed type. Codex's file would therefore **not** mislabel the bump — it would exclude it. What survives, and is now the whole ground of the settlement, is the second half of revision 1's argument, which the correction strengthens rather than weakens: every expelled dependency gets an individual pull request (documented, evidence log section 3), and for Cargo the expelled set is not just `1.x → 2.x` majors but **every pre-1.0 minor release**, which is a large recurring share of a Rust tree's weekly churn. Codex's file re-partitions the pull-request count rather than reducing it, against essential behavior 2, and each expelled bump consumes a slot of the 5-PR budget. **Limits of this settlement, stated plainly:** the volume claim is a reasoned expectation about a dependency set P03 has not yet fixed, not a measurement, and A3/A4/A10 are what settle it; and the two-group shape that removes the volume objection entirely — alternative D — is rejected on separate grounds recorded under `### Principles and implementation`, not on this one.
