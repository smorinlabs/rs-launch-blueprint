## Decision

**Adopt the two-entry, catch-all-group Dependabot configuration**: one `.github/dependabot.yml` declaring exactly the ecosystems this template has manifests for — `cargo` and `github-actions` — each with a single wildcard version-update group, a weekly Monday cadence, an explicit 5-day cooldown, the default open-PR budget written out, and one Conventional-Commits prefix contract. py's role taxonomy (`runtime` / `dev-tools` / `lint-and-format` / `test`) is **not** ported, because the `cargo` ecosystem cannot express a development-versus-production distinction at all. ts's `update-types: [minor, patch]` filter is **not** ported to the `cargo` entry either — but for the opposite reason to the one revision 1 gave. Revision 1 claimed the filter would *admit* a Cargo-incompatible `0.1 → 0.2` bump because Dependabot's `minor` is plain SemVer; **that mechanism does not exist**, and the classifier at the very pin revision 1 cited refutes it (`### Principles and implementation`, *Why B is rejected*, and `## Empirical check` sections 5a–5e). Dependabot classifies a Cargo `0.1 → 0.2` bump as `major`, so a `[minor, patch]` group **excludes** it. The filter is rejected because that exclusion, applied to a Rust dependency tree, is dense: every pre-1.0 minor release falls out of the group into an individual pull request, which re-partitions the review load rather than batching it and defeats essential behavior 2. The two rejections rest on different kinds of evidence and are stated separately at their exact evidential strength — the taxonomy rejection on a capability the `cargo` ecosystem does not have, the filter rejection on a volume consequence of a capability it does have — under `### Principles and implementation`; this paragraph is the headline, not the full claim.

This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). It records what the research found and what it recommends; P03 builds the template and its CI proves the recommendation. Dependabot is a hosted service whose behavior is observable only on a live repository, so *no* part of this configuration has been executed — what the empirical check below verifies is the schema, the running implementation behind it, and the live behavior of other people's repositories. `## Engines` lists what P03 must validate and what remains unproven. A decision that does not survive implementation is revised against this recorded research, not researched again from scratch.

### Principles and implementation

**Shared requirement, its source, and the agreement level.** The principle behind both source configurations is: *a repository's dependency and workflow-action versions are refreshed automatically, on a fixed cadence, in a small number of reviewable pull requests that are themselves subject to the repository's own commit contract.* Source: py `.github/dependabot.yml` at pin `b08bccfb` (ecosystems `uv`, `github-actions`, `npm`; four name-keyed groups; `cooldown.default-days: 5`; `labels`; `commit-message` with `prefix: chore`, `prefix-development: chore`, `include: scope`; `open-pull-requests-limit: 5`; `schedule.day: monday`) and ts `.github/dependabot.yml` at pin `cb1cbcb2` (ecosystems `github-actions`, `npm`; one `update-types: [minor, patch]` group per ecosystem; weekly; no cooldown, labels or commit-message key) — both re-read through their pins in this run (evidence log section 12). `docs/port/DIVERGENCE-ANALYSIS.md:103` classifies R19 as class **A**, `harmonize: partly` — "grouping-strategy shape can be one org value; the `cargo` ecosystem key itself is Rust-specific". The agreement level is therefore **policy**: the *shape* of the answer (how many groups, whether routine updates are batched, whether a cooldown exists and how long, whether PRs are identifiable by label, whether bot commits conform to the commit contract) is one org value; the ecosystem keys, and any key whose availability is ecosystem-bound, are necessarily per-repository.

**Essential behaviors any answer must produce.**

1. Every dependency source the repository actually has is declared, and nothing else.
2. Routine version updates arrive batched, on a fixed cadence, in a bounded number of open PRs.
3. A newly published release is not proposed the instant it appears.
4. Security updates are never delayed or batched behind the routine cadence.
5. Every Dependabot commit satisfies the repository's own commit-message contract (`commit-message-convention`, owned by R38).
6. A batched PR cannot land a change that violates a fixed parameter — here the MSRV policy — without CI catching it.

**Why A cannot be ported (capability, not taste).** Dependabot's Cargo package manager registers its production check as a constant:

```ruby
Dependabot::Dependency.register_production_check("cargo", ->(_) { true })
```

read at `dependabot/dependabot-core` commit `1abafc5ca0900334fd970832e9ef43f2afc78233`, path `cargo/lib/dependabot/cargo.rb` (retrieved 2026-09-10, evidence log section 2; the npm package manager registers a non-trivial check at the same layer, section 2b, which is the control — that one line is cited from the **r3** rerun of 2026-09-12, because the cited r2 log's section 2b is a TLS handshake timeout, as `## Empirical check` records). Every Cargo dependency is therefore "production" to Dependabot, whatever manifest table it sits in. Three documented keys follow, and none reaches `cargo`: `groups.<id>.dependency-type` is "Supported by: `bundler`, `composer`, `mix`, `maven`, `npm`, and `pip`"; `commit-message.prefix-development` is "Supported by: `bundler`, `composer`, `mix`, `maven`, `npm`, `pip`, and `uv`"; and `commit-message.include: scope`, which appends "`deps` or `deps-dev`", can only ever append `deps` for a Cargo entry. Both support lists quoted verbatim from the options-reference source, `github/docs` commit `dd75c5f38a14d1c07c3982beddb471a605b142f7`, path `content/code-security/reference/supply-chain-security/dependabot-options-reference.md` (retrieved 2026-09-10, evidence log section 3), rendered at <https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference>. **The precise claim:** py's runtime-versus-dev-tools *predicate* is a capability the Cargo ecosystem does not have. A hand-maintained list of crate *names* could imitate the grouping, and that residue is what the template-fit argument below rejects; what no configuration can recover is the dev/production distinction itself.

**Why A is also wrong for a template (fit).** py's four groups name roughly twenty concrete packages (`click`, `pydantic`, `ruff`, `pytest*`, …) at pin `b08bccfb`. A template's dependency names are the first thing a consumer replaces; the day a consumer swaps one crate for another or drops the web crate, a name-keyed group silently stops matching, and the documented rule "Any outdated dependencies that do not match a rule are updated in individual pull requests" (options-reference source, retrieved 2026-09-10) quietly restores the noise the group existed to remove. A `patterns: ["*"]` group contains no repository-specific string and so cannot rot this way. The three surveyed projects that do keep name-keyed families — servo, nushell, datafusion — each have a versioned crate family (`objc2*`, `polars-*`, `arrow*`) that must move in lockstep; a three-crate template has none.

**What the classifier actually does — the correction that forced revision 2.** Revision 1 asserted that Dependabot's `minor` is plain SemVer with no Cargo-aware variant, so a `[minor, patch]` group would *admit* a `0.1 → 0.2` bump. Three files read at `dependabot/dependabot-core` commit `1abafc5ca0900334fd970832e9ef43f2afc78233` — the pin revision 1 itself named — establish the opposite, and each is asserted on by the check (evidence log sections 5a–5c, retrieved 2026-09-10):

1. `cargo/lib/dependabot/cargo/version.rb` defines `Dependabot::Cargo::Version.update_type`, which returns `standard_semver_type(...)` only when `from_major >= 1` and otherwise returns `cargo_pre_1_0_type(...)`. That method reads `return "major" if to_minor > from_minor`, with the preceding branch — `return "major" if from_minor.zero? && (to_minor > from_minor || to_patch > from_patch)` — making any increase breaking for a `0.0.z` version. So the classifier implements Cargo's left-most-non-zero rule directly.
2. `cargo/spec/dependabot/cargo/version_spec.rb` asserts it: `expect(described_class.update_type("0.1.0", "0.2.0")).to eq("major")`, alongside `update_type("0.1.0", "0.1.1")` being `"patch"`.
3. `updater/lib/dependabot/updater/group_update_creation.rb` is the group-update path. `semver_rules_allow_grouping?` begins `return cargo_semver_rules_allow_grouping?(group, dependency, checker) if job.package_manager == "cargo"`, *before* the plain-SemVer branch that other ecosystems take; that path ends in `cargo_update_type_allowed?`, whose test is `group_update_types.include?(actual_update_type)` where `actual_update_type = Dependabot::Cargo::Version.update_type(...)`.

**So a Cargo group declaring `update-types: [minor, patch]` does not admit `0.1 → 0.2`; it excludes it.** The same `Version` class also overrides `ignored_minor_versions` to return `ignored_major_versions` whenever the major component is zero, so `ignore.update-types` is Cargo-aware in the same way — which matters because the MSRV remediation below is an `ignore` entry. The classification landed in commit `2e059329` (pull request **#13349**, "Fix Cargo pre-1.0 semantic versioning classification (0.y.z minor updates as major)", authored 2025-10-21), read from the commit history of `version.rb` *at* the pin, which is deterministic (evidence log section 5d). **Issue #9681 remains open and revision 1 misread its scope**: filed 2024-05-06 — seventeen months before #13349 — it asks for two *additional, explicitly named* values, `cargo-compatible` and `cargo-incompatible`, on `ignore.update-types` and `groups.*.update-types`. Its being open is not evidence that the plain values are SemVer-naive, which is how revision 1 used it (state `open`, created 2024-05-06, updated 2026-08-04, 2 comments, `GET https://api.github.com/repos/dependabot/dependabot-core/issues/9681`, retrieved 2026-09-10, evidence log section 5e). Revision 1 also cited `common/lib/dependabot/dependency_group.rb` containing no Cargo-specific rule as corroborating absence; that was the wrong file — the Cargo rule lives in the two files above — and the citation is withdrawn rather than qualified.

**Why B is nonetheless rejected for the `cargo` entry (volume, not semantics).** With the classification correct, the filter's defect is what it does to the pull-request count. The documented fallback is unchanged: "Any outdated dependencies that do not match a rule are updated in individual pull requests" (options-reference source at `github/docs` commit `dd75c5f3`, retrieved 2026-09-10, evidence log section 3). Under `[minor, patch]` a Cargo group admits 1.x minor and patch bumps and 0.y *patch* bumps, and expels two classes into individual pull requests: every `1.x → 2.x` major, **and every `0.y → 0.(y+1)` release**. Pre-1.0 crates are ordinary rather than exceptional in a Rust dependency tree, so the second class is not a tail case — it is a large, recurring fraction of the weekly churn, and each expelled bump consumes one slot of `open-pull-requests-limit: 5`. The filter therefore re-partitions the review load instead of reducing it, which is precisely the outcome essential behavior 2 exists to prevent. **What B genuinely buys, stated rather than dismissed:** the weekly grouped pull request would contain *only* bumps Cargo itself considers compatible, and every incompatible bump would arrive isolated for individual review. That is a real reviewability gain, and it is the reason alternative D is considered rather than waved past. The filter would be harmless on `github-actions`, whose versions are release tags with no 0.x convention; it is dropped there only so both entries carry one house shape. **The limit of this rejection:** it is an argument about expected pull-request volume for a template whose dependency set P03 has not yet fixed, not a measurement. Nothing here has been executed against a live Dependabot installation; acceptance criteria A3, A4 and A10 are what convert it into a result, and A10 is stated so that its count measures exactly this cost.

**Why D is rejected, and on what terms it returns.** Declaring both `update-types: [minor, patch]` and `update-types: [major]` on one ecosystem leaves no update unmatched, so it recovers B's compatibility separation without B's volume penalty — the objection above does not touch it. It is rejected on three narrower grounds and one general one. First, for Cargo specifically the `major` group is a poor risk signal: because the classifier is Cargo-aware, that group collects every pre-1.0 release alongside genuine `1.x → 2.x` breaks, so a group named for breaking changes would be dominated by routine `0.y` bumps and the separation it advertises would not be the separation a reviewer gets. Second, it doubles the steady-state pull-request count for a three-crate template whose dependency set is small — the condition that makes separation worth its cost is a dependency tree large enough that one weekly pull request is unreviewable, and P03's template is not that. Third, `github-actions` has no 0.x convention, so the same two-group shape partitions the two entries on different meanings, and writing it on only one entry gives up the house symmetry this decision keeps everywhere else. Generally, GitHub's own advice is wildcard-first and treats a targeted split as a response to observed pain rather than a starting position (quoted under *Why C preserves each behavior*), and neither source repository configures the shape. **Why the template's small size counts against D but not in favour of B**, since the two rejections appear to use size in opposite directions. They do not, because the two defects are of different kinds. B's defect is **structural**: whatever the dependency set's size, every expelled bump becomes its own pull request, so B fails essential behavior 2 by construction and a smaller tree only makes the failure cheaper, never absent. D's cost is **proportional**: it batches correctly at every size and merely charges two pull requests a week instead of one, which is worth paying exactly when one weekly pull request has grown unreviewable. Size therefore decides D and not B — and it is the one input to D's rejection that P03 will actually measure, which is why D is recorded as the successor rather than merely dismissed. **The terms of its return are recorded, not left implicit:** if P03's A3 and A10 evidence shows the single weekly grouped pull request is too large or too mixed to review, D is the successor to adopt, and this paragraph is the recorded analysis it is adopted against.

**Why C preserves each behavior.** Behavior 2: "All updates for dependencies that match a rule are combined in a single pull request", and a wildcard pattern matches every dependency, so nothing falls back to an individual PR through non-match (options-reference source, retrieved 2026-09-10). GitHub's own guidance names this the starting point — "A single wildcard group is the simplest starting point. If you later find you want, say, patch-level and major-version updates handled differently, break the wildcard into more targeted named groups" (<https://github.blog/security/supply-chain-security/tame-dependabot-group-your-updates-slow-the-cadence-keep-security-fast/>, retrieved 2026-09-10, carried over from the Opus raw). Behavior 3 and 4: the platform now applies "a **default cooldown period of 3 days** to version updates, even when `cooldown` is not configured", and "**This default cooldown does not apply to security updates**" (options-reference source, retrieved 2026-09-10, evidence log section 3); `default-days: 5` raises the window to py's recorded value and states the policy where a template consumer will read it. Security PRs are additionally exempt from the PR budget: "_Security update_ pull requests are not subject to this limit and do not count toward it" (same source). Behavior 5: `prefix: "chore"` with `include: "scope"` yields `chore(deps): …`, and `chore` is in R38's eleven-type enum. Behavior 6 is *not* provided by any Dependabot key — see the MSRV paragraph below.

**Two absences argued from evidence rather than from taste.**

*Labels.* `dependabot-core` registers a label per ecosystem — `register_label_details("cargo", name: "rust", …)` and `register_label_details("github_actions", name: "github_actions", …)` — on top of `DEFAULT_DEPENDENCIES_LABEL = "dependencies"` (paths `cargo/lib/dependabot/cargo.rb`, `github_actions/lib/dependabot/github_actions.rb`, `common/lib/dependabot/pull_request_creator/labeler.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log sections 2 and 2c). Those defaults were then observed on live pull requests at `ratatui/ratatui`, which declares no `labels` key: `dependencies+rust` on Cargo PRs and `dependencies+github_actions` on Actions PRs (evidence log section 10, retrieved 2026-09-10). Dependabot "creates these default labels automatically, as necessary in your repository", whereas of a custom label the same page says "If any of these labels is not defined in the repository, it is ignored" (both sentences read verbatim from the pinned options-reference source, evidence log section 16). A template is copied into forks whose label sets the template does not control, so the declared form carries a failure mode the omitted form does not — and py's own file illustrates it: py declares the hyphenated `"github-actions"`, while the default Dependabot creates is the underscored `github_actions`. Acceptance criterion A8 is met by the defaults; the taxonomy belongs in a comment, not in a key. This is the one place where restating a default is *not* safe, which is why `open-pull-requests-limit: 5` and `applies-to: version-updates` — both documented defaults whose effect depends on nothing outside the file — are written out for the reader while `labels` is not.

*`prefix-development` and a `deps-dev` scope.* Both are unavailable for `cargo` (support list above) and could not fire even if accepted, since no Cargo dependency is ever in Dependabot's "Development dependency group". The template's documentation should say so: a Cargo bump always scopes as `(deps)`, never `(deps-dev)`, which is a real loss of information relative to py's `uv` entry and is not recoverable by any key.

**Why the commit-message keys are written rather than inherited.** Dependabot's default is "Commit messages follow similar patterns to those detected in the repository" (pinned options-reference source, evidence log section 16) — a heuristic, not a contract. This run watched the heuristic work: `ratatui/ratatui` declares no `commit-message` key and its Dependabot titles read `build(deps): bump duct from 1.1.1 to 1.1.2` (evidence log section 11, retrieved 2026-09-10). `build` happens to be in R38's enum too, but the heuristic reads a repository's *own* history, which a freshly generated template consumer's repository does not have, and R38's F157 fails the PR when a guess lands outside the enum. **One consequence must be stated rather than glossed:** a grouped subject is long. The live grouped titles observed in this run take two forms — `chore(deps): bump the all-other-cargo-deps group across 1 directory with 6 updates` (datafusion) and `build(deps): bump the rust-dependencies group across 1 directory with 23 updates` (helix), against the shorter `bump the arrow-parquet group with 9 updates` form (evidence log section 7). For this decision's group identifiers, the longer form measures **68 columns** for `cargo` and **77** for `github-actions`, or **60** and **69** under F152's soft-line measurement (to the last space) — all above R38's 50-column header cap. R38's F156 relaxes only the width rules for pull requests opened by `dependabot`, keeping grammar and the type enum enforced, so the configuration is compatible with the commit contract *because of that exemption*, not despite short titles. Those four numbers are arithmetic over the live title format, not an executed `committed` run; A7 is the check that settles it.

**Why `versioning-strategy` is written on the `cargo` entry.** The value restates today's Cargo default, and the implementation says why that default is right here: `RequirementsUpdateStrategy::BumpVersionsIfNecessary`, commented "Cargo resolves to the newest compatible version and a bare version is a caret-equivalent (compatible) requirement, so only raise the requirement when it doesn't already allow the new version. Avoids needless churn and MSRV bumps." (`cargo/lib/dependabot/cargo/update_checker.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log section 6). Cargo also accepts only three of the five documented values — `ALLOWED_UPDATE_STRATEGIES = [LockfileOnly, BumpVersions, BumpVersionsIfNecessary]`, with `check_update_strategy` raising "Unknown update strategy" otherwise (`cargo/lib/dependabot/cargo/update_checker/requirements_updater.rb`, same commit) — so the documented `widen` value is not available to a Cargo entry even though the key's own page lists `widen` generically. The key is not in the `github-actions` support list ("Supported by: `bundler`, `cargo`, `composer`, `helm`, `mix`, `npm`, `pip`, `pub`, and `uv`", evidence log section 3), hence its absence there. Writing it costs one line and pins the behavior the MSRV policy wants; it carries no consumer-repository dependency, unlike the label case.

**The Rust-specific risk no Dependabot key addresses: MSRV.** The fixed `msrv-policy` requires `rust-version` in `Cargo.toml` and an MSRV job in CI. Dependabot does not read `rust-version`: the request to do so is open — `dependabot/dependabot-core` issue **#5423**, created 2022-07-26, updated 2026-01-05, 7 comments (`GET https://api.github.com/repos/dependabot/dependabot-core/issues/5423`, retrieved 2026-09-12 in the **r3** rerun, evidence log section 5f — the cited r2 log's section 5f is a TLS handshake timeout, as `## Empirical check` records, and revision 1 numbered this section `5b`). Cargo's own resolver did gain MSRV awareness (`resolver = "3"`, `resolver.incompatible-rust-versions`, with `edition = "2024"` selecting it — <https://doc.rust-lang.org/cargo/reference/resolver.html>, retrieved 2026-09-10, evidence log section 14), so the fixed `rust-edition` puts the resolver in the MSRV-aware mode; that is a mitigation, not a substitute, because Dependabot picks a target version before Cargo resolves. **The guard is the CI MSRV job, and this item does not weaken it.** The template's documentation carries the remediation: a grouped PR that fails the MSRV job is resolved by adding an `ignore` entry for the offending crate, never by relaxing the job.

**Ecosystem set, and the one workspace fact that fixes `directory`.** Of the 14 Rust repositories surveyed by the Opus raw, 11 declare `cargo`, 14 declare `github-actions`, and 0 declare `rust-toolchain`. `cargo` is the only key that reads `Cargo.toml`/`Cargo.lock`; `github-actions` is what keeps R20's SHA-pinned actions fresh, so omitting it strands that policy. `rust-toolchain` is live on github.com and "supports automatic updates for Rust toolchain versions defined in `rust-toolchain.toml` and `rust-toolchain` files" for "Versioned toolchains such as `channel = "1.xx.yy"` and `channel = "1.xx"`" and dated nightly/beta channels (`data/reusables/dependabot/supported-package-managers.md` at `github/docs` commit `dd75c5f3`, retrieved 2026-09-10, evidence log section 15). R42 commits `rust-toolchain.toml` but leaves the `channel` **value** to R27, which is open (`research/topics/42-dev-toolchain-provisioning/DECISION.md:18`), so this entry is deferred rather than declined on principle: it becomes correct the moment R27 fixes a numeric channel. On `directory`, Dependabot's Cargo parser calls `check_rust_workspace_root` and raises "This project is part of a Rust workspace but is not the workspace root" when pointed at a member (`cargo/lib/dependabot/cargo/file_parser.rb` at commit `1abafc5c`, retrieved 2026-09-10, evidence log section 6b) — so one entry at `/` covers the CLI, library and web-service crates, and a per-crate entry would be an error rather than merely redundant.
