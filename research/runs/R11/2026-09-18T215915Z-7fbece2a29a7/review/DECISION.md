# 2026-09-18 — R11 — ci-workflow-job-structure (bundle, Deep) — decision (revision 1)

## Decision

**Status.** This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). `rs-launch-blueprint` has no `.github/` tree, no Rust source and no Cargo manifest today. P02 is research; P03 builds the template and its CI is what proves or disproves what is recorded here. Nothing below has run on a GitHub-hosted runner: no workflow was dispatched, no cache was written, no check was required. What `## Engines` lists is what P03 must validate. A recommendation that does not survive implementation is **revised against this recorded research**, not researched again from scratch.

**Recommendation — one stack: the named pattern `plan-gated compile-tier CI`.** Checks are partitioned into GitHub Actions jobs by **whether they compile Rust**, never by which check they are, inside one `.github/workflows/ci.yml` that adds **no third-party action beyond the one R10 already selected**. Six job ids in three tiers hang off one always-run detector:

```
plan          tier 0  always      ubuntu-latest  no toolchain, no cache, 4 literal outputs
 |
 |-- hygiene        tier 1  always (no needs edge)   the checks that compile nothing
 |-- workflow-lint  tier 1  if workflows == 'true'   R29's and R20's slots
 |-- check          tier 2  if code == 'true'        matrix over os; clippy / tests / doc as ordered steps
 |-- msrv-floor     tier 2  if code == 'true'        the rust-version floor, its own toolchain
 `-- install-smoke  tier 2  if code == 'true'        R50's recipe, web leg as a conditional step
```

Triggers are `pull_request` and `push` restricted to `main`, plus `merge_group`. The file declares `permissions: {}` at workflow level with a per-job re-grant whose scopes are R08's, and workflow-level `concurrency` with `cancel-in-progress: true` keyed to the pull-request number or, when there is none, the commit sha. Every gated job reads the detector through `needs: plan` and a **positive** `== 'true'` predicate. `ci.yml` carries **no** `on.<event>.paths` or `paths-ignore` filter of any kind.

The complete candidate file is committed as a fixture at `review/evidence/ci.candidate.yml` (195 lines, sha256 `f2d5efe252d9ef37a484c51239b5128e1713d2e6bf537c61b544fc436a24be1b`), so the sha256 above names a file a reader can open, lint and mutate rather than a file that was deleted with its scratch directory.

### Landscape, and the alternatives compared before any tool

**The category.** This is not a crate decision. It is the *shape of a CI job graph* and the *mechanism by which a run scopes itself to what changed*: which jobs exist in `.github/workflows/ci.yml`, what `needs:` edges join them, and how a detector makes heavy jobs skip on a pull request that cannot affect them. Everything inside a step — which formatter, which linter, which test runner — belongs to another item and is treated here as a **slot**: a named job or step position with a stated rule for filling it.

**Bin 1 — built-in or first-party.** `jobs.<job_id>.needs`, `jobs.<job_id>.if`, `jobs.<job_id>.outputs`, `on.<event>.paths`/`paths-ignore`, `concurrency` with `cancel-in-progress`, `strategy.matrix`; Cargo's own `-p` / `--workspace` / `--features` / `--locked` scoping; and `git diff --name-only <base>...HEAD` in a `run:` step, which needs `actions/checkout` with `fetch-depth: 0`. Every primitive this recommendation is built from is in this bin.

**Bin 2 — established industry standard.** Four patterns: a hand-rolled detector job publishing literal `true`/`false` outputs consumed through `needs` by positive predicates (what `py-launch-blueprint` and `astral-sh/uv` both do); `dorny/paths-filter`, the long-standing third-party detector action (3,337 stars, not archived, `pushed_at` 2026-08-05T12:20:34Z — `T11`–`T13`); a dedicated always-run cheap job per non-compiling check (`rustfmt` as its own job is near-universal); and one aggregate job that all others feed — **that last one is R12's, named here only because its correctness constrains what this file may emit.**

**Bin 3 — up-and-comers.** `tj-actions/changed-files`, the newer detector action, carries **GHSA-mrrh-fwg8-r2c3**, severity `high`, published 2025-03-15T06:30:34Z, "tj-actions changed-files through 45.0.7 allows remote attackers to discover secrets by reading actions logs" (`T14`–`T16`). Merge-queue-aware gating through the `merge_group` event is the other, and this recommendation adopts it. Third-party hosted runners are out of scope: `target-os-matrix` is owner-fixed.

**Authorities, and why each counts.** GitHub's own documentation, read from the `github/docs` repository at commit `1fa3a6df3560daedd7c8a69e8eff1a730b58c1af` rather than from a rendered page, and **snapshotted into `review/evidence/snapshots/`** so the quotations are asserted offline and a page that reorders a list cannot move the result (`P0`–`P4a`). The Cargo Book's *Continuous Integration* chapter, a Rust **project** publication. `crates.io` and `api.github.com` as the endpoints the prompt's figure table names (`T1`–`T16`). `rustsec.org` with a control package, so an absent advisory page is a real absence (`T17`). `actionlint` 1.7.12, the maintainer's own workflow type-checker, used here as an **instrument** rather than a recommendation: it converts several design claims from assertion into an executed result and, at `NC2`, refutes one. No single blog post is used as an authority anywhere.

**The four architectural alternatives.**

| Alternative | What it is | Compile cost per pull request | Cache claim | Required-check behaviour | Verdict |
|---|---|---|---|---|---|
| **A. One job, every check a step** (ts's shape) | a single `ci` job, recipe steps in sequence | one dependency compile per runner | 1 entry per runner | one check per runner; a docs-only pull request pays the whole compile | **Rejected.** Sound on compile cost, but it can express no skip at all, and one failing step hides every later check |
| **B. One job per check** (py's shape; `tokio`, `axum`) | `fmt`, `clippy`, `test`, `doc`, `build` each their own job | **N dependency compiles per runner** — in Rust the dominant cost, not the startup cost it is in Python or Node | N entries per runner | maximal parallelism, finest-grained reporting | **Rejected as the default**, on `B6`: filled out for this template's real slot list it is **12** job ids against this design's **6**, which crosses R10's written threshold by construction |
| **C. Compile-tier partition** | jobs partitioned by *whether the check compiles* | one dependency compile per runner, plus one at the floor toolchain | **4** job-runner pairs, computed at `B2` | each tier reports its own check; cheap checks still report when the compile tier skips | **Selected** |
| **D. Native `on.<event>.paths` filtering** | the path filter on the workflow trigger | zero when it fires | none | **breaks required checks** | **Rejected on the vendor's own instruction** (`P1a`, `P1d`) |

### Principles and implementation

**The shared requirement, its source, and the level at which agreement is required.** Ledger rows F038 and F040 state the capability: *every quality gate reports as a check a branch-protection rule can require, and a pull request pays only for the gates its change can affect.* The level at which `py-launch-blueprint`, `ts-launch-blueprint` and `rs-launch-blueprint` must agree is **capability plus policy**, not mechanism.

| Must agree — capability and policy | May vary — ecosystem-local |
|---|---|
| Every gate reports a check branch protection can require | How many jobs the gates occupy, and what they are named |
| A pull request that cannot affect a gate does not pay for it | Which paths make a gate skippable, and how they are detected |
| A skipped gate still **reports**, and reports success | — but see the constraint below, which makes this a policy rather than a free choice |
| The floor language version is proven in CI (`msrv-policy`) | Whether the floor is a matrix leg or its own job — **this item**, and settled above |
| Every runner in `target-os-matrix` runs the gates that are OS-sensitive | Which gates are OS-sensitive |

**Missing capability versus justified ecosystem difference, classified per repository because this decision supplies the rationale for the py and ts follow-on.** **`ts-launch-blueprint` has a missing capability, not a justified difference**: its single `ci` job can express no skip at all, so a docs-only pull request pays the whole check sequence, and the capability row above — *a pull request that cannot affect a gate does not pay for it* — is simply unmet there. Closing it is a follow-on project and would take the same device this decision recommends, since the constraint that forces a detector **job** rather than a trigger filter (`P1a`, `P1d`) is the platform's and not Rust's. **`py-launch-blueprint`'s per-check job split is a justified ecosystem difference**: per-job startup is cheap in Python, so splitting buys parallelism at little cost, whereas in Rust the same shape duplicates the **dominant** cost — one dependency compile per job per runner — which is what `B6` prices at 12 job ids against this design's 6. py's shape is right for py and wrong for rs, and that is a difference in the mechanism layer the table above marks as free to vary, not a defect in either repository. **What all three must share is the capability and the policy**, and rs meets them with a different mechanism for a reason that is measured rather than stylistic.

**The constraint that turns the third row into policy, quoted rather than summarised.** GitHub's own troubleshooting page for required status checks tabulates the two kinds of skip as **different outcomes** (`P1a`, `P1b`, asserted offline against the committed snapshot):

> | A workflow is skipped by path filtering, branch filtering, or a commit message | Associated checks stay in a "Pending" state and block merging | Avoid requiring workflows that can be skipped. |
> | A job is skipped by a conditional | The job reports "Success" | |

The same page states that "Successful check statuses are `success`, `skipped`, and `neutral`" (`P1c`), and the reusable it embeds says outright (`P1d`):

> You should not use path or branch filtering to skip workflow runs if the workflow is required to pass before merging.

That is the whole answer to the prompt's LOW question about `on.push.paths`, and it is an instruction rather than a preference: a trigger-level path filter on `ci.yml` would make a docs-only pull request **unmergeable** the moment R12 makes any check in that file required. Check `P1e` is the negative control on `P1b` — the page does not also say a conditionally skipped job reports Pending — so the quotation is a real distinction and not a phrase lifted out of a longer sentence.

**Two further platform facts fix the detector's shape.** First, "If a job fails or is skipped, all jobs that need it are skipped unless the jobs use a conditional expression that causes the job to continue" (`P2a`), which is what makes a gated job skip when `plan` does. Second, the `needs` context carries `outputs` per dependency, and the documentation's own worked example shows a non-successful job with `"outputs": {}` — an **empty map** (`P3a`, `P3b`).

**Those two together make the positive-predicate rule mandatory, and this decision adds an executed reason the rule cannot be delegated to lint.** A gate must read `needs.plan.outputs.<key> == 'true'`, never `!= 'false'`: a skipped or failed detector publishes the **empty string**, the empty string is not equal to `'false'`, so the negated form runs the heavy job in exactly the case the gate exists to prevent. R18 revision 6 found this bug in its own draft (`I21`) and R86 carries the same rule (`I20`). **What is new here is negative control `NC2`: `actionlint` 1.7.12 accepts the fail-open form silently, exit 0, zero diagnostics.** The linter *does* catch the neighbouring mistakes — a misspelled output name (`NC1`, "property \"codee\" is not defined in object type"), a `needs` edge to a job that does not exist (`NC4`), and a job condition reading `secrets` (`NC3`) — which is what makes the gap specific rather than a general observation that linters are incomplete. `NC5` widens it: `actionlint` does not reject a detector body that drops `set -o pipefail` either. **The clause this decision mirrors, named exactly**: the `plan` job is structurally the same device as R18 revision 6's and R86's `credential-preflight` job — *an always-run job that publishes a literal string output which dependants consume through `needs` with a positive predicate* (`I20`, `I21`) — and `NC3` is the reason both must be **jobs** rather than job conditions, since a job-level `if:` may read `github`, `needs`, `vars` and `inputs` and may not read `secrets` (`P4a`). The owner chose that device on 2026-09-11 for R18 (`I22`); this item adopts it for a different input, a diff rather than a credential. **So the positive-predicate rule travels in prose, into this item's owned value and into the shape R12 and R13 inherit, and is not left to tooling.**

**Why C rather than B, on arithmetic computed from the fixture rather than asserted.** The prompt's first HIGH question asks whether R10's cache erases the parallelism benefit of job-splitting. It does not erase it; it **prices** it, and R10 wrote the price down before this item existed. R10's accepted decision leaves `add-job-id-key` at its default `"true"`, which reads `GITHUB_JOB` and "does not include matrix values" (`B7a`, R10 assertion A3.6), so **each job id that runs `cargo` claims its own `target/` cache entry per runner** (`I08`); and R10's re-verify line names the threshold: "R11 resolving with a job count materially above six per OS" re-opens `save-if` (`B5a`). Check `r11-cache-budget.sh` derives the per-job table from the fixture rather than restating it:

| Job id | Carries a rust-cache step | Runners | Contribution |
|---|---|---|---|
| `plan`, `hygiene`, `workflow-lint` | no | 1 each | 0 |
| `check` | yes | 2 | 2 |
| `msrv-floor` | yes | 1 | 1 |
| `install-smoke` | yes | 1 | 1 |

**4 cache-bearing job-runner pairs** (`B2`), **3 cache-bearing job ids on the busier runner and 6 job ids in the file** (`B3`, `B5b`) — under R10's threshold on either reading of "job count". Alternative B, filled out for this template's real slot list (fmt, clippy, test-feature-off, test-feature-on, doc, build-serve, install-smoke, msrv, coverage, deny, docs-gate, openapi-snapshot) is **12** job ids (`B6`). So B does not merely cost more runner minutes; it violates a constraint an already-accepted item recorded in advance.

**A correction to R10's own shorthand, settled here rather than carried.** R10 hands this item the sentence "the entry count against the storage budget is two times the number of job ids" (`B4a`). Applied to this design that gives **6**; the figure computed from the fixture is **4** (`B4b`). The general formula is the **sum over cache-bearing job ids of that job id's runner count**; R10's shorthand is the special case in which every cache-bearing job is matrixed across both entries of `target-os-matrix`, which `msrv-floor` and `install-smoke` are not. This is a refinement of a sentence in an accepted decision, not a `CONFLICT:` — R10 owns no parameter this prompt consumes, and the correction moves the figure in the safe direction. What the figure counts is **job-runner pairs**, which is the unit R10's threshold is expressed in; whether `Swatinem/rust-cache` writes exactly one GitHub Actions cache entry per pair was not measured here and is P03's (R10 criterion A5).

**Why the web surface does not get its own compile gate — the prompt's MEDIUM question, answered against an executed result from another item.** R02's accepted decision recommends a four-package workspace — `rs-launch-blueprint` at the root, `rs-launch-blueprint-core`, `rs-launch-blueprint-cli`, and the optional `rs-launch-blueprint-web` at `crates/web/` (`I02`) — and its check **B3** executed the fact that governs this item's job shape: "a **workspace-scoped** build compiles the web member with the feature off, because workspace membership, not the root package's feature, decides which members are built" (`I01`). R02 hands that check here by name (`I03`). The consequence: on a pull request touching only the CLI, any `--workspace` command **already compiles** `axum` and `tokio`. Splitting the web checks into their own job would therefore **duplicate** that compile rather than avoid it. The correct shape is the opposite of a split — run the feature-off and feature-on commands as **ordered steps of the same job**, sharing one `target/`, where Cargo's fingerprinting makes the second configuration an incremental cost rather than a fresh graph.

Two corollaries follow and both are in the fixture. The feature-off *test* is **root-scoped** by `-p` to the three non-web packages (`I41`), so the property "the default build carries no web" is **proven rather than assumed** — a `--workspace` feature-off test would prove nothing, because B3 says it compiles the member anyway. And a **Cargo-feature matrix dimension is forbidden** (`B7c`): `features: [default, web]` legs would collide on one cache key under assertion A3.6 unless an extra `key:` segment were added, a complication that buys nothing once the configurations are steps. The fixture declares exactly one matrix dimension and it is `os` (`B7b`). R69 revision 10 additionally asks `ci.yml` for "a `--features web` axis and a `--no-default-features` build — shape owned by R11" (`I12`); both are ordered steps of `check` (`I42`).

**Is skip-gating worth its maintenance cost at all — the prompt's second HIGH question, answered rather than assumed.** The question's premise is that Rust's `cargo check` on an unchanged crate is fast enough to make the machinery not worth maintaining. **Three things answer it, and the first is executed.** (1) **There is no cheap no-op compile here.** R02 check `B3` (`I01`) establishes that a workspace-scoped command compiles the optional `crates/web` member with the feature off, so on a cold runner — which every pull-request job is, before a cache restore, and every job is on a lockfile change — the compile tier pays `axum` and `tokio` whatever the diff contained. The premise holds for a warm incremental `cargo check` on a developer's machine, not for a CI job. (2) **The machinery is small and has no dependency.** The detector body measured at `D0a` is **22 lines** of `bash`, dependency-free, type-checked by `actionlint` as part of the workflow (`A2`) and lint-clean under `shellcheck` when extracted (`D0d`); the alternative it replaces is a full three-job compile tier on every docs-only pull request. (3) **The fit signal, and this part is carried rather than executed.** The Opus raw's survey found that five of six well-regarded Rust projects split by check and have **no** detector at all, and that every one of those five is a library or tool repository whose entire content is code; the one project that also carries a large prose tree, `astral-sh/uv`, is the one that built a detector, as did `py-launch-blueprint`. **A template is mostly not code**, which is why the detector earns its keep here and does not in `ripgrep`. The honest cost, stated with the benefit: `fetch-depth: 0` makes `plan` a full clone rather than a shallow one, and the skip-list is a regular expression a contributor can get wrong in a way that fails **open** — which is why `D1` through `D11` assert all four outputs on fourteen inputs rather than spot-checking one.

**Where web skip-gating genuinely belongs.** R69 revision 10's owned value ends "path-based skip-gating keys on `crates/web/**`, the serve binary's source file and the web test files" (`I11`). This decision spends those keys on a `web` output that gates the jobs that are *purely* web — R71's and R84's OpenAPI and typed-client drift slots — and **not** on the compile tier. There is no symmetric "core-only" key, because `crates/web` depends on `crates/core`, so a web change must re-run the core tests anyway and, once the job's `target/` is warm, those tests are the cheap part. The `web` key also fires on a change under `.github/workflows/` (`D6`), because a workflow edit can change the web gate itself; that is the conservative direction and it costs a rare extra run of a cheap job.

**The floor version is a job, not a matrix leg, and the reason is the cache rather than taste.** Cargo's own CI guide verifies `rust-version` in a **separate single-runner job**, introduced by "When publishing packages that specify `rust-version`, it is important to verify the correctness of that field". R10's criterion A3 states the consequence directly: "A toolchain change — including the MSRV floor job beside the stable job — produces distinct cache entries and restores no `target/` across `rustc` versions" (`I07`). A toolchain matrix leg *inside* `check` would give the two legs the **same job id** and therefore the same cache key while their compilers differ — the exact collision A3.6 describes; a separate job id gets distinct keys for free. `axum` (`test-msrv`) and `bat` (`min_version`) both ship it as a separate job.

**What runs inside that job is a slot, not this item's selection.** The reference command is Cargo's guide's own, `cargo hack check --locked --rust-version --workspace --all-targets --ignore-private`; the no-extra-tooling alternative is `cargo +<floor> check --locked --workspace --all-targets`. `cargo-hack`'s figures are re-derived here rather than carried: 90-day downloads **219,720**, all-time **1,893,214**, newest non-yanked **0.6.45** released 2026-05-30T14:50:51Z, licence `Apache-2.0 OR MIT`, declared `rust_version` `1.85`, 862 stars, not archived, `pushed_at` 2026-09-02T12:45:59Z, **35** open issues from `search/issues` `total_count`, and no RustSec page against a control that returns 200 (`T1`–`T10`, `T17`). Maintenance state **active**. Which of the two commands P03 writes turns on an install cost nobody has measured.

**A correction this decision makes to the Opus raw report's detector, on executed ground.** The raw report's skip-list treats `LICENSE-MIT`, `LICENSE-APACHE` and — through a general `\.md$` rule — `CHANGELOG.md` as skippable, while forcing `README.md` non-skippable on the argument that it is a packaging input. R49's published `- owns build-tool-output-shape` value names the `[package] include` allow-list as exactly `/src`, `/README.md`, `/LICENSE-MIT`, `/LICENSE-APACHE`, `/CHANGELOG.md` (`I14`), so **all five are packaging inputs and the argument applies to all five**. Under the raw report's rule a pull request touching only `LICENSE-MIT` or only `CHANGELOG.md` yields `code=false` (`D12b`, `D12c`, executed against a driver rebuilt with that rule), which skips `install-smoke` and every future packaged-content gate on a change to a packaged file. This decision's detector forces `code=true` for every entry of that allow-list (`D2`, `D2b`, `D2c`). The cost is that a CHANGELOG-only pull request pays the compile tier; in practice release-please edits `CHANGELOG.md` together with a version bump in `Cargo.toml`, which sets `code=true` regardless.

**Minimal realistic example, and what was actually run.** The candidate file is `review/evidence/ci.candidate.yml`. `actionlint` 1.7.12 exits **0** on it with zero diagnostics (`A2`), and the file declares exactly the six job ids this decision names (`A3`) — a control that can fail rather than one that cannot. It carries no `paths`/`paths-ignore` filter (`I45`) and zero negated `needs`-output predicates (`I46`). The detector's shell body was **extracted from that fixture** rather than retyped, with only its one `git diff` line replaced by the test input and that replacement asserted to have applied (`D0b`, `D0c`), then run against fourteen changed-file lists (`D0`–`D11`) each asserting all four outputs. Each negative control asserts, with `cmp`, that its mutation actually changed the file **before** linting — the failure mode the Opus raw recorded against itself, where a GNU `0,/re/` `sed` address range is a no-op under this host's BSD `sed` and a "control" lints an unmodified file.

**Fitness gates, answered before popularity is weighed.**

1. **License** — `inapplicable — owner ruling 2026-09-12 (Q7.B): licence compatibility is not evaluated for any dependency or tool` (`I30`). Recorded rather than deleted, because the binding prompt still carries the gate. `cargo-hack`'s `Apache-2.0 OR MIT` is noted at `T5` as a figure, not as a gate result.
2. **MSRV** — **inapplicable to the pattern**: a workflow file has no `rust-version` and no dependency tree. For `cargo-hack`, the declared `rust_version` is `1.85` (`T6`), with the standing caveat that whether the MSRV gate reaches a non-linked *developer tool* at all is an open owner question; the tool is a slot, not a selection.
3. **Advisories and `unsafe`** — the pattern has neither. For `cargo-hack`, no RustSec page against a control that returns 200 (`T17`); its `unsafe` posture was **not audited here** and is stated as unverified. The excluded up-and-comer `tj-actions/changed-files` fails this gate outright on GHSA-mrrh-fwg8-r2c3 (`T14`–`T16`).
4. **Both runners** — satisfied by construction for the pattern: the `check` job runs on `ubuntu-latest` and `macos-latest`, and `plan`, `hygiene`, `workflow-lint`, `msrv-floor` and `install-smoke` are single-runner **by design**, each for a stated reason. `cargo-hack`'s own CI platform coverage was **not inspected** and is a named P03 check rather than an assumption.
5. **Default features and async-runtime coupling** — **inapplicable**: nothing this decision selects enters `Cargo.toml`.

**Disagreement 3 — Perplexity's serial `needs: [changes, check]` edge, settled against Perplexity on the platform's own skip rule.** Perplexity gates `test` on `check` succeeding. GitHub's documented behaviour is that "if a job fails or is skipped, all jobs that need it are skipped" (`P2a`), so a single clippy warning would skip the entire test job and a contributor would learn about one class of failure per round-trip. The same shape also pays `check`'s dependency compile a second time in `test`, with its own cache entry, which is the cost `B6` prices. This decision has **no check-to-check `needs` edge**: every gated job depends on `plan` and on nothing else, so a failure in one tier never hides another tier's result, and `fail-fast: false` extends that across the two runners. **Settled against Perplexity.**

**Disagreement 4 — Perplexity's `--all-features` in the `check` job, settled against it on R02's executed check.** Perplexity writes `cargo check --workspace --all-targets --all-features`. R02 check `B3` establishes that a workspace-scoped command compiles the optional web member **with the feature off** (`I01`); adding `--all-features` on top of that means **no command in the file ever exercises the default configuration**, and the property R69's whole design rests on — that the default build carries no web surface — would be assumed rather than proven. This decision runs the feature-off test **root-scoped by `-p`** (`I41`) and the feature-on test workspace-scoped, as consecutive steps sharing one `target/`. **Settled against Perplexity.**

**Disagreement 5 — `dtolnay/rust-toolchain` as the toolchain step, settled against two legs on a published decision.** Perplexity and Gemini both name it; Gemini goes further and claims to own `toolchain-provisioning-utility` and `artifact-preservation-utility` as parameters. R42's published decision commits `rust-toolchain.toml` (`I15`), which is what lets the stable compile job need no toolchain-install action at all, and R10's re-verify trigger (5) records that whether a CI toolchain-install **action** is named is R42's still-undecided question. Neither leg may settle it here, and this decision does not: the fixture's `check` job installs nothing, and the floor job's second toolchain is named as R42's mechanism. **Settled against Perplexity and Gemini.**

**Disagreement 6 — `Swatinem/rust-cache@v2` with a shared key, settled against Perplexity on two accepted decisions.** Perplexity writes `Swatinem/rust-cache@v2` "with a shared key (e.g. `main-ci`)" so that `test` can reuse `check`'s artifacts. That breaks both accepted inputs at once: R10 pins the action by full commit SHA with a trailing version comment (`I06`, reproduced verbatim in the fixture at `I40`), and R20's published `enforced-owner-prefix-pinning` rule requires a 40-character SHA for every `uses:` clause whose owner is neither `actions` nor `github` (`I16`) — so a floating `@v2` is not available to this template. A `shared-key` across jobs also defeats the per-job partition R10's `add-job-id-key` default provides (`I08`), which is the mechanism this decision's budget arithmetic depends on. **Settled against Perplexity.**

**Disagreement 7 — the detector mechanism. All three Doxa legs choose `dorny/paths-filter`; this decision keeps the hand-rolled step, and says plainly what that costs.** The grounds are three. First, **maintenance**: under R20 every third-party `uses:` clause is a 40-character SHA pin plus a Dependabot-tracked version comment (`I16`), a standing cost a `run:` step does not carry. Second, **supply-chain surface in this exact category**: the other detector action in the field, `tj-actions/changed-files`, is the subject of GHSA-mrrh-fwg8-r2c3 — severity `high`, "allows remote attackers to discover secrets by reading actions logs" (`T14`–`T16`) — and a detector job runs on every pull request, including from forks. Third, **precedent**: both directly relevant precedents hand-roll it. `dorny/paths-filter` is **not excluded by a fitness gate**: it is maintained and widely used (`T11`–`T13`), and it is the **ranked runner-up**, with a stated winning condition — P03 finding the `fetch-depth: 0` full clone the `git diff` step requires to be materially slower than a shallow clone plus the action, or finding the shell body harder to maintain than a YAML filter block once more than four keys exist. **What this decision did not do is execute `dorny/paths-filter`**; the comparison is on documented behaviour and policy cost, and that limit is stated rather than glossed. The Doxa legs' reasoning is not wrong on its own terms — a YAML filter block is more readable than a regular expression — it is answered by a repository-level pinning policy none of the three legs read.

**Disagreement 8 — the parameter lines. Three Doxa legs wrote lines that would fail publication, and this is recorded rather than quietly corrected.** OpenAI's `assumes msrv-policy` appends "; concrete research-date floor is 1.96 because current stable is 1.98.1" to the registry value and its `assumes web-extra-surface` substitutes a one-line paraphrase; the packaging validator compares everything after `= ` byte-for-byte with `docs/port/PARAMETERS.md`, so both would fail. Perplexity invents four parameters — `owns changes-detector-topology`, `assumes rust-cache`, `assumes rust-toolchain`, `assumes msrv-os` — none of which is a registry row and none of which this item owns. Gemini claims three parameters it does not own, writes `assumes web-extra-surface = true` (discarding R69's owner-accepted value entirely), and reduces the owned value to the two words `folded-steps`, which cannot populate a registry row that seventeen items read. **This decision writes one owns line and five assumes lines, the five asserted byte-identical to the live registry at `I55` and the owns line asserted free of backticks and pipe characters at `I54`, because a pipe would break the registry table cell the value is written into.**

**Disagreement 9 — the detector's skip-list, settled against the Opus leg.** Recorded in full under `### Principles and implementation`: the Opus raw skip-lists `LICENSE-MIT` and `LICENSE-APACHE` by name and `CHANGELOG.md` through a general `\.md$` rule, while arguing that `README.md` must not be skippable *because it is a packaging input*. R49's published allow-list makes all five packaging inputs (`I14`). Checks `D12b` and `D12c` execute the raw report's own rule and observe `code=false` for a `LICENSE-MIT`-only and a `CHANGELOG.md`-only pull request; checks `D2`, `D2b` and `D2c` observe `code=true` under this decision's rule. **Settled against Opus.**

**Where the Opus leg was re-derived and found right.** Its `cargo-hack` figures, its GHSA identifier, severity and publication date, and its four quotations from `github/docs` at the pinned commit were all **re-fetched here** rather than carried, and every one agrees (`T1`–`T16`, `P1a`–`P4a`). Its `NC1`, `NC3` and `NC4` results reproduce on a fixture this run wrote independently. Its arithmetic — six job ids, four cache entries, twelve under alternative B — reproduces from the fixture at `B2`, `B3` and `B6`. **One presentational defect was corrected**: the raw report's candidate declares the floor job with the id `msrv` while naming it `msrv-floor`, and R12 will write `needs:` against **ids**, so the fixture uses `msrv-floor` for both.

**What P03 must validate**, each a proposal this research could not execute: that a docs-only pull request leaves `check`, `msrv-floor` and `install-smoke` reporting **skipped** and satisfies a required check on any of them (criterion 6); that the repository holds 4 cache entries well inside the 10 GB budget after a full matrix run (criterion 7, R10's A5); that `msrv-floor` and `check (ubuntu-latest)` restore different `target/` caches (criterion 9, R10's A3); that the `check` job's per-runner wall clock does not make serialising the steps worse than the duplicate compiles a per-check split would pay, which is the single measurement that could reopen alternative B; that `ImageOS` is non-empty on both runners (R10's A7); that a force-push cancels the superseded pull-request run while two consecutive pushes to `main` both complete; that a `merge_group` entry runs the workflow and reports; that `cargo-hack` — if P03 writes it rather than plain `cargo +<floor> check` — installs on the chosen runner; and that the `hygiene` job's rustup toolchain download is cheap enough to justify its having no `needs` edge.

**Confidence, split because the halves are not equally supported.** The **topology rule** — partition by compile, not by check — is **high**: it rests on an executed result from another item (R02's `B3`), on an accepted item's written arithmetic and threshold re-derived here (`B2`–`B6`), and on a vendor instruction that removes one alternative outright. The **detector-as-a-job choice** is **high**: the platform's own documentation makes it a policy rather than a preference (`P1a`–`P1d`) and two directly relevant precedents implement it identically. The **positive-predicate rule** is **high, and better supported than when R18 and R86 stated it**, because `NC2` executed here shows the linter will not catch its violation. The **specific key set, the step order inside `check`, the concurrency group key, and the choice of a hand-rolled detector over `dorny/paths-filter`** are **medium**: each is a judgement no measurement in this decision settles, and each is named above as a P03 measurement rather than asserted. **The absence of the Codex leg lowers every one of those by the amount a second model family's independent reading would have added**, which this decision cannot quantify and does not pretend to.
