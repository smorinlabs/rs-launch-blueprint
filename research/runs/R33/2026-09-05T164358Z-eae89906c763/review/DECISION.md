### Principles and implementation

**Shared requirement, source, and agreement level.** Two principles are in play and they agree at different levels.

*Principle A (F122) — invariants at serialization seams are checked over a described input space, not over hand-picked examples.* Source: py@b08bccfb `tests/core/test_properties.py`, whose module docstring states the rationale in its own words: "Example-based tests check the cases we thought of; these check a *property* of every input Hypothesis can generate, at the two seams where a silent serialization bug would be costly: the domain model's JSON wire form and the config file's persist→reload cycle" (check 10, quoted from the pinned file). Agreement level: **capability** — the template ships generative round-trip testing at its serialization seams, with automatic counterexample minimization and reproducible replay of a discovered failure. The library may vary by ecosystem; the two named seams and the shrink-and-replay behavior are what must agree.

*Principle B (F123) — every command's help text is a reviewed artifact, and an unintended change to it fails the build.* Source: py@b08bccfb `tests/cli/test_help_snapshots.py`, whose F123 evidence line is `assert result.output == snapshot` (check 10, line 36 as the ledger cites) and whose docstring carries the regeneration command `uv run pytest tests/cli/test_help_snapshots.py --snapshot-update` (check 10, line 7). Agreement level: **policy plus one architectural property**. The policy is that help output for every command is compared against a committed reference, drift fails CI, and regeneration is one documented command. The architectural property that must agree is that the reference lives in a **committed file separate from the test source** — py's is `tests/cli/__snapshots__/test_help_snapshots.ambr` (check 10) — because that separation is what makes the change reviewable as a diff in a pull request. Presentation details (file format, macro spelling, review UI) may vary.

**What must vary by ecosystem, and why that is justified rather than drift.** py realizes both principles as pytest plugins injected through fixtures, because pytest's extension model is fixtures and plugins. Rust's `libtest` has no plugin model: a Rust test is a plain function. The same principles are therefore realized as a macro that *is* the test body (`proptest! { … }`) and a macro that *is* the assertion (`insta::assert_snapshot!`). One artifact class is genuinely new on the Rust side: proptest persists a discovered counterexample's seed to a `proptest-regressions/` file next to the test and replays it on later runs, where Hypothesis keeps its example database in an uncommitted `.hypothesis/` cache. Committing that directory strengthens Principle A's replay requirement rather than weakening it — the counterexample travels with the repository instead of living on one developer's machine — and it is the one thing a contributor must be told about. (The persistence mechanism and its `PROPTEST_DISABLE_FAILURE_PERSISTENCE` override are cited from `https://docs.rs/proptest/latest/proptest/test_runner/struct.Config.html` by `raw/opus.md`, retrieved 2026-09-10; this synthesis did not re-fetch that page and did not observe a regressions file being written, because that needs a workspace that does not exist — see `## Engines`.)

**The B2 architecture is conditional on R60, and is stated that way everywhere it appears.** R60 (`cli-parsing-framework`) is open. B2 requires the CLI framework to expose an in-process help renderer and a way to enumerate subcommands. `clap` provides both, and its documentation supplies the determinism pins B2 depends on: `Command::render_long_help` and `Command::get_subcommands` are present in the `Command` method index, and `StyledStr`'s `Display` implementation is documented "Color-unaware printing. Never uses coloring.", with a separate `ansi()` method opting into escape codes (check 9, `https://docs.rs/clap/latest/clap/builder/struct.StyledStr.html` and `.../struct.Command.html`, both HTTP 200, retrieved 2026-09-10). Colour determinism is therefore a type-level property under clap rather than an environment variable — but only under clap. If R60 selects a framework without an in-process renderer, this item's *architecture* moves to B1 and `insta-cmd` or `trycmd` enters the stack; the principle, the assertion crate, and every gate verdict are unaffected.

**Why the selected design preserves each principle.** For A: `proptest`'s strategies are explicit values rather than a per-type trait, which maps one-to-one onto py's explicit `st.text(st.characters(exclude_categories=("Cs","Cc")), max_size=60)` composition — py deliberately narrows the alphabet so "the property is about *our* round-trip, not the encoder's escaping minutiae" (check 10, quoted from the pinned file), and proptest's regex-backed string strategies express exactly that narrowing. `proptest!` expands to a plain `#[test]` function — both raws state this from the crate's own documentation and neither this synthesis nor either raw compiled it — so the suite is neutral to R32's runner choice as long as that runner still executes `#[test]` functions, which is a conditional on an open item, not a property observed here. For B: `insta::assert_snapshot!` writes its reference to a `.snap` file beside the test, which is the separate-file property, and its CI behavior (criterion 6) needs no wiring. `cargo insta review` supplies criterion 7 with a per-snapshot accept/reject gate; py's `--snapshot-update` accepts everything in the selected scope unconditionally, so this is a place where the Rust port improves on the py baseline while preserving the principle rather than merely matching it.

Where a gate is inapplicable to a member's *form* rather than unverified, the table says so and why: gate 5's feature question and gate 6's compile-time question do not apply to `cargo-insta` because it is a provisioned binary, not a linked dependency.

**The `filters` feature is recommended conditionally, and its stated premise is unproven.** `raw/opus.md` recommends `insta = { version = "1.48", features = ["filters"] }` so that a crate version appearing in `--help` can be replaced with a stable sentinel, and cites `astral-sh/uv` as a maintained example of that pattern. The premise — that this template's `--help` output will contain the version string — is not established. clap's `Command::help_template` documentation lists `{version}` as a tag a template opts into and describes `help_template` as "overriding the default format", and the fetched page does not quote the default template's text, so what a default `--help` contains is not settled by the evidence gathered here (check 9b). The recommendation therefore is: enable `filters` **only if** the help output P03 actually produces contains a volatile field (a version, a path, an `[env: …]` annotation); otherwise normalize before asserting and keep default features. `json`, `yaml` and `redactions` are not enabled either way; `redactions` would pull `pest` and `pest_derive`, the most expensive option in the feature list, for a plain-text artifact that does not need it.

**The third member, and where the two engines disagreed about it.** `cargo-insta` is adopted for the **local** review workflow, which is uncontested: without it, regeneration falls back to `INSTA_UPDATE=always cargo test`, which reproduces syrupy's blanket-accept weakness — the exact failure Principle B exists to prevent. What is contested is a CI step. `raw/opus.md` recommends `cargo insta test --unreferenced=reject` in the CI test job to fail the build on snapshot files that outlive their tests; `raw/codex.md` says "do not install `cargo-insta` in CI; it is a contributor review tool, while CI's role is to fail on an unreviewed change". This decision takes the narrow position: **the local review tool is recommended; the CI orphan sweep is optional, and P03 decides whether to wire it.** Three reasons. First, criterion 6's unreviewed-change failure needs no tool at all — it is the documented `CI`/`INSTA_UPDATE` behavior (check 13), so the sweep buys only the orphan-file guard, which has no py analogue and is an improvement rather than a carried requirement. Second, `--unreferenced`'s documented default is `ignore` (check 13: "controls what should happen with unreferenced snapshots. The default is `ignore`. Valid values are `ignore`, `warn`, `reject`, `delete` and `auto`"), so the sweep is opt-in by construction and costs nothing to defer. Third, installing an `Apache-2.0` binary into the CI job is precisely the class of question the open R42 ruling covers, and under the strict licence branch above the tool is not in the stack at all. The CI job's shape is owned by R11 and the tool's provisioning by R42; neither is decided here.
