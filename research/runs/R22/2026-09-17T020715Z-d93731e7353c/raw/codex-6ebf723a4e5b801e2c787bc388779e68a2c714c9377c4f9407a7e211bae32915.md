### Principles and implementation

The shared requirement is one source of truth: `Cargo.toml`’s `[package] version` is the only authored base-version value, and every reporting surface reads one accessor derived from that field. This is an architectural pattern, not a demand that Python, TypeScript, and Rust use the same mechanism. The pinned Python implementation resolves installed distribution metadata at import/runtime; the pinned TypeScript implementation resolves the manifest field during bundling. Rust’s native equivalent is compile-time package metadata because Cargo injects `CARGO_PKG_VERSION` while compiling each package and explicitly shows `env!("CARGO_PKG_VERSION")` as the access form ([Cargo manifest reference](https://doc.rust-lang.org/cargo/reference/manifest.html#the-package-section), retrieved 2026-09-16; [Cargo environment variables](https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-crates), retrieved 2026-09-16).

The recommended minimal implementation is in the library root, so the binary and the optional web module consume the same public value:

```rust
/// The package version from Cargo.toml.
pub const VERSION: &str = env!("CARGO_PKG_VERSION");
```

The CLI passes `rs_launch_blueprint::VERSION` to its parser/version output, diagnostics format that same value, and the web health/status response serializes that same value. The value is a `&'static str` constant: no filesystem access, registry lookup, allocation, async-runtime coupling, or runtime initialization is needed. A statically linked, copied, containerized, or cross-compiled binary therefore reports the version with which it was compiled. Cargo’s build-script guidance says runtime checking of Cargo-provided variables is discouraged because it ties execution to Cargo’s environment; this directly rejects a Python-style runtime metadata lookup for the host package ([Cargo build scripts](https://doc.rust-lang.org/cargo/reference/build-scripts.html#rustc-env), retrieved 2026-09-16).

The alternatives have distinct responsibilities. A runtime package lookup would need an invented sidecar convention or a parse of a manifest/registry directory that may be absent from a `cargo install` result, release archive, container, or production host. It would also report whichever metadata file happens to be found, not necessarily the binary’s compiled identity. A generated module from `built` or `shadow-rs` can expose package data, but both add a build script and generated-code surface for a value Cargo already supplies. `vergen-gix` is appropriate when the binary also needs Git/build/compiler metadata: its documented workflow adds `build.rs` and emits `cargo:rustc-env` values consumed by `env!`; it is not a better base-version source ([`built` source documentation](https://docs.rs/built/latest/src/built/lib.rs.html), retrieved 2026-09-16; [vergen-gix usage](https://docs.rs/vergen-gix/latest/vergen_gix/), retrieved 2026-09-16).

For the web target, the optional `web` feature changes compiled routes and handlers, not the package manifest version. Both the CLI and service binaries therefore receive the same constant when built from one package. A deployment can still run an old binary after a new binary is published, but a runtime lookup would not solve that identity problem; it could make it worse by reading a mismatched mounted manifest. Health output should describe the running artifact, so compile-time embedding is the correct behavior. This conclusion is an inference from Cargo’s compile-time contract and the target’s single-package shape, with the consumed target shape recorded under Parameters.

Acceptance criteria are observable: (1) no source call site contains a second version literal; (2) the library accessor equals Cargo’s package version; (3) CLI `--version`, diagnostics, and web health/status report byte-identical base versions; (4) building with and without `web` does not change the value; and (5) the consistency test fails if the accessor is replaced by a stale literal or another package’s metadata. A realistic test can assert `rs_launch_blueprint::VERSION == env!("CARGO_PKG_VERSION")` in the package’s integration test, then separately compare release-please’s manifest file and any Cargo.lock member version as owned by the release/lockfile decisions. No acceptance check was executed because the Rust template does not exist and this is research, not implementation.

### Dominant choice

Use the first-party compile-time constant `pub const VERSION: &str = env!("CARGO_PKG_VERSION");` in the shared library crate. This is the smallest design that satisfies single source, all three target shapes, stable Rust, the MSRV policy, and zero added dependency or build-script cost. `clap` may consume this constant for explicit CLI wiring; its automatic version feature is a consumer convenience, not the library/web accessor.

### Fit for this template

**CLI.** `env!` works for a statically linked executable and gives the parser an immutable `&'static str`; it does not require the CLI framework’s optional Cargo metadata feature. `clap`’s automatic `version` behavior is acceptable only if the CLI is the sole consumer. The shared library constant is safer because the same value can feed custom diagnostics and the separate service binary ([clap derive reference](https://docs.rs/clap/latest/clap/_derive/), retrieved 2026-09-16).

**Library.** The library is the natural ownership point for a public `VERSION` constant. It has no runtime I/O, no async coupling, and no dependency-tree cost. A generated module would make the public API depend on `build.rs` output and the generator’s feature policy. A runtime lookup is not portable as a library contract because an installed library is normally linked into a consumer binary without its own package metadata directory ([Cargo environment variables](https://doc.rust-lang.org/cargo/reference/environment-variables.html#environment-variables-cargo-sets-for-crates), retrieved 2026-09-16).

**Web service.** The optional web feature compiles the same package’s version constant into health/status handlers. This reports the running artifact and remains identical across the feature boundary. Runtime lookup creates no benefit for a long-lived service; it adds a file/sidecar availability and cache policy, and a mounted manifest can disagree with the running binary. The only related deployment risk is an old process remaining alive after a new artifact is deployed, which is an operational rollout check rather than an accessor choice.

Performance is workload-specific: the accessor workload is three or more short formatting/serialization call paths per process or request. `env!` contributes a compile-time `&'static str` load with no syscall, allocation, parsing, or synchronization; the output formatter and web serializer dominate. `built`, `vergen-gix`, and `shadow-rs` move work to build time but add dependency resolution, build-script compilation, generated code, and—when Git metadata is enabled—repository inspection. No latency, throughput, binary-size, or compile-time benchmark was run, so no absolute performance ranking is claimed.

### Recommendation

Adopt the single-library-constant pattern: `pub const VERSION: &str = env!("CARGO_PKG_VERSION");`. Make every CLI, diagnostics, and web call site consume that symbol. Use no version-accessor crate and no runtime metadata lookup. Add build-time Git/compiler metadata only if R60 explicitly requires it, keeping those fields separate from `VERSION`.

### Ranked runner-up

`vergen-gix` is the runner-up when the owner requires Git describe data, dirty-state policy, compiler data, or reproducible build metadata in the same binary. It wins only after its complete dependency-tree MSRV and RustSec status are verified against the then-current policy, and only as an extension layered beside `env!("CARGO_PKG_VERSION")`; it does not win for the base version alone ([vergen-gix documentation](https://docs.rs/vergen-gix/latest/vergen_gix/), retrieved 2026-09-16).

### Tradeoffs

Compared with `clap`’s automatic version feature, the pick adds one explicit public constant and one explicit CLI wiring point, but it also covers the library and web service and prevents those surfaces from silently acquiring separate metadata logic. Compared with `built`, the pick gives up generated package/dependency/compiler tables, but avoids a build script, generated `OUT_DIR` file, optional feature matrix, and a crate that fails the current MSRV gate. Compared with `vergen-gix`, the pick gives up Git/build provenance, but keeps the base-version contract independent of repository availability, build-script reruns, and dependency-tree MSRV. Compared with `shadow-rs`, it gives up a rich convenience module, but avoids unnecessary metadata, default Git coupling, generated source, and unresolved advisory risk. Those costs are accepted because R22 owns the base package version, while extended build metadata is explicitly out of scope.
