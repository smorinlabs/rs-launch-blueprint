## Decision

**Recommendation.** `rs-launch-blueprint` carries py-launch-blueprint's template-press machinery unchanged in shape — the external `template-press` CLI, **version 4.0.1** (PyPI, released 2026-08-18, `GET https://pypi.org/pypi/template-press/json`, retrieved 2026-09-09), driven by **two separate workflow files** — with three Rust-specific additions that the empirical check showed are required rather than optional: a `substring_rewrite_fields = ["app_name"]` rule, a seventh identity field `display_name`, and a `cargo metadata` cross-check test that restores the tool's Python-only discovery guard.

Settles ledger row **F044** (`docs/port/COMMONALITY.md:50`, verdict `DIVERGENT`, py-only): rs adopts the py pattern; the ts absence is an undocumented timing gap, not a decision (see Engines).

### Principles and implementation

**Shared requirement and its source.** Owner direction of 2026-09-04 (`docs/port/OWNER-REVIEW.md:57`): "You should be using template-press just the way PyLaunch Blueprint does, and the same thing for TypeScript. We should all be using the same mechanism." The requirement is that every repo in the family is a `template-press` target that (P1) proves on every PR that a hermetic self-press leaves no source identity behind, and (P2) never commits the press receipt to the template.

**Agreement level.** Capability plus policy plus one architectural commitment:
- P1, capability, must agree: `press/press-source.toml` committed and authoritative; `press verify` exit 0 on `main` and on every PR head.
- P2, policy, must agree: `press/press-receipt.toml` never enters the template; the guard is template-only and is `[[remove]]`d in forks (py `press/press-rules.toml`, `[[remove]] file = ".github/workflows/template-receipt-guard.yml"`, reason "template-only receipt guard; a fork legitimately commits its receipt", retrieved 2026-09-09).
- P3, architecture, must agree: two workflow files, not one. py states the reason in `template-receipt-guard.yml:1-5`: `press-verify.yml` ships to forks and must carry no identity literal, while the receipt guard is identity-scoped to the template. This is forced by the mechanism (the press rewrites literals and removes whole files), so R11 (`ci-job-structure`) cannot merge the two into one job or file.
- May vary per ecosystem: how the `press` executable is provisioned (py: `uv sync --group dev` from `uv.lock`; rs: hash-pinned `press/requirements.txt`, because rs has no Python project to lock); the `[[regenerate]]`/`[[reset]]`/`[[remove]]` entries; and the compensating identity cross-check that substitutes for the tool's Python-only discovery.

**Essential behaviors and observable acceptance criteria** (all six were executed in this run, on macOS and on Linux; see Empirical check):
1. `press verify` on the clean template exits 0 and prints `verified: no identity leftovers survived the hermetic self-press (clean over the scanned set).`, mutating nothing (`git status --porcelain` empty).
2. An identity-bearing file excluded from rewrite makes it exit 1 naming file, line and column.
3. A `press/press-source.toml` that disagrees with the repository exits 2 before any sandbox is built: a stale `package_name` is reported as `undiscoverable and absent`; a wrong `owner` is reported against the git origin.
4. A real `press rebrand` of a clone exits 0, writes `press/press-receipt.toml`, removes `template-receipt-guard.yml`, rewrites `press-source.toml` to the new identity, and the pressed copy passes `cargo test --workspace`.
5. The receipt guard's shell body exits 1 with the `::error::` line where a receipt exists and 0 on the template.
6. `cargo test --test press_source` passes on stable and on the MSRV floor, and fails naming the drifted target when `[[bin]] name` no longer matches `app_name`.

**Correction to the prompt's paraphrase, on the record.** `press verify` does not build or test the pressed copy. Its own help text (captured in `review/evidence/install-template-press-macos.log`) says it "presses via the HERMETIC `engine.apply` ... no doctor, no receipt, no lockfile regeneration: verify must be a pure, repeatable observation, never a mutation". The F044 ledger text "hermetic self-press check" is accurate, so no `BASELINE-REVIEW:` line is carried; the prompt's "re-generate itself" wording overstates the check.

**Why the selected design preserves each principle in Rust.** `template-press` is language-agnostic by construction: its only external tool is `git` (`press check-tools` output: `git — /usr/bin/git`, exit 0), and the six-plus-one identity fields map onto Cargo cleanly (`repo_name` = `[package] name`; `package_name` = `[lib] name`; `app_name` = `[[bin]] name`; `owner` = git origin owner; `display_name` = README title). Three Rust-specific facts, all measured here, shape the rules:
1. *Suffix-glued app name.* Cargo's first-party integration-test idiom `env!("CARGO_BIN_EXE_<name>")` glues `app_name` as a suffix. The identifier-aware matcher rewrote the prefix-glued `RSLBP_HOME` but left `CARGO_BIN_EXE_rslbp` behind: `press verify` exit 1 at `tests/cli.rs [content L12:C34] app_name='rslbp'`, and — more seriously — `press rebrand` exited 0, wrote a receipt reading `verified = true`, and the pressed copy then failed to compile (`error: environment variable CARGO_BIN_EXE_rslbp not defined at compile time`). `substring_rewrite_fields = ["app_name"]` closes it (run 2: verify 0, pressed copy `cargo test` 0). This is py's G3 class (py `press-rules.toml`, `substring_rewrite_fields = ["app_name", "app_name_upper"]`). `["app_name"]` sufficed in this fixture, whose only upper-case form is the prefix-glued `RSLBP_HOME` (rewritten as `[replace] src/lib.rs — fields=['app_name_upper']`); a suffix-glued upper form was not exercised, so add `app_name_upper` if and when `press verify` reports one — the same "let verify earn each entry" rule that governs the rest of the rules file.
2. *`display_name` is a real, practically required field.* py's `press-source.toml` declares it (`display_name = "Py Launch Blueprint"`); the tool accepts it and rewrites the README title as `display_name_spaced`. With it omitted, verify exits 1 reporting `README.md [content L1:C2] package_name=... repo_name=...` — the spaced title survives as a derived variant. Any template with a human-readable title needs the field.
3. *Discovery is Python-only.* Opus read `discovery.py:64-134` (retrieved 2026-09-09): only `owner` and `repo_name` come from the git origin; the rest fall back to a presence check. Runs E/F reproduce it: the stale `package_name` is caught only because it is absent everywhere (`undiscoverable and absent`), the wrong `owner` is caught against the origin. `tests/press_source.rs` restores the cross-check natively, and it also forces the underscored `package_name` to occur in tracked content (`use rs_launch_blueprint::run` in `tests/cli.rs`), which verify requires on pain of exit 2.

**What must agree versus what may vary.** Must agree across py, ts and rs: the tool, the seven-field `press-source.toml`, the hermetic verify on every PR, the template-only receipt guard removed in forks, and the two-file split. May vary: provisioning of `press` (`uv.lock` dev group in py; `press/requirements.txt` in rs; ts will need its own lock or pin), the rules entries, and the compensating control (rs: `cargo metadata`; ts will land in the same 2-of-6 discovery position and wants the same control against `package.json`).

**Ranked runner-up and its condition.** Alternative D, the press-and-build lane, wins the moment `press verify` is observed to pass while a pressed copy does not compile. The leak scan proves no *old* identity survives; it cannot prove the *new* identity is coherent — a `macro_rules!` or proc-macro that assembles a path from fragments, an `include!`/`include_str!` with a computed path, or a `[workspace] members` glob left stale by a member-directory rename all escape a text scan. Two constraints if adopted: build the pressed copy outside the template tree (rust-github/template moves the generated project to `${{ runner.temp }}` citing `rust-lang/cargo#9922`, retrieved 2026-09-09), and no `Cargo.lock` surgery is needed (the root package entry carries no `checksum`; Opus executed 2026-09-09, and this run's press rewrote `Cargo.lock` as text and the copy built). Until the family adopts it everywhere, the lane runs **once, off CI, as a mandatory implementation-PR rehearsal**: exactly the `press rebrand` + `cargo test --workspace` sequence executed here. Rationale: run 1 showed the rebrand's own post-press doctor can write a receipt over a copy that does not compile, so the one-time rehearsal has demonstrated value, while py — whose behavior the owner told us to match — runs no per-PR build lane, and a build on two OS legs is the most expensive job in the set. A cheaper CI form worth proposing family-wide is a weekly scheduled lane (as `cargo-generate`'s own `e2e-test.yml` does; R34 owns scheduled lanes).

**Tradeoffs accepted.** A Python 3.13 + uv provisioning step in one leaf job of a Rust repository (mitigated: no other job depends on it; `template-press` has zero runtime dependencies — `Installed 1 package`, `Requires:` empty). A bus-factor-1, 0-star tool as a required check (mitigated: exact hash pin; if the tool disappears the guard degrades to the receipt check plus the `cargo metadata` test, both repo-local). A weaker discovery guard on Rust than on Python until an upstream Cargo discovery backend exists (mitigated by `tests/press_source.rs`). A format-blind, length-changing rewrite of binary assets that verify cannot see (Opus run G, unmeasured on real PNG/font/archive files): keep identity out of binary assets or declare each in `extra_exclude_files` with a neutralizing `[[regenerate]]`/`[[remove]]`.
