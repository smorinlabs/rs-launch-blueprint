### Principles and implementation

**Shared requirement and agreement level.** The shared capability is that every sibling blueprint can be rebranded safely and can continuously detect template drift. The shared architectural pattern is: a committed source identity is transformed in an isolated target, source identity leaks fail the check, a successful real rebrand produces a receipt, and the template rejects that receipt because a fork legitimately owns it. The owner further made the low-level engine shared: `template-press` in py, ts, and rs. Source: [R15 owner direction](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/OWNER-REVIEW.md) (retrieved 2026-09-05).

The existing py reference is a maintained complete composition: [`press/press-source.toml`](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/press/press-source.toml) declares source identity; [`press/press-rules.toml`](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/press/press-rules.toml) removes the template-only receipt workflow in forks; [`press-verify.yml`](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/.github/workflows/press-verify.yml) installs the locked tool and executes `press verify`; and [`template-receipt-guard.yml`](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/.github/workflows/template-receipt-guard.yml) fails if `press/press-receipt.toml` is committed (all retrieved 2026-09-05). `template-press` documents that `press verify` creates a sandbox copy, presses it to a synthetic identity, and scans for old identity without mutating the target; exits are 0 for clean, 1 for leaks, and 2 for configuration/environment failure. Source: [CLI reference](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) (retrieved 2026-09-05).

What must agree is the owner-required engine, identity/receipt invariant, isolated verification, and template-vs-fork receipt scope. What may differ is the package manager that supplies `template-press`, identity field values, and native viability commands: rs uses Cargo's format, lint, and test commands after pressing; py uses its locked `uv` project; ts will use its own lockfile and build commands. This is an ecosystem adaptation, not an accidental capability drop.

**Architectural alternatives.** A bespoke Rust replacement duplicates an owner-required cross-language engine and loses its config/receipt safeguards. `cargo-generate` uses a different authoring model—Liquid templates plus Rhai hooks—so it would require rewriting the existing-repository identity transformation rather than exercising it. Source: [cargo-generate README](https://github.com/cargo-generate/cargo-generate/blob/main/README.md) (retrieved 2026-09-05). A shell-only receipt check is appropriate as the narrow guard but cannot establish regeneration correctness. The selected composition is therefore `template-press` for transformation/identity safety plus Cargo for generated-artifact viability.

**Observable acceptance criteria.** On Ubuntu and macOS, CI must (a) run `press verify` against the checkout with no mutation, (b) clone to a temporary target, press it with a non-source identity supplied outside that target, (c) confirm the pressed target has no source-identity report and contains its expected receipt, (d) run `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace` there, and (e) fail the template-only job if the template checkout contains `press/press-receipt.toml`. The end-to-end commands are proposed, not run: no Rust package exists yet.

### Dominant choice

Adopt the owner-required **`template-press` external-target rebrand pattern**, with two GitHub workflows: a cross-platform `press-verify.yml` that performs hermetic identity verification and a real temporary-clone press plus Cargo smoke check, and a template-only `template-receipt-guard.yml` that rejects exactly `press/press-receipt.toml`. `template-press` writes the receipt only after no-leak verification and refreshes source identity for a future re-press; that is the invariant the guard protects. Source: [template-press CLI reference](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) (retrieved 2026-09-05).

### Fit for this template

**CLI.** `Cargo.toml` must carry the pressable package and binary names, and CLI help/snapshots must use the same identity fields. A real pressed-copy `cargo test --workspace` catches a broken binary name, doctest, or help assertion that a string leak scan cannot. Cargo's native commands make this host-language-specific check inexpensive and representative. Source: [Cargo CI guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html) (retrieved 2026-09-05).

**Library.** The package name, library crate name, package metadata, documentation links, and any public examples must be in the press identity/scan set. The selected target clone exercises the library through the workspace test command, without coupling the cross-language rebrand engine to Rust implementation details. `template-press` accepts additional identity fields in `[verify]`, beyond its default field scan. Source: [verify configuration](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) (retrieved 2026-09-05).

**Web service.** The same rebrand reaches service crate names, server binary names, OpenAPI/documentation URLs, container labels, and integration-test fixture names. `cargo test --workspace` must include the web integration suite once it exists; adding a service-specific smoke request is a later test-harness decision, not a reason to split the shared press pattern. The owner requires all sibling blueprints to ship CLI, library, and web shapes. Source: [owner review](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/OWNER-REVIEW.md) (retrieved 2026-09-05).

### Recommendation

Implement `template-press` 4.0.1 as a locked, isolated CI tool project—not a Rust runtime dependency—and retain both named workflows. Put its Python lock and dependency declaration under a dedicated tooling directory, then invoke it with `uv run --project <tooling-dir> press ...`; this preserves py's non-floating, lock-backed installation principle while keeping Cargo's graph pure. The py workflow's `uv sync --group dev` followed by `uv run press verify` is the direct precedent; the directory placement is a Rust-repository adaptation proposed here. Source: [py workflow](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/.github/workflows/press-verify.yml) (retrieved 2026-09-05).

Define source identity explicitly in `press/press-source.toml`: `package_name = "rs-launch-blueprint"`, `crate_name = "rs_launch_blueprint"`, `binary_name = "rs-launch-blueprint"`, `repo_name`, `app_name`, `owner`, and `display_name`. In `press/press-rules.toml`, add `crate_name` and `binary_name` to `[verify].extra_fields`, retain scoped justification for any exclusion, and declare `template-receipt-guard.yml` as a `[[remove]]` rule so a pressed fork may retain its legitimate receipt. `template-press` documents that removal is performed in the hermetic sandbox and that a successful real press writes `press/press-receipt.toml`; its py reference removes exactly that guard from forks. Sources: [CLI reference](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) and [py rules](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/press/press-rules.toml) (retrieved 2026-09-05).

Keep the receipt guard narrow. It has independent merit as a template-invariant guard, but it should not become a vague "no tool output" policy: a receipt is expected and commit-worthy in a pressed fork, and a broad `press/**` rule would reject valid configuration or fork state. General generated-output hygiene needs an allowlist and separate ownership; it is not decided by R15. Source: [template-press post-rebrand behavior](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) (retrieved 2026-09-05).

### Tradeoffs

The dominant choice adds a small Python/uv tooling surface to a Rust template and requires an OS matrix for that external command. It is accepted because it preserves the settled cross-repo mechanism and gives source-config, mismatch, leak, and receipt safeguards that Cargo cannot provide. Source: [`template-press` safety model](https://github.com/smorinlabs/template-press/blob/v4.0.1/README.md) (retrieved 2026-09-05).

Against `cargo-generate`, the choice gives up a Rust-native generator and its widely used Liquid/Rhai authoring model, but avoids a second template language and avoids changing an existing repository into a generator-specific template. Against a bespoke tool, it gives up an all-Rust toolchain but avoids duplicating the semantics and splitting future py/ts/rs behavior. Against a receipt-path-only guard, it costs a real press run but detects leaked identities and invalid rebrand configuration rather than merely one accidental file. Sources: [cargo-generate README](https://github.com/cargo-generate/cargo-generate/blob/main/README.md), [template-press README](https://github.com/smorinlabs/template-press/blob/v4.0.1/README.md), and [py receipt guard](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/.github/workflows/template-receipt-guard.yml) (retrieved 2026-09-05).

### Validation strategy

These commands are **planned acceptance checks, not executed results**; the repository has no Rust code yet.

```bash
# On each required GitHub Actions runner, from the repository root:
uv sync --project tools/template-press --locked
uv run --project tools/template-press press verify --json
```

Expected: exit 0, no checkout mutation, no source-identity findings in scanned files, and an explicit report of any declared exemptions. `press verify` is intentionally a no-mutation sandbox check. Source: [verify contract](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) (retrieved 2026-09-05).

```bash
# Still on the runner: use a clean clone so the real press can write its receipt.
tmp_dir="$(mktemp -d)"
git clone --no-local . "$tmp_dir/pressed"
cat >"$tmp_dir/answers.toml" <<'EOF'
[answers]
package_name = "example-pressed"
crate_name = "example_pressed"
binary_name = "example-pressed"
repo_name = "example-pressed"
app_name = "ep"
owner = "example-owner"
display_name = "Example Pressed"
EOF
uv run --project tools/template-press press rebrand --target "$tmp_dir/pressed" --config "$tmp_dir/answers.toml"
cd "$tmp_dir/pressed"
test -f press/press-receipt.toml
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Expected: `press rebrand` exits 0 and writes the receipt only after its no-leak scan; Cargo commands exit 0 in the pressed clone. A deliberate source token added to a scanned file must make `press verify` exit 1. A deliberately committed `press/press-receipt.toml` in the template checkout must make the receipt workflow fail, while that receipt remains permitted in the pressed clone. Source: [rebrand exit/receipt contract](https://github.com/smorinlabs/template-press/blob/v4.0.1/docs/source/reference/cli.md) and [py receipt guard](https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccf/.github/workflows/template-receipt-guard.yml) (retrieved 2026-09-05).
