### Principles and implementation

**The shared requirement and where it comes from.** A caller must be able to
handle *any* failure of this service without knowing which layer produced it:
one media type, one member set, one place to read the machine identity. The
source is py at the pin, which states the requirement in its own module
docstring: "EVERY non-2xx response body is an ``application/problem+json``
document with the same shape, including FastAPI's own 422 validation errors and
bare ``HTTPException``s" (`py src/py_launch_blueprint/web/problems.py`, docstring,
read at pin `b08bccfb`), implemented by four handlers registered in
`install_problem_handlers` — `PyError`, `StarletteHTTPException`,
`RequestValidationError`, and a bare `Exception` catch-all. ts contributes
nothing: it has no web service at all, no dependency, no decision entry
(`docs/port/areas/web-service.md:98-100`: "`ts: package.json` — no feature: no
web/HTTP-framework dependency present"; "`ts: docs/port/TS_PORT_DECISIONS.md` —
no feature: no decision entry addresses web-service scope"). The verdict is
`DIVERGENT` on a one-sided precedent.

**Agreement levels — what must agree and what may vary.**

| # | Principle | Agreement level | Must agree | May vary |
|---|---|---|---|---|
| W1 | Every non-2xx response carries one media type and one member set | **standard** (RFC 9457) | `application/problem+json`; the RFC's member names for the members that are present | whether absent members are omitted or spelled out |
| W2 | Every non-2xx response carries the failure's stable machine identity | **standard, shared with R67** | the identity is R67's `RSLB` catalog token, the same string the CLI prints | which member carries it |
| W3 | Every layer's failure — domain, framework, extractor, panic — goes through one funnel | **architectural pattern** | that no code path can emit a non-2xx body that bypassed the funnel | how many extension points the ecosystem needs to reach that |
| W4 | A domain failure's HTTP status is a reviewable table, not scattered literals | **architectural pattern** | one place, total over the published catalog, tested | `match`, trait method, or derive |
| W5 | A failure message never discloses server internals to a client | **policy** | the classes withheld, and that the full text is still logged | the wording of the substitute |

W1, W2 and W5 are inherited from py; W3 and W4 are py's structure restated so
that a Rust implementation can be judged against them rather than against
FastAPI's mechanics. W4 is *also* a Rust-specific requirement that py does not
have: py's `ERROR_STATUS: dict[type[PyError], int]` has no completeness test, so
a new `PyError` subclass silently falls to `ERROR_STATUS.get(type(exc), 500)`.

**W5 is where this item's rule and the CLI's rule point in opposite directions,
and the opposition is real rather than a wording clash.** The config items
require the *opposite* of redaction for a terminal user: R55 revision 3 makes "a
degraded load is never silent, and the warning names the file and the key" an
observable acceptance criterion (`research/runs/R55/2026-09-17T020714Z-62a04ad8fee1/review/DECISION.md:283`),
resting on the org CLI Design Standard's R5.8 "precise file/key diagnostics" and
R7.6's "name the offending input in quotes"
(`research/runs/R53/2026-09-17T020714Z-d0b567b4b9f1/review/DECISION.md:204-212`).
Over HTTP, a server-side path or config key **is** an internal disclosure. The
rule that satisfies both is not a compromise: the full message is produced
exactly as the CLI items require and is written to the log, and
`detail_is_public(code)` decides whether that same text reaches the client.
`WebError::log_detail()` exists for precisely that split. Secret *values* never
reach either surface: R56 revision 2 makes masking a property of the value type
rather than of each call site — executed evidence that `Debug` of the secret
renders `SecretBox<str>([REDACTED])`
(`research/runs/R56/2026-09-17T033528Z-785d25a9d608/review/DECISION.md:165-167,265-268`) —
so this item inherits that guarantee and adds nothing to it.

**Why the config codes are 500 and never 4xx, on the record rather than by
assertion.** The config items assign their own codes: an explicit layer that is
unreadable is `RSLB104`/1 and one that is unparsable is `RSLB202`/2
(`…/R55/…:156-157`, `…/R54/2026-09-17T033527Z-8dfef31d60fc/review/DECISION.md:400-404`),
and a failed schema validation is `RSLB203`/2 (`…/R53/…:281-283`). Every one of
those describes *this process's own* configuration. For the web binary they are
startup failures, not request failures — R57 revision 2 goes further and requires
that the web surface not even resolve per-user paths at startup, "the web
surface's settings come from environment variables (R77)"
(`research/runs/R57/2026-09-17T020714Z-8fdb5c2010e7/review/DECISION.md:303-310`).
They therefore get 500 rows so the table stays total, and a request can normally
never raise them.

**Is the shared pattern still appropriate in Rust?** Yes, and the check is not
rhetorical. Against it: Rust's most visible single-org HTTP framework, Oxide's
dropshot, ships a bespoke body instead (cited above), and the first-party tier
offers no help, so adopting RFC 9457 is work the ecosystem does not do for you.
For it: the RFC is an IETF Proposed Standard with registered media types; a
well-regarded Rust service at ISRG uses it; the template's purpose is to be
copied, so a documented standard beats a house shape; R71 must publish a schema
for the error body either way, and a standard shape is the one a generated
client already understands. **Keep the pattern.** Note that dropshot's members
map onto this design without contradiction — its `error_code` is this design's
`code` and its `message` is this design's `detail`; the disagreement is about
the wrapper, not about what a client needs.

**The decision, and the reason it is not close either way.** Take the crate.
The deciding argument is not the 50 lines — it is that those 50 lines encode a
standard the template's users will read the RFC to check, and a crate whose CI
builds every feature combination and pins an MSRV job has already done that
checking in public. The bus-factor objection is real and is answered
structurally rather than dismissed: the crate is reached only through
`crates/web/src/problems.rs`, which owns `Problem`, `ProblemExt` and
`WebError`; no handler, no route module and no test names `problem_details`
directly. If the crate goes dormant, the replacement is the 50-line struct this
report already compiled, behind an unchanged module surface. **That is the
tradeoff stated plainly: a one-crate dependency on a bus-factor-1 maintainer, in
exchange for a standard implemented by someone who read it, with a pre-written
escape hatch.** A synthesizer that weighs bus factor above that can substitute
the hand-rolled member without touching any other part of this recommendation —
the envelope contract, the status table and the funnel are all crate-agnostic.

**The `code` member, and the question R69 handed this item.** R69 revision 10
states the question so it would not be lost: "whether the HTTP surface mirrors
R67's three keys, adopts RFC 9457's member names, or carries both — and, if RFC
9457, how `code` survives, since a stable catalog token is what R67's `RSLB` rows
exist to provide" (`…/R69/…/review/DECISION.md:1396-1399`). **Answer: RFC 9457's
member names, plus `code` as an RFC 9457 extension member carrying R67's token
verbatim.** RFC 9457 §3.2 provides for extension members explicitly, and the
crate flattens a typed extension struct into the top-level object, so `code` is
a sibling of `title` and `status` on the wire, not nested. The result is one
identity string in both surfaces: `rslbp` prints `RSLB301` on stderr and
`rslbp-serve` returns `"code":"RSLB301"` in the body.

Three consequences, each a deliberate rule rather than a default:

1. **`type` is omitted, not spelled `about:blank`.** RFC 9457 §3.1.1 says an
   absent `type` is assumed to be `about:blank`, so omission is conformant, and
   the crate's `skip_serializing_if = "Option::is_none"` omits it. py emits
   `"type": "about:blank"` explicitly (`Problem.type: str = "about:blank"` with
   `model_dump(exclude_none=True)`). **This differs from py and the difference
   is intentional:** two fields cannot both be the identity. Where a project
   later publishes error documentation, `ProblemDetails::with_type` sets `type`
   to `<docs base>/<code>` from the same token, with no change to the table.
2. **`hint` is not an HTTP member.** R67 defines `hint` as a CLI remediation
   line ("rendered as its own line in human output"). Its analogue over HTTP is
   documentation behind `type`, not a body member. If a later item wants it,
   R67's contract permits documented additions and RFC 9457 §3.2 permits
   extension members; this item adds one extension member and no more, plus the
   optional `errors` map below.
3. **`instance` is the request path**, matching py's `instance=request.url.path`.

**W4 — the status table, and the mechanism R67 already specified for it.**
R67 resolved this in its own Disagreement 7: `ErrorCode` is
`#[non_exhaustive]`, so a *different* crate "cannot match exhaustively and needs
a `_ =>` arm. The `ALL` constant is the compensation: R70's status table is
coverage-tested by iterating `ErrorCode::ALL` and asserting every member maps, so
totality is enforced by a failing test instead of by the compiler"
(`research/topics/67-error-and-exit-code-contract/DECISION.md:148-153`;
resolution at `:653-662`). This report adopts that mechanism unchanged and
**verified that it behaves as R67 predicted**: in a single-crate probe the `_`
arm drew `warning: unreachable pattern … no value can reach this`, and after
moving `ErrorCode` into a second crate the same code compiled with no warning —
the arm is required and reachable across the crate boundary. The answer to the
second HIGH question is therefore: **neither a bare `match` on a domain enum nor
a crate-provided derive, but a free `const fn http_status(ErrorCode) -> StatusCode`
made total by a test over `ErrorCode::ALL`.** A derive was rejected for the same
reason R67 rejected `strum`: a status that is derived from a variant identifier
turns a compiler-checked rename into a silent wire change.

**Why this needs no `CONFLICT:` line, and where a synthesizer might disagree.**
The obvious pressure point is that R67's catalog, written for a CLI, has no code
meaning "the client's request body failed validation". The resolution is py's own
structure, not a new code. py has **three** status sources, not one:
`ERROR_STATUS.get(type(exc), 500)` for domain errors; `exc.status_code` passed
straight through for `StarletteHTTPException`; and a hardcoded 422 for
`RequestValidationError`. The Rust design mirrors that exactly — a framework
rejection keeps **axum's own status** via `rejection.status()` and carries
`RSLB201` as its identity. So `RSLB201` names one thing ("the caller's input was
not usable") while 422, 400 and 415 distinguish *how*, which is precisely the
information axum already computed. R67's exit code 2 for `RSLB201` is a process
contract the web binary never exercises and is not in tension with this.
**The alternative is to ask R67 to append `RSLB206 request payload invalid`.**
That is a legitimate future append — R67's catalog is append-only and the table
has a `_` arm — and it would cost one table row and no redesign. It is recorded
here as a documented option, not raised as a `CONFLICT:`, because the
recommendation does not need the consumed value changed to work.

**`BASELINE-REVIEW:` — none is emitted, and the reason is on the record.** F305
and F306 are this item's own `DIVERGENT` rows (`docs/port/COMMONALITY.md:309-310`),
not settled `COMMON → REUSE` or `ADOPT` rows. R67 recorded exactly this trap: two
engines emitted `BASELINE-REVIEW:` lines for their own `DIVERGENT` rows and those
lines were "the answers themselves, misfiled under a review label"
(`research/topics/67-error-and-exit-code-contract/DECISION.md:683-689`). No
`BASELINE-REVIEW:` line is emitted by this report.

#### Envelope contract problem+json/v1

##### Landscape

A pattern member, not a crate: the exact member set, media type and omission
rules of the document body. The field holds three shapes — RFC 9457's member set
(the standard, bin 2), R67's CLI stderr envelope `{"error":{"code","message","hint"?}}`
(project-normative, published), and bespoke bodies such as dropshot's
`{request_id, error_code, message}` (bin 1 practice). Crate figures are
**inapplicable**: this member names no crate. Its maintenance state is likewise
**inapplicable** — it is a contract this repository owns, not a third-party
artifact; its "maintenance" is the append-only discipline stated below.

##### Principles and implementation

Realizes W1, W2 and W5. The contract, in full:

| Member | Source | Rule |
|---|---|---|
| `type` | RFC 9457 §3.1.1 | **omitted** by default (absent means `about:blank`). Set to `<docs base>/<code>` only where a project publishes error documentation |
| `title` | RFC 9457 §3.1.2 | `StatusCode::canonical_reason()` — the exact analogue of py's `HTTPStatus(status_code).phrase` |
| `status` | RFC 9457 §3.1.3 | the numeric status, always present, always equal to the response's own status line |
| `detail` | RFC 9457 §3.1.4 | present only when a public message exists; substituted for a generic string when W5 withholds it; never `null` |
| `instance` | RFC 9457 §3.1.5 | the request path, matching py's `instance=request.url.path` |
| `code` | RFC 9457 §3.2 extension | **always present.** R67's `ErrorCode::as_str()` token verbatim; the only identity |
| `errors` | RFC 9457 §3.2 extension | `BTreeMap<String, Vec<String>>`, omitted when absent; field name → messages. `BTreeMap` rather than `HashMap` so the JSON member order is deterministic and R71's snapshot is stable |

Two omission rules, both inherited from py and both enforced by serde rather than
by convention: every optional member carries
`#[serde(skip_serializing_if = "Option::is_none")]` (py's `exclude_none=True`),
and no member is ever serialized as `null` — the same rule R67 states for `hint`.
Media type: `application/problem+json`, supplied by
`JsonProblemDetails::CONTENT_TYPE` so the string exists once.

**Append-only, like the catalog it carries.** A member may be added; none may be
removed, renamed or have its type changed without a new contract name. This
mirrors R67's discipline for the catalog and is what makes R71's published schema
a stable client contract.

##### Dominant choice

RFC 9457's member set. It is the only option in the field that is an IETF
Proposed Standard with IANA-registered media types, and it is what both the
source precedent (py) and the owner-supplied reference independently chose.

##### Qualified shortlist

1. **RFC 9457 members + `code` extension** — chosen.
2. **RFC 9457 members + identity in `type` only** (alternative B3) — conformant
   and self-describing, but recovers the token only by parsing a URI and spells
   the identity differently on the two surfaces.
3. **R67's three keys over HTTP** (alternative B2) — one shape across both

#### Domain code to HTTP status table

##### Landscape

A pattern member: the mechanism that turns a library failure into a status code.
The field holds four mechanisms — an inline `match` inside `IntoResponse` (what
the owner reference's wiring block shows, and what most axum tutorials show); a
trait method `fn status_code(&self) -> StatusCode` implemented per error type; a
crate-provided derive attribute (`#[status(NOT_FOUND)]`, offered by several small
crates); and a free function over a published code enum, made total by a test.
Crate figures are **inapplicable**: the recommendation names no crate, and that
is itself the finding — the derive option was rejected on principle before
adoption was weighed, so no derive crate needed figures.

##### Principles and implementation

Realizes W4, and answers the second HIGH question. py's analogue is
`ERROR_STATUS: dict[type[PyError], int]` mapping five exception classes to five
statuses, read by exactly one line: `status_code = ERROR_STATUS.get(type(exc), 500)`
(`py …/web/problems.py`, in `handle_py_error`). Its lookup is *by exact type*,
which the module documents with a comment explaining why the two not-found
subclasses are listed explicitly rather than inheriting `APIError`'s 502 — a
subtlety Rust removes, because R67's `ErrorCode` is a flat enum with no
inheritance.

The chosen mechanism is a free `const fn http_status(ErrorCode) -> StatusCode` in
`crates/web/src/problems.rs`, plus:

- a `_ =>` arm, which is **required and reachable** because `ErrorCode` is
  `#[non_exhaustive]` and lives in another crate. Verified both ways: a
  single-crate probe emitted `warning: unreachable pattern … no value can reach
  this` at that arm; moving `ErrorCode` into a second crate removed the warning
  entirely, with the arm unchanged;
- a `pub const NOT_REQUEST_REACHABLE: &[ErrorCode]` naming the codes no request
  can raise, so "500" records an intent instead of hiding one;
- a coverage test iterating `ErrorCode::ALL`, which is the mechanism R67
  designed for this exact consumer
  (`research/topics/67-error-and-exit-code-contract/DECISION.md:148-153`);
- a **framework override**: `WebError::framework(status, code)` takes the status
  from the framework and the identity from the catalog, which is how py handles
  `StarletteHTTPException` and `RequestValidationError`.

**Answering the fourth question — can this be designed before R67's enum is
known?** It already was, and then wired to R67's actual catalog without a
redesign. The seam is a trait:

```rust
pub trait ProblemSource {
    fn error_code(&self) -> ErrorCode;
    fn detail(&self) -> Option<String> { None }
    fn field_errors(&self) -> Option<BTreeMap<String, Vec<String>>> { None }
}
```

Any error type that can name a catalog code answers the envelope; `WebError::from_source`
is generic over it. In the probe, `crates/core`'s domain error implements it in
six lines and `crates/web` needs no change. R67 resolving differently — more
variants, a different `as_str` — costs table rows, never structure, because the
`_` arm and the `ALL` test absorb the difference.

##### Dominant choice

There is no dominant *crate*; the dominant *practice* in axum codebases is the
inline `match` inside `into_response`, which the owner reference reproduces
(`inputs/owner-reference-…md:274-283`). It is rejected here (alternative B6) for
one testability reason: a table inside a response method cannot be called by a
test that iterates `ErrorCode::ALL` without building a `Response` per code.

##### Qualified shortlist

1. **Free `const fn` over `ErrorCode`, `_` arm, `ALL` coverage test** — chosen.
2. **Trait method `fn status(&self) -> StatusCode` on the domain error type**
   — sound and idiomatic, but it puts an HTTP concept in `crates/core`, which
   under R02's topology is the crate `crates/cli` also depends on; the CLI would
   then compile `http::StatusCode`. Rejected on layering, not on style.
3. **Inline `match` in `IntoResponse`** — rejected above.
4. **Derive crate (`#[status(...)]` attributes)** — rejected on the same ground
   R67 rejected `strum`: coupling the wire behaviour to a variant identifier or
   an attribute on a variant makes a silent refactor a wire change. R67 states
   it directly at `:135`: "A variant rename is a compiler-checked, silent
   refactor in Rust — which is exactly why a derived code is dangerous."

##### Excluded by gate

No candidate reaches a gate: options 1–3 name no crate, so **all six gates are
`inapplicable`** — there is no license, no MSRV, no advisory surface, no OS
matrix, no feature set and no compile cost belonging to a function this
repository writes. Option 4 was excluded before gates, on principle.

##### Up-and-comers

tested, because option 4 is excluded on principle and adoption cannot rehabilitate

#### Framework error funnel at axum extension points

##### Landscape

A pattern member: the wiring that guarantees no non-2xx body escapes the
envelope. This is where the first HIGH question is actually answered, and the
answer is **no crate does it** — the four extension points in the `### Landscape`
table are supplied by axum, but the funnel that connects them is template code
in every option. Crate figures are **inapplicable** for the pattern itself; the
one crate that could have been recruited here, `axum-extra` and its
`WithRejection` helper, is evaluated below and not taken.

##### Principles and implementation

Realizes W3. py funnels four sources; axum has four too, and they do not line up
one-to-one:

| py source | py handler | Rust analogue | Mechanism |
|---|---|---|---|
| `PyError` | `handle_py_error` | a handler returning `Err(WebError)` | `impl IntoResponse for WebError` |
| `StarletteHTTPException` (404/405 and bare raises) | `handle_http_exception` | axum's router-level misses | `Router::fallback` (404) and `Router::method_not_allowed_fallback` (405) |
| `RequestValidationError` (FastAPI's 422) | `handle_validation_error` | an extractor rejection | a newtype extractor whose `type Rejection = WebError`, preserving `rejection.status()` and `rejection.body_text()` |
| bare `Exception` catch-all | `handle_unexpected_error` | a panic or a `JoinError` | `tokio::task::JoinError` from R05's `spawn_blocking` bridge → `RSLB000`/500; a panic *outside* that bridge is `tower_http::catch_panic`, which is R75's layer |

**Answering the third question — does the framework's own validation response
need reshaping, and what hook does that require?** Yes, and the hook is the
extractor's associated `Rejection` type. axum's `JsonDataError` is 422
(`axum-0.8.9/src/extract/rejection.rs:11`), `JsonSyntaxError` is 400 (`:23`) and
`MissingJsonContentType` is 415 (`:34`), and all three emit a **plain-text**
body by default. A newtype extractor replaces the body and keeps the status:

```rust
pub struct ProblemJson<T>(pub T);

impl<T, S> FromRequest<S> for ProblemJson<T>
where
    axum::Json<T>: FromRequest<S, Rejection = JsonRejection>,
    S: Send + Sync,
{
    type Rejection = WebError;
    async fn from_request(req: Request, state: &S) -> Result<Self, Self::Rejection> {
        let axum::Json(value) = axum::Json::<T>::from_request(req, state).await?;
        Ok(ProblemJson(value))
    }
}
```

That is the whole hook: about ten lines, one per extractor family that accepts
client input (`Json`, `Query`, `Path`). It **needs no `macros` feature** — which
matters, because R69's accepted `axum` feature list is `form, http1, json,
matched-path, original-uri, query, tokio, tower-log, tracing` and does not
include `macros`, so `#[derive(FromRequest)]` is unavailable without widening a
value this item does not own. Writing the impl by hand avoids that entirely, and
is why this member raises no `CONFLICT:`.

**`axum-extra`'s `WithRejection` was considered and not taken.** It would add a
crate to `crates/web` for a wrapper the four-line impl above already provides,
and it changes the handler *signature* (`WithRejection<Json<T>, WebError>`)
rather than staying invisible. R69 records `axum-extra` as an open hand-off
(`…/R69/…:2342`), so recruiting it here would pre-empt that hand-off.

**The completeness argument for W3, stated as a checkable rule rather than a
hope.** Every non-2xx body originates in exactly one of: a handler's `Err`, the
router's two fallbacks, an extractor rejection, a middleware layer, or a panic.
The first four are covered by this member and executed below. Middleware errors
(timeouts, body limits, rate limiting) and panics outside `spawn_blocking` are
**R75's layer stack** and are a recorded hand-off, not a gap this item can close:
the rule R75 inherits is that any layer added to the stack must render its own
rejection through `WebError`, and the enforcement is a test that walks every
route and asserts the content type.

##### Dominant choice

axum's own extension points. There is no competing mechanism: a tower layer that
rewrote every non-2xx body after the fact was considered and rejected, because it
would have to re-encode a body it did not produce and would strip the structured
`errors` detail that only the rejection has.

##### Qualified shortlist

1. **Hand-written newtype extractors + `fallback` + `method_not_allowed_fallback`
   + `impl IntoResponse`** — chosen.
2. **`#[derive(FromRequest)]` with `#[from_request(via(...), rejection(WebError))]`**
   — equivalent behaviour, but requires axum's `macros` feature, which R69's
   owned value does not enable.
3. **`axum_extra::extract::WithRejection`** — a crate and a visible signature
   change; pre-empts R69's open `axum-extra` hand-off.
4. **A post-hoc tower layer rewriting non-2xx bodies** — rejected above.

Options 1, 2 and 4 name no crate, so all six gates are **`inapplicable`**.

`RSLB203` config value invalid → 2 (**this template's choice, not derived from the standard — see `## Engines`, Disagreement 4**); `RSLB204` secret supplied through a prohibited channel → 2 (**likewise this template's choice; the standard assigns secrets no exit code**); `RSLB205` required non-auth input or consent missing because prompting is disabled or unavailable — `--no-input`, no TTY, or closed stdin — → 2; `RSLB301` resource not found → 3; `RSLB401` credentials absent → 4; `RSLB402` credentials rejected → 4; `RSLB501` conflict/precondition failed → 5; `RSLB901` SIGINT → 130; `RSLB902` SIGTERM → 143; `RSLB903` prompt interrupted by Ctrl-C → 130 (a closed prompt stdin is **not** this code: it is required input that prompting cannot supply, so it is `RSLB205`/2 — see `## Engines`, Disagreement 4). **Envelope** — a single stderr JSON object `{"error":{"code","message","hint"?}}`; `hint` is an optional structured string field carried beside `code` and `message`, omitted (not `null`) when absent and rendered as its own line in human output — its Rust return type is P03's choice and must be able to name the offending input per R7.6, so a borrowed-or-owned string is expected rather than a `&'static str`; stdout stays byte-empty on the error path. This item defines exactly those three keys and defines no trace, cause-array or diagnostic field; R7.8 permits further documented fields, and any such field is a separate addition owned by the item that needs it. What a *stack trace* may do is deliberately absent from this contract: it is F301's, and F301's acceptance criteria are an open owner question (see `## Decision`). **Broken pipe** — a `BrokenPipe` result on the *result* stream ends the process at `0`, silently, with no envelope; a `BrokenPipe` while writing an already-selected error envelope to stderr retains the original application exit status rather than overriding it; a `BrokenPipe` on any other application stream is `RSLB101`/1; no `SIGPIPE` handler is installed and `println!`/`print!` are lint-denied in binary crates. **Boundary precedence** — signal → broken pipe → domain downcast → unexpected; `main` returns `ExitCode` and does not call `process::exit` on the error path; all streams are flushed before exit on every path including signal. **Crash record** — CLI surface only, UNEXPECTED class only, an injected best-effort sink writing `0600` newline-delimited JSON with timestamp, version, PID, code and sanitized cause chain and never argv, environment, headers, tokens or config contents; a write failure never changes the envelope or the exit code; **the location is not decided here and the default sink is a no-op until R57 answers**. **Layering** — `thiserror` in the library crate, `anyhow` (`>= 1.0.103`) in binary crates only; the library crate must not depend on `anyhow`, must install no signal handler or panic hook, and must write to no process stream or file.
