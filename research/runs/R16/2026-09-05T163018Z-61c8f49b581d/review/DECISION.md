### Principles and implementation

**Shared requirement.** The repository's CodeQL scan must be worth a maintainer's attention: broad enough to cover the vulnerability classes the codebase can exhibit, and pointed at code that ships. Source: py `.github/codeql/codeql-config.yml` at `b08bccf` (`queries: - uses: security-extended`; `paths-ignore: tests/**, docs/**`, with the comment "Scan shipped code only: test fixtures and docs config carry intentional patterns that are noise for a security scan"), referenced from py `.github/workflows/codeql.yml:63`; ts `.github/workflows/codeql.yml` at `cb1cbcb` has no `config-file:` and carries the upstream starter template's untouched commented-out `# queries: security-extended,security-and-quality` line, so ts's shape is an unexamined gap of D-022(4), not a considered rejection (both engines, read from the pinned local clones; opus 2026-09-09).

**Agreement level: policy, not low-level values.** The two levers py bundles into one file behave differently in Rust, so the literal paths cannot transfer; the policy — select the broader suite where it adds coverage, exclude non-shipped code where the exclusion actually reaches it, keep the selection in one reviewable artifact — transfers unchanged. Per the research mandate, a shared low-level value is recommended only on explicit owner requirement or same-tradeoff evidence in every ecosystem; that holds for `security-extended` (the suite selectors are language-independent: every `*-security-extended.qls` applies `misc/suite-helpers/security-extended-selectors.yml`, opus 2026-09-09; the selector file is byte-identical at `codeql-cli/v2.26.0` and `v2.26.4`, `evidence/doc-crosschecks.log`) and does not hold for the path list.

**Essential behaviors.**

- B1 — the scan runs every first-party Rust security query whose class the template can exhibit, including the two `security-extended` additions.
- B2 — alerts describe shipped code; Cargo integration tests, benches and fuzz targets are excluded in every workspace member; examples stay in scope. (Observed for `tests/` and `benches/`, at the root and in a nested member; `fuzz/` follows by the same glob form but no `fuzz/` directory existed to exclude — see the unproven list under `## Engines`.)
- B3 — the selection lives in one reviewable, versioned file, and no workflow input silently overrides it.
- B4 — the workflow's action pin resolves the bundle this run's binding evidence executed (2.26.4; the supplementary runs executed 2.26.0 by design), so the CLI the binding evidence verified is the CLI the pinned Action ships. Action-level behaviour (bundle download, SARIF upload) is not verified here.

**Why the selected design preserves each principle.** B1: the file names a suite, not queries, so upstream Rust query growth arrives automatically — a `CWE-078` directory absent at `codeql-cli/v2.26.4` is present at `codeql-cli/v2.27.0`, holding `CommandInjection.ql`, whose metadata declares `@id rust/command-line-injection` (both read statically from the `github/codeql` contents API and raw source; `evidence/doc-crosschecks-r2.log`), and the template will receive it at the next pin bump. Whether that query is in the `security-extended` set at 2.27.0 was not resolved — 2.27.0 was not executed. B2: `paths-ignore` is honoured for Rust at *extraction time* — with the config in force the source archive held 5 fixture files instead of 8 and CodeQL reported "scanned 5 out of 5 Rust files" — so ignored code is neither extracted nor analysed, and the `**/` prefix reached the nested member's `tests/`; GitHub Docs states the applicability: "You can use this option when you run the CodeQL actions on an interpreted language (Python, Ruby, and JavaScript/TypeScript) or when you analyze a compiled language without building the code (currently supported for C/C++, C#, Java and Rust)" (retrieved 2026-09-09). B3: `config-file:` is the only place both levers can be reviewed together, and the A3 guard is a one-line assertion P03 can wire into CI — here it was executed only as a local YAML parse, not as a CI step. B4: the pin guard (every `github/codeql-action` step at `v4.37.9`) is the same local assertion extended by one field, and is likewise a P03 wiring task. The default-setup NOTE at the top of the file is carried from py because advanced setup and GitHub's default setup are mutually exclusive and the failure mode (rejected SARIF upload) is invisible from the workflow file.
