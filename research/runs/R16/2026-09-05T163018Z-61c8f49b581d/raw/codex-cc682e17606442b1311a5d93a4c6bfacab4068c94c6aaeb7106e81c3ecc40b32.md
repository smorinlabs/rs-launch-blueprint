### Principles and implementation

The shared requirement is **reviewable, high-signal security analysis of shipped code**, at the capability/standard level: all three repositories must run CodeQL where GitHub Code Security is available and select a maintained security-query policy, but they need not share a language-specific path filter. F027 fixes the runtime availability gate, not query policy; F045 is the divergent configuration decision. The essential observable behaviors are: the Rust workflow initializes CodeQL with a repository-owned policy; the policy runs `security-extended`; normal shipped Rust code remains analyzable; and an intentional fixture does not become silently unscanned merely because it lives under `tests/` ([GitHub configuration reference](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05).

`security-extended` is not merely a Python convention. GitHub defines it as the default suite plus lower-precision/lower-severity security queries, and explicitly says a selected extra suite runs with the default set ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05). GitHub publishes distinct Rust `default`, `security-extended`, and `security-and-quality` suites, and its Rust query help includes security categories relevant to a web service such as cleartext transmission/storage, SQL injection, SSRF, path injection, weak cryptography, and TLS checks ([Rust query help](https://codeql.github.com/codeql-query-help/rust/), retrieved 2026-09-05). This establishes broader maintained Rust security coverage, but not a measured alert-rate improvement for this unimplemented template.

The alternatives are bare defaults, a local configuration containing `security-extended`, and that same configuration plus source filters. A file is preferable to an inline `queries` value because it makes the durable security policy independently reviewable and leaves room for an evidence-backed query exception. GitHub documents `config-file` precisely for that role ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05). Do **not** copy Python's `paths-ignore`: Markdown docs are not Rust extractor inputs, `target/` is normally untracked, and no Rust fixture/noise measurement exists. More importantly, directory filters work for Rust only when CodeQL analyzes without building; for a compiled-language build, exclusions must be achieved by changing build steps ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05).

Minimal realistic example: a workspace has a CLI package, a library package, an optional `axum` web package, and a deliberately vulnerable source fixture retained in the test suite. The config contains only `queries: - uses: security-extended`; the workflow references it through `config-file`. The planned acceptance check confirms an alert is emitted for a shipped web-path flaw and that moving the same flaw to a test fixture does not make it disappear. No CodeQL workflow was executed in this research run.

### Excluded by gate

The `security-extended` plus `paths-ignore: [tests/**, docs/**]` variant is excluded by the evidence/applicability gate. GitHub permits Rust directory filters only for analysis without a build; the inherited workflow's Rust build mode is not an R16 decision and no fixture-alert measurement proves that the exclusions remove noise rather than coverage ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05). `security-and-quality` is excluded from this security policy because it adds maintainability and reliability queries beyond `security-extended`, increasing non-security signal without a stated acceptance need ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05).

### Up-and-comers

CodeQL model packs are an up-and-comer extension path, not a current template default: GitHub labels them public preview, even though Rust analysis can consume them ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05). Revisit only when a chosen Rust web stack lacks first-party data-flow coverage and a maintained model pack has an explicit MSRV, license, and advisory review.

### Fit for this template

**CLI:** `security-extended` covers the extra security queries without bringing in `security-and-quality`; it is appropriate for command parsing, file paths, environment handling, and HTTP client use, while a blanket test exclusion could hide command-invocation regressions ([Rust query help](https://codeql.github.com/codeql-query-help/rust/), retrieved 2026-09-05).

**Library:** the local policy covers exported helpers and downstream-facing parsing/crypto behavior without imposing a Cargo dependency, feature flag, runtime, binary-size, or compile-time cost ([GitHub query suites](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-query-suites), retrieved 2026-09-05).

**Web:** this is the strongest fit: GitHub's Rust support list includes web frameworks and common HTTP/database libraries, and the extended security suite covers classes such as SSRF, SQL injection, path injection, TLS and cleartext handling ([supported languages](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/), [Rust query help](https://codeql.github.com/codeql-query-help/rust/), retrieved 2026-09-05). The optional web surface remains owned by R69; this recommendation does not assume a framework.

### Recommendation

Ship `.github/codeql/codeql-config.yml` with:

```yaml
name: "rs-launch-blueprint CodeQL"
queries:
  - uses: security-extended
```

Reference it from `github/codeql-action/init` using `config-file: ./.github/codeql/codeql-config.yml`. Do not set `disable-default-queries`; GitHub documents that a selected extra suite runs with the default set, and `security-extended` itself contains the default queries plus extras ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05). Do not add `paths-ignore`, including `target/**`: build output is ordinarily untracked and there is no demonstrated Rust false-positive problem. Treat a future exclusion as a separate, reproducible alert-noise change with a build-mode check.

### Ranked runner-up

**Bare default configuration** wins if the first scheduled `security-extended` run produces an untriageable, reproducible false-positive burden and no query-level suppression can preserve the discovered security coverage. GitHub explicitly characterizes `default` as the higher-precision/lower-false-positive suite ([query suites](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-query-suites), retrieved 2026-09-05).

### Tradeoffs

Against bare defaults, the recommendation accepts more low-confidence findings and CI analysis work for additional maintained security queries; no template-specific latency, throughput, memory, or alert-rate measurement was available, so it makes no performance claim ([query suites](https://docs.github.com/en/code-security/concepts/code-scanning/codeql/codeql-query-suites), retrieved 2026-09-05). Against Python's filtered configuration, it accepts possible fixture noise to avoid an unsupported or coverage-reducing compiled-language exclusion. Against `security-and-quality`, it gives up generalized quality diagnostics so CodeQL remains a security gate rather than duplicating R31 or lint/static-analysis work ([workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options), retrieved 2026-09-05).
