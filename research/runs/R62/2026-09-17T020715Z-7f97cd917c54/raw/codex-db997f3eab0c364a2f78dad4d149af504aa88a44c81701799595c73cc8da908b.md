### Principles and implementation

The shared requirement is **additive result delivery with an explicit, recoverable environmental failure**: `--copy` must not replace the normal result sink, and unavailable clipboard access must become a typed, catchable domain failure rather than a panic. The agreement level is an architectural pattern and user-facing policy, not a shared low-level dependency. The pinned TypeScript command writes its selected result to stdout or file before attempting the injected clipboard writer, then wraps rejection as `CliError`; its adapter dynamically imports `clipboardy`. [pinned `projects.ts` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00`, retrieved 2026-09-16](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/src/commands/projects.ts) [pinned `adapters.ts` at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00`, retrieved 2026-09-16](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/src/lib/adapters.ts) [ledger rows F281/F282, retrieved 2026-09-16](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/areas/cli-framework-ux.md)

What must agree is the opt-in flag name, additive ordering, clear diagnostic, and testable failure path. What may vary is the native mechanism: TypeScript uses a dynamic module plus external Linux programs, whereas Rust can use a crate with target-specific native protocol bindings. The reference's `clipboardy` decision itself says headless Linux lacks a clipboard; that supports the policy, not copying its external-process mechanism. [pinned TypeScript decision D-016(7) at `cb1cbcb2e88b898e8c081b0abbfabc1630079c00`, retrieved 2026-09-16](https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/docs/port/TS_PORT_DECISIONS.md)

Compare four architectures. Direct `arboard` calls in a command preserve behavior but couple command tests to a display server. A `ClipboardWriter` port owned by the library/adapter boundary permits a deterministic fake and preserves a source error. A subprocess wrapper around `xsel`, `xclip`, or `wl-copy` creates a PATH/package-manager requirement and is rejected. Omitting `--copy` would discard the established capability without an evidenced benefit and is rejected. The recommended boundary is synchronous because `arboard::Clipboard::new` and `set_text` are synchronous `Result` APIs; it does not impose an async runtime on the CLI or web service. [arboard API documentation, retrieved 2026-09-16](https://docs.rs/arboard/3.6.1/arboard/struct.Clipboard.html) [arboard source, retrieved 2026-09-16](https://github.com/1Password/arboard/blob/v3.6.1/src/lib.rs)

Proposed minimal example: define `ClipboardWriter::write_text(&mut self, text: &str) -> Result<(), ClipboardWriteError>` in the library-facing CLI seam; its production adapter owns `arboard::Clipboard`, calls `Clipboard::new` and `set_text`, and maps `arboard::Error` into `ClipboardWriteError { source }`. The command first emits the result to its selected ordinary sink, then invokes the port when `--copy` is present; it maps only `ClipboardWriteError` into R67's later domain-error catalog. `arboard::Error` is non-exhaustive, implements `std::error::Error`, and its constructor/write operations return `Result`, so the adapter can preserve a typed source without matching every variant. [arboard error documentation, retrieved 2026-09-16](https://docs.rs/arboard/3.6.1/arboard/enum.Error.html) [arboard error source, retrieved 2026-09-16](https://github.com/1Password/arboard/blob/v3.6.1/src/common.rs)

Observable acceptance criteria are: (1) with a usable desktop clipboard, `--copy` leaves normal output intact and copies exactly the formatted result; (2) with neither `DISPLAY` nor `WAYLAND_DISPLAY`, the command neither panics nor silently reports success, preserves the already-emitted result, and returns the typed clipboard-write path; (3) a fake writer can prove both order and error conversion without OS access; and (4) no `xsel`, `xclip`, or `wl-copy` process is required. These are proposed checks, not executed results. `arboard` documents X11 by default and optional Wayland data-control support, including compositor limitations; it documents errors from clipboard creation where the desktop environment does not support a clipboard, but it does not prove a no-hang guarantee for every headless configuration. [arboard README, retrieved 2026-09-16](https://github.com/1Password/arboard/blob/v3.6.1/README.md) [arboard API documentation, retrieved 2026-09-16](https://docs.rs/arboard/3.6.1/arboard/struct.Clipboard.html)

No `BASELINE-REVIEW:` line is emitted: F281/F282 are `ts-only → DIVERGENT`, so the ledger has not inherited a Rust mechanism to challenge. [ledger rows F281/F282, retrieved 2026-09-16](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/areas/cli-framework-ux.md)

### Recommendation

Adopt the one-member stack **`arboard` 3.6.1 plus a synchronous injected `ClipboardWriter` boundary**, with `default-features = false` and `features = ["wayland-data-control"]`. Keep `--copy` without a short form. This gives macOS, Windows, X11, and optional native Wayland support without invoking external clipboard binaries; it makes an unavailable desktop a typed error that the command can render cleanly after its normal result sink. The application must not synthesize a private clipboard or report “copied” when the OS write fails.
