## Findings

### Finding 1 — the image job's path gate omits build inputs (JF-5, JF-7, JF-10). Blocking.

**The failed claim** (DECISION.md:676–680): "the recommendation is **one job in its own workflow file on `ubuntu-latest`** … path-gated on `crates/web/**`, `Dockerfile` and `.dockerignore`". DECISION.md:984–986 adds that "Every path in this decision — the CI job's path filter, the `.dockerignore`, and the stand-in workspace … — uses **revision 10's `crates/web` form**".

**Evidence.**

- **The consumed value names a key that the gate omits.** R69 revision 10's owned line (`research/runs/R69/2026-09-18T020601Z-f304731ab06f/review/DECISION.md:1791`) and the live registry row both end with this clause: "path-based skip-gating keys on crates/web/** [registry: src/web/**], **the serve binary's source file** and the web test files". R69 revision 10 places that file at `src/bin/<app>-serve.rs` in the root package (R69 `:1608`). The decision's own stand-in also declares `[[bin]] rslbp-serve` on the root package (DECISION.md:1050–1052). The gate therefore never runs when the source of the image's own `ENTRYPOINT` binary changes. The decision adopted one of R69's three skip-gating keys, and its claim at :984–986 hides the other two.
- **Published R11 rejected this allow-list shape on evidence.** R11 revision 7 (`research/topics/11-ci-workflow-job-structure/DECISION.md:61`) changed its `web` output from an allow-list ("set only by `crates/web/`, the serve binary's source and `.github/workflows/`") to a fail-closed rule. Its reason: "R69's web adapter consumes shared core types, so core or manifest changes can break `--features web`." The R11 table at `:195`–`:202` records `crates/core/src/lib.rs`, `Cargo.lock` and `crates/cli/src/main.rs` as changes that must set `web`. The table notes that a lockfile change "can move `axum` or `tokio`", and that the root package hosting the serve binary depends on `crates/cli`. The R51 decision cites R11 as the authority for where the job goes (DECISION.md:665–681). It then adopts a gate narrower than the list R11 discarded: R11's rejected list at least included the serve binary's source.
- **The gate contradicts the decision's own reasoning.** The build context is `COPY . .`, which is the whole tree except `.git` and `target` (DECISION.md:112, :158–160). `Cargo.lock` is deliberately kept in that context. Member 2 states that `-slim` "becomes wrong the moment a crate needs a native library" (:442–444). A `Cargo.lock` bump, for example from Dependabot, is exactly the change that can introduce such a crate, and this gate never builds the image on it. Member 5 selects the CI job for **verifiability** ("a recipe nobody builds rots silently", :639–640). Under this gate, the recipe can rot silently whenever a change lands outside `crates/web/**`.
- **The R12 hand-off at :692–697 does not cover this.** It concerns required-status `Pending` behavior under a trigger-level filter. It does not address inputs that the filter leaves out.

**Repair.** Gate the image job on every build-context input that `.dockerignore` admits. One form is root `Cargo.toml`, `Cargo.lock`, `src/**`, `crates/**`, `Dockerfile` and `.dockerignore`. The other is R11's fail-closed `code` condition, which is the negation of R11's skip-list. Cite R11 `:61` and `:195`–`:202` as the evidence. Correct the claim at :984–986 so it names all three of R69's skip-gating keys. Add a sources check that asserts the gate's path list contains the serve binary's source file and `Cargo.lock`. Restate gate 6's cost in member 5's ledger (:705), because the job then runs on every code-touching pull request.

### Finding 2 — `astral-sh/uv` is misrepresented as a cache-mount reference implementation (JF-4). Blocking.

**The failed claim** (DECISION.md:270–273): "`astral-sh/uv` composes cache mounts with a digest-pinned builder and a contents-minimal final stage. Neither composes all five selections, which is why the composite built here is the primary compatibility evidence and the adopters are the corroboration."

**Evidence.** The only source for uv's Dockerfile is the Opus raw report. The decision lists it as carried without independent verification (:1350–1353). At `raw/opus.md:50` it records uv's shape as "`RUN --mount=type=cache` **for apt**, `FROM scratch` as the final stage. No chef". At `:231`–`:232` it says uv uses "**no** dependency-caching tool at all — uv uses cache mounts for apt and nothing for cargo". Muse is the other engine. It names cache mounts alone only through "two small-project leads", which it discounts as "insufficient weight" (`raw/muse.md:162`). So neither engine cites any surveyed adopter that uses cache mounts for the Cargo registry or `target/`. Member 1's selection is exactly that use. The prompt requires: "For every recommendation cite a maintained reference implementation, or state the evidence gap" (`inputs/prompt.md:44`). The decision instead offers uv as corroboration for a mechanism uv does not apply to Cargo. The measured result `C4b`/`C5b` (0 against 50 recompiled crates) is sound. The fault is the adopter claim, not the measurement.

**Repair.** Rewrite :270–271 to Opus's actual reading: uv digest-pins its builder and uses cache mounts only for `apt`. Add an explicit evidence-gap sentence to member 1: no surveyed well-regarded project applies BuildKit cache mounts to the Cargo registry and `target/`, and the committed fixture is the only implementation. List the gap in `## Engines` under "Evidence gaps".
