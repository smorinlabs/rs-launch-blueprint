### Landscape

This item decides a **CI-tier repository secret scanner**: an independent GitHub Actions workflow that scans pushed or proposed Git history after local hooks may have been bypassed. It does not decide the hook-tier scanner (R39), dependency vulnerability scanning (R13), or the required-check graph (R11/R12). The three-bin field map is: **built-in or first-party toolchain** — GitHub secret scanning, which is platform-provided rather than a portable workflow and has entitlement/configuration variability; **established industry standard** — TruffleHog OSS and Gitleaks, both maintained scanners with GitHub Actions integration; **up-and-comer** — Nosey Parker, a Rust workspace scanner whose upstream repository is now archived. This categorization is based on the maintainers' implementation/documentation and the live GitHub repository state, not on language familiarity. [GitHub secret-scanning documentation](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning) (retrieved 2026-09-05); [TruffleHog action manifest](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/action.yml) (retrieved 2026-09-05); [Gitleaks Action README](https://raw.githubusercontent.com/gitleaks/gitleaks-action/master/README.md) (retrieved 2026-09-05); [Nosey Parker repository API endpoint](https://api.github.com/repos/praetorian-inc/noseyparker) (retrieved 2026-09-05).

The authority set is deliberately mixed: GitHub documentation is authoritative for Action triggers and platform secret scanning; TruffleHog's `action.yml` and README are authoritative for the action's executed command and verified-result behavior; Gitleaks' README is authoritative for its rule/baseline model and integration; Rust's Cargo CI guide is authoritative for the distinction between Rust build/test matrices and an external repository-scanning job. An independent comparative paper is only contextual evidence about false-positive/recall trade-offs and is not used to select a tool because its workload predates current releases. [GitHub workflow syntax](https://docs.github.com/en/actions/writing-workflows/workflow-syntax-for-github-actions) (retrieved 2026-09-05); [TruffleHog README](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/README.md) (retrieved 2026-09-05); [Gitleaks README](https://raw.githubusercontent.com/gitleaks/gitleaks/master/README.md) (retrieved 2026-09-05); [Cargo CI guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html) (retrieved 2026-09-05); [comparative study](https://arxiv.org/abs/2307.00714) (retrieved 2026-09-05).

Practice survey: the pinned Python source is a maintained reference implementation of the exact architecture — separate `secret-scan.yml`, `pull_request` diff range, `push` full history, and TruffleHog `--only-verified`; the TypeScript source has no CI-tier counterpart, so its absence is not evidence against the capability. Three well-regarded Rust projects were sampled only as a negative-control check: Cargo (the official Rust package manager), Tokio (the widely used Rust async runtime), and Serde (the standard serialization ecosystem) have no `trufflehog`, `gitleaks`, or `secret-scan` reference in their primary checked-in CI workflow at the URLs below. This limited sample is not adoption proof and should not be treated as a reason to omit the capability. [pinned Python workflow](https://raw.githubusercontent.com/smorinlabs/py-launch-blueprint/b08bccfb55d05f15e46a83b52c5660b1881d19f5/.github/workflows/secret-scan.yml) (retrieved 2026-09-05); [Cargo primary CI workflow](https://raw.githubusercontent.com/rust-lang/cargo/master/.github/workflows/ci.yml) (retrieved 2026-09-05); [Tokio primary CI workflow](https://raw.githubusercontent.com/tokio-rs/tokio/master/.github/workflows/ci.yml) (retrieved 2026-09-05); [Serde primary CI workflow](https://raw.githubusercontent.com/serde-rs/serde/master/.github/workflows/ci.yml) (retrieved 2026-09-05).

### Principles and implementation

The shared requirement is **defence in depth against committed credentials**, at the **capability/policy** agreement level: a bypassable local hook must not be the only detector, and CI must fail only on evidence actionable enough for a contributor to rotate a credential. The Python implementation supplies one realization; the TypeScript omission is a missing capability, not a justified language difference, because secret-bearing Git history is language-agnostic. F050 is already `DIVERGENT`, so there is no inherited `COMMON → REUSE` baseline to overturn and no `BASELINE-REVIEW:` finding to emit. [F050 source record](https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/areas/ci-workflows.md) (retrieved 2026-09-05); [pinned Python workflow](https://raw.githubusercontent.com/smorinlabs/py-launch-blueprint/b08bccfb55d05f15e46a83b52c5660b1881d19f5/.github/workflows/secret-scan.yml) (retrieved 2026-09-05).

The essential behaviors are: PR scans compare base SHA to head SHA; pushes to `main` scan the full available history; the workflow has only `contents: read`; `fetch-depth: 0` makes the chosen range available; a confirmed credential fails; a merely regex-shaped, unverified value does not; and the scan remains a separate workflow from R39's local scanner. Observable acceptance criteria are therefore one planned positive verified-fixture failure, one planned unverified-lookalike pass, one planned PR range failure, and one planned first-push full-history run without an equal-base/head error. TruffleHog's composite action accepts `base`, `head`, `extra_args`, and `version`; its action implementation executes `trufflehog git ... --since-commit ... --branch ... --fail`, while its README documents verified-only Git scanning and exit status 183 for valid credentials. [TruffleHog action manifest](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/action.yml) (retrieved 2026-09-05); [TruffleHog CI documentation](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/README.md) (retrieved 2026-09-05).

Architectural alternatives were compared before tools: (1) platform secret scanning alone is not a portable, versioned workflow and cannot express this template's verified-only policy; (2) one Gitleaks engine at both hook and CI tiers reduces setup diversity but is regex/rule based and therefore does not establish live-credential verification; (3) a dedicated verified CI scanner plus a fast local rule scanner assigns the tiers different false-positive budgets; (4) a Rust-native executable would not improve detection simply because the scanned files are Rust, and no shortlisted native project reaches the verification gate. TruffleHog is the selected architecture because its detector verification performs an external validity check where a detector supports one, reducing CI failure noise; this cost is intentional network activity and incomplete coverage for credential types without a verifier. [TruffleHog custom-detector verification documentation](https://github.com/trufflesecurity/trufflehog#custom-detectors) (retrieved 2026-09-05); [Gitleaks configuration documentation](https://raw.githubusercontent.com/gitleaks/gitleaks/master/README.md) (retrieved 2026-09-05).

Representative cost is workload-dependent: a PR scan costs one container startup plus detector work over `base..head`; a push scan costs the repository's reachable history, so it scales with history and changed blobs rather than Rust crate count. No comparable current benchmark with identical history, detector sets, verification settings, runner, latency, throughput, and resource measurement was found; no absolute performance ranking is claimed. Proposed instrumentation is GitHub job elapsed time and the action's emitted result count for a fixed fixture repository, recorded separately for a one-commit PR and a full-history push. [TruffleHog action implementation](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/action.yml) (retrieved 2026-09-05).

### Dominant choice

**TruffleHog OSS GitHub Action, major line `>=3.97.4, <4.0.0`; initially action input `version: "3.97.4"`.** The maintained reference action explicitly finds and verifies leaked credentials, supports PR base/head ranges, and supports `--only-verified`; it is independent of the template's implementation language. The immutable `uses:` commit SHA is deliberately deferred to R20's third-party-action pinning policy, rather than treating a tag as a supply-chain policy decision. The latest release observed was `v3.97.4` on 2026-09-03. ### Fit for this template

**CLI:** the scanner is intentionally out-of-process and does not add a runtime dependency, binary size, feature flag, async runtime, or `unsafe` posture to the CLI. **Library:** the scanner does not appear in the public API or dependency tree, preserving library consumers' build surface. **Web:** the scanner reads Git history rather than running the optional web service, so its workflow remains valid whether the `web` feature is enabled or disabled. These are reasons to use a standalone CI workflow, not claims that the action tests the Rust program on macOS; the action should run once on Ubuntu because duplicate history scanning contributes no platform signal. [TruffleHog action manifest](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/action.yml) (retrieved 2026-09-05); [Cargo features reference](https://doc.rust-lang.org/cargo/reference/features.html) (retrieved 2026-09-05).

### Recommendation

Adopt a dedicated `.github/workflows/secret-scan.yml` using `trufflesecurity/trufflehog` major v3, initially container version `3.97.4`, with `extra_args: --only-verified`. Trigger it on every `pull_request` with the PR base/head SHAs and on `push` to `main` with empty `base` and `head: HEAD`, after `actions/checkout` with `fetch-depth: 0`. The empty push base is deliberate: it selects full history and avoids the action's documented equal-base/head failure on a first push. Keep R39's hook scanner separate: it catches broad patterns before commit; this workflow catches confirmed credentials after server-side history exists. This is a proposed design, not an executed workflow. [pinned Python workflow](https://raw.githubusercontent.com/smorinlabs/py-launch-blueprint/b08bccfb55d05f15e46a83b52c5660b1881d19f5/.github/workflows/secret-scan.yml) (retrieved 2026-09-05); [TruffleHog action implementation](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/action.yml) (retrieved 2026-09-05).

### Ranked runner-up

`gitleaks/gitleaks-action@v3` is the runner-up **only if the owner changes the policy from “CI fails on verified credentials” to “CI fails on every configured secret-like match,” and accepts the organization license-key requirement.** It then wins on a single-engine operational model with the R39 hook scanner, mature configuration and baseline handling, but it does not satisfy the present verified-only acceptance criterion. [Gitleaks Action README](https://raw.githubusercontent.com/gitleaks/gitleaks-action/master/README.md) (retrieved 2026-09-05); [Gitleaks README](https://raw.githubusercontent.com/gitleaks/gitleaks/master/README.md) (retrieved 2026-09-05).

### Tradeoffs

TruffleHog gives up Gitleaks' one-engine simplicity, its local TOML/baseline continuity, and its MIT core license; it accepts an external verifier's network calls and the upstream AGPL action image. The cost is accepted because the workflow's purpose is to reduce actionable CI false positives, while R39 retains the fast broad-pattern local lane. It gives up Nosey Parker's Rust implementation and native scanner build, but that is immaterial to a language-agnostic Git-history scan and cannot compensate for an archived upstream or missing verification. No tool is selected on benchmark throughput: no controlled, current, like-for-like benchmark was found. [TruffleHog README](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/README.md) (retrieved 2026-09-05); [Gitleaks README](https://raw.githubusercontent.com/gitleaks/gitleaks/master/README.md) (retrieved 2026-09-05); [Nosey Parker repository endpoint](https://api.github.com/repos/praetorian-inc/noseyparker) (retrieved 2026-09-05).

### Validation strategy

The following are **planned, not executed** checks. They prove the policy without committing a credential to the template repository.

```sh
# 1. In a disposable repository, invoke the chosen pinned TruffleHog image
# against TruffleHog's maintained test fixture; expect a non-zero (documented
# 183) result when a verified fixture credential is present.
trufflehog git https://github.com/trufflesecurity/test_keys --results=verified --fail

# 2. In a temporary PR fixture, run the workflow with base/head set to a
# one-commit range containing the maintained verified fixture; expect failure.
# Then run a regex-shaped unverified lookalike fixture; expect success with
# `--only-verified`.

# 3. Push a newly initialized fixture repository to main and inspect the
# workflow log; expect a full-history scan, not "BASE and HEAD commits are the same".
```

The integration workflow should use `fetch-depth: 0`, PR `base`/`head`, push empty `base` plus `head: HEAD`, `version: "3.97.4"`, and `extra_args: --only-verified`; capture elapsed job time and verified-result count for the PR and full-history fixtures. A reviewer should also inspect `permissions:` and confirm only `contents: read` at job scope. [TruffleHog verified-fixture usage](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/README.md) (retrieved 2026-09-05); [TruffleHog action implementation](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/action.yml) (retrieved 2026-09-05).
