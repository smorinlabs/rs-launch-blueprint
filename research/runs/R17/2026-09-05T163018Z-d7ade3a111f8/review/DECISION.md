**A residual fail-open in the gate rule, found by executing the rule instead of reading it.** Revision 3 closed the fail-open the revision-2 audit named: the rule allow-lists the scanner's documented exit codes and fails the job on anything else. It left a second path open one level down. **The rule tells an implementer to capture the scanner's exit code and never says which shell is allowed to capture it.** GitHub's default `run:` shell is `bash -e {0}` and carries no `pipefail` — asserted at a pinned `github/docs` commit (`10h`) — so when the scan command is the non-final element of a pipeline, which is what teeing the scan into a step log or piping the report through `jq` produces, the captured status is the *last* command's, and that is `0`. The allow-list passes `0`, and **the job succeeds although the scanner never ran.** That is executed here rather than argued: section 12 runs the rule's literal implementation under the two shell command lines extracted from that pinned file, with the scanner first given a flag it rejects (exit `2`, the value `10e` proves) and then replaced by an absent binary. Under `bash -e` with a pipeline the step exits `0` both times — the security gate passes a job in which nothing was scanned (`12c`, `12f`). Under the explicit `shell: bash` form, `bash --noprofile --norc -eo pipefail`, the same step fails; under the default shell without the pipeline it also fails (`12d`, `12e`, `12g`, `12h`). Those four negative controls isolate the pipeline as the mechanism instead of assuming it. The rule therefore gains two requirements and loses one permission: the step declares `shell: bash` (or sets `pipefail` in its own script); the scanner does not sit upstream of an unguarded pipe; and **reading the report's `findings` array stops being an alternative to the exit-code allow-list and becomes an additional condition applied after it**, because a scanner that delivered no verdict also wrote no report, and an absent or stale report reads as zero findings. **Revision note — the defect revision 5 repairs, named plainly.** Revision 4 (sha256 `81bf62f1…`) was rejected by `review/audit-codex.md`, finding F1: its assertion `07g` did not reproduce. `07g` was the unauthenticated negative control for `gh attestation verify`. It ran `env -i PATH="$PATH" HOME="$NOAUTH_HOME" gh attestation verify …` and asserted the pair `4 1` — exit `4`, and one line of stderr carrying `gh auth login`. In the auditor's environment `gh` on `PATH` resolved to a `mise` shim; under the emptied environment that shim re-read a configuration it no longer trusted and aborted with exit `1` before the gh CLI started, so the control reported `FAIL (expected=4 1 actual=1 0)` and the whole run ended `PASS=58 FAIL=1`. **The defect is that the control asserted a specific exit number produced by whatever executable `PATH` happened to resolve, so it could only reproduce on a host where that executable was the gh CLI itself.** The sharper half of the defect is the one the summary line hides: a control that exits non-zero *for the wrong reason* is indistinguishable from the refusal it is supposed to demonstrate. Had that shim exited `4` for reasons of its own, `07g` would have **passed** while proving nothing about authentication — the same trap in the opposite direction.

**The repair, in the order this programme prefers: make the control environment-independent, and assert the property rather than the number.** (1) The control resolves an executable that *is* the gh CLI rather than a launcher: each candidate is probed under the control's own empty environment, one whose `--version` does not begin `gh version` is skipped with its resolved path printed, and one whose resolved path is not named `gh` — a `mise`, `asdf` or `rtx` shim — is kept only as a last-resort fallback. The log prints which `gh` was first on `PATH` and which was used, so a bypassed shim is visible rather than inferred. (2) **`07g` asserts the precondition that makes the control mean anything**: the resolved CLI reports the same version string as the `gh` the positive checks used, so the negative control exercises the same build as `07a` and `07f`. It can fail — a host carrying two gh builds fails it — so it is evidence and not decoration. (3) **`07h` asserts the refusal itself**, as a triple: the command exits non-zero, its stderr carries gh's own `gh auth login` remedy, and it writes zero bytes of attestation output. That triple is what separates "gh refused for want of authentication" from "the launcher fell over"; the pair revision 4 asserted could not separate them. (4) **`07i` grounds the number without writing it into the script**: it reads the code from the resolved gh's own `gh help exit-codes` topic ("If a command requires authentication, the exit code will be 4") and asserts the observed exit equals what that topic documents. A gh build that changed the code moves both sides of the assertion together; a build that ships no such topic **skips** the assertion with its reason rather than passing on a literal this script remembered. Where the number appears in prose it is now stated as an observation with its conditions — gh's documented authentication code, observed as `4` at `gh version 2.98.0 (2026-08-20)` — and never as an unconditional fact about the command. If no executable on a host starts the gh CLI under an empty environment, `07g`–`07i` are **skipped**, not passed, and the prerequisite stands on gh's documentation until the control is rerun where it can execute.

## Decision

Every decision in this programme is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). This document records what the research found and what it recommends; P03 builds the template and its CI proves or disproves the recommendation. A recommendation that does not survive implementation is revised against this recorded research, not researched again from scratch. `## Engines` lists what P03 must validate.

The decision has two parts, and they carry different confidence, so they are stated separately rather than as one recommendation. Part 1 is high confidence and unchanged since revision 2. Part 2 is stated with its confidence split between the tool, which the owner's ruling settles and the sibling's practice supports, and the packaging and gate, which nobody has yet run.

**Part 1 — keep a dedicated CI-tier secret-scanning workflow (high confidence).** `rs-launch-blueprint` ships `.github/workflows/secret-scan.yml`: one job, triggered on `pull_request` and on `push` to `main`, that fails when a live credential is present in the content being scanned. Both engines reached this independently. It survives the strongest contrary evidence in the item — that 0 of 10 surveyed well-regarded Rust projects run such a job (Opus raw, `### Landscape`, workflow inventories retrieved 2026-09-10) — because those projects are all public repositories, where GitHub's native secret scanning is free, whereas a template's principal deployment is a clone into a private repository, where the free tier stops (`https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning`, retrieved 2026-09-10, carried from the Opus raw), and because native scanning raises alerts rather than a pull-request status check that branch protection or R12 can require (same page, same retrieval).

**Part 2 — implement it with the TruffleHog OSS CLI, version range `>= 3.97.0, < 4.0.0`, installed as a pinned release binary in a `run:` step with provenance verified, `--only-verified --fail` (owner ruling W0-R17b, 2026-09-15; the tool is settled by that ruling, its packaging and gate are this document's).** Install the pinned release binary in a `run:` step and verify the provenance the release actually publishes, rather than calling `trufflesecurity/trufflehog@<tag>`; scan in one mode — full history, no `--since-commit`, no `base`/`head` conditional expressions; filter with `--only-verified`; add `--fail` so a finding reaches the exit code at all, and `--fail-on-scan-errors` so a scan error does too; write the findings to the job log in a format that does not print the credential; and **gate by allow-listing the scanner's documented exit codes, in a step whose shell cannot hide the scanner's status from the allow-list, never by testing the exit's sign.** **Confidence, split because the two halves are not equally supported: the TOOL is high, and it rose from revision 6's medium** — it is an owner ruling, and behind the ruling stand the sibling project's own CI practice at the programme pin (`01a`–`01c`) and a verified detection executed here against the vendor's published corpus at the documented failing code (`09a`), where revision 6's tool rested on gate answers and documented semantics with no adopter at all. **The packaging and the gate stay medium**: neither sibling installs this scanner as a pinned binary, so the install step, the flag set, the output format and the exit-code allow-list have no reference implementation anywhere and were executed as a scanner on a developer machine and never as a workflow step on a hosted runner. What P03 may overturn is therefore no longer the tool; it is this document's shape for running it.

**The gate rule, stated once in full for the tool the ruling selects. Every later mention of the gate in this document carries this paragraph and the one after it by reference.** TruffleHog's documented exit codes are exactly three, and they are **not** Kingfisher's — `0` (no errors and no results), `1` (an error was encountered; sources may not have completed scans), `183` (no errors, but results were found; returned only when `--fail` is passed) — read from `README.md` at the pinned tag `v3.97.4`, from the section headed `Exit Codes:`, and asserted as a set rather than summarised (assertion `06a`; the shipped `--help` documents `--fail` as "Exit with code 183 if results are found", `06b`). **Because `1` is a documented code that means the scan may not have completed, the allow-list of passing codes is `0` and nothing else** — where Kingfisher's rule allowed two codes to pass, this one allows one. The scan step therefore **captures the exit code explicitly and then allow-lists it**: `0` **passes**; `183` **fails the job** (a verified credential was found); `1` **fails the job** (the tool reported an error); and **any code outside that documented set also fails the job as a tool error**, because a code the tool does not document means the tool did not deliver a verdict. Executed: eleven invocations in section 07 produced only `0`, `1` and `183`, and none outside the set (`07k`); an unknown flag exits `1` (`07f`); a binary that is absent altogether does not produce a code of the tool's at all: the value is the *shell's*, and it lands on either side of the documented set depending on which shell ran — a plain shell reports `127`, which is outside it, while bash 3.2 under `errexit` reported `1` in revision 6's section 12, which is **inside** it and is a failing code there anyway. Either way the job fails, and that is the point: allow-listing the one passing code is what makes both outcomes safe, where enumerating failing codes would have to anticipate both.

**A fourth requirement belongs to this tool and not to the runner, and it is the one an implementer will miss: `--fail-on-scan-errors`.** TruffleHog treats a per-source scan error as non-fatal. Without that flag the process logs the error and **exits `0`**: a `filesystem` target that does not exist exits `0` with `encountered errors during scan` in the log (`07g`), and the same command with `--fail-on-scan-errors` exits `1` (`07h`). The sharper case is a partial scan — one readable target and one broken one — where the broken half is swallowed entirely and the exit reports only what the good half found: `183` without the flag, `1` with it (`07i`). A second route to the same silence is a `--since-commit` value the repository does not contain: the git source exits `0` having scanned `0` chunks (`07j`), which is an independent reason this decision recommends single-mode full history with no `--since-commit` at all. Kingfisher has no equivalent of either path, so this requirement is new with the ruling's tool rather than carried from revision 6.

**Three further conditions hold that allow-list up. They belong to the GitHub runner rather than to the scanner, so they are carried unchanged from revision 6, where they were executed.** *First*, the code must be **captured** rather than left to the shell, because GitHub's default shell for a `run:` step is `bash -e {0}`, so an uncaptured `183` aborts the step before any handler can run (executed in revision 6: `10h`–`10i`, read from `github/docs` at a pinned commit; `review/evidence/secret-scanning-ci-workflow-r6-repo.log`). *Second*, the step must declare **`shell: bash`** — `bash --noprofile --norc -eo pipefail {0}` — or set `pipefail` in its own script, and **the scanner must not sit upstream of an unguarded pipe.** Capturing the code is what switches `errexit` off for that command, so from that point the allow-list is only as good as the status handed to it; the default shell carries no `pipefail`, so a scanner piped into `tee` or `jq` hands it the *pipeline's* last status, which is `0`. Executed in revision 6, with a scanner given a flag it rejects and again with the scanner replaced by an absent binary: the rule's literal implementation under `bash -e` with a pipeline **passes the job** although nothing was scanned (`12c`, `12f`); the same step fails under the `pipefail` shell and fails under the default shell without the pipe (`12d`, `12e`, `12g`, `12h`). Those assertions are about bash and the two shell command lines GitHub documents, not about Kingfisher, which is why they transfer to this tool intact — and TruffleHog's `--json` output is exactly the thing an implementer pipes into `jq`, so the condition is more likely to bite here, not less. *Third*, **the scanner's own report is an additional condition and never an alternative**: once the code is allow-listed, a report carrying a verified result also fails the job. It cannot stand in for the code, because a scanner that never ran wrote no report, and an absent or stale report reads as zero findings — the one reading that must never pass. **Never gate on "exit code is non-zero", and never on the human-readable summary**: with this tool the first clause forbids nothing useful, because `1` and `183` both fail here, but it still licenses neither treating an undocumented code as a pass nor accepting a code the shell has masked. (TruffleHog's report shapes are its `--json` line-delimited results and its `--sarif` output; **the `--json` form is what was executed here**, and the SARIF form is documented, not executed. Every later mention of "the report" in this document means those two, in that order of evidence.) That gate rule is not a detail: it is what makes the workflow verified-only *and* what keeps it from passing silently when the scanner fails to run, and the empirical check below shows both halves (`review/evidence/secret-scanning-ci-workflow-r8-repo.log`, assertions `07a`–`07d` for the verified-only half, `06a`–`06e` and `07e`–`07k` for the allow-list half). On the evidence run here — one fixture of template-shaped fake credentials, which `--only-verified` passes and the same scan unfiltered fails — **no repository-specific configuration file, allowlist or exclusion file is needed at this tier**; that is the answer to the prompt's LOW question, and its evidence is one fixture plus the tool's documented filter semantics, so P03 re-runs the same check against the real template rather than inheriting the conclusion.

**A fifth requirement, and the one this tool forces that neither revision 6 nor the ruling anticipated: the step must not print the credential it finds.** TruffleHog ships no `--redact` flag, and that is **executed** rather than inferred from `--help`: invoked with it, the pinned binary answers `trufflehog: error: unknown long flag '--redact', try --help` and exits `1`, on both the `filesystem` and the `git` source, where the accepted control flag `--no-verification` exits `0` on both (`08e`, `08f`). (Revision 7 derived this from a `--help` search, which `06d` had already shown this release defeats by hiding flags; that is round 7's finding F1.) Both output formats an implementer reaches for first then write the matched secret verbatim: the default human-readable output prints `Raw result: <the credential>` for the PAT and the AWS access key id — **not** for the AWS secret access key, which reaches only `--json`'s `RawV2` field — and `--json` carries all three (`08a`, `08b`, both executed by counting occurrences of the fixture's own values, never by echoing the output). A GitHub Actions job log is readable by everyone with read access to the repository and is retained by default, so a **verified** finding printed there converts a leak into a second, wider leak. The executed answer is TruffleHog's own `--github-actions` output format: on the same fixture it writes **zero** occurrences, on stdout and on stderr, of **each of the three values this scanner detects** — asserted one value at a time, so each can fail on its own (`08h`, `08i`, `08j`) — and emits one `::warning file=…,line=…` annotation per finding, naming file and line, and it still exits `183` (`08c`, `08d`). The fixture's fourth value, a `localhost` database URI, is **not detected at this pin** and no claim is made for it beyond that (`08g`, `08k`). P03's scan step therefore uses `--github-actions` for what reaches the log, and any `--json` report it keeps for the gate's report condition is written to a file that is not echoed and not uploaded as an artifact.

The ranked runner-up is the **Kingfisher CLI, `>= 2.2.0, < 3.0.0`, installed the same way** (a pinned binary in a `run:` step), with `--only-valid` and `--redact`. It was revision 6's recommendation and the owner's ruling made it the runner-up; its winning condition is therefore the **reverse** of the one it held then, and it is testable rather than re-arguable: **Kingfisher wins back if TruffleHog OSS is archived or its CLI stops shipping release binaries for both owner-fixed runners, or if P03 measures a live credential that TruffleHog misses and Kingfisher catches.** **If P03 switches back, the gate rule above transfers in form but not in values**: Kingfisher's documented set is `0` / `200` / `205` and its allow-list passes *two* codes rather than one, which revision 6 executed at `v2.2.0` (`10a`–`10g` of `review/evidence/secret-scanning-ci-workflow-r6-repo.log`) and this revision does not re-execute. Two of the requirements above are TruffleHog-specific and **would be dropped**, not carried: `--fail-on-scan-errors` has no Kingfisher equivalent, and `--redact` makes the output-format requirement unnecessary. **The rule's three runner conditions transfer unchanged, values and all**, because they are properties of the GitHub runner and not of the scanner: capture the code, declare `shell: bash` and keep the scanner out of an unguarded pipe, and treat the report as an additional condition rather than a substitute. The failure they guard against is identical in both tools: a code the tool does not document means no scan happened, and it must fail the job; and a shell that masks that code passes the job either way.

### Principles and implementation

**The shared requirement.** *A credential that is live at merge time must not reach the default branch without a server-side check failing first.* Source: ledger row F050 (`docs/port/COMMONALITY.md:56`), realized in py by `.github/workflows/secret-scan.yml` at pin `b08bccfb` (read through the pin, 2026-09-10; reproduced in full in the evidence log, section 01).

**Agreement level: capability and policy — not tool, not configuration.** The three repositories must agree that a non-bypassable CI-tier check exists and that it fails on a validated credential. They need not agree on which binary produces that verdict, because the scanner is an executed build tool: it enters no repository's public API and no repository's dependency graph.

| Must agree (capability and policy) | May vary (ecosystem-local) |
|---|---|
| A CI-tier job exists that fails on a live credential | Which scanner binary produces the verdict |
| The verdict is server-side and a contributor cannot skip it | How the binary reaches the runner (Action, container, release tarball) |
| The job runs on `pull_request` and on `push` to `main` | Whether the scan is diff-scoped or full-history |
| The failure is a check that branch-protection rules can require | Which runner OS the single scan job lands on (R11 owns this) |

**Essential behaviors.** (1) Scan the content a pull request would add, and the history already present. (2) Attempt live validation against the issuing provider and distinguish verified from candidate. (3) **Fail the gate when a verified credential is present, and fail it when the scanner produced no verdict at all** — with the TruffleHog CLI the workflow allow-lists the tool's documented exit codes rather than testing the exit's sign, in a step whose shell cannot mask the scanner's status (the rule and its conditions are stated in full in Part 2: `0` passes, `183` and `1` fail, any code outside the documented set fails as a tool error; `--fail` and `--fail-on-scan-errors` are both passed; the code is captured, the step declares `shell: bash` with the scanner out of an unguarded pipe, and the report is an additional condition rather than a substitute). `--fail` has to be passed because without it a verified finding leaves the process at `0` — `183` is documented as returned "only … if `--fail` flag is used" (`06a`, `06b`); `--fail-on-scan-errors` has to be passed because a non-fatal scan error otherwise also leaves it at `0` (executed: `07g`–`07j`); and the shell condition is not optional, because under the default `run:` shell a piped scanner hands the allow-list a `0` it did not earn and the job passes unscanned (executed in revision 6, section 12). (4) Name the finding's location without printing the secret — this tool has **no** `--redact`, executed by invoking the binary with that flag and asserting its refusal on both source kinds against an accepted-flag control (`08e`, `08f`), so the behavior is obtained from the output format instead: `--github-actions` emits one `::warning file=…,line=…` annotation per finding and writes zero occurrences, on stdout and stderr, of each of the three fixture values this scanner detects, asserted one value at a time (`08c`, `08h`–`08j`), where the default and `--json` formats write them verbatim (`08a`, `08b`). The fixture's fourth value is not detected at this pin and carries no such claim (`08g`, `08k`). (5) Require no vendor account and no paid licence key.

**The py split, verified at the pinned tag — what it does and does not establish.** The Opus raw's load-bearing finding is that py's diff-scan-on-PR / full-scan-on-push split is a workaround for the incumbent Action's error when base and head are equal, not an independent requirement. I verified it rather than accepting it, and it holds, at this width:

- py's own comment names the tool error as the reason for the conditional: "on push (esp. a new repo's FIRST push) base==head, which TruffleHog rejects ('BASE and HEAD commits are the same')" (`.github/workflows/secret-scan.yml`, at pin `b08bccfb`, evidence log section 01).
- The error exists in the tool's own action definition at **`v3.95.9`, the exact tag py pins**: `if [ "$base_commit" == "$head_commit" ] ; then echo "::error::BASE and HEAD commits are the same…"; exit 1; fi` (`https://raw.githubusercontent.com/trufflesecurity/trufflehog/v3.95.9/action.yml`, sha256 `c3847cdb…`, retrieved 2026-09-10; executed in revision 6, evidence log section 03, and not re-fetched in this revision).
- The same file shows the guard is reached **only when the workflow supplies a non-empty `base` or `head`**, and that the Action's own `else` branch derives the range from the event, including the all-zeros first push. So the split is a consequence of how py drives the Action, not a property of secret scanning.

What this changes about the item: the diff/full split is **not** part of the shared requirement and does not have to be ported. What it does **not** license is the stronger claim that only a different tool can drop it — py's own push path already passes an empty `base`, which produces a full-history scan through the same Action, so **single-mode full-history is achievable with either tool**; what the recommendation buys is dropping the two conditional GitHub expressions, which either tool permits. Kingfisher additionally has no equal-commit guard at all: omitting `--since-commit` scans full history (`docs/USAGE.md:598-605,644`, retrieved 2026-09-10; and executed as acceptance criterion 2 above).

**What the owner's ruling adds to that paragraph, executed at this revision's pin.** The sentence above is about the Action and about Kingfisher, and both halves stand; the tool the ruling selects needed its own check. The TruffleHog **CLI** has no equal-commit guard either — the guard lives in `action.yml`, not in the binary — and a repository with exactly one commit, which is the shape of a template's first push, scans to exit `0` with zero `BASE and HEAD commits are the same` errors (`07e`). Its full-history behaviour with no `--since-commit` is executed too (`07c`). The ruling's stated reason for preferring the CLI over py's Action form — that the Action is `docker`-based, `ubuntu-latest`-only and carries the first-push failure — therefore holds on primary evidence in all three parts.
