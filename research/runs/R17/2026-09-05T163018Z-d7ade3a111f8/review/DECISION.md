## Decision

Every decision in this programme is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). This document records what the research found and what it recommends; P03 builds the template and its CI proves or disproves the recommendation. A recommendation that does not survive implementation is revised against this recorded research, not researched again from scratch. `## Engines` lists what P03 must validate.

The decision has two parts, and they carry different confidence, so they are stated separately rather than as one recommendation.

**Part 1 — keep a dedicated CI-tier secret-scanning workflow (high confidence).** `rs-launch-blueprint` ships `.github/workflows/secret-scan.yml`: one job, triggered on `pull_request` and on `push` to `main`, that fails when a live credential is present in the content being scanned. Both engines reached this independently. It survives the strongest contrary evidence in the item — that 0 of 10 surveyed well-regarded Rust projects run such a job (Opus raw, `### Landscape`, workflow inventories retrieved 2026-09-10) — because those projects are all public repositories, where GitHub's native secret scanning is free, whereas a template's principal deployment is a clone into a private repository, where the free tier stops (`https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning`, retrieved 2026-09-10, carried from the Opus raw), and because native scanning raises alerts rather than a pull-request status check that branch protection or R12 can require (same page, same retrieval).

**Part 2 — implement it with the Kingfisher CLI, version range `>= 2.2.0, < 3.0.0` (medium confidence; the tool is the part P03 may overturn).** Install the pinned release binary in a `run:` step and verify its build provenance, rather than calling a third-party GitHub Action; scan in one mode — full history, no `--since-commit`, no `base`/`head` conditional expressions; filter with `--only-valid`; and **gate by allow-listing the scanner's documented exit codes, never by testing the exit's sign.**

**The gate rule, stated once in full. Every later mention of the gate in this document carries this paragraph by reference.** Kingfisher's documented exit codes are exactly three — `0` (no findings), `200` (findings discovered), `205` (validated findings discovered) — read from `docs/USAGE.md` at the pinned tag `v2.2.0` and asserted on, not summarised (assertion `10a`; the shipped `--help`, `scan --help` and README document no exit code at all, `10b`–`10d`). The scan step therefore **captures the exit code explicitly and then allow-lists it**: `0` and `200` **pass**; `205` **fails the job**, and so does a non-empty `findings` array in the JSON report; and **any code outside that documented set fails the job as a tool error**, because a code the tool does not document means the tool did not deliver a verdict. Executed examples of that third case: a rejected flag exits `2` and an unreadable scan target exits `1`, neither of which is in the documented set (`10e`–`10g`); by shell convention a missing binary exits `127`, which is convention, not executed here. The code must be *captured* rather than left to the shell, because GitHub's default shell for a `run:` step is `bash -e {0}` — an explicit `shell: bash` is `bash --noprofile --norc -eo pipefail {0}` — so an uncaptured `200` aborts the step before any handler can run (executed: `10h`–`10i`, read from `github/docs`). **Never gate on "exit code is non-zero", and never on the human-readable summary**: that clause forbids treating `200` as a failure, and it does not license treating an undocumented code as a pass. The allow-list belongs to the *tool*: the ranked runner-up's exit codes are documented and not executed here, so a switch to it re-derives its allow-list at its own pin before the gate is written, rather than inheriting Kingfisher's three codes. (The JSON report's `findings` array is what was executed here; the SARIF report carries its findings as `runs[].results[]` instead, and that form is documented, not executed. Every later mention of "the report" in this document means those two, in that order of evidence.) That gate rule is not a detail: it is what makes the workflow verified-only *and* what keeps it from passing silently when the scanner fails to run, and the empirical check below shows both halves (`review/evidence/secret-scanning-ci-workflow.log`, assertions `08a`–`08d` for the verified-only half, `10a`–`10i` for the allow-list half). On the evidence run here — one fixture of template-shaped fake credentials, whose report came back empty — **no repository-specific configuration file, allowlist or fingerprint-suppression file is needed at this tier**; that is the answer to the prompt's LOW question, and its evidence is one fixture plus the tool's documented filter semantics, so P03 re-runs the same check against the real template rather than inheriting the conclusion.

The ranked runner-up is the **TruffleHog OSS CLI, `>= 3.97.0, < 4.0.0`, installed the same way** (a pinned binary in a `run:` step, not `trufflesecurity/trufflehog@<tag>`), with `--only-verified --fail`. **If P03 switches to it, the gate rule above transfers in form but not in values**: TruffleHog's documented exit codes were not executed here (the CLI was never downloaded — see `## Empirical check`), so the switch means reading that tool's documented set at its own pin and allow-listing *it*, not reusing `0` / `200` / `205`. The failure this guards against is identical in both tools: a code the tool does not document means no scan happened, and it must fail the job. The conditions under which the runner-up wins are listed in `## Engines` as testable triggers rather than as re-arguable preferences.

### Principles and implementation

**The shared requirement.** *A credential that is live at merge time must not reach the default branch without a server-side check failing first.* Source: ledger row F050 (`docs/port/COMMONALITY.md:56`), realized in py by `.github/workflows/secret-scan.yml` at pin `b08bccfb` (read through the pin, 2026-09-10; reproduced in full in the evidence log, section 01).

**Agreement level: capability and policy — not tool, not configuration.** The three repositories must agree that a non-bypassable CI-tier check exists and that it fails on a validated credential. They need not agree on which binary produces that verdict, because the scanner is an executed build tool: it enters no repository's public API and no repository's dependency graph.

| Must agree (capability and policy) | May vary (ecosystem-local) |
|---|---|
| A CI-tier job exists that fails on a live credential | Which scanner binary produces the verdict |
| The verdict is server-side and a contributor cannot skip it | How the binary reaches the runner (Action, container, release tarball) |
| The job runs on `pull_request` and on `push` to `main` | Whether the scan is diff-scoped or full-history |
| The failure is a check that branch-protection rules can require | Which runner OS the single scan job lands on (R11 owns this) |

**Essential behaviors.** (1) Scan the content a pull request would add, and the history already present. (2) Attempt live validation against the issuing provider and distinguish validated from candidate. (3) **Fail the gate when a validated credential is present, and fail it when the scanner produced no verdict at all** — with Kingfisher the workflow allow-lists the tool's documented exit codes rather than testing the exit's sign (the rule is stated in full in Part 2: `0` and `200` pass, `205` fails, any code outside the documented set fails as a tool error). `205` has to be tested specifically because `--only-valid` is a *report* filter and leaves the process exit at `200` when an unvalidated candidate was matched (executed, see `## Empirical check`); a code outside the documented set has to fail because it means no scan happened (`2` on a rejected flag, `1` on an unreadable target — both executed, section 10). (4) Name the finding's location without printing the secret (`--redact` is available and was used in every executed scan). (5) Require no vendor account and no paid licence key.

What *is* executed here is the set the allow-list rests on and two codes outside it (`10a`–`10g`); the gate that consumes them is P03's |

**The py split, verified at the pinned tag — what it does and does not establish.** The Opus raw's load-bearing finding is that py's diff-scan-on-PR / full-scan-on-push split is a workaround for the incumbent Action's error when base and head are equal, not an independent requirement. I verified it rather than accepting it, and it holds, at this width:

- py's own comment names the tool error as the reason for the conditional: "on push (esp. a new repo's FIRST push) base==head, which TruffleHog rejects ('BASE and HEAD commits are the same')" (`.github/workflows/secret-scan.yml`, at pin `b08bccfb`, evidence log section 01).
- The error exists in the tool's own action definition at **`v3.95.9`, the exact tag py pins**: `if [ "$base_commit" == "$head_commit" ] ; then echo "::error::BASE and HEAD commits are the same…"; exit 1; fi` (`https://raw.githubusercontent.com/trufflesecurity/trufflehog/v3.95.9/action.yml`, sha256 `c3847cdb…`, retrieved 2026-09-10; evidence log section 03).
- The same file shows the guard is reached **only when the workflow supplies a non-empty `base` or `head`**, and that the Action's own `else` branch derives the range from the event, including the all-zeros first push. So the split is a consequence of how py drives the Action, not a property of secret scanning.

What this changes about the item: the diff/full split is **not** part of the shared requirement and does not have to be ported. What it does **not** license is the stronger claim that only a different tool can drop it — py's own push path already passes an empty `base`, which produces a full-history scan through the same Action, so **single-mode full-history is achievable with either tool**; what the recommendation buys is dropping the two conditional GitHub expressions, which either tool permits. Kingfisher additionally has no equal-commit guard at all: omitting `--since-commit` scans full history (`docs/USAGE.md:598-605,644`, retrieved 2026-09-10; and executed as acceptance criterion 2 above).

| # | Architecture | Gives | Costs | Verdict |
|---|---|---|---|---|

**Shape C's safety advantage over shape B, and the environment that advantage depends on. This paragraph and the next state the qualification once in full; every later mention of provenance verification in this document carries them.** Executed rather than asserted: `gh attestation verify kingfisher-darwin-arm64.tgz --repo mongodb/kingfisher` exits `0`, and the attestation it verifies carries the sha256 of the exact tarball downloaded here — `4e741aba…`, asserted equal to the local file's digest (evidence log section 07, assertions `07a` and `07d`). The certificate records `buildSignerURI` `https://github.com/mongodb/kingfisher/.github/workflows/release.yml@refs/heads/main` and `runnerEnvironment: github-hosted` (assertion `07e`). Those two fields are **read from the certificate, not enforced by the flags this check passes**: `--repo mongodb/kingfisher` constrains the repository identity only, and pinning the signer workflow requires `--signer-workflow` or `--cert-identity` (`gh attestation verify --help`, gh 2.98.0), which this check does not pass and which P03's install step should. A tag-pinned third-party Action offers no equivalent attestation at all.

**The command is environment-dependent, and revision 1 recorded it as though it were not — that is the defect this revision repairs.** `gh attestation verify` builds its Sigstore verifier from TUF trusted-root metadata that it refreshes into `$XDG_CACHE_HOME/gh/.sigstore` (default `$HOME/.cache/gh/.sigstore`). Three prerequisites must hold, or the command fails before it looks at the artifact at all: (1) that cache path must be writable — otherwise gh exits `1` printing `error creating Sigstore verifier: no valid Sigstore verifiers could be initialized`, executed here as a negative control (assertion `07f`); (2) `gh` must be authenticated — otherwise it exits `4` and directs the caller to `gh auth login` (assertion `07g`), so a CI step needs a token in its environment; (3) the host must reach `api.github.com`, `tuf-repo-cdn.sigstore.dev` and `tuf-repo.github.com`. Revision 1's check inherited the caller's `$HOME`, so it passed in a permissive shell and then failed, exit `1`, under the revision-1 audit's sandbox, whose writes were confined to the workspace and `$TMPDIR` (`review/audit-codex.r1.md`, finding F1). The repaired check redirects the cache into its own working directory, and the log cited below was produced with the outer cache deliberately made unwritable, so the repair is demonstrated in the environment that broke it rather than only in a permissive one. **What section 07 establishes is a developer-machine fact, not a CI fact.** No GitHub Actions job has run this command for this template — none exists yet — so the install shape's dependence on provenance verification being available in CI is a requirement on the implementation phase, recorded in the unproven table above and in the migration implications below, not a settled fact here.

**How the selected design preserves each principle.** *Non-bypassable server-side verdict*: the job runs on GitHub-hosted infrastructure on both triggers, so a contributor's `--no-verify` cannot reach it. *Fails on a live credential and not on a fake one*: `--only-valid` (documented as the compatibility alias for `--validation-filter active`, `docs/USAGE.md:64`, verified in the shipped `--help`) keeps only provider-confirmed findings in the report, and the executed fixture shows a template-shaped fake credential leaving the report empty — with the gate allow-listing the documented codes (`205` fails, `0` and `200` pass, any other code fails as a tool error; Part 2 states the rule in full), not reading the exit's sign. *A requireable check*: the job is an ordinary workflow job, so R11 and R12 can fold it in. *No vendor onboarding*: Kingfisher needs no account, licence key or API token, unlike `gitleaks/gitleaks-action` (organizations), GitGuardian `ggshield` and Semgrep Secrets. *Runs on this template's matrix*: release assets exist for `darwin-arm64`, `darwin-x64`, `linux-x64` and `linux-arm64`, its own CI runs `ubuntu-24.04`, `ubuntu-24.04-arm` and `macos-14`, and the macOS binary was executed here (`kingfisher 2.2.0`) — the check that TruffleHog's Action cannot pass, because a GitHub-hosted macOS runner has no container runtime (that exclusion is conditional; the next paragraph states the condition and governs every mention of it in this document).

**One qualification that governs every mention of the macOS exclusion in this document.** TruffleHog's *Action* fails the prompt's literal constraint that "every recommendation must work on all of them [`ubuntu-latest, macos-latest`]" because its composite step ends in `docker run`. The evidentiary basis for "a GitHub-hosted macOS runner cannot run a container", stated once here because every other mention of the exclusion points back to this paragraph: the `docker run` line in `action.yml` at `v3.95.9` is primary evidence and was executed-read here; the runner limitation itself is carried from the Opus raw and rests on `https://github.com/orgs/community/discussions/25777` and `https://github.com/actions/runner/issues/1866` (retrieved 2026-09-10), not on a normative GitHub Docs page — the Opus raw records that it looked for one and did not find it, and I did not run a macOS job to test it. R11 owns which runner the scan job lands on, and a single scan job pinned to `ubuntu-latest` would never meet the limitation in practice. The exclusion therefore removes the Action's *only* real advantage — one-line integration — rather than removing TruffleHog itself: the TruffleHog **CLI** ships macOS binaries and is the ranked runner-up under the same shape C. Every later reference to "the Action fails the macOS gate" carries this qualification.

**Maturity, dependability, performance and integration cost.** TruffleHog is the mature incumbent: 27,756 stars at the cited log's retrieval instant, AGPL-3.0, latest release `v3.97.4` on 2026-09-03 (verified, evidence log section 04); its AGPL licence attaches no obligation to `MIT OR Apache-2.0` template artifacts because the scanner is executed as a build tool and is never linked or redistributed. Kingfisher is 16 months old: created 2025-05-08, 1,226 stars, Apache-2.0, not archived, `v2.0.0`/`v2.1.0`/`v2.2.0` released on 2026-08-23, 2026-08-30 and 2026-09-09 (verified, evidence log section 05). On raw maturity TruffleHog wins, and that is the strongest argument against Part 2. The counterweight is measured maintainer responsiveness, carried from the Opus raw and **not re-executed here**: of the 10 most recently created issues per repository, 9 of 10 answered by a maintainer at a 2.48-day median for Kingfisher, versus 0 of 10 for both TruffleHog and Gitleaks (Opus raw, `### Principles and implementation`, method and issue numbers recorded there, retrieved 2026-09-10; the method counts only `OWNER`/`MEMBER`/`COLLABORATOR` repliers, which the raw itself flags as a possible undercount). Performance: no independent benchmark exists. MongoDB's vendor-authored `docs/COMPARISON.md` reports, on the `gitlab` repository, Kingfisher at 135.41 s and 17 network requests against TruffleHog at 325.93 s and 15,624 network requests for the **same 6 validated findings**; the figure that bears on this item is the network-request count, because each validation request transmits a candidate string to a third party. **The finding that changes the design.** Section 08 is not a confirmation; it is a correction. `--only-valid` is documented in the shipped `--help` as "Display only validated findings", and it behaves exactly that way: the *report* is emptied of the unvalidated candidate, but the *process exit code* stays `200` ("findings discovered"), and the human-readable summary still counts the filtered candidate — so the two output formats disagree for a single scan. A workflow that failed on "non-zero exit" would therefore fail on the template's own example credentials, and the Opus raw's acceptance criterion 2 ("Expected: the job passes") would not hold as written.
