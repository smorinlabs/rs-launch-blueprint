**Revision note — the defect revision 5 repairs, named plainly.** Revision 4 (sha256 `81bf62f1…`) was rejected by `review/audit-codex.md`, finding F1: its assertion `07g` did not reproduce. `07g` was the unauthenticated negative control for `gh attestation verify`. It ran `env -i PATH="$PATH" HOME="$NOAUTH_HOME" gh attestation verify …` and asserted the pair `4 1` — exit `4`, and one line of stderr carrying `gh auth login`. In the auditor's environment `gh` on `PATH` resolved to a `mise` shim; under the emptied environment that shim re-read a configuration it no longer trusted and aborted with exit `1` before the gh CLI started, so the control reported `FAIL (expected=4 1 actual=1 0)` and the whole run ended `PASS=58 FAIL=1`. **The defect is that the control asserted a specific exit number produced by whatever executable `PATH` happened to resolve, so it could only reproduce on a host where that executable was the gh CLI itself.** The sharper half of the defect is the one the summary line hides: a control that exits non-zero *for the wrong reason* is indistinguishable from the refusal it is supposed to demonstrate. Had that shim exited `4` for reasons of its own, `07g` would have **passed** while proving nothing about authentication — the same trap in the opposite direction.

**The repair, in the order this programme prefers: make the control environment-independent, and assert the property rather than the number.** (1) The control resolves an executable that *is* the gh CLI rather than a launcher: each candidate is probed under the control's own empty environment, one whose `--version` does not begin `gh version` is skipped with its resolved path printed, and one whose resolved path is not named `gh` — a `mise`, `asdf` or `rtx` shim — is kept only as a last-resort fallback. The log prints which `gh` was first on `PATH` and which was used, so a bypassed shim is visible rather than inferred. (2) **`07g` asserts the precondition that makes the control mean anything**: the resolved CLI reports the same version string as the `gh` the positive checks used, so the negative control exercises the same build as `07a` and `07f`. It can fail — a host carrying two gh builds fails it — so it is evidence and not decoration. (3) **`07h` asserts the refusal itself**, as a triple: the command exits non-zero, its stderr carries gh's own `gh auth login` remedy, and it writes zero bytes of attestation output. That triple is what separates "gh refused for want of authentication" from "the launcher fell over"; the pair revision 4 asserted could not separate them. (4) **`07i` grounds the number without writing it into the script**: it reads the code from the resolved gh's own `gh help exit-codes` topic ("If a command requires authentication, the exit code will be 4") and asserts the observed exit equals what that topic documents. A gh build that changed the code moves both sides of the assertion together; a build that ships no such topic **skips** the assertion with its reason rather than passing on a literal this script remembered. Where the number appears in prose it is now stated as an observation with its conditions — gh's documented authentication code, observed as `4` at `gh version 2.98.0 (2026-08-20)` — and never as an unconditional fact about the command. If no executable on a host starts the gh CLI under an empty environment, `07g`–`07i` are **skipped**, not passed, and the prerequisite stands on gh's documentation until the control is rerun where it can execute.

## Decision

Every decision in this programme is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). This document records what the research found and what it recommends; P03 builds the template and its CI proves or disproves the recommendation. A recommendation that does not survive implementation is revised against this recorded research, not researched again from scratch. `## Engines` lists what P03 must validate.

The decision has two parts, and they carry different confidence, so they are stated separately rather than as one recommendation.

**Part 1 — keep a dedicated CI-tier secret-scanning workflow (high confidence).** `rs-launch-blueprint` ships `.github/workflows/secret-scan.yml`: one job, triggered on `pull_request` and on `push` to `main`, that fails when a live credential is present in the content being scanned. Both engines reached this independently. It survives the strongest contrary evidence in the item — that 0 of 10 surveyed well-regarded Rust projects run such a job (Opus raw, `### Landscape`, workflow inventories retrieved 2026-09-10) — because those projects are all public repositories, where GitHub's native secret scanning is free, whereas a template's principal deployment is a clone into a private repository, where the free tier stops (`https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning`, retrieved 2026-09-10, carried from the Opus raw), and because native scanning raises alerts rather than a pull-request status check that branch protection or R12 can require (same page, same retrieval).

**Part 2 — implement it with the Kingfisher CLI, version range `>= 2.2.0, < 3.0.0` (medium confidence; the tool is the part P03 may overturn).** Install the pinned release binary in a `run:` step and verify its build provenance, rather than calling a third-party GitHub Action; scan in one mode — full history, no `--since-commit`, no `base`/`head` conditional expressions; filter with `--only-valid`; and **gate by allow-listing the scanner's documented exit codes, in a step whose shell cannot hide the scanner's status from the allow-list, never by testing the exit's sign.**

**The gate rule, stated once in full. Every later mention of the gate in this document carries this paragraph and the one after it by reference.** Kingfisher's documented exit codes are exactly three — `0` (no findings), `200` (findings discovered), `205` (validated findings discovered) — read from `docs/USAGE.md` at the pinned tag `v2.2.0` and asserted on, not summarised (assertion `10a`; the shipped `--help`, `scan --help` and README document no exit code at all, `10b`–`10d`). The scan step therefore **captures the exit code explicitly and then allow-lists it**: `0` and `200` **pass**; `205` **fails the job**; and **any code outside that documented set fails the job as a tool error**, because a code the tool does not document means the tool did not deliver a verdict. Executed examples of that third case: a flag the **top-level** command rejects exits `2`, and a `scan` whose target does not exist exits `1`; neither value is in the documented set (`10e`–`10g`). A binary that is absent altogether also exits outside the set, and there the exact value is the *shell's* rather than the tool's — bash 3.2 under `errexit` reported `1` for an absent path in this check where a plain shell reports `127` (`12f`–`12h`) — which is a further reason the rule allow-lists the passing codes instead of enumerating failing ones.

**Three conditions hold that allow-list up, and all three are part of the rule.** *First*, the code must be **captured** rather than left to the shell, because GitHub's default shell for a `run:` step is `bash -e {0}`, so an uncaptured `200` aborts the step before any handler can run (executed: `10h`–`10i`, read from `github/docs` at a pinned commit). *Second*, the step must declare **`shell: bash`** — `bash --noprofile --norc -eo pipefail {0}` — or set `pipefail` in its own script, and **the scanner must not sit upstream of an unguarded pipe.** Capturing the code is what switches `errexit` off for that command, so from that point the allow-list is only as good as the status handed to it; the default shell carries no `pipefail`, so a scanner piped into `tee` or `jq` hands it the *pipeline's* last status, which is `0`. Executed: with the scanner given a flag it rejects, and again with the scanner replaced by an absent binary, the rule's literal implementation under `bash -e` with a pipeline **passes the job** although nothing was scanned (`12c`, `12f`); the same step fails under the `pipefail` shell and fails under the default shell without the pipe (`12d`, `12e`, `12g`, `12h`). *Third*, **the report's `findings` array is an additional condition and never an alternative**: once the code is allow-listed, a non-empty `findings` array also fails the job. It cannot stand in for the code, because a scanner that never ran wrote no report, and an absent or stale report reads as zero findings — the one reading that must never pass. **Never gate on "exit code is non-zero", and never on the human-readable summary**: that clause forbids treating `200` as a failure, and it licenses neither treating an undocumented code as a pass nor accepting a code the shell has masked. The allow-list belongs to the *tool*: the ranked runner-up's exit codes are documented and not executed here, so a switch to it re-derives its allow-list at its own pin before the gate is written, rather than inheriting Kingfisher's three codes. The three conditions belong to the *runner* instead, so they transfer to any scanner unchanged. (The JSON report's `findings` array is what was executed here; the SARIF report carries its findings as `runs[].results[]` instead, and that form is documented, not executed. Every later mention of "the report" in this document means those two, in that order of evidence.) That gate rule is not a detail: it is what makes the workflow verified-only *and* what keeps it from passing silently when the scanner fails to run, and the empirical check below shows both halves (`review/evidence/secret-scanning-ci-workflow.log`, assertions `08a`–`08d` for the verified-only half, `10a`–`10i` and `12a`–`12h` for the allow-list half). On the evidence run here — one fixture of template-shaped fake credentials, whose report came back empty — **no repository-specific configuration file, allowlist or fingerprint-suppression file is needed at this tier**; that is the answer to the prompt's LOW question, and its evidence is one fixture plus the tool's documented filter semantics, so P03 re-runs the same check against the real template rather than inheriting the conclusion.

The ranked runner-up is the **TruffleHog OSS CLI, `>= 3.97.0, < 4.0.0`, installed the same way** (a pinned binary in a `run:` step, not `trufflesecurity/trufflehog@<tag>`), with `--only-verified --fail`. **If P03 switches to it, the gate rule above transfers in form but not in values**: TruffleHog's documented exit codes were not executed here (the CLI was never downloaded — see `## Empirical check`), so the switch means reading that tool's documented set at its own pin and allow-listing *it*, not reusing `0` / `200` / `205`. **The rule's three conditions transfer unchanged, values and all**, because they are properties of the GitHub runner and not of the scanner: capture the code, declare `shell: bash` and keep the scanner out of an unguarded pipe, and treat the report as an additional condition rather than a substitute. The failure this guards against is identical in both tools: a code the tool does not document means no scan happened, and it must fail the job; and a shell that masks that code passes the job either way. The conditions under which the runner-up wins are listed in `## Engines` as testable triggers rather than as re-arguable preferences.

### Principles and implementation

**The shared requirement.** *A credential that is live at merge time must not reach the default branch without a server-side check failing first.* Source: ledger row F050 (`docs/port/COMMONALITY.md:56`), realized in py by `.github/workflows/secret-scan.yml` at pin `b08bccfb` (read through the pin, 2026-09-10; reproduced in full in the evidence log, section 01).

**Agreement level: capability and policy — not tool, not configuration.** The three repositories must agree that a non-bypassable CI-tier check exists and that it fails on a validated credential. They need not agree on which binary produces that verdict, because the scanner is an executed build tool: it enters no repository's public API and no repository's dependency graph.

| Must agree (capability and policy) | May vary (ecosystem-local) |
|---|---|
| A CI-tier job exists that fails on a live credential | Which scanner binary produces the verdict |
| The verdict is server-side and a contributor cannot skip it | How the binary reaches the runner (Action, container, release tarball) |

**Essential behaviors.** (1) Scan the content a pull request would add, and the history already present. (2) Attempt live validation against the issuing provider and distinguish validated from candidate. (3) **Fail the gate when a validated credential is present, and fail it when the scanner produced no verdict at all** — with Kingfisher the workflow allow-lists the tool's documented exit codes rather than testing the exit's sign, in a step whose shell cannot mask the scanner's status (the rule and its three conditions are stated in full in Part 2: `0` and `200` pass, `205` fails, any code outside the documented set fails as a tool error; the code is captured, the step declares `shell: bash` with the scanner out of an unguarded pipe, and the report is an additional condition rather than a substitute). `205` has to be tested specifically because `--only-valid` is a *report* filter and leaves the process exit at `200` when an unvalidated candidate was matched (executed, see `## Empirical check`); a code outside the documented set has to fail because it means no scan happened (`2` on a rejected flag, `1` on an unreadable target — both executed, section 10); and the shell condition is not optional, because under the default `run:` shell a piped scanner hands the allow-list a `0` it did not earn and the job passes unscanned (executed, section 12). (4) Name the finding's location without printing the secret (`--redact` is available and was used in every executed scan). (5) Require no vendor account and no paid licence key.

**The finding that changes the design.** Section 08 is not a confirmation; it is a correction. `--only-valid` is documented in the shipped `--help` as "Display only validated findings", and it behaves exactly that way: the *report* is emptied of the unvalidated candidate, but the *process exit code* stays `200` ("findings discovered"), and the human-readable summary still counts the filtered candidate — so the two output formats disagree for a single scan. **Where the evidence is incomplete, and I say so rather than smoothing it.** Part 2 rests on gate answers and executed semantics, not on adoption: no third-party well-regarded Rust project is known to run Kingfisher; no global adoption count exists for any of these scanners because GitHub's code-search API rejects the unscoped query; the only head-to-head performance and detection comparison is vendor-authored; and the 485-rule count I executed is a *total*, not the validating subset, so detector-breadth parity with TruffleHog's 700+ verifying detectors is unproven in both directions. A reasonable reviewer could prefer the mature incumbent's CLI on those grounds; the cost of being wrong is one workflow-file edit, which is why the recommendation is made with the triggers stated rather than deferred.

**What P03 must validate (the proposal's test list).** Acceptance check 1 (live credential fails the job at exit `205`, file and line named, credential revoked afterwards); acceptance check 2 (template example credentials leave the report empty — executed here on a fixture, to be re-run in the real template); acceptance check 3 (first push to a repository created from the template runs cleanly); **acceptance check 5 (a scan step whose scanner cannot run fails the job — binary replaced by `false`, a rejected flag added, and either breakage with the scan command piped into `tee` — asserted to fail, not pass, in all three)**; the gate allow-lists the documented exit codes as defined in Part 2 (`0` and `200` pass, `205` fails, any code outside the documented set fails as a tool error) and *additionally* fails on a non-empty report rather than reading the report instead of the code, never the exit's sign, and it captures the code in a step that declares `shell: bash` with the scanner out of an unguarded pipe rather than leaving the code to the step's default `bash -e` shell; the install step's `gh attestation verify` passes **on a GitHub-hosted runner**, which this research did not test — it needs `GH_TOKEN` in the step's environment, a writable `$XDG_CACHE_HOME/gh/.sigstore`, and egress to `api.github.com`, `tuf-repo-cdn.sigstore.dev` and `tuf-repo.github.com`, and it should additionally pass `--signer-workflow`; the credential classes the web surface leaks (database URIs, JWT signing keys, OIDC client secrets) are actually detected; and an explicit version-refresh path exists for the pinned scanner.

**Re-verify triggers.** (1) `GET https://api.github.com/repos/mongodb/kingfisher` shows `archived: true`, or no release for six months, or MongoDB posts a maintenance notice — any one flips the recommendation to the TruffleHog CLI. (2) Kingfisher publishes a first-party GitHub Action, or TruffleHog's Action stops shelling out to a container runtime — either changes the architecture-shape calculus. (3) GitHub makes secret scanning free on private repositories **and** adds a pull-request status check — together those would make architecture A viable and could retire the workflow; either alone would not. (4) R39 selects Kingfisher for the hook tier — then the `BASELINE-REVIEW: F050` line must be resolved by the owner before both tiers share a tool. (5) R11 or R12 constrains the scan job in a way that assumes a first-party Action or a specific runner OS. (6) P03 measures a live credential that TruffleHog catches and Kingfisher misses, or a third-party well-regarded Rust project adopts Kingfisher in CI — the first flips the tool, the second raises Part 2's confidence from medium to high without changing it.
