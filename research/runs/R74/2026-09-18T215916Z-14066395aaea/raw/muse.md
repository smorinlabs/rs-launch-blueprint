# Raw research answer — R74 rate-limiting middleware (bundle) — Muse engine

Engine: muse (Meta) substituting for Codex under the `engine_overrides` pilot. Crate and repository figures below come from the run's evidence snapshots (`review/evidence/snapshots/`, retrieved 2026-09-19 per `MANIFEST.tsv`); crate-source readings are from the registry copies listed, read 2026-09-26. Nothing in this report was executed: all checks are proposed, not run.

### Landscape

Category decided: per-caller HTTP admission control for the optional web surface — a middleware, inert until one configuration value is set, that rejects requests above a declared quota with `429 Too Many Requests` and an accurate `Retry-After`, keeping per-key counters in this process's memory. Three separable sub-decisions live inside it: the *layer mechanism* (how the check attaches to the router and what the rejection is), the *algorithm* (what "over quota" means and when the next admission is), and the *store* (where per-key state lives and how it stays bounded). They are the three members under `### Members`.

Three-bin map of the Rust field (figures: `GET https://crates.io/api/v1/crates/<name>` and `/versions`, retrieved 2026-09-19; `recent` = 90-day downloads, `all` = all-time):

### Principles and implementation

Shared requirement (source: py precedent, `src/py_launch_blueprint/web/settings.py:70` declaring `rate_limit: str | None = None` with "None (the default) disables rate limiting entirely (WEB-22)", gating `app.py:143`'s `if settings.rate_limit:` and the `Limiter(key_func=get_remote_address, default_limits=[...], headers_enabled=True)` at `app.py:220` with no `storage_uri`; rows F316/F323, verdict `DIVERGENT`; ts has no web service so there is no second precedent). Agreement level: a **capability plus a policy** — the service can refuse excess traffic per caller; the capability is off unless one configuration value turns it on; the refusal is a standards-conformant 429 whose `Retry-After` derives from limiter state; the state is single-instance by design with a named swap point. Nothing about slowapi, `limits` notation internals, GCRA or token buckets is part of the agreement. What may vary: the algorithm, the map type, headers beyond `Retry-After`, and whether the check is a `tower` layer or a function.

Essential behaviors and observable acceptance criteria: (B1) off by default — with the setting unset, unbounded request counts all succeed and no limiter state exists; (B2) one value turns it on — setting exactly one environment variable, with no recompilation, makes the same binary refuse; (B3) correct admission — with quota `N/period`, the first `N` requests from one key are admitted and the `N+1`-th refused; (B4) per-key isolation — a second key is unaffected by the first key's exhaustion; (B5) standards-conformant refusal — status 429 and `Retry-After` a non-negative decimal integer (RFC 9110 §10.2.3: `delay-seconds = 1*DIGIT`); (B6) accurate `Retry-After` — derived from limiter state, never a constant, never earlier than the true next admission; (B7) in-memory, bounded, single-instance — state lives in this process, cannot grow without bound, and the distributed swap point is a named type; (B8) one envelope — the refusal renders through the service's single error representation (R70's), not a second ad-hoc body.

Architectural alternatives compared before libraries. (A1) A `tower::Layer`/`Service` pair (the `tower_governor` shape): the check runs in `Service::call`, composes with `ServiceBuilder`, reuses outside axum — but the rejection must be built as a raw `http::Response`, because a `Service` error type is not axum's `IntoResponse`; rendering through R70's envelope needs a handler that calls the envelope function, a second code path. (A2) `axum::middleware::from_fn_with_state`: an `async fn(State, Request, Next) -> Result<Response, E> where E: IntoResponse`, which axum wraps into a layer sitting in the same `.layer()` stack R75 orders — and the rejection is a *value of the web member's own error type*, so whatever `IntoResponse` R70 lands on renders it by construction. (A3) Per-handler extractor or per-route layer: rejected — F323's precedent is app-wide (`default_limits`), and a per-route quota surface is an unasked feature. (A4) Push limiting out of process (gateway/sidecar): the right production architecture at scale, since per-instance memory enforces `quota × instances` — but rejected for this item because a template must demonstrate the shape in the artefact it ships; the operator who fronts with a gateway leaves the variable unset. It belongs in the docs beside the swap point.

The shared pattern stays appropriate in Rust with one substitution: py's truthy-settings gate becomes `Option<T>` with conditional registration — `match policy { None => router, Some(p) => router.layer(..) }` compiles with no adapter since `Router::layer` consumes and returns `Router`. A Cargo feature gate is rejected on principle: it moves the gate to compile time, so the shipped binary would no longer *contain* a limiter that one variable turns on — the behavior F323 records. R69's `web` feature already gates whether the web tree exists; a second compile-time gate inside it buys nothing and loses the property.

Why the ecosystem's dominant pair is not the recommendation. `governor` 0.10.4 and `tower_governor` 0.8.0 both **fail fitness gate 2**: neither published manifest declares `rust-version` (`governor-0.10.4/Cargo.toml`: `edition = "2018"`, no `rust-version`; `tower_governor-0.8.0/Cargo.toml`: `edition = "2021"`, none — read from the registry copies, 2026-09-26, matching the `rust_version: null` in the `/versions` snapshots), and `governor`'s manifest at `HEAD` still declares none (snapshot `gh-contents-governor-Cargo.toml.json`, 2026-09-19), so this is standing policy, not release lag. The owner withdrew the lenient reading of that gate ("an unknown version is insufficient to clear a bar the prompt says must be cleared", `docs/planning/p02/owner-decisions.md`), and R69 applied the strict reading to exclude `warp`, `viz`, `pavex` and `tide`. Applying the same rule — to candidates, not to every transitive crate, per R69 — excludes both. The MSRV floor itself is 1.96: current stable is 1.98.1 (snapshot `channel-rust-stable-pkg-rust.txt`, `version = "1.98.1 (48a229cea 2026-09-01)"`), minus two minors.

Three first-hand source readings corroborate the exclusion independently of the gate. First, `tower_governor` 0.8.0 computes its header as `NotUntil::wait_time_from(now).as_secs()` (`src/lib.rs:125-127` and `:293-295`, read 2026-09-26) — `as_secs` **truncates**, so a true wait of 29.99s renders as `29`, and a sub-second wait renders as `0`; a client obeying the header retries inside the window and is refused again, violating B6. (The header is present — both `retry-after` and `x-ratelimit-after` are inserted at `:143-144` and `:312-313` — so any claim the crate emits only the legacy header is wrong; the defect is the value, not the presence.) Second, the default key extractor maps a missing `ConnectInfo` to `GovernorError::UnableToExtractKey` (`src/key_extractor.rs:76,113`), whose response is **`500 Internal Server Error`** (`src/errors.rs:58-61`) — and R69's accepted serve path (`axum::serve(listener, app)`) and `oneshot` test idiom install no `ConnectInfo`, so the default configuration 500s on the template's own paths. Third, maintenance: `benwis/tower-governor` shows `pushed_at` 2025-08-14 (13 months), 19 open issues (`search/issues`, `total_count`, 2026-09-19) — verdict **at-risk** on the concrete signal. `boinkor-net/governor` is by contrast **active** (938 stars, pushed 2026-08-24): excluded by the gate, not by neglect.

What remains once the gates are applied, and why the template owns the layer. `tower-resilience-ratelimiter` 0.13.0 is a single global limiter with no key extraction (its error hard-codes `retry_after: None`; its docs say a 429 "could" be returned "in HTTP context" — i.e. by the caller): it cannot express B4 or B6. `gcra` 0.6.0 has the right shape but zero reverse dependents, no release since 2024-08-01, and pins `dashmap` 5.x/`thiserror` 1.x behind current majors. `axum-governor` 2.1.0 is the most standards-complete option (emits `retry-after`, the draft's `RateLimit` field and legacy `x-ratelimit-*`; `src/headers.rs`, read 2026-09-26) but has zero reverse dependents, 25 stars, and declares `rust-version = "1.95"` — one minor below the 1.96 floor, *less* headroom than the two minors on which R69 excluded `salvo`; it also depends on `governor` 0.10 (`[dependencies.governor] version = "0.10"`, read 2026-09-26), so adopting it puts the gate-excluded engine in the tree behind a compliant wrapper. `axum_gcra` 0.1.1 declares no `rust-version` at all (gate 2 again). `tower-rate-limiter` 0.1.6 is the interesting newcomer — keyed fixed-window over moka-or-Redis, `Retry-After` always on 429, edition 2024, `rust-version = "1.96.0"` — but it sits *exactly* on the floor with zero headroom, has 294 downloads and 0 reverse dependents, turns key-extraction failure into 500 exactly like `tower_governor` (`response.rs`, `RateLimitError::Key` → `INTERNAL_SERVER_ERROR`, read 2026-09-26), and as a fixed window reports window-end as the wait, which over-states the wait for every request but the last (B6, weakly violated). Verdict: watch, do not adopt.

So the template owns a small layer. The behavior is genuinely small: GCRA's per-key state is one `Instant` and the decision is two comparisons; the store is a capacity-bounded map behind a trait that is the named swap point; the middleware is one axum function. It adds **zero crates** to `crates/web` — std plus the `axum` R69 already selected — where `tower_governor` with `tonic` disabled still pulls `governor`, `dashmap`, `quanta`, `parking_lot`, `rand` and both `thiserror` majors, and its *default* features (which include `tonic`) drag a gRPC stack into a template with no gRPC.

No `BASELINE-REVIEW:` finding is raised. ### Recommendation

One stack: adopt a rate-limiting middleware that `rs-launch-blueprint` owns, adding **no new crate** to `crates/web`. The layer mechanism is `axum::middleware::from_fn_with_state` from the `axum` 0.8.9 R69 already selected, keyed by `axum::extract::ConnectInfo<SocketAddr>`; the algorithm is GCRA over `std::time::Instant`, whose per-key state is one theoretical-arrival-time instant yielding the exact next admission that `Retry-After` is the ceiling of; the store is a capacity-bounded `std::sync::Mutex<HashMap<RateLimitKey, Instant>>` behind a `RateLimitStore` trait that is the named distributed-store swap point. The capability is gated by one optional setting — R77 names the variable; this item fixes its grammar as py's `limits` notation `"<count>/<period>"` — read once at router construction, with the layer simply not registered when unset. `tower_governor` 0.8.0 and `governor` 0.10.4, the ecosystem's dominant pair and the owner reference's C11 pick, are excluded by fitness gate 2 (no declared `rust-version` under the settled strict reading) and corroborating first-hand source findings (truncated `Retry-After`, 500 on missing key, 13-month-silent maintainer).

##### Principles and implementation

The principle is that the rejection must be expressible in the same currency as every other error the service produces, so F305's single envelope survives without a second rendering path. A `tower::Service` responds with `http::Response<B>` — a `Layer`-based limiter can only *build a response* — while an axum middleware function returning `Result<Response, E> where E: IntoResponse` *returns an error value*. That decides the member: with `from_fn_with_state` the 429 is a `RateLimited` value, and whichever `IntoResponse` R70 lands on renders it, with the rate-limit code owning only the `Retry-After` value. `from_fn_with_state` also carries the shared limiter through axum's `State`, which is the owner reference's "build one and reuse" (line 415) made unexpressible-otherwise: the store is constructed once in `install_rate_limit` and moved into the layer. The key comes from `req.extensions().get::<ConnectInfo<SocketAddr>>()`, py's `get_remote_address` in Rust. Observable criteria: B1–B5 and B8. Reference implementation: axum's own documented middleware adapter plus its in-repo examples; the composition itself has no maintained reference (gap G1). Maturity: axum 0.8 series stable, 476M downloads; dependability: the framework R69 already bet the web surface on. Performance: one `State` clone (an `Arc`) and one header-free function call per request — negligible by construction, no benchmark run (G2). Integration cost: nil — no new crate, one function, one registration call.

##### Up-and-comers

##### Fit for this template

The template is CLI + library + web service, the web service an optional Cargo feature and the limiter one of roughly eight layers R75 will order. Three properties decide fit. First, the mechanism must not add a crate to a feature whose selling point is costing nothing when off — `from_fn_with_state` adds none; `tower_governor` adds dozens (with `tonic` on by default). Second, the rejection must render through R70's single envelope; only the `Result<Response, E>` form does that by construction. Third, it must work under R69's accepted `axum::serve(listener, app)` and `oneshot` paths; `tower_governor`'s and `tower-rate-limiter`'s default extractors return **500** under both unless `ConnectInfo` is installed (read in source, 2026-09-26). Against py the fit is exact: `from_fn_with_state` + `ConnectInfo` is `SlowAPIMiddleware` + `get_remote_address`, and conditional registration is `if settings.rate_limit:`. Against ts there is nothing to fit — no web service.

##### Recommendation

Use `axum::middleware::from_fn_with_state(state, rate_limit)` inside `install_rate_limit`, with the limiter state shared through axum `State`. Take the key from `ConnectInfo<SocketAddr>` when present. When absent, fall back to a single global bucket **and warn exactly once** through `std::sync::Once`, so the degradation is loud rather than silent; failing closed with a 500 is rejected because a limiter that turns a configuration slip into a total outage is worse than one that over-restricts while saying so. #### GCRA admission algorithm over std time Instant — pattern member

##### Landscape

The algorithm category: what "over quota" means and what the wait until the next admission is. This is a **pattern member**: the candidates are algorithms, and crates implementing them are named only as evidence — crate figures (downloads, stars, issues, advisories, adopters) are `inapplicable` to the pattern itself, with the implementing crates' figures reported instead. Bin 1 (built-in/first-party): none — the standard library ships no rate-limiting algorithm; `tower::limit::RateLimitLayer`'s fixed-window counter over `tokio::time` is the closest first-party thing. Bin 2 (established industry standard): **GCRA** (Generic Cell Rate Algorithm, ITU-T I.371, reused for HTTP limiting), implemented by `governor` 0.10.4 (recent 15,833,152, 483 dependents) and `gcra` 0.6.0; **token bucket**, implemented by unkeyed single buckets; **fixed window**, implemented by `tower::limit` and `tower-rate-limiter` 0.1.6; **sliding window**, implemented by `tower-resilience-ratelimiter` 0.13.0. Bin 3 (up-and-comers): nothing algorithmically new — every recent crate reimplements one of these four (`tower-rate-limiter` is fixed-window; `axum-governor` delegates to `governor`'s GCRA). Authorities: the ITU-T algorithm via the reference the shipped `gcra` 0.6.0 source itself cites; RFC 9110 §10.2.3 for what the computed wait must render as; the crates' own source. Well-regarded projects surveyed: `governor`'s GCRA is what Cloudflare's `foundations` 5.10.2, `alloy-transport` 2.4.2 and `sc-rpc-server` 32.1.0 use — the strongest available evidence GCRA is the ecosystem's settled choice.

##### Principles and implementation

The principle behind py's `headers_enabled=True` and its "never a guess" comment is that the refusal must carry the limiter's own knowledge of *when* the next request succeeds. An algorithm qualifies only if it answers "when", not merely "no". GCRA answers it exactly: its entire state is one theoretical arrival time `tat`; with emission interval `T = period / burst` and tolerance `tau = (burst − 1) · T`, a request at `now` is admitted when `max(tat, now) ≤ now + tau`, and when refused the next admission is exactly `max(tat, now) − tau`. Token bucket answers it too but needs two fields plus a refill division per check; fixed window answers only "the window end", overstating the wait for every request but the last (B6, weakly violated — this is `tower-rate-limiter`'s shape); sliding-window-log answers exactly but stores one timestamp per request, unbounded in the wrong dimension. GCRA is also the only one whose state is a single `Copy` value, which is what keeps the store member a plain map. Observable criteria: B3, B4, B6. Maturity: the algorithm is decades old and its dominant implementation carries 77.9M downloads; the six-line direct implementation is checkable by inspection. Performance: two comparisons, no allocation, no division on the hot path; no benchmark run (G2).

##### Dominant choice

GCRA, on adoption of its implementations rather than on theory: `governor` 0.10.4 has recent 15,833,152 and all-time 77,888,772 downloads with 483 reverse dependents (`.../governor`, `.../reverse_dependencies`, 2026-09-19), and four separate framework communities wrapped `governor` rather than writing their own limiter — the clearest signal GCRA is this ecosystem's default answer. `governor`'s repository is **active** (938 stars, pushed 2026-08-24, `archived: false`). It is excluded as a *dependency* by gate 2 (see below); the algorithm it implements is adopted directly.

##### Qualified shortlist

1. **GCRA** — exact next-admission instant, one `Instant` of state per key, no division on the hot path. Recommended.
2. **Token bucket** — equivalent behavior, two fields of state, a refill computation per check. Rejected narrowly on fit: not worse, just bigger, and its crates are unkeyed single buckets, so the keyed map stays template-owned either way.
3. **Sliding window counter** — smooths the window boundary at the cost of two counters per key and an approximated wait. Rejected: the extra fidelity is invisible at a template's quota granularity.
4. **Fixed window counter** — simplest, but the reported wait is the window end for every refused request, violating B6. Rejected (this also retires `tower-rate-limiter`'s algorithm for this item).
5. **Sliding window log** — exact, but O(quota) memory per key. Rejected against B7.

##### Excluded by gate

No algorithm is excluded by a gate: gates 1–6 are crate properties and this is a pattern member (crate figures `inapplicable` for that reason). Recorded for completeness: the two crates that would have supplied GCRA across a crate boundary are excluded elsewhere — `governor` 0.10.4 by **gate 2** (published `Cargo.toml` declares `edition = "2018"` and no `rust-version`, registry copy read 2026-09-26; manifest at `HEAD` declares none either, snapshot `gh-contents-governor-Cargo.toml.json`, 2026-09-19) and `gcra` 0.6.0 on practice evidence (see the store member). Implementing the arithmetic directly carries no gate exposure at all.

##### Up-and-comers

None. Every crate released in the last twelve months on this map implements GCRA, a token bucket or a window counter; `axum-governor` 2.1.0 delegates its arithmetic to `governor`'s GCRA outright (`[dependencies.governor] version = "0.10"`, read 2026-09-26), and `tower-rate-limiter` 0.1.6 is fixed-window. There is no new algorithm to consider — itself the finding: this category is settled, and the open questions are packaging questions.

##### Fit for this template

The template's quota is one app-wide policy in py's `N/period` grammar, keyed by peer address, with an accurate `Retry-After` as the visible contract. GCRA delivers exactly that with one `Instant` per key and two comparisons per request, and its refusal carries the exact next-admission instant that `Retry-After` is the ceiling of — strictly better than the incumbent, which truncates the same answer with `Duration::as_secs()` (`tower_governor-0.8.0/src/lib.rs:125-127`, read 2026-09-26), rendering sub-second waits as `0`. One thing could not be verified: slowapi's own header computation was not read (a dependency of the pinned repo, not a file in it), so whether py truncates or rounds is **unverified** (G4) — the ceiling here is this template's argued choice from RFC 9110 plus the observation that a value below the true wait guarantees a second refusal.

##### Recommendation

Implement GCRA directly over `std::time::Instant`: `emission_interval = period / burst`, `tolerance = emission_interval · (burst − 1)`, `tat = max(stored, now)`; refuse with next admission at `tat − tolerance` when `tat > now + tolerance`, else store `tat + emission_interval` and admit. Render `Retry-After` as the ceiling of the remaining wait in whole seconds, floored at 1, never 0. Parse the policy from py's `limits` notation `"<count>/<period>"` with `period ∈ {second|sec|s, minute|min|m, hour|hr|h, day|d}`, rejecting zero counts via `NonZeroU32` and unknown periods explicitly.

##### Ranked runner-up

1. Token bucket over `std::time::Instant`, same store, same middleware. Choose it only if a future requirement needs variable-cost requests, where a bucket level is more natural than one arrival time.
2. `gcra` 0.6.0's check-and-modify API — this exact arithmetic behind a crate boundary (MIT, `rust-version` 1.80.0). Choose it if the owner would rather import the arithmetic than own it; see the store member for why it is not the recommendation.

##### Tradeoffs

Gained: an exact next-admission instant, one `Copy` value of state per key, no allocation and no division on the hot path, and full control of the `Retry-After` rounding the incumbent gets wrong. Given up: the reassurance of an ITU-standard algorithm implemented by someone else — mitigated by GCRA being checkable by inspection in six lines and pinnable by tests (burst size, exact header value, parser rejections). Risk accepted: an off-by-one in `tolerance` silently shifts the burst size by one (`tau = burst · T` admits `burst + 1`); the proposed `2/minute` test pins the exact third-request refusal to catch it.

#### In-memory keyed store behind a RateLimitStore port — pattern member

##### Landscape

The store category: where per-key state lives, how concurrent requests reach it, how it stays bounded, and what the documented swap point to a distributed store is. A **pattern member**: crate figures are `inapplicable` to the pattern itself; figures for the crates discussed are reported where they are discussed. Bin 1 (built-in/first-party): `std::sync::Mutex<std::collections::HashMap<K, V>>` and `RwLock<HashMap<K, V>>`. Bin 2 (established industry standard): `dashmap` 6.x (the sharded concurrent map `governor` uses under its `dashmap` feature) and `governor`'s own keyed state store; `moka`/`quick_cache` as TTL/eviction caches. Bin 3 (up-and-comers): `gcra` 0.6.0's `RateLimiter<T>` (a `dashmap` 5.5.3 map with `max_data_capacity` and `prune_expired()`), `axum-governor` 2.1.0's `gc.rs` eviction task, `tower-rate-limiter` 0.1.6's moka-backed `MemoryStore` (moka 0.12, `sync` feature). Authorities: the standard library documentation; the crates' own source; `tower_governor`'s own README pattern of spawning an interval task calling `limiter.retain_recent()` — the ecosystem's acknowledgement that the `governor` keyed store is otherwise unbounded. Well-regarded projects surveyed: the same `governor` dependents — Cloudflare's `foundations` 5.10.2, `alloy-transport` 2.4.2, `sc-rpc-server` 32.1.0 — all inheriting the `dashmap`-backed keyed store.

##### Principles and implementation

Two principles meet here. F316's is that the store is **in-memory and single-instance by design**, with the distributed swap documented and not built — py realises it by constructing the limiter with no `storage_uri` and documenting the Redis swap point. The template's own R01 principle is that a substitutable dependency is a trait erased at the composition root. Together they make the swap point a **type, not a comment**: `trait RateLimitStore { fn check(&self, key: &RateLimitKey, now: Instant) -> Result<(), Instant>; }`, with `InMemoryRateLimitStore` as the shipped implementation and the middleware holding `Arc<dyn RateLimitStore>`. A Redis-backed implementation is then a new type, not a middleware rewrite — what "documented swap point" should mean in a language with traits. The second principle is that an in-memory keyed limiter must be **bounded**, because its key space is attacker-controlled: the store carries a capacity, evicts expired cells when full, and admits the untracked request if still full (fail-open, recorded as a deliberate trade below). Observable criteria: B4, B7, and the named swap point. Maturity: `Mutex<HashMap>` is as mature as Rust gets; the novelty is only the trait seam. Performance: one mutex acquisition per check; same complexity class as the sharded alternatives at this template's scale — no benchmark run (G2). Integration cost: one module, no dependency.

##### Dominant choice

`dashmap`-backed sharded maps, as used by `governor` 0.10.4 — recent 15,833,152 downloads, 483 reverse dependents including Cloudflare's `foundations` 5.10.2 (`.../governor/reverse_dependencies`, 2026-09-19). `dashmap` itself carries one RustSec advisory, RUSTSEC-2022-0002, **patched in ≥ 5.1.0**, so neither `dashmap` 5.5.3 nor 6.x is affected (the `dashmap` RustSec page exists — HTTP 200 in `rustsec-status.txt`, 2026-09-19 — while `governor`, `tower_governor`, `gcra`, `axum-governor`, `axum_gcra` and `tower-rate-limiter` all return HTTP 404, i.e. no advisory page exists). The dominant choice is not adopted, because adopting it means adopting `governor` or `gcra`, and both are excluded below.

##### Qualified shortlist

1. `std::sync::Mutex<HashMap<RateLimitKey, Instant>>` with a capacity, behind `RateLimitStore`. No crate, no gate exposure, bounded by construction. Recommended.
2. `dashmap` 6.x directly, behind the same trait. Passes gates 1–3 on its own terms (MIT; declared `rust_version`; the one advisory patched far below the resolved version). Rejected on fit: it adds a crate plus transitive packages to buy sharding this template's throughput does not need, and it does not bound itself.

##### Recommendation

`InMemoryRateLimitStore { policy, capacity, cells: Mutex<HashMap<RateLimitKey, Instant>> }` implementing `RateLimitStore`, held by the middleware as `Arc<dyn RateLimitStore>`. Eviction is lazy and O(capacity): only when the map is full and the key is new does it `retain` cells whose arrival time has passed (carrying no state). If the map is still full afterwards, the request is **admitted** — the limiter fails open. That is a deliberate security trade, recorded as one: an attacker with many source addresses can fill the map and disable limiting for new keys, whereas failing closed lets the same attacker deny service to every new client. A limiter must not become the outage. Mitigations: a capacity large enough to cost real resources (default 65,536 cells, a few MiB) and a saturation counter handed to R79 so the condition is observable, not silent. `RateLimitKey` is an enum — `Peer(IpAddr)` plus `Global` — so the degraded no-`ConnectInfo` path has a representable key rather than an error.

2. `gcra` 0.6.0's `RateLimiter<T>`, supplying both this member and the algorithm member. Take it if the owner prefers an imported implementation to an owned one and accepts a zero-dependent, single-author crate.

The matrix is `axum` 0.8.9 (`rust-version` 1.80) + `tokio` 1.53.1 (R69's accepted pair) + `tower` 0.5.3 (in the non-dev tree through axum; a dev-dependency for the `oneshot` test idiom) + the standard library — all within the 1.96 floor, all `MIT`/`MIT OR Apache-2.0`, no shared transitive dependency to reconcile because the new code's tree is empty. Cross-member seams were checked where they could fail: the algorithm member returns `Result<(), Instant>` and the store member is the only thing constructing those instants, so a tolerance change cannot desynchronise them; the layer member's `retry_after_seconds` is the only reader of that instant; `RateLimitKey::Global` exists precisely so the layer's degraded path has a key the store accepts. No shared adopter or shared example repository exists for this exact composition (gap G1) — this is the honest consequence of the gates excluding the crates that would be it — and no example was built by this engine (G2). The composition that is additionally **not** proven is rendering the 429 body through R70's envelope, because R70 has not published; the design renders it by construction (`IntoResponse`), which is an argument, not a test.
