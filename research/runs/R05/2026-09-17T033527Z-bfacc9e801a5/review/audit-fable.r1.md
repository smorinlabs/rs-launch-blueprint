## Findings

**JF-1 — blocking. The archive-extraction rerun's reported counts cannot be produced by the committed script, and no log of that run is committed.** `## Empirical check` states that the script was run once from a `git archive HEAD | tar -x` extraction, that "It exited `0` with `passed=19 failed=0 skipped=1` — C00 reporting `SKIP C00 — no .git entry (git archive extraction)` by name, exactly as designed — and every other check produced output identical to the committed log apart from the two path header lines and the summary counts." The committed script has exactly 21 check sites, `pass C00` through `pass C20`, with a matching `fail C##` for each and `skip C00` as the only skip site; the committed log has 21 `PASS` lines. A run of that script in which C00 skips and nothing fails reports `passed=20 failed=0 skipped=1`. It cannot report 19. So one of two things is true and the decision does not let a reader tell which: either the archive run executed a script with one fewer check than the one committed, in which case "every other check produced output identical to the committed log" is false because one check has no counterpart at all; or the figure is mistranscribed, in which case a provenance claim is being carried on a number nobody can reconcile. This is the defect class the synthesizer contract names twice — "an auditor reruns the script and counts", and "never describe a log as the complete reproduced output of a command you have not just re-run against it" — and it lands on the one paragraph whose whole purpose is to establish that the evidence is reproducible from a clean tree. *Resolution:* rerun the extraction against the committed 21-check script, report the counts it actually produces, and commit that run's log beside `r05-check.log` so the claim is readable rather than asserted; or, if the numbers are to stand, state precisely which check was absent and why. *Recommendation impact:* none. The claim concerns the portability of the evidence script, not any result it produced; the committed log's `21/0/0` is independently intact.

**JF-2 — non-blocking. Alternative B is twice said to require changing two owner-accepted values, where R01's registered clause fires as written and only R69's needs a `CONFLICT:`.** The alternatives table says of B that "both require changing an owner-accepted value", and the engine-disagreement section repeats it: "Neither makes async impossible — the honest route would be a `CONFLICT:` line against R69 — but both require the owner to change an accepted value." R01's registered value already contains the async branch — "under an async R05 the trait keeps dyn compatibility with async-trait 0.1.92" — so under alternative B that clause *fires* and the port picks up a dependency; the registered value itself does not change. The decision knows this and says so in two other places: line 22 describes the clause as conditional and untriggered, and `## Parameters` correctly names R69 alone as the value that would have forced a `CONFLICT:` line. The two sentences above are therefore stated more absolutely than the decision's own evidence, and they inflate the mechanical ground by half. *Resolution:* qualify both sentences to say that R69's value would have to change while R01's conditional clause would fire at the cost of `async-trait 0.1.92`, and enumerate by search rather than by re-reading, since the claim's subject appears in at least four places. *Recommendation impact:* none. The `async-trait` cost (C09) and the R69 parse error (C07) are both real, and the evidential ground — 93 default dependencies against 38, conceded in direction by two of the three providers — stands on its own.

**JF-3 — non-blocking. Four star counts are attributed to an endpoint that does not serve them.** The practice-usage paragraph introduces its figures as "Opus's survey, read at each project's default branch through the GitHub contents API on 2026-09-17", and then states `rust-lang/cargo` (15,484 stars), `rust-lang/rustup` (7,044), `ducaale/xh` (8,080) and `astral-sh/uv` (89,891 stars). The contents API returns file contents, not `stargazers_count`. Opus's raw states the correct provenance — manifests through `GET https://api.github.com/repos/<o>/<r>/contents/Cargo.toml` and "stars, `archived` and `pushed_at` come from `GET https://api.github.com/repos/<o>/<r>` on the same date" — so the retrieval date is right and only the endpoint attribution is lost in the condensation. The prompt requires every number to carry its endpoint. *Resolution:* name the repos endpoint for the star figures alongside the contents endpoint for the manifests. *Recommendation impact:* none; the stars are context for "well regarded", and the decision's actual reading — that the Rust CLI camp splits by workload, evidenced by the manifests rather than by the counts — does not rest on them.

**JF-4 — non-blocking. The single "throughout" hit is placed in a section that begins after it.** The naming correction says "the single hit is in the Caveats section and is about rustls". The hit is at line 407 of the owner reference, under the heading `## Recent-Bugs-vs-Plan Register (next 6 months)` at line 401; the document's `## Caveats` heading is at line 430, twenty-three lines later. C06's log output quotes the hit line and never claims a section, so the section label is added in the decision beyond what the check shows. Everything else in the correction is exact and I reproduced it: `tokio throughout`=0, `throughout`=1, and the hit is the rustls mitigation sentence. *Resolution:* name the Recent-Bugs-vs-Plan Register, or drop the section label and keep the line reference the log supplies. *Recommendation impact:* none.
