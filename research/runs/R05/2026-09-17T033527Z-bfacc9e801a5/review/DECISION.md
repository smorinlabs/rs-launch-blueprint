## Decision

**Adopt a synchronous, blocking execution model for the library crate and the CLI binary, and confine async to R69's optional `web` feature.** The driven-I/O port and every function that reaches it are ordinary `fn` that block the calling thread; the CLI entry point is `fn main() -> ExitCode` with no executor anywhere in the default dependency tree; when — and only when — the `web` feature is on, axum's `async fn` handlers reach the same synchronous port through `tokio::task::spawn_blocking`.

This is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). It records what this research found and what it recommends; P03 builds the template and its CI proves the recommendation. A decision that does not survive implementation is revised against this recorded research, not researched again from scratch. What P03 must validate is listed under `## Engines`.

### Principles and implementation

**Shared requirement, its source and agreement level.** Every inbound front end — the CLI, and the optional web service — reaches one use-case layer, which reaches the outside world through the driven-I/O port R01 defines; the template must build and test on `ubuntu-latest` and `macos-latest` at an MSRV floor of stable minus two minor versions. The execution model is the *mechanism* by which that requirement is met, not the requirement itself. Source: `docs/port/COMMONALITY.md` rows F016 and F022 (check C01). **Agreement level: mechanism — Rust decides alone.** The two source repositories do not agree and neither answer is portable. py is sync end-to-end because CPython's blocking `requests` is its ecosystem default, and its web tier bridges into FastAPI's async handling through a threadpool; the prompt's `## Context` records the evidence at the py pin (`src/py_launch_blueprint/core/adapters/py_api.py:38`, `import requests`; `src/py_launch_blueprint/web/routers/projects.py:25`, "Handlers are sync (``def``) because ``ProjectsService`` uses ``requests``; FastAPI runs them in its threadpool"). ts is async end-to-end because JavaScript has no blocking I/O to choose (`src/router.ts:182`, `export async function runCli`; `src/lib/api.ts:108`, `async function request`), and the prompt records that `TS_PORT_DECISIONS.md` has no entry choosing async — "there was no sync option to reject". What transfers is py's *shape*, a synchronous core with a bridged async web tier, which is a real architectural pattern; ts's *absence* of a choice is not evidence for one. Both pins are quoted from the prompt's `## Context` and from the Opus raw's reading of them; this synthesis did not re-open either source repository, and says so rather than implying a fresh read.

**What must agree, and what may vary.** Must agree across py, ts and rs: that one use-case layer serves both front ends, and that the web tier is a thin adapter over it. May vary: whether the functions in that layer block.

**Why the selected design preserves each principle.** *One use-case layer serving both front ends* is preserved because the port's signature does not change between front ends: the CLI calls it directly and the handler calls the identical method inside `spawn_blocking`, which check C14 exercised end-to-end with byte-identical results on both paths. *A thin web adapter* is preserved because the adapter adds exactly one wrapper per handler — `spawn_blocking` is tokio's own documented mechanism for calling blocking code from an async context, not a workaround invented here. *The optional web surface* (F017 `ADOPT`, and R69's owned `web-extra-surface`) is preserved in the only way Cargo permits: R69's value declares `web = ["dep:axum", "dep:tokio"]`, and a `dep:` clause is legal only against an optional dependency (C07/C08), so the feature can only stay additive while the always-present code needs no runtime. *The MSRV and two-OS constraints* are met: every probe manifest declared `rust-version = "1.96"` and `edition = "2024"`, and the probes built and ran on macOS 26.4 `arm64` under rustc 1.98.0.

**The engine disagreement, and the grounds that settle it.** It is a clean 1-against-3 on the central question, so it is set out in full rather than summarised.

1. **Sync core (Opus) against async end-to-end (all three Doxa providers).** Settled for the synchronous core, on two grounds of different kinds.

   *The mechanical ground.* Check C18 counts, with `/usr/bin/grep -c` over each of the three normalized provider bodies, zero occurrences of `dep:tokio`, zero of `R69` and zero of `async-trait` — in all three. So none of them priced the Cargo constraint or the macro, and none of them saw R69 at all. That is not a failure on their part: the prompt's `## Couplings` declares no consumed parameter, tells the reader to "treat R01's direction as open", and never mentions R69, which was published after this run's inputs were prepared. The nearest any provider comes is OpenAI, which keeps R01 open and hands the question back to it — "R01 remains responsible for whether the async port is a generic bound, object-safe boxed future, native async trait, or direct injection", and it lists "R01 chooses a seam form that exposes an unforeseen async object-safety constraint" among its own risks. It identified the constraint's existence and left it unpriced. The published R01 value resolves it in the other direction (no `async fn` on the port, `async-trait` conditional on this item), and checks C03 and C09 show what an async core would therefore cost. An async core makes `tokio` non-optional, which turns R69's registered `web = ["dep:axum", "dep:tokio"]` into a manifest parse error (C02 plus C07), and it puts `async fn` on a port that R01 registers as having none, which costs `async-trait` because a native `async fn` breaks dyn compatibility (C03, C09). Neither makes async impossible, and only one of them asks the owner for anything: **R69's registered value would have to change**, for which a `CONFLICT:` line is the honest route, whereas **R01's registered value stays as written** — its clause "under an async R05 the trait keeps dyn compatibility with async-trait 0.1.92" fires rather than breaks, so the cost there is the added macro dependency, not a renegotiated parameter.

   *The evidential ground.* Every check in all three Doxa reports is labelled planned; none was executed. OpenAI's report additionally marks twelve of its own figure fields `NOT CAPTURED` because its crates.io and GitHub snapshots did not render. Against that, the cost claim was measured here: 93 dependencies against 38 in the default build, and a release build that took more than twice as long on this host (C11, C13; the timing is informational and only the ordering is asserted). **Two of the three providers concede the direction of that cost in their own words** — OpenAI: "Sync ureq alternative: likely smaller and faster to compile; this is the strongest argument for sync"; Gemini: "Adopting `reqwest` introduces a massive dependency tree … heavily increases initial compilation times". Perplexity asserts the cost is "acceptable" without measuring it. A measured figure outranks an asserted one.

2. **"Bridging is not a first-class pattern" (Perplexity, Gemini) against "the bridge is one documented wrapper" (Opus).** Perplexity's objection is specific: sync-first "often requires explicit use of `tokio::task::spawn_blocking` … which comes with additional complexity and potential performance pitfalls if overused". The complexity half is answered by execution: check C14 runs the whole bridge — `rt.block_on(async { spawn_blocking(fetch).await })` — and gets a result byte-identical to the direct blocking call, with one wrapper per handler and no second public surface. The performance half is **conceded as unmeasured**: no latency, throughput or blocking-pool-saturation figure was produced by any engine or by this synthesis, and "if overused" is a real hazard for a web surface under concurrency. Opus cites tokio's `max_blocking_threads` default of 512 from `docs.rs/tokio/1.53.1/tokio/runtime/struct.Builder.html`; that figure was **not re-verified here** and is carried as Opus's. This is listed below as something P03 must measure.

3. **OpenAI's ranked runner-up contradicts its own policy line.** OpenAI names `ureq` 3.4.2 "the strongest blocking alternative" and offers it as the runner-up "but only if the owner changes the complete architecture to synchronous CLI, core, and web execution … It is not recommended behind Axum's handlers", and it writes an acceptance criterion that "the primary HTTP path contains no `reqwest::blocking`, `ureq`, `spawn_blocking`, or `block_in_place`". The premise is that a blocking client behind axum needs a sync-first *server* too. Check C14 falsifies that premise directly: `ureq` 3.4.2 ran inside a tokio multi-thread runtime through `spawn_blocking` and returned the same 559 bytes as the direct call. OpenAI's criterion is a policy assertion, not a finding, and it is not adopted.

4. **What the three Doxa providers reject under the name "mixed" is alternative C, not alternative A.** Perplexity's "mixed design" is explicitly "a sync CLI while using an async web service … the CLI can call into async library functions by blocking on a runtime using `tokio::runtime::Runtime::block_on`", and it rejects it because "the core library may need to offer both sync and async variants of its I/O functions". That is Opus's alternative C and Opus rejects it on the same ground. **The two engines agree on C and disagree only on A against B**, which narrows the disagreement considerably and is the reason this decision states A and B as the only live pair.

5. **Intra-Doxa disagreement on the CLI runtime flavour** (recorded because it shows the async branch is not itself settled): OpenAI specifies `#[tokio::main(flavor = "current_thread")] async fn main`; Gemini specifies the current-thread scheduler for the CLI and the multi-threaded one for the web layer; Perplexity specifies `#[tokio::main]` with "the multi-threaded executor (or current-thread variant if desired)".
