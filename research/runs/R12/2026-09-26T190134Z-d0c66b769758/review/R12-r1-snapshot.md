## Decision

**Status.** This decision is a **proposal validated in the implementation phase** (owner ruling, 2026-09-10). `rs-launch-blueprint` has no `.github/` tree today. P02 is research; P03 builds the template and its CI proves or disproves what is recorded here. Nothing below has run on a GitHub-hosted runner: no workflow was dispatched, no queue entry was enqueued, no check was required. A recommendation that does not survive implementation is **revised against this recorded research**, not researched again from scratch.

**Recommendation — the named pattern `always-on aggregate required check`.** `.github/workflows/ci.yml` gains one job, `ci-ok`, and branch protection (or its ruleset successor) requires exactly `ci-ok` — and nothing else — for that file:

1. **`ci-ok` folds in every other job in the file.** `needs:` lists exactly R11's six job ids — `plan`, `hygiene`, `workflow-lint`, `check`, `msrv-floor`, `install-smoke` — including `plan`, which is how R11's handover is met: a failed detector fails `ci-ok` rather than skipping every gate green. `if: ${{ always() }}`, `timeout-minutes: 5`, `permissions: {}`, `runs-on: ubuntu-latest`, no checkout. One step prints each needed result, then fails unless `needs` is non-empty and every result is `success` or `skipped` — the positive allow-list `length > 0 and all(.[]; .result == "success" or .result == "skipped")` over `toJSON(needs)` passed through `env:`, never interpolated into shell. `!cancelled()` is an accepted equivalent for the `if:` line (Disagreement 3); the deny-list spelling is not (Disagreement 1).
2. **A completeness guard travels with it, as a step of R11's `workflow-lint` job.** It fails CI when the job set of `ci.yml` minus `ci-ok` differs from `ci-ok`'s `needs:` in either direction, naming the jobs. Its whole input is `ci.yml`, which the `workflows` key's pattern contains by R11's construction, so the step belongs in `workflow-lint` under R11's own slot rule — and it runs on every pull request that touches the workflow file, every push to `main`, and every `merge_group` entry.
3. **The required check is source-pinned.** The settings surface — a repository ruleset preferred, classic branch protection accepted — requires context `ci-ok` with the GitHub Actions app (`integration_id` 15368) as the expected source. The template cannot set this; it ships as documentation P03 applies.
4. **`ci-ok` is unique across all workflow files, and each gating workflow gets its own aggregate.** `needs:` cannot cross files, so any other workflow whose checks must block merging declares its own single required context, or its own `<name>-ok` aggregate if it has several jobs. This is clippy's four-`conclusion_*` pattern and clap's `CI`-plus-others pattern, not an invention.
5. **Every future required job joins `needs:` when it lands.** R04's semver job is first in line; the guard, not review discipline alone, enforces it.

**File-level changes in the template.** `.github/workflows/ci.yml` gains the `ci-ok` job (~20 lines) and the guard step in `workflow-lint` (~8 lines); no other job is modified. The repository setup documentation gains a "Required checks" section naming `ci-ok` as the only required context for `ci.yml`, source GitHub Actions, with the ruleset cutover P03 applies. The contributor doc gains one sentence: a new `ci.yml` job must join `ci-ok`'s `needs:`, and CI enforces this. Files *not* added: no third-party action, no `allowed-skips` list, no per-job settings documentation, no extra toolchain.

**Ledger row this decision settles: F041** (`docs/port/COMMONALITY.md:47`, `Single aggregate required-status-check job folding in all other job results`, `ci-workflows`, `py-only`, `DIVERGENT`, `Item: R12`; check `I-f041`). The answer is `yes, one aggregate job` for rs, with the hardened form and the guard above.

### Landscape, and the alternatives compared before any tool

**The category.** This is not a crate decision. It is a *merge-gate topology* decision: which check name(s) branch protection requires before a pull request may merge — one aggregate job that folds every other job's result into a single verdict, or each job listed individually — plus what computes the verdict. Every candidate is a GitHub-platform mechanism or a GitHub Action; none enters `Cargo.toml`. The Rust-specific content is the job graph R11 produces and the practice of Rust projects.

**Bin 1 — built-in or first-party.** `jobs.<job_id>.needs` with the `needs` context (`success` | `failure` | `cancelled` | `skipped` per job); job-level `if: ${{ always() }}` to opt out of skip propagation; `toJSON(needs)` plus a `jq` verdict as the verdict device; branch protection's required-status-check list and its successor rulesets with an expected-source app restriction; the `merge_group` trigger for merge-queue entries. Every primitive the recommendation uses is in this bin.

**Bin 2 — established industry standard.** (a) The hardened hand-rolled aggregate: `needs:` over every required job including the detector, `always()` (or `!cancelled()`), explicit per-result inspection, `skipped` as pass — py's `ci-ok`, cargo's / rust-analyzer's `conclusion`, uv's and ruff's `required-checks-passed`, clap's `CI`. (b) The naive aggregate: `needs:` only, unconditional succeeding step — hyper's `ci-pass` shape, excluded at Disagreement 5. (c) Per-job required checks with no aggregate — tokio's 46 contexts, bevy's 24. (d) The maintained third-party aggregator `re-actors/alls-green`: composite action taking `toJSON(needs)` with `allowed-failures` / `allowed-skips`.

**Bin 3 — up-and-comers.** (a) Check-run pollers across workflow files (`poseidon/wait-for-status-checks`, `upsidr/merge-gatekeeper`) — the only in-repository cross-workflow answer, rejected on design. (b) The organization-ruleset rule "Require workflows to pass before merging" — platform-native cross-workflow gating, but configured in organization settings, which a template cannot assume. (c) A static completeness guard asserting the aggregate's `needs:` covers its file — no published tool; the guard above fills the gap until `actionlint` or zizmor ships the rule.

**Authorities, and why each counts.** GitHub's own documentation at pinned commit `18945a31` (2026-09-25), read from `github/docs` and snapshotted (`S-docs-*`): the required-status troubleshooting page decides most of this item. The runner vendor's own image inventory for `jq`/`yq` availability (`S-runner-*`). Live repository rulesets and branch protection of Rust-project-team and Astral repositories — primary evidence of what is actually *required*, not only what workflow files contain (`S-cargo-ruleset`, `S-ra-ruleset`, `S-uv-ruleset`, `S-clippy-multi`, `S-tokio-long`, `S-clap-perwf`, `S-py-live*`). Actions run records for cancelled-run behavior (`S-cancelled-*`). The aggregator's own README, `action.yml` and verdict source (`S-ag-*`). py and ts at their task-pinned commits plus their live settings (`S-py-*`, `S-ts-*`; py is additionally audited across its whole `ci-ok` history, `S-py-history`). `actionlint` 1.7.12, `shellcheck` 0.11.0, `jq` 1.8.2 and PyYAML 6.0.3, used as **instruments**. No single blog post is used as an authority anywhere.

The reading: **every Rust-project-team repository surveyed and both Astral repositories require exactly one aggregate context per gating workflow, app-pinned where the surface exposes it.** Individual listing (tokio) is a real, workable second practice for a single repository with an attentive admin — its 46-entry list was in sync on the sampled PR — not a fringe one. Popularity does not separate the camps. What separates them for *this* consumer is that branch protection is repository state no template ships: py's PROBLEM-15 documents the individual-list failure in a generated repository, and rust-analyzer documents the aggregate's own drift mode, an omitted detector — which is why the guard is part of the pattern rather than advice.

### Principles and implementation

**The shared requirement, its source, and the level at which agreement is required.** No change merges unless every quality gate that applied to it passed; a gate that legitimately did not apply must not block it; a gate that failed, was cancelled, or never produced a verdict must block it; and only the CI app's verdict counts. Source: py's header comment ("`ci-ok` is the single required status for branch protection (skipped jobs count as ok)", `S-py-header`), the vendor's required-checks pages (`S-docs-*`), and R11's handover ("a failed `plan` must itself fail a required check", R11 `DECISION.md:180`).

| ID | Principle | Agreement level across py / ts / rs |
|---|---|---|
| P1 | **Gate completeness.** Every blocking check blocks the merge when it fails, is cancelled, or never ran for an unexplained reason | **policy** — must agree in all three |
| P2 | **The blocking set lives in version control.** The out-of-band settings reduce to a minimal, stable set of names defined by a reviewed file | **policy** — must agree; the file format may vary |
| P3 | **A skip passes only when a trusted decision caused it.** `skipped` is a pass only because R11's detector fails closed *and* the detector's own failure is folded into the verdict | **policy** — must agree wherever skip-gating exists |
| P4 | **Source authenticity.** Only the CI app can satisfy the required context | **policy** — must agree |
| P5 | **Merge-queue parity.** The same context reports on the queue's speculative merge | **capability** — must agree where a queue is used (F025) |

**What must agree and what may vary.** P1–P5 must agree across the three repositories: the threat and the platform are identical, and nothing about Python, TypeScript or Rust changes how GitHub evaluates a required check. The mechanism may vary — a `jq` line, a shell loop, or an action — and the context name *should* agree (`ci-ok`) for a concrete reason: one shared name lets one organization ruleset gate every blueprint repository. That last point is a convenience proposal, not a correctness requirement.

**Essential behaviors, with observable acceptance criteria.**

**Why the allow-list, not py's deny-list (Disagreement 1, adjudicated).** Four decision rules were executed against nine needs-vectors (`r12-verdict.sh`; the recommended rule and py's loop were both extracted from their files, not retyped):

| Case | Recommended allow-list | py deny-list (real bytes) | cargo all-`success` | naive `!contains(failure)` |
|---|---|---|---|---|
| T1 all success | PASS | PASS | PASS | PASS |
| T2 docs-only, gated jobs skipped | PASS | PASS | **FAIL** | PASS |
| T3 `plan` failed, gated skipped | FAIL | FAIL | FAIL | FAIL |
| T4 `plan` cancelled, gated skipped | FAIL | FAIL | FAIL | **PASS** |
| T5 one `check` leg failed | FAIL | FAIL | FAIL | FAIL |
| T6 `check` cancelled | FAIL | FAIL | FAIL | **PASS** |
| T7 `hygiene` failed | FAIL | FAIL | FAIL | FAIL |
| T8 unrecognized result value | FAIL | **PASS** | FAIL | **PASS** |
| T9 empty `needs` | FAIL | **PASS** | **PASS** | **PASS** |

The deny-list passes anything it does not name (T8) and passes vacuously when there is nothing to inspect (T9; `all()` over `{}` is `true`, `V0-empty`). R11's fail-closed policy — every required gate, compiling or not — requires the allow-list spelling plus the `length > 0` guard. The cost is one `jq` line instead of a shell loop; `jq` 1.7 ships on the runner (`S-runner-jq`), and the `jq`-over-`toJSON(needs)` form is what the rust-lang and Astral aggregates use. The py follow-on proposes the same spelling there.

**Why `always()`, and why `!cancelled()` is accepted (Disagreement 3, adjudicated).** Without either, a failed dependency skips the aggregate (`S-docs-skipprop`), and a skipped job reports Success (`S-docs-skipped-success`) — a false green; `actionlint` accepts that broken shape (`L2`), so the `if:` line travels in prose and review. Between the two forms: the vendor's required-check page prescribes `always()` (`S-docs-always`), R11's slot row prescribes it, and py uses it. The feared hazard of `!cancelled()` — a cancelled run leaving the aggregate `skipped`-green — did not materialize in 9 of 9 sampled cancelled runs: 6 of 6 `!cancelled()` aggregates (cargo, rust-analyzer) concluded `cancelled`, and 3 of 3 `always()` aggregates (uv) ran to `success`/`failure` (`S-cancelled-*`). The docs' hang warning against `always()` does not apply: `ci-ok` has no checkout, no network, and a 5-minute cap. `!cancelled()` remains an accepted equivalent; the sample is small and contains no hand-cancelled head run of an open pull request (P03 checks it).

**Why the guard is part of the pattern, not advice (Disagreement 2, adjudicated).** A job left out of `needs:` is invisible to *every* verdict rule, and lint does not catch it either (`L3`). That is not hypothetical: rust-analyzer's `conclusion` omits its `changes` detector while `typescript` is gated on that detector's outputs (`S-ra-drift`) — so a failed detector skips `typescript` and the aggregate counts the skip as a pass, exactly the hazard R11 hands over. py kept its in-repo list in sync across 21 revisions by review alone (`S-py-history`), which proves review *can* work, not that it always does. The guard closes the mode mechanically: it exits 0 on the fixture and exits 1 naming the jobs when one is added (`G2`), when `plan` is dropped (`G3`), and when one is renamed (`G4`). It costs one `yq | jq` step in a job that already checks out the tree (`yq` 4.53.6 on the runner, `S-runner-yq`).

**Why no `merge_group` logic (the LOW question).** Nothing extra is needed in the aggregate. R11 already puts `merge_group` in `ci.yml`'s triggers and publishes `true` on every detector output for non-`pull_request` events, so nothing is skip-gated in the queue; `ci-ok` runs there like any job (P03 verifies live queue reporting under criterion 8). Two conditions must hold: the queue's required check is the same `ci-ok` context, and the name is unique across workflow files (`S-docs-unique`) — clippy's per-workflow aggregates show the shape. Without the trigger, the required check never reports and every queue entry deadlocks at "Expected" — py documents that failure mode in its own file header.

**Matrix legs need no special handling.** The platform folds `check`'s per-OS legs into one per-job result, so one `needs:` entry covers both runners. The same matrix is part of why the aggregate pays: without it, `check (ubuntu-latest)` and `check (macos-latest)` are two settings entries that change whenever the owner-fixed matrix changes — ts shows the single-job version of that cost with its two `continuous-integration` contexts.

**Does the value depend on R11 (the first HIGH question)? It depends on multi-context CI, not specifically on skip-gating — and R11 settled multi-context CI.** Without any skip-gating the aggregate still pays: the matrix contexts above, plus the template argument (settings do not copy into generated repositories; PROBLEM-15). With R11's skip-gating the aggregate is load-bearing rather than merely convenient: a failed `plan` skips every gated job, and a skipped job reports success. Under a single-job, non-matrix shape the aggregate would be pure overhead and E would win — that branch is decided fact in the other direction since R11 revision 7.

**Fitness gates, answered before popularity is weighed.** (1) License: `inapplicable` per the owner ruling above; `alls-green`'s `BSD-3-Clause` is a figure, not a gate result. (2) MSRV: `inapplicable` — a workflow file, a `jq` line and a composite Python action have no `rust-version`. (3) RustSec / `unsafe`: `inapplicable` — no crate enters any dependency tree; RustSec does not cover GitHub Actions. (4) OS matrix: passes in adapted form — the aggregate needs only a hosted runner with `bash` and `jq`, true of both matrix entries; it is pinned to `ubuntu-latest` (cheapest, no toolchain, no cache, matching `plan`). (5) Default features / async-runtime coupling: `inapplicable` — nothing is linked into the template. (6) Binary size / compile time: `inapplicable` to the artifact; CI cost is one ~10-second job per run plus one `yq | jq` step in `workflow-lint`. No candidate is excluded by a fitness gate; B is excluded by this item's own fail-closed requirement (Disagreement 5).

**Cross-ecosystem realization (the third HIGH question).** P1–P5 hold in all three repositories; only the mechanism varies where structure forces it. rs realizes them with the aggregate above over R11's six job ids — same platform, same skip-gating design as py, same hardened form, same `ci-ok` name (a shared low-level value justified by identical tradeoffs: same vendor, same verdict semantics, one organization ruleset able to gate every blueprint). py already realizes them with `ci-ok`; its two weaknesses are the deny-list spelling (T8/T9) and the unguarded `needs:` — both fixed by the follow-on below, for which this answer supplies the rationale. ts realizes none of P1–P5 today: no required check, no aggregate, no `merge_group` — missing capability per the BASELINE-REVIEW finding, not drift and not a justified difference. If ts ever promotes a second job to required, P1 requires the aggregate in form A, not B.

### Consumers of this decision, and the rule each inherits

**The rule is one sentence: a new `ci.yml` job joins `ci-ok`'s `needs:` in the same pull request, and the guard fails the run until it does.** R04's semver job is the first consumer: R11 places it as its own job with `needs: plan` gated on `code`, and R12's row there names this item as deciding its aggregate membership — it joins `needs:` when it lands. A possible R35 coverage job and every further R11 slot inherit the same sentence. A *non-voting* job (allowed to fail, e.g. a nightly leg) does not join the allow-list as-is; it reopens the runner-up (alls-green's `allowed-failures`), because the `jq` rule would need editing per job.

Other workflow files are each their own item's: R17's scanner, R38's commit-message lint, and any further gating workflow each declare one required context, or their own `<name>-ok` aggregate if they hold several jobs — `needs:` cannot cross files, and this decision's guard covers `ci.yml` only. R20 governs the SHA-pin form of the `actions/checkout` step the guard needs in `workflow-lint` (the fixture's `@v4` is a placeholder); the guard and the aggregate add no third-party action of their own. `ci-ok` carries `permissions: {}`, so it needs no R08 re-grant — it makes no API calls.
