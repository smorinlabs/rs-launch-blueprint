### Principles and implementation

The shared requirement is a single contributor-recognition implementation with a durable, reviewable state file and a generated Markdown projection. The agreement level is an architectural pattern, not a language-specific library choice. Across py-launch-blueprint, ts-launch-blueprint, and rs-launch-blueprint, the essential behaviors are:

1. `.contributors.yml` remains the project configuration and `.contributors.jsonl` remains the durable contributor ledger.
2. The local recipe and the CI action use the same `contributors-please` engine and the same rendering rules.
3. CI updates the ledger and Markdown in a bot pull request rather than writing directly to `main`.
4. A fresh template has an explicit bootstrap path; a repeat render does not need GitHub discovery or credentials.
5. Generated output is reproducible from the committed ledger and configuration.

The first three behaviors are language-neutral and should agree. The package runner, the Justfile syntax, and any Rust-specific provisioning are ecosystem mechanisms that may vary. The fixed Rust edition, MSRV policy, license, and target OS matrix are not owned by R47 and remain unchanged. (Sources: https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/README.md, https://github.com/smorinlabs/rs-launch-blueprint/blob/main/docs/port/PARAMETERS.md, https://raw.githubusercontent.com/smorinlabs/contributors-please-action/main/README.md; retrieved 2026-09-05.)

The current package exposes three operational subcommands plus version output. `validate` reads and validates the YAML configuration; `render` reads an existing state file, applies filtering/sorting and template configuration, and writes the Markdown output; `init` performs GitHub and Git-history discovery, merges the discovered records with existing state, and writes both the state file and Markdown output. The published package is `contributors-please@1.4.3`, released according to the npm registry metadata on 2026-06-17, and declares Node `>=24`. The bundled CLI's fallback usage string omits `init`, but the README, source, and tests document and exercise it; that omission is a CLI help defect, not evidence that `init` was removed. (Sources: https://registry.npmjs.org/contributors-please, https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/test/cli.test.ts, https://github.com/smorinlabs/contributors-please/blob/main/README.md; retrieved 2026-09-05.)

`render` still implements the same final ledger-to-Markdown operation that the action performs. The equivalence is narrower than the TypeScript decision text implies: action `pull-request` mode first calls the engine's `run()` operation, which reads GitHub contributors and Git history, joins identities, classifies records, merges them into the ledger, and renders output; it then commits, pushes, labels, and opens or updates a pull request. The standalone `render` subcommand starts after discovery and merge, reading only the committed ledger and configuration. Therefore, `render` is the correct single implementation for the projection stage, but it is not an exact lifecycle equivalent to the whole CI `pull-request` mode. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://raw.githubusercontent.com/smorinlabs/contributors-please-action/main/src/index.ts, https://raw.githubusercontent.com/smorinlabs/contributors-please-action/main/README.md; retrieved 2026-09-05.)

The fresh-template case changes the recipe shape. Current `render` requires `.contributors.jsonl`; it does not create an absent state file. I executed `npx --yes contributors-please@1.4.3 render --config-file .contributors.yml` in a fresh checkout of ts-launch-blueprint with no ledger. It exited 1 with `ENOENT` for `.contributors.jsonl`. Current `init --non-interactive` is the documented bootstrap command and supplies owner/repository information so the engine can discover and write the initial ledger. The current TypeScript CI workflow handles this by passing `bootstrap: 'true'` to the action, but its local render recipe does not itself handle a missing ledger. (Sources: https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/.github/workflows/update-contributors.yml#L74-L86, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts; executed command and result retrieved 2026-09-05.)

The resulting reference pattern is guarded bootstrap plus steady-state render:

```just
contributors_runner := "pnpm dlx contributors-please@1"

@contributors-update:
    #!/usr/bin/env sh
    set -eu
    if test -f .contributors.jsonl; then
        {{contributors_runner}} render --config-file .contributors.yml
    else
        {{contributors_runner}} init --non-interactive \
            --owner {{contributors_owner}} \
            --repo {{repo_name}} \
            --config-file .contributors.yml
    fi
```

The conditional is the proposed acceptance implementation, not code executed in this run. It keeps the dominant subcommand `render` for normal local updates while making the first invocation explicit and usable. A repository that commits an intentionally empty `.contributors.jsonl` may use render from the first invocation, but that would produce an empty projection and would not discover the initial contributors; it is not an equivalent bootstrap. The runner spelling and version pin belong to R42, so the snippet uses a provisional runner variable and must not be read as deciding that separate parameter. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/Justfile#L237-L244, https://github.com/smorinlabs/rs-launch-blueprint/blob/main/research/topics/42-dev-toolchain-provisioning/prompts/dev-toolchain-provisioning.prompt.md; retrieved 2026-09-05.)

Observable acceptance criteria are:

- With a committed valid ledger and configuration, the local recipe invokes `render`, exits zero, and writes the same Markdown bytes as the package renderer for that ledger/configuration.
- With no ledger in a fresh repository, the recipe invokes `init --non-interactive` with explicit owner and repository inputs, writes `.contributors.jsonl` and the configured output, and exits nonzero with a clear credential or API error rather than silently producing an empty list.
- With a changed ledger, the next render changes only the generated projection according to the configuration; it does not call GitHub or mutate the ledger.
- CI continues to use the already-settled action `mode: pull-request`, with full checkout and the existing state/output paths; R47 changes only the local recipe content.

### Fit for this template

**CLI.** The recipe is a developer-facing command, so a short external command with a deterministic steady-state path is preferable to embedding GitHub and rendering logic in the Rust application. `render` reads the committed state and config, has no GitHub credential requirement, and has work proportional to the number of ledger records and template output. `init` is appropriate only when discovery is required; its latency and resource cost are dominated by GitHub API calls and Git-history traversal, and its output depends on remote state. The package source establishes these operations; no benchmark was run, so these are code-path-based qualitative conclusions, not absolute performance claims. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts; retrieved 2026-09-05.)

**Library.** The Rust library should not depend on the contributor updater at runtime. The contributor recipe is repository furniture, while the application library's public API should remain usable without Node, npm credentials, or GitHub access. A Rust-native implementation could be a separate development tool if later justified, but adding contributor discovery to the product library would increase compile-time, binary, credential, and API-surface cost without serving the library's runtime contract. This boundary is a design recommendation derived from the template shape and the external package's CLI/library split. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/README.md, https://doc.rust-lang.org/cargo/reference/manifest.html; retrieved 2026-09-05.)

**Web service.** The web service has no reason to perform contributor discovery on request. The local `render` path is offline and bounded by the committed ledger; `init` requires remote GitHub access and should remain an explicit maintenance operation in a developer or CI context. Keeping the service out of this flow avoids turning contributor metadata into request-time availability or credential coupling. This is an architectural fit judgment, not an observed runtime benchmark. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://raw.githubusercontent.com/smorinlabs/contributors-please-action/main/README.md; retrieved 2026-09-05.)

### Recommendation

Adopt a `contributors-update` recipe whose steady-state subcommand is `contributors-please render`, with an explicit file-existence guard that runs `contributors-please init --non-interactive --owner ... --repo ...` when `.contributors.jsonl` is missing. Keep `.contributors.yml`, `.contributors.jsonl`, and the generated Markdown paths aligned with the CI action. Leave `npx` versus `pnpm dlx`, exact version pinning, and Node provisioning to R42. This recommendation preserves the shared engine and generated-output contract, avoids unnecessary network/API work on repeat local runs, and remains usable from an empty-history template. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://raw.githubusercontent.com/smorinlabs/contributors-please-action/main/action.yml, https://github.com/smorinlabs/ts-launch-blueprint/blob/cb1cbcb2e88b898e8c081b0abbfabc1630079c00/Justfile; retrieved 2026-09-05.)

### Ranked runner-up

The runner-up is unconditional `init --non-interactive`. It wins if the local recipe's primary purpose is always to discover current GitHub and Git-history contributors, if the repository deliberately wants every local run to refresh the ledger, or if the template guarantees credentials and network access for every invocation. It loses for ordinary repeat rendering because it performs remote discovery and state mutation where a committed-ledger projection is sufficient. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://github.com/smorinlabs/py-launch-blueprint/blob/b08bccfb55d05f15e46a83b52c5660b1881d19f5/Justfile#L457-L462; retrieved 2026-09-05.)

### Tradeoffs

Compared with unconditional `init`, the recommendation gives up automatic remote refresh on every local invocation. The accepted cost is that refresh becomes explicit: delete or update the ledger through the bootstrap branch, use the CI action, or run `init` directly. In return, normal rendering is offline, reproducible, and less dependent on credentials.

Compared with unconditional `render`, the recommendation gives up a one-line recipe and adds a first-run branch. The accepted cost is necessary because current `render` fails when the state file is absent; omitting the branch makes a fresh template unusable unless it ships a pre-seeded ledger or relies on a separate undocumented setup step. Compared with a new Rust-native tool, the recommendation retains a Node 24 dependency and the package-manager provisioning decision, but avoids implementing and maintaining a second contributor-recognition engine. These tradeoffs follow from the cited source behavior; no unlike benchmark was used to claim an absolute fastest option. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts, https://registry.npmjs.org/contributors-please; retrieved 2026-09-05.)

### Validation strategy

The following checks are proposed for the implementation; they were not run against an rs-launch-blueprint Rust template because no Rust code or final Justfile exists yet:

1. **Steady-state render.** In a temporary Git repository containing a valid `.contributors.yml` and a committed `.contributors.jsonl`, run the proposed recipe with network access disabled. Expect exit 0, no GitHub request, and `CONTRIBUTORS.md` equal to the output from `npx` or `pnpm dlx contributors-please render --config-file .contributors.yml`.
2. **Missing-ledger bootstrap.** In a fresh temporary Git repository containing `.contributors.yml` but no `.contributors.jsonl`, run the proposed recipe with a bounded test GitHub client or an authorized test repository. Expect the recipe to select `init`, create the ledger and output, and preserve the configured classification and markers. A missing credential or API response must produce a nonzero failure and no fabricated ledger.
3. **Inverse control.** Remove the owner/repository inputs or credentials from the missing-ledger case. Expect bootstrap to fail clearly. This proves the guard is not silently treating “no history” as “no contributors.”
4. **Projection determinism.** Run `render` twice from identical ledger/config/output inputs. Expect byte-identical Markdown and no ledger mutation.
5. **Action parity.** Run the action's existing `mode: pull-request` workflow in a test repository with `fetch-depth: 0`, then compare its generated projection with a local `render` from the committed resulting ledger and identical config. Expect matching projection bytes; pull-request branch, commit, label, and API side effects are action-only and are not expected from local render.

The executed checks in this research were limited to live package/source inspection, `npx --yes contributors-please@1.4.3 --version` returning `1.4.3`, and the fresh ts-launch-blueprint negative control: `render --config-file .contributors.yml` exited 1 with `ENOENT` for the absent `.contributors.jsonl`. No paid provider, GitHub mutation, Rust build, or final template integration was executed. (Sources: https://github.com/smorinlabs/contributors-please/blob/main/test/cli.test.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/cli.ts, https://github.com/smorinlabs/contributors-please/blob/main/src/engine/contributors.ts; retrieved 2026-09-05.)
